# 微服务架构演进与CAP理论

> **核心定位**：从单体到微服务的架构演进路径，以及 CAP/BASE 理论——分布式系统的理论基石。

## 1. 架构演进

```
┌─────────────────────────────────────────────┐
│ 架构演进路线                                  │
├─────────────────────────────────────────────┤
│                                              │
│ 1. 单体架构（Monolithic）                    │
│    单一 WAR 包，所有功能在一个进程            │
│    优点：简单、部署方便                      │
│    缺点：代码膨胀、技术栈受限、扩展困难      │
│                                              │
│ 2. 垂直拆分                                  │
│    按业务拆分为多个单体                      │
│    优点：独立部署                            │
│    缺点：重复代码、数据冗余                  │
│                                              │
│ 3. ★ 微服务架构（Microservices）             │
│    按业务域拆分，独立数据库、独立部署         │
│    优点：独立扩展、技术自由、故障隔离        │
│    缺点：分布式复杂度、运维成本              │
│                                              │
│ 4. 服务网格（Service Mesh）                  │
│    Sidecar 代理 + 控制平面                   │
│    优点：语言无关、流量管控                  │
│    缺点：Sidecar 开销、学习曲线陡峭          │
│                                              │
│ 5. Serverless                                │
│    FaaS + BaaS                               │
│    优点：按需付费、零运维                    │
│    缺点：冷启动、调试困难                    │
└─────────────────────────────────────────────┘
```

## 2. 微服务核心原则

```
┌─────────────────────────────────────────────┐
│ 微服务设计原则                                │
├─────────────────────────────────────────────┤
│                                              │
│ 1. ★ 单一职责（Single Responsibility）      │
│    每个服务只做一件事                         │
│                                              │
│ 2. ★ 独立数据库（Database per Service）     │
│    每个服务有私有数据库                       │
│    服务间通过 API 通信，不共享数据库          │
│                                              │
│ 3. 服务自治                                  │
│    独立部署、独立技术栈、独立扩展             │
│                                              │
│ 4. 去中心化                                  │
│    无全局架构，各服务自行决策                │
│    智能端点，哑管道（Smart endpoints,        │
│    dumb pipes）                              │
│                                              │
│ 5. 容错设计                                  │
│    每个服务都可能失败                         │
│    ★ 限流、熔断、降级、重试、超时            │
│                                              │
│ 6. 事件驱动                                  │
│    异步通信、最终一致性                      │
│                                              │
│ 7. 自动化                                    │
│    CI/CD、自动化测试、自动化部署              │
└─────────────────────────────────────────────┘
```

## 3. CAP 理论

```
┌─────────────────────────────────────────────┐
│ CAP 理论（分布式系统三选二）                  │
├─────────────────────────────────────────────┤
│                                              │
│           C (Consistency)                    │
│          / \                                   │
│         /   \                                  │
│        /  ★  \                                 │
│       /  CAP  \                               │
│      /         \                              │
│     /___________\                             │
│  A              P                            │
│  (Availability) (Partition Tolerance)       │
│                                              │
│ C：一致性                                     │
│   所有节点在同一时间看到相同数据              │
│                                              │
│ A：可用性                                     │
│   每次请求都能获得响应（不保证是最新）         │
│                                              │
│ P：分区容错                                   │
│   网络分区时系统仍能运行                      │
│                                              │
│ ★ 在分布式系统中 P 不可避免（网络必分区）     │
│ ★ 因此只能选 CP 或 AP                        │
│                                              │
│ CP：强一致（Zookeeper、etcd）                │
│    分区时牺牲可用性，保证数据一致             │
│    注册慢（Leader 选举期间不可用）            │
│                                              │
│ AP：高可用（Nacos 默认、Eureka）              │
│    分区时牺牲一致性，保证可用                 │
│    注册快（最终一致）                         │
│                                              │
│ ★ 微服务注册中心推荐 AP（可用性优先）         │
└─────────────────────────────────────────────┘
```

## 4. BASE 理论

```
┌─────────────────────────────────────────────┐
│ BASE 理论（CAP 的工程实践）                   │
├─────────────────────────────────────────────┤
│                                              │
│ B：Basically Available（基本可用）           │
│   允许损失部分可用性（响应时间增加、          │
│   非核心功能降级）                            │
│                                              │
│ S：Soft State（软状态）                       │
│   允许数据存在中间状态（不要求强一致）         │
│                                              │
│ E：Eventually Consistent（最终一致性）       │
│   数据副本最终达到一致                        │
│                                              │
│ ★ BASE 是 AP 的工程实践                       │
│ ★ 微服务主流选择：BASE + 最终一致性           │
│                                              │
│ 实现方式：                                    │
│ - 消息队列（异步 + 重试）                     │
│ - 本地消息表 + 定时补偿                      │
│ - 事务消息（RocketMQ）                       │
│ - TCC（Try-Confirm-Cancel）                  │
│ - Saga（长事务补偿）                         │
└─────────────────────────────────────────────┘
```

## 6. 微服务拆分

```
┌─────────────────────────────────────────────┐
│ 微服务拆分策略                                │
├─────────────────────────────────────────────┤
│                                              │
│ 1. ★ DDD 领域驱动设计                        │
│    按业务领域（Bounded Context）拆分          │
│    例：用户域、订单域、商品域、支付域          │
│                                              │
│ 2. 按业务能力                                 │
│    认证、用户管理、订单、库存、支付            │
│                                              │
│ 3. 按变化频率                                 │
│    高频变化的独立部署                         │
│    稳定的合并                                │
│                                              │
│ 4. 按团队组织（康威定律）                     │
│    每个团队负责一个或多个服务                 │
│    团队边界 = 服务边界                        │
│                                              │
│ 拆分原则：                                    │
│ - ★ 高内聚低耦合                             │
│ - ★ 合适粒度（不过细也不过粗）               │
│ - ★ 数据库独立                              │
│ - ★ 无状态服务（便于水平扩展）               │
│                                              │
│ 常见电商拆分：                                │
│ 用户服务 / 商品服务 / 订单服务 / 支付服务     │
│ 库存服务 / 促销服务 / 物流服务 / 通知服务     │
└─────────────────────────────────────────────┘
```
