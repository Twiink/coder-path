# Spring Cloud 学习路线

Spring Cloud 像一位穿着整齐的分布式管家：注册、配置、调用、网关、熔断、消息和观测都能替你接线，但他也会把版本兼容、依赖管理和默认行为写成一张很长的菜单。学会菜单不等于学会做菜，服务边界和故障设计仍然要由人负责。

这条路线以当前官方维护的 Spring Cloud 组件为主，理解 Spring Boot 与 Spring Cloud 的 release train 和兼容矩阵；同时把 Netflix 早期组件当作迁移背景，把 Spring Cloud Alibaba、Kubernetes 与服务网格放在清晰的边界上。少写样板代码，多验证请求链、配置变更、失败、数据一致性和发布回滚。

**推荐顺序** ---- 版本地图 → 应用边界与配置 → 服务发现 → 服务调用 → 网关 → 弹性治理 → 消息与一致性 → 可观测与安全 → 发布运维 → 平台边界与演进

**这条线怎么用** ---- 每站先画组件之间的控制面和数据面，再用一个包含订单、库存、通知的场景贯穿练习；任何“自动配置”都要追问它在失联、超时、重试和旧版本共存时的行为。

## 第一站：先看清 Spring Cloud 的菜单

第一站的 Spring Cloud 像一位会递菜单的服务员：他能把很多菜端上桌，却不能决定客人到底想吃什么。先厘清平台、框架和业务的边界，才能避免依赖一多就把整个应用煮成一锅汤。

**Spring Boot 与 Spring Cloud 的关系** ---- Boot 负责应用启动、自动配置和运行基线，Cloud 提供分布式系统的连接、治理与集成能力；两者不是同一个版本号，也不能随意拼装

**Release Train 与兼容矩阵** ---- 学会查 Spring Cloud release train、Spring Boot、Java、Spring Framework 和第三方组件的兼容关系；用 BOM 管理版本，避免单独升级某个 starter 破坏整套依赖

**官方主线与生态组件** ---- 认识 Spring Cloud Gateway、LoadBalancer、OpenFeign、Circuit Breaker、Config、Stream、Bus 和 Kubernetes 集成；Nacos、Sentinel、Seata 等属于额外生态，选用时要单独核对版本和维护边界

**Netflix 组件的历史位置** ---- 了解 Eureka、Ribbon、Hystrix、Zuul 曾经解决什么问题，以及官方替代方向；历史组件适合读旧系统，不应因为教程还在使用就直接作为新项目默认

**自动配置与条件装配** ---- 理解 starter、条件注解、Bean 覆盖、属性绑定和配置优先级；自动配置省下样板代码，也可能隐藏连接池、线程池和超时默认值，排障时要会看实际生效配置

**控制面与数据面** ---- 注册、配置、规则和元数据属于控制面，请求、消息和业务数据属于数据面；控制面短暂不可用时，应用应使用最后有效配置或安全默认，而不是每次请求都依赖控制面

**Spring Cloud 的边界** ---- 它能帮你连接和治理服务，不能替你划限界上下文、设计数据所有权、定义资金一致性或修复糟糕的接口；框架能力越强，越要把领域决策留在业务代码

## 第二站：应用启动、配置与服务边界

第二站的配置像一位有很多抽屉的管家：本地抽屉、环境抽屉、远端抽屉和启动参数都在说“听我的”。只有明确优先级、秘密边界和失败默认，配置才不会在凌晨互相争吵。

**配置来源与优先级** ---- 认识命令行、环境变量、配置文件、profile、配置中心和远端配置的覆盖关系；把“当前值从哪里来、何时加载、是否可刷新”作为排障的三连问

**Profiles 与环境隔离** ---- 用开发、测试、预发布和生产 profile 表达环境差异，避免把生产地址和密钥编进镜像；环境差异越多，越要靠验证和模板减少漂移

**外部化配置** ---- 将端口、上游地址、超时、限流、开关和非秘密参数外置，保持构建产物可复用；配置中心不是数据库，不能随意塞入大对象和业务数据

**秘密管理** ---- 密码、Token、证书和加密密钥应由秘密系统或平台安全注入，限制读取、轮换、吊销和审计；配置刷新时尤其要防止秘密出现在日志、异常和 Actuator 响应

**动态刷新** ---- 了解哪些 Bean 能安全刷新，哪些连接池、线程池、客户端和业务缓存不能贸然热替换；热更新需要版本、校验、灰度、回滚和变更审计

**服务边界与包结构** ---- 按业务能力、数据所有权和团队责任组织应用，而不是按 controller、service、repository 技术层拆成远程服务；先在单体中验证模块边界，再决定是否部署拆分

**启动检查与就绪** ---- 区分应用进程已启动、能接流量、能访问关键依赖和业务真正可用；不要让启动时强依赖一个暂时不可用的服务导致整个集群无法扩容

**配置中心故障** ---- 设计本地兜底、最后有效配置、只读运行、重试退避和安全默认；配置拉取失败时拒绝高风险变更，通常比启动随机值更安全

## 第三站：服务发现与配置分发

第三站的服务实例像一群不断换座位的学生：名字没变，地址在变，老师还要知道谁迟到、谁请假、谁只能接低年级。发现系统解决定位与状态，但不保证业务调用一定成功。

**客户端发现** ---- 调用方从 Eureka、Nacos、Consul 或其他注册中心获得实例，再由客户端负载均衡；它能减少中间跳数，却把缓存、更新和选择策略放进应用

**服务端发现** ---- 由网关、代理、Kubernetes Service 或平台负责把逻辑服务名解析到实例；客户端更简单，但代理、DNS 和平台自身成为新的观测与故障边界

**注册生命周期** ---- 理解注册、心跳、租约、TTL、健康检查、摘除、恢复和优雅下线；实例已经退出但列表仍未更新时，调用方必须有连接超时和失败重选

**注册中心一致性** ---- 区分临时实例、服务元数据和配置数据的可靠性要求，理解 AP、CP、网络分区和读旧列表；注册中心本身也需要集群、备份、权限和容量规划

**命名与环境隔离** ---- 用应用名、命名空间、分组、集群、区域和租户标签避免测试流量误入生产；服务名是契约的一部分，重命名需要兼容窗口和迁移计划

**负载均衡** ---- 掌握轮询、加权、最少活跃、区域优先、一致性哈希和预热；选择策略要结合实例能力、缓存亲和、热点和发布阶段，而非只依赖默认值

**发现缓存与 stale 数据** ---- 本地缓存能承受注册中心短暂抖动，但旧列表可能包含已下线实例；给缓存设刷新、过期、失败重试和安全降级策略，并观测列表年龄

**配置分发与规则治理** ---- 路由、超时、限流和熔断规则可以动态下发，但必须有版本、审批、校验、审计、灰度和撤销；动态配置是发布，不是“免发布魔法”

## 第四站：服务调用、协议与客户端

第四站的客户端像一位很有礼貌的电话员：它会帮你拨号，却不能保证对方接听，更不能把通话时间拉到无限长。远程调用要把代理、连接、序列化、上下文和失败语义一起学会。

**OpenFeign 与声明式客户端** ---- 理解接口代理、参数编码、错误解码、服务名解析和拦截器；声明式调用只是外观，底层仍是网络、连接池、序列化和远端失败

**RestClient、WebClient 与调用模型** ---- 比较同步阻塞和响应式非阻塞客户端，按线程模型选择 API；不要在事件循环里执行阻塞数据库或文件操作，也不要为了“响应式”把简单应用变成难以维护的混合模型

**Spring Cloud LoadBalancer** ---- 了解实例选择、缓存、健康、权重、区域和自定义策略；负载均衡只负责选择目的地，连接超时、重试和业务幂等仍要单独设计

**HTTP、gRPC 与消息的选择** ---- HTTP/REST 适合公开契约和跨语言，gRPC 适合强类型高频内部调用，消息适合解耦与削峰；选择要结合即时性、顺序、回压、调试和版本演进

**连接池与线程池** ---- 关注最大连接、空闲回收、连接建立、读取超时、线程数、队列和拒绝策略；一个下游的慢调用不能耗尽所有业务线程

**超时预算** ---- 从入口 SLO 反推每次调用的 deadline、连接超时、响应超时和总预算；下游超时必须早于上游请求失效，否则请求会在每层重复等待

**重试与幂等** ---- 只对瞬时错误、连接失败和明确幂等操作进行有限重试，使用退避和抖动；创建订单、扣款等写操作不能因为客户端重试就产生重复副作用

**错误契约** ---- 统一区分参数错误、认证失败、资源不存在、业务拒绝、依赖不可用和超时；异常堆栈留给日志，客户端需要稳定的错误码、可重试标记和 Trace ID

**上下文传播** ---- 传递 Trace、租户、语言、区域、用户和截止时间，限制 Header 大小与可信来源；异步线程、消息和线程池切换时要验证上下文是否丢失或串用

## 第五站：Spring Cloud Gateway 与入口治理

第五站的 Gateway 像一位反应很快的前台主管：它能看路径、Header 和方法，马上决定把人送去哪个房间，但让它替每个房间做业务决定，前台很快就会罢工。

**Route、Predicate 与 Filter** ---- 掌握路由、匹配条件和过滤器的职责，理解匹配顺序、路由优先级、路径重写与前缀剥离；配置逻辑应可读、可测试、可审计

**WebFlux 与非阻塞** ---- 了解 Reactor、事件循环、背压和异步响应的基本心智；过滤器里调用阻塞 SDK 会放大延迟，必须通过非阻塞客户端或隔离调度器处理

**服务名路由** ---- 使用逻辑服务名结合 LoadBalancer 把请求送到实例，观察发现缓存、路由刷新和健康摘除；服务名解析失败应有明确的 5xx、降级或静态故障页

**认证与安全过滤器** ---- 在入口做 TLS、JWT/OAuth2、API Key、CORS、请求大小和基础黑名单检查；资源级权限、订单状态和金额校验必须回到后端服务

**限流与熔断过滤器** ---- 结合请求速率、并发、配额、上游超时和断路器保护后端；策略要定义 Key、状态存储、超限响应、恢复条件和多实例一致性

**聚合与 BFF 边界** ---- 少量并行聚合可以改善客户端体验，但复杂编排、补偿和持久化应放入独立 BFF 或领域服务；Gateway 不应长成超级服务

**网关观测** ---- 用 Actuator、Micrometer、日志和 Trace 记录路由、上游、过滤器、重试和限流结果；敏感 Header、Cookie 和请求体必须脱敏

**网关高可用** ---- 保持无状态、多实例、优雅排空、配置回滚和低依赖；网关是关键入口，任何新增过滤器都要做压力、故障和升级演练

## 第六站：熔断、限流、隔离与恢复

第六站的 Resilience4j 和 Sentinel 像一组消防员：一个负责关门，一个负责限客，一个负责隔离水管，另一个负责给重要客人留出口。它们不是装饰品，必须与业务优先级和数据语义相配。

**Circuit Breaker** ---- 在错误率、慢调用或连续失败达到阈值时打开，经过半开探测恢复；要区分可预期的业务 4xx 与基础设施故障，并按依赖分别配置

**Retry** ---- 将重试次数、退避、抖动、可重试异常和总耗时写成策略；重试要避免与网关、客户端、消息消费者和数据库驱动层层叠加

**Bulkhead 舱壁** ---- 按依赖或业务优先级隔离线程池、信号量、连接池和并发额度；慢支付不能占满查询线程，低优先级任务不能拖垮核心接口

**Rate Limiter** ---- 比较令牌桶、并发限制、滑动窗口和分布式配额，分别处理突发、资源占用和公平性；限流状态的共享会增加延迟和可用性依赖

**TimeLimiter 与背压** ---- 限制异步任务等待、队列长度和消费速率，让系统主动放弃低价值工作；没有背压的响应式流只是把排队搬到内存

**Fallback 降级** ---- 为非核心查询提供缓存、默认值、只读或异步受理，为关键写入返回明确失败；降级不能把未知状态伪装成成功

**健康与优雅下线** ---- 结合 Actuator 健康组、存活、就绪、依赖状态和连接排空，让实例先停止接新流量再退出；健康检查不能无限递归调用下游

**阈值与基线** ---- 用流量、错误类型、尾延迟、依赖容量和业务损失校准阈值，避免照抄示例百分比；阈值变更也要可观测和可回滚

**故障演练** ---- 通过延迟、500、连接拒绝、线程池耗尽和配置错误验证保护链；要确认告警、用户提示、数据补偿和恢复时间都符合预期

## 第七站：消息驱动与跨服务数据一致性

第七站的消息总线像一位热心但健忘的邮差：他可能重复送信、晚点送信，甚至把信暂存在死信仓库。Spring Cloud Stream 能帮你接线，却不能替业务决定重复消费是否安全。

**Spring Cloud Stream 与 Binder** ---- 理解应用函数、绑定器、消息目的地、消费者组和不同 broker 的抽象边界；抽象减少接入成本，但顺序、分区、重试和事务语义仍由具体 broker 决定

**Kafka 与 RabbitMQ 的取舍** ---- Kafka 偏日志、分区、重放和高吞吐，RabbitMQ 偏路由、确认、队列和灵活投递；选择依据是顺序、消费模式、延迟、运维和成本，而不是流行度

**消息确认与投递语义** ---- 理解 at-most-once、at-least-once 和“端到端 exactly-once”的边界；消费者应默认面对重复消息，确认时机要在业务处理和本地提交之后

**幂等消费与去重** ---- 用业务幂等键、唯一约束、Inbox、状态机或版本号防止重复副作用；去重记录要有生命周期、容量和故障恢复策略

**重试、死信与补偿** ---- 区分可重试错误和毒消息，设置退避、最大次数、死信、人工重放和告警；无限重试会让一封坏信堵住整条邮路

**顺序、分区与热点** ---- 先定义业务真正需要的顺序，再选择 key、分区和并发；全局顺序成本高，按订单或租户分区更常见，但热点 key 仍需治理

**Outbox 与本地事务** ---- 在同一数据库事务中写业务状态和待发送事件，再由投递器发送；这解决提交与发送间隙，不自动解决下游幂等和最终一致

**Saga、Seata 与边界** ---- 了解 Saga、TCC、AT 等分布式事务方案的流程、锁、补偿和侵入成本；跨服务流程优先设计可重试、可补偿和可对账，慎用全局强一致

**事件 schema 演进** ---- 新增字段保持兼容，消费者忽略未知字段，设置版本、保留期和重放验证；事件是长期契约，不能像内部 DTO 一样随意重命名

## 第八站：可观测性、Actuator 与安全

第八站的 Actuator 像一只很会记账的猫：它能告诉你应用的健康、指标和环境，却也可能不小心把钥匙叼到门外。观测端点要服务排障，同时严格收好暴露面。

**Actuator 端点** ---- 了解 health、info、metrics、loggers、mappings、threaddump 和 prometheus 等端点的用途与敏感性；只暴露必要端点并通过独立管理端口、网络和权限保护

**Micrometer 指标** ---- 记录请求速率、错误、延迟、线程池、连接池、熔断、限流、消息积压和 JVM 资源；控制标签基数，不把用户 ID、订单 ID 直接做无限增长的标签

**OpenTelemetry 与 Trace** ---- 传播 W3C Trace Context，串联网关、客户端、服务、消息和数据库；采样要优先保留错误、慢请求和关键业务，并计算存储成本

**结构化日志** ---- 统一服务、版本、实例、Trace、租户、业务键、错误码和重试次数，按环境设置级别；秘密、令牌、个人信息和完整请求体必须脱敏

**SLO 与业务指标** ---- 用可用性、尾延迟、成功率、配置新鲜度、消息积压和补偿量定义目标；只有能触发行动的指标才值得长期保留

**Spring Security 与资源授权** ---- 区分认证、会话、OAuth2 Resource Server、JWT、scope、role 和资源级授权；网关验过令牌不代表服务可以跳过自己的权限判断

**服务间身份** ---- 使用短期凭证、mTLS、工作负载身份或客户端凭证，限制受众和传播范围；内网、服务名和 Header 都不是天然可信

**审计与管理平面安全** ---- 记录登录、配置变更、路由规则、权限拒绝、人工重放和发布，管理端点与业务端口分离；审计日志需有保留、防篡改和访问控制

## 第九站：测试、发布与生产运维

第九站的发布流水线像一位谨慎的列车长：他允许新旧版本同车，却不允许车轮、轨道和信号灯同时换规格。Spring Cloud 的“自动”越多，越要用测试和观测把它们钉在现实上。

**测试层次** ---- 用单元测试验证业务规则，组件测试验证客户端、过滤器和配置，契约测试验证接口，集成测试连接真实 broker 或注册中心，少量 E2E 验证关键旅程

**Testcontainers 与真实依赖** ---- 对消息、数据库、注册中心和配置中心做可重复集成测试；Mock 可以隔离故障，但不能替代真实协议、序列化、权限和网络行为

**配置与契约门禁** ---- 在 CI 校验配置 schema、路由冲突、依赖版本、API 兼容和消息 schema；把“启动后才发现配置错”提前到构建阶段

**容器化与优雅停机** ---- 设置 JVM 内存、线程、连接池、探针、启动和停止超时，先停止接流量再排空请求；容器重启不是恢复策略，状态和未完成任务要有明确处理

**滚动、蓝绿与金丝雀** ---- 滚动适合资源敏感的常规发布，蓝绿适合快速切换，金丝雀适合风险验证；发布期间要支持旧新版本共存和流量按租户或权重控制

**数据库扩展式变更** ---- 先加兼容字段和索引，再发布读写逻辑、回填和切换，最后删除旧结构；大表 DDL、锁、回滚和旧应用兼容必须纳入发布计划

**回滚与前滚** ---- 代码可以回滚，配置、数据库和事件不一定能倒带；优先向前兼容和修复发布，并准备降级、流量归零、补偿和人工开关

**升级与故障切换** ---- 观察 Boot、Cloud、JDK、驱动、broker、注册中心和容器平台的兼容矩阵，演练升级、重启、连接失效和注册中心故障；版本升级是架构变更，不只是改一个数字

## 第十站：平台边界、成本与架构演进

最后一站的 Spring Cloud 像一位懂得适可而止的管家：他知道 Kubernetes 能接管一部分发现与发布，Istio 能下沉一部分通信治理，也知道应用仍要负责领域规则和数据一致性。成熟方案不是组件越多越豪华，而是重复能力越少越清楚。

**Spring Cloud 与 Kubernetes** ---- Kubernetes Service、DNS、探针、ConfigMap、Secret、Deployment 和 HPA 能提供平台能力；Spring Cloud 仍可承载应用级调用、配置、网关和领域侧策略，关键是避免双重配置和责任重叠

**Spring Cloud 与服务网格** ---- 网格擅长 mTLS、东西向路由、熔断、追踪和流量策略，应用框架擅长业务语义、用户权限、事务和领域事件；两边同时重试或同时做超时，会形成难以解释的叠加

**依赖与资源成本** ---- 计算每个 starter、线程池、连接池、Sidecar、日志、追踪、配置中心和多环境副本的资源；“开箱即用”并不代表免费，默认线程和连接也会占容量

**性能分析** ---- 用基线、压测和火焰图定位序列化、阻塞调用、连接池、GC、事件循环、日志和网络开销；不要用增加实例数掩盖错误的调用模型

**服务化路径** ---- 从模块化单体开始，先抽取高变化、高负载或清晰数据边界的能力，再用契约、事件和流量切换完成绞杀；服务数量增长应与团队、平台和观测能力同步

**多区域与单元化** ---- 按租户、区域或业务单元划分故障域，明确数据驻留、跨区延迟、复制、路由和成本；多区域不是简单复制 Deployment，而是重新设计一致性和恢复

**平台标准化** ---- 把日志、Trace、指标、认证、发布、服务目录和依赖基线做成平台能力，但给团队保留合理的技术选择；标准应减少重复劳动，而不是把所有服务绑成同一套脚手架

**毕业项目** ---- 用 Nacos 或 Kubernetes Service 发现两个服务，用 OpenFeign 或 WebClient 调用，配置一个 Gateway，加入限流熔断和消息 Outbox，再用 Actuator、Micrometer、Trace、契约测试和金丝雀发布串成完整闭环；最后注入依赖超时和配置中心故障，验证恢复与回滚

## 通关标准

能查并解释 Spring Boot、Spring Cloud 与第三方组件的兼容矩阵；能按业务边界启动两个服务，完成注册发现、配置加载、客户端负载均衡、Gateway 路由和统一观测；能给读写接口配置超时、有限重试、熔断、舱壁、限流和降级，并说明每层的防护对象；能用消息、Outbox、幂等和 Saga 处理最终一致性；能保护 Actuator、OAuth2/JWT、服务间身份与秘密；能完成契约测试、数据库扩展式变更、金丝雀发布、故障注入和回滚；还能说清 Spring Cloud、Kubernetes、服务网格和 Spring Cloud Alibaba 的能力边界与成本。

## 下一站去哪

想深挖 Java 内部 RPC，可进入 Dubbo，比较接口代理、Triple、应用级服务发现与集群容错；想理解入口治理，进入 API 网关；想把东西向通信、安全与观测下沉到平台，再进入 Istio；所有路线都应回到微服务设计模式，重新检查边界和一致性。

## 结语

Spring Cloud 的价值是把分布式基础设施接得更顺，而不是替你做架构判断。它能减少重复代码，却不能消除网络、数据和组织的复杂度；它能快速提供组件，却也要求你认真管理版本、默认值、依赖和运维成本。

当你能读懂自动配置，测出一次调用链的真实耗时，解释一次消息重复为何安全，保护好管理端点，并让新旧版本平稳共存，Spring Cloud 才真正从“全家桶”变成了你能掌控的工程工具。
