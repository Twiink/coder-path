# Elasticsearch 学习路线

Elasticsearch 是那位把“我想搜一下”听成“请帮我建立分布式倒排索引”的搜索管家：它擅长全文检索、日志分析、指标聚合、地理搜索和向量召回，却不适合替你的订单数据库保管一生一世。它站在 Lucene 之上，把文档、索引、分片和 REST API 组合成一套可扩展的搜索系统；真正学会它，要能从 JSON 查询一路追到 Segment、文件系统缓存、分片路由和故障恢复。

**推荐顺序** ---- 搜索心智模型与 Lucene → Mapping 与分析器 → 查询与评分 → 聚合与分析 → 写入与近实时 → 集群与分片 → 运维、安全与容量 → 场景选型

**这条线怎么用** ---- 每一站先弄清“数据如何落下去、如何被找到、如何变得可用”，再做小规模实验。搜索系统最容易让人被一条漂亮的查询骗走；看到结果后，还要追问它是否相关、是否稳定、是否能在故障和增长之后继续工作。

## 第一站：先认识这位搜索管家

第一站不急着背 DSL。先把 Elasticsearch 放回系统地图：关系数据库负责事务真相，消息系统负责传递变化，Elasticsearch 负责把可搜索的投影整理得很快。它很聪明，但没有聪明到可以替业务决定哪笔订单真的存在。

**Elasticsearch 的定位** ---- 理解它是分布式搜索与分析引擎，适合全文搜索、日志检索、聚合报表、地理查询和向量检索；普通增删改查、强事务约束和唯一事实仍应由主数据库承担

**Index、Document 与 Field** ---- 把 Index 理解为文档集合的逻辑命名空间，Document 是 JSON 文档，Field 是文档字段；它们可以类比表、行、列，但不要因此误以为 Elasticsearch 具备关系数据库的事务语义

**Mapping 与 Analyzer** ---- Mapping 描述字段类型、索引方式和是否存储，Analyzer 决定文本如何被拆成可搜索的词；字段类型选错，后面再聪明的查询也只能认真地得到错误结果

**Primary Shard 与 Replica Shard** ---- 主分片是数据与写入的基本切片，副本分片用于冗余和读扩展；分片是物理资源，不是免费的小文件，数量会影响内存、集群状态和查询扇出

**Data Stream、Alias 与 Template** ---- 认识数据流适合持续写入的时序数据，别名用于无感切换和抽象索引名，模板用于统一新索引的设置与映射；生产索引通常不应靠手工逐个创建

**REST API 与观测入口** ---- 熟悉健康检查、索引目录、分片目录、节点信息、集群设置和任务接口；先学会看集群，再学会让集群替你搜东西

## 第二站：Lucene、倒排索引与文件结构

这站要去地下室见 Lucene。Elasticsearch 的“毫秒级搜索”不是魔法，而是一群提前整理好的文件在值班；你输入一个词，它们不用挨个叫醒文档，只要去词条目录查门牌号。

**正排与倒排** ---- 正排是“文档找到它包含的词”，倒排是“词条找到包含它的文档”；全文搜索的核心是后者，查询不必扫描所有文档的完整正文

**Term Dictionary 与 Term Index** ---- 词条字典保存排序后的词，词条索引帮助快速定位字典范围；Lucene 会用压缩结构和内存索引降低磁盘查找成本，不能把它简化成一个普通哈希表

**Posting List** ---- 倒排表保存词条对应的文档编号以及词频、位置等信息；多个词查询时需要合并 posting list，跳表、块压缩和文档编号顺序会直接影响速度

**Segment** ---- Lucene 写入后形成不可变 Segment；更新通常是写入新版本并标记旧文档删除，删除标记要等后台合并才真正回收，因此“删了但磁盘没立刻变小”是正常现象

**Stored Fields 与 `_source`** ---- `_source` 保存原始 JSON，Stored Fields 负责按需取回字段；搜索字段与返回字段是两件事，列表页可用 source filtering 减少网络和反序列化成本

**Doc Values** ---- keyword、数值、日期等字段通常用列式 Doc Values 支撑排序、聚合和脚本访问；它主要在磁盘上工作，和把 text 字段强行打开 fielddata 的内存代价不同

**Translog、Refresh 与 Flush** ---- 写入先进入内存缓冲和事务日志，refresh 让新 Segment 对搜索可见，flush 把持久化状态整理并截短 translog；refresh 决定“多久能搜到”，不是“多久才安全落盘”

**Merge 与删除回收** ---- 后台 merge 合并小 Segment、清理删除标记并重写索引文件；force merge 只适合已经不再写入的只读索引，在线热索引强行合并会制造大量 I/O 和段写放大

**近实时而非实时** ---- 默认搜索可见性存在 refresh 间隔，写入确认、磁盘持久化和查询可见性分别由不同机制控制；理解这三个时间点，才能解释“请求成功但马上搜不到”

## 第三站：Mapping、分词与字段设计

第三站是类型选择站。Mapping 像给每个字段发工作证：`text` 去做全文搜索，`keyword` 去做精确匹配；要是把员工派错岗位，聚合、排序和查询会一起跑来投诉。

**Analyzer 三段式** ---- 字符过滤器先处理原文，Tokenizer 切分词元，Token Filter 再做小写化、停用词、同义词或词干处理；索引时 analyzer 与查询时 analyzer 的配合决定“搜得到”还是“看起来应该搜得到”

**`text` 与 `keyword`** ---- `text` 面向分词后的全文检索，`keyword` 保存整体值，适合精确过滤、排序、聚合和连接业务编号；状态、ID、标签、邮箱通常要优先考虑 keyword 语义

**Multi-fields** ---- 一个字段可以同时提供 `title` 的全文搜索和 `title.keyword` 的精确能力；这是常见的两条轨道，但会增加索引体积，不能无条件给每个字段复制一整套子字段

**数值、日期、布尔、IP 与地理类型** ---- 按查询方式选择 numeric、date、boolean、ip、geo_point 或 geo_shape；日期要统一时区和格式，IP 不要当字符串排序，地理数据也不要只存两段经纬度文本

**`object`、`nested` 与 `flattened`** ---- object 的数组对象默认会被扁平化，可能把不同对象的字段错误拼配；需要保持对象内部关联时用 nested，动态键很多且查询要求较轻时再评估 flattened

**`dense_vector` 与向量字段** ---- 向量字段用于近似最近邻或 kNN 检索，维度、相似度、量化与召回率要一起评估；向量搜索不是把 BM25 换成一个按钮，实际应用常需要文本与向量混合召回

**动态映射与动态模板** ---- 自动推断适合快速试验，生产更应显式控制字符串、数字和日期的推断；通过 dynamic templates 统一字段规则，必要时使用 strict 让脏字段在写入时失败而不是悄悄长出新字段

**Runtime Fields** ---- runtime field 在查询时计算，适合少量临时派生字段和迁移过渡；它节省重建索引的即时成本，却把计算推迟到查询路径，不适合高频大范围聚合

**不可随意改类型** ---- 已有字段类型不能直接改成另一种语义；通常要新建索引、reindex、校验结果，再通过别名原子切换，迁移过程要同时处理双写、回滚和旧索引保留

**Mapping Explosion** ---- 用户自定义字段、日志标签或 JSON 动态键可能让字段数量失控；通过白名单、字段上限、flattened、动态模板和摄入端清洗控制集群状态与 JVM 压力

## 第四站：查询 DSL、评分与稳定分页

这一站让搜索管家开始接待客人。它会给“稀有词命中”更高分，也会因为一个不稳定的排序让下一页突然换人；相关性和确定性，要同时管。

**全文查询** ---- 掌握 match、match_phrase、multi_match、query_string 与 simple_query_string 的差异；面向用户的输入优先限制语法面，避免让 query_string 变成一台可以随意改写查询的遥控器

**精确与范围查询** ---- term、terms、range、exists、prefix、wildcard、regexp 和 fuzzy 各有成本与适用字段；term 查询通常针对 keyword，不能拿它去碰已经分词的 text

**Bool 查询** ---- must 参与评分，filter 只负责是否匹配且更适合缓存，should 表示偏好或可选命中，must_not 用于排除；状态、租户、时间范围等硬条件通常放进 filter

**BM25 评分** ---- 了解词频、逆文档频率和字段长度归一化如何共同影响相关度；评分是统计意义上的排序，不是业务真理，商品销量、库存、时效等信号要通过明确的业务排序补充

**Boost 与 Function Score** ---- 用字段权重、业务函数、衰减函数或脚本做重排时，先确定业务目标与可解释性；脚本能解决问题，也能把 CPU 账单写成一封很长的信

**查询上下文与过滤上下文** ---- 区分“我要找相关内容”和“我只要满足条件的文档”；把不需要评分的条件放入 filter 能减少计算，但不能替代正确的 mapping 和索引设计

**排序与 tie-breaker** ---- 相关度、日期、数值排序都要设置稳定的第二排序键，通常使用唯一且有明确语义的字段；否则同分文档在分页和刷新后可能漂移

**深分页、`search_after` 与 PIT** ---- from/size 适合浅页，深分页会让每个分片保留更多候选；search_after 配合稳定排序适合连续翻页，PIT 用于在一段时间内保持一致的搜索视图，scroll 更适合批量导出而不是在线翻页

**高亮、建议与补全** ---- highlighter 用于显示命中片段，suggest 处理纠错或建议，completion suggester 适合前缀补全；先核对分词器、语言和返回体积，再决定是否开启这些附加能力

**地理与混合检索** ---- geo_distance、geo_bounding_box、向量 kNN 与 BM25 可以组合成附近搜索、语义召回和混合排序；召回、过滤、重排的责任要分层，否则一次请求会同时变成 CPU、内存和网络考试

## 第五站：聚合与分析查询

第五站是报表部。聚合很会把海量文档切桶、算均值、找 P99，但它不会因为报表名字叫“实时”就自动拥有无限内存；桶数量和基数，都是它的饭量。

**桶聚合** ---- terms 类似分组，date_histogram 用于时间趋势，range、histogram、filters 用于区间和条件分桶；terms 默认只返回部分热门桶，不能把返回的 TopN 当成全量分组结果

**Composite 聚合** ---- composite 适合按多个字段稳定地分页遍历大量桶；它牺牲一些一次性便利换取可控的结果集，适合导出或持续处理高基数维度

**指标聚合** ---- avg、sum、min、max、stats、extended_stats 解决常规统计，percentiles 观察 P50、P95、P99 等分位数；延迟、金额、大小等字段要先确认单位、缺失值和异常值

**Cardinality** ---- cardinality 使用近似算法估算去重数，内存和准确率可调；它适合趋势与监控，不应在财务结算中未经验证地当作精确 COUNT DISTINCT

**Top Hits 与 Top Metrics** ---- 每个桶取代表文档或代表指标适合做分类 TopN、最新事件和摘要；要控制每桶返回条数，否则“每类取一条”很快会变成“每类取一车”

**管道聚合** ---- 对已有桶结果继续做导数、移动平均、累加和桶排序；先画清聚合树与中间粒度，避免把一个可以在摄入端计算的指标重复算数百次

**`doc_values` 与 fielddata** ---- 聚合、排序和脚本优先依赖 Doc Values；对 text 打开 fielddata 会把词项结构带入堆内存，通常应改用 keyword 子字段或重新设计字段

**查询、聚合与返回体分离** ---- `size: 0`、source filtering、只取必要聚合和限制桶数量可以减少无效工作；“只想要报表却顺手返回一千篇正文”是很常见的浪费

**Transforms 与时序分析** ---- 对重复聚合、实体最新状态或时序汇总，可评估 transform、滚动索引与下游分析系统；搜索集群适合交互式分析，不代表所有数仓任务都应该搬进来

## 第六站：写入路径、并发与近实时

这一站让你从“会搜”升级到“知道数据为什么这样搜”。写入要经过路由、主分片、translog、refresh 和副本；每一步都可能把一次小修改变成一串有顺序的工程选择。

**单文档写入与 Bulk** ---- 单文档 API 便于低频操作，Bulk 适合批量灌入和日志采集；批次大小要用压测确定，同时关注请求体、解析 CPU、translog、拒绝数和失败重试

**幂等写入** ---- 使用稳定 `_id`、外部版本或业务事件 ID 设计重放策略；网络超时并不等于服务端没写成功，重试之前要能判断重复写、版本冲突和部分 Bulk 失败

**路由与热点** ---- 默认按文档 ID 路由到主分片，自定义 routing 可以让同一租户或用户的数据聚集以减少扇出；代价是热点租户可能压垮单个分片，路由键必须结合分布和故障域选择

**主分片写入与副本同步** ---- 写请求先到主分片，再按配置同步到副本；`wait_for_active_shards` 可以提高写入时的可用副本要求，副本数不是“写完后再补的一份文件”那么简单

**Refresh、Flush 与持久化** ---- refresh 控制搜索可见性，translog durability 与 flush 影响崩溃后的恢复路径；不要为了“马上搜到”把 refresh 调得极端频繁，也不要把 flush 当成查询刷新按钮

**更新与删除** ---- Segment 不可变使更新通常表现为旧文档删除标记加新文档写入；高频小更新会制造段和 merge 压力，适合考虑按事件重建、批量更新或重新安排索引模型

**乐观并发控制** ---- `_seq_no` 与 `_primary_term` 可用于防止旧写覆盖新写；版本冲突是并发事实的提醒，不应一律用“最后一次重试成功”把冲突吞掉

**刷新策略与 Bulk 调优** ---- 日志灌入可以放宽 refresh interval，离线导入可在隔离窗口调整副本策略；写入优化必须同时设定恢复步骤，不能留下没有副本或没有可搜索保障的索引

**摄入管道与数据清洗** ---- ingest pipeline 可做字段解析、重命名、类型转换、地理解析和失败路由；复杂 ETL、敏感数据脱敏与可重放流程常应放在采集或消息层，避免把节点 CPU 变成隐藏的 ETL 集群

## 第七站：集群、分片与数据生命周期

第七站来到集群调度室。主节点在分配座位，数据节点在搬箱子，协调节点在收集各桌的答案；分片规划错了，所有角色都会用自己的方式提醒你。

**集群状态与集群管理** ---- 集群状态包含索引、映射、分片分配和节点元数据，由具备 master 资格的节点协同维护；频繁变更索引设置、字段和模板，会给集群状态传播增加负担

**节点角色** ---- 认识 master-eligible、data、ingest、coordinating，以及 hot、warm、cold、frozen、ml 等按版本与发行版提供的角色；角色分离是资源隔离手段，不是节点越多越高级

**主分片数量的承诺** ---- 主分片数通常在索引创建时确定，后续扩容可通过 reindex、split 或 shrink 等路径完成；先按数据增长、查询并发、单分片大小和恢复时间估算，再决定数量

**分片路由与搜索扇出** ---- 一次搜索可能发往多个分片，由协调节点做 query phase、fetch phase 与结果合并；routing、别名过滤和时间索引可以减少扇出，盲目增加分片只会让每次请求问更多人

**集群健康颜色** ---- green 表示主分片与副本齐全，yellow 表示主分片可用但副本未分配，red 表示至少有主分片不可用；单节点带副本的开发环境 yellow 很常见，但生产不能把它当成“装饰色”

**索引模板与别名切换** ---- component template 复用通用设置，index template 绑定命名模式，读写别名把应用与真实索引名解耦；重建 mapping 时可用新索引接收数据并切换别名，形成可回滚的迁移边界

**Data Stream 与 Rollover** ---- 时序数据按时间或大小滚动到 backing indices，写入别名指向当前写索引；滚动条件要结合每日写入量、段合并、恢复时间和查询时间范围

**ILM 生命周期** ---- hot、warm、cold、frozen、delete 等阶段表达不同的成本与访问目标；迁移前先说明数据是否只读、是否需要搜索、是否允许压缩和恢复等待，不能只按机器价格分层

**跨集群能力** ---- Cross-cluster search 与 cross-cluster replication 可用于跨集群检索或灾备场景；网络延迟、版本兼容、权限、带宽和故障切换演练比“配上一个远端地址”更重要

## 第八站：运维、故障与容量

第八站是生产值班室。Elasticsearch 出问题时通常不会只说“我坏了”，而是用未分配分片、线程池拒绝、GC 停顿、磁盘水位和查询超时一起写一封投诉信；要按证据逐层拆解。

**堆、文件系统缓存与磁盘** ---- JVM 堆通常不应超过物理内存的一半，并要结合 JVM 压缩指针阈值与版本验证；Lucene 依赖操作系统页缓存，SSD、足够内存和稳定磁盘延迟通常比盲目扩大堆更重要

**分片容量规划** ---- 按文档增长、平均文档大小、索引开销、副本倍数、merge 临时空间和恢复窗口估算；单分片大小没有适合所有场景的神奇数字，应以恢复时间、查询延迟和节点承载做压测

**磁盘水位与只读保护** ---- 监控低水位、高水位、洪水水位和索引只读保护，提前为快照、merge 和重定位预留空间；磁盘满不仅不能写，还可能让恢复、日志和运维命令一起失去退路

**慢查询与线程池** ---- 查 search/index slowlog、任务接口、线程池队列与 rejected 计数；拒绝通常意味着过载或下游背压，不能只把线程池调大来掩盖查询、聚合或客户端批次设计问题

**JVM、断路器与字段爆炸** ---- 观察 Old GC、堆使用、fielddata、请求断路器、聚合桶和映射字段数；断路器是最后的护栏，真正的修复要回到查询上限、字段模型、聚合基数和数据清洗

**未分配分片排障** ---- 先看集群健康与分片分配解释，再检查节点离线、磁盘水位、分配过滤、副本同节点限制、版本和损坏；不要一看到 red 就直接删除索引或强行分配

**滚动重启与升级** ---- 升级前检查版本路径、插件、模板、客户端兼容与快照，按节点角色和分片分配逐步重启；先在恢复环境验证，再安排可回滚的生产窗口

**Snapshot 是备份边界** ---- 使用受支持的 snapshot repository 做增量快照和恢复演练；直接复制运行中的数据目录既不等价于快照，也不能替代恢复流程和权限检查

**监控基线** ---- 至少观察集群健康、主副本状态、分片数、文档数、磁盘、JVM、GC、refresh/flush/merge、查询与写入延迟、线程池拒绝和节点变化；指标要配告警阈值、负责人和处置手册

**故障演练** ---- 演练节点掉线、主节点切换、磁盘逼近水位、慢查询、Bulk 部分失败、snapshot restore 和跨可用区网络抖动；恢复时间与数据丢失窗口必须通过实测回答，不能靠副本数量猜

## 第九站：安全、生态与选型

最后一站要给搜索管家办身份证。搜索集群一旦暴露公网，任何一个开放的写接口都可能把成本、数据和告警一起打包寄走；安全不是部署后再贴的门牌，而是索引、客户端和快照的一部分。

**传输层与 HTTP 层 TLS** ---- 区分节点间 transport TLS、客户端访问的 HTTP TLS，以及由外部代理终止 TLS 的边界；证书 SAN、轮换、协议版本和内部信任链都要纳入演练

**认证、授权与最小权限** ---- 使用内置用户、角色、API key 或企业统一身份能力限制索引、别名、集群管理和快照仓库权限；应用不应拿管理账号查询业务索引，读写权限也应按租户和用途拆分

**密钥与审计** ---- 将密码、证书私钥和云存储凭据放入受保护的 keystore 或密钥系统，审计高风险管理操作；日志、快照和 `_source` 可能含个人信息，保留、脱敏和删除策略要有主人

**租户隔离与查询防护** ---- 在应用层固定索引与租户过滤，限制 wildcard、regexp、脚本、聚合桶、返回条数和请求体大小；只靠前端隐藏筛选条件不算隔离

**数据库与 Elasticsearch 的分工** ---- 通常由数据库保存权威事实，再通过 CDC、消息或 outbox 把可搜索投影送入 Elasticsearch；双写要考虑顺序、重放、删除、mapping 变更和对账，搜索结果不应悄悄改写支付事实

**日志与可观测生态** ---- 了解 Beats、Logstash、ingest pipeline、Kibana、APM、OpenTelemetry 与对象存储的边界；采集、解析、索引、保留和查询要按成本设计，日志不是无限期存放的黑洞

**搜索、分析与向量选型** ---- 需要全文相关度、过滤和交互式聚合时评估 Elasticsearch；事务查询留给 MySQL/PostgreSQL，重分析可评估 ClickHouse，简单站内搜索可评估专用轻量引擎，向量工作负载则比较 Elasticsearch、pgvector 与专用向量库

## 通关标准

能独立做到：画出文档从 Bulk 写入、translog、refresh、Segment、merge 到副本同步的路径；为商品或文章设计 text/keyword、多字段、nested、日期和向量 mapping；写出 bool 查询、稳定分页、高亮与聚合报表，并说明评分和 filter 的区别；根据数据量、增长速度和恢复窗口估算主分片、副本与生命周期；能从集群健康、分片分配、慢日志、JVM、磁盘和线程池拒绝中定位方向；完成一次快照恢复演练和一次字段迁移；为客户端、索引、快照和管理接口配置最小权限。达到这些标准，才算真正拥有 Elasticsearch 的搜索通行证。

## 结语

Elasticsearch 的核心不是“会写几条 JSON”，而是理解 Lucene 如何把搜索变快，理解分片如何把请求摊开，理解 refresh、merge、复制和快照如何把近实时系统变成可运维系统。把权威数据、搜索投影和分析任务放在合适的位置，你学到的就不只是一套引擎，而是一种面对复杂数据系统时先问边界、再问性能、最后问故障的工程习惯。
