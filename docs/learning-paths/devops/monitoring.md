# Prometheus + Grafana 监控学习路线

监控系统像机房里那位睡眠很浅的值班员：它不负责修 bug，却要在问题扩大前叫醒正确的人，并且把“我觉得变慢了”翻译成有时间、范围、对象和证据的事实。Prometheus 擅长采集和查询时间序列，Grafana 擅长把数据变成可读的画面，告警系统则负责把画面变成行动。

这条路线从可观测性心智模型开始，经过指标、Prometheus 架构、exporter 与埋点、PromQL、Grafana、告警、SLO、日志追踪联动、规模化、资源与成本，再到安全、排障和演进。图表不是终点，可靠的决策和可重复的响应才是。

**推荐顺序** ---- 监控与可观测性 → 指标模型与基数 → Prometheus 采集与存储 → 应用与系统指标 → PromQL → Grafana 面板 → 告警与 SLO → 日志追踪联动 → 高可用、规模与成本 → 安全、排障与演进

## 第一站：监控、可观测性与信号模型

第一站请值班员介绍望远镜。监控回答“已知问题是否发生”，可观测性更进一步，帮助你从输出推断未知内部状态；如果只做漂亮大屏，系统只是穿了西装的报警器。

**监控与可观测性** ---- 区分健康检查、监控、告警、可观测性和调试；监控面向已知症状，可观测性依赖足够丰富的结构化信号解释未知故障

**指标、日志、追踪与事件** ---- 指标适合趋势和聚合，日志适合细节，追踪适合单次请求路径，事件记录变更与控制器动作；四类信号要靠时间、服务、版本和请求标识关联

**RED 与 USE** ---- 服务关注 Rate、Errors、Duration，资源关注 Utilization、Saturation、Errors；不同层次使用不同视角，避免用 CPU 图代替用户体验

**黄金信号与业务信号** ---- 观察延迟、流量、错误、饱和度，也观察订单、支付、消息积压、转化和数据新鲜度；平台健康不等于业务成功

**症状与原因** ---- 告警优先描述用户可感知症状，再链接可能原因和排查路径；CPU 高只是线索，不能直接当成根因

**时间与标签** ---- 统一时区、采样时间、服务名、环境、区域、版本和实例标识；标签是查询维度也是成本来源，先设计语义再加标签

**行动导向** ---- 每条重要告警都应有负责人、严重级别、影响范围、抑制条件、运行手册和升级路径；没有行动的告警只是电子烟花

## 第二站：指标类型、标签与基数

第二站进入指标仓库。Counter 像只会上涨的里程表，Gauge 像会来回波动的体温计，Histogram 和 Summary 则负责描述分布；选错类型，后面 PromQL 会像拿温度计测距离。

**Counter** ---- 用于请求总数、错误总数、处理字节等单调累加量；重启会归零，查询时要用 rate 或 increase 还原速率和增量

**Gauge** ---- 表示可升可降的当前值，如内存、队列深度、并发、温度和副本数；对 Gauge 直接求 rate 往往没有清晰业务含义

**Histogram** ---- 通过桶、总和与计数描述延迟、大小和持续时间分布，适合聚合与分位数估算；桶边界要贴近 SLO，不要无限增加精度

**Summary** ---- 在客户端计算分位数，适合单实例观察但难以跨实例聚合；了解它与 Histogram 的取舍，避免把两者当成同一种数据

**标签设计** ---- 使用低基数、稳定、可解释的标签，如服务、方法、状态、环境和区域；用户 ID、请求 ID、URL 原文和异常堆栈通常不应直接成为标签

**基数与时间序列爆炸** ---- 每个标签组合形成一条时间序列，基数会增加内存、查询、远程写入和账单；控制自由文本、路径参数、容器 ID 和短生命周期实例

**命名与单位** ---- 遵循统一命名、单位和帮助文本，明确总量、当前值和分布；指标名清楚，查询和面板才能跨团队复用

## 第三站：Prometheus 架构、采集与存储

第三站请 Prometheus 讲讲它的胃口。它会按目标主动抓取指标、把样本写入本地时间序列库并在内存里建立索引；抓不到不等于目标一定坏，也可能是网络、认证、标签或采集配置出了岔子。

**Pull 模型** ---- Prometheus 按 scrape interval 从 HTTP endpoint 拉取指标，能够观察 scrape duration、样本量和失败原因；拉取模型让采集器控制节奏，也要求目标可达

**Targets 与 Service Discovery** ---- 静态目标适合简单环境，文件、云、Kubernetes、Consul 等发现机制适合动态环境；发现到的目标还要经过 relabel、过滤和权限检查

**Exporter** ---- node_exporter、数据库、黑盒、容器和云服务 exporter 把外部系统转换为 Prometheus 指标；了解 exporter 的开销、权限、版本和指标语义，不要把“装上 exporter”当成完成监控

**本地 TSDB** ---- 理解样本、时间序列、块、压缩、WAL、保留期和磁盘空间；Prometheus 重启恢复依赖 WAL，磁盘延迟和容量直接影响采集可靠性

**relabeling** ---- 在采集前后重写或丢弃目标、标签和样本，控制环境、区域、实例和敏感标签；relabel 规则复杂时用实际目标与样本验证，避免悄悄丢掉关键数据

**Pushgateway 的边界** ---- 短生命周期批处理可用 Pushgateway 保存最后结果，但它不是通用推送总线；实例消失后旧指标可能继续存在，必须设计清理和语义

**Remote write 与读取** ---- 将样本发送到长期存储或集中查询系统，关注队列、重试、压缩、网络、租户和回压；远程系统故障时要知道本地还能保留多久

## 第四站：系统、应用与运行时指标

第四站让监控员学会看不同房间。系统指标告诉你宿主机是否喘气，运行时指标告诉你进程是否在积压，应用指标告诉你用户是否被挡在门外；缺一层都可能把故障认错。

**主机资源** ---- 采集 CPU 使用与饱和、内存与 swap、磁盘空间与 I/O、网络带宽与错误、文件描述符和负载；关注利用率之外的队列、延迟和失败

**进程与运行时** ---- 观察进程数、线程、GC、堆、连接池、文件句柄、事件循环、线程池和容器 cgroup；进程存活不代表运行时没有卡死

**服务指标** ---- 为请求速率、状态码、延迟直方图、并发、超时、重试、熔断和依赖错误建立指标；指标命名与标签要保证能按服务、接口和版本聚合

**队列与异步任务** ---- 观察队列深度、最老消息年龄、消费速率、重试数、死信数和处理延迟；队列短暂增长不一定坏，但年龄持续增长通常意味着吞吐不足

**数据库与缓存** ---- 关注连接、锁、慢查询、命中率、复制延迟、磁盘和事务；缓存命中率漂亮也可能掩盖源站错误，必须和业务结果关联

**Kubernetes 与调度** ---- 监控 Pending 时间、调度失败、节点资源、驱逐、重启、探针、期望副本与实际副本；平台对象指标要和应用请求指标串起来

**黑盒探测** ---- 从用户视角检查 DNS、TCP、TLS、HTTP、关键业务动作和证书到期；黑盒发现“真的不可用”，白盒解释“为什么不可用”，两者互补

## 第五站：PromQL 查询语言

第五站是 PromQL 厨房。它能把一锅时间序列变成速率、比例、分位数和预测，但查询写得越长不等于越聪明；先定义问题和时间窗口，再决定函数。

**选择器与过滤** ---- 用标签选择器缩小服务、环境、方法和状态范围，理解精确匹配、正则、否定和缺失标签；查询前先估算基数和结果量

**rate 与 increase** ---- 对 Counter 计算每秒速率或时间窗口增量，理解重启、抓取间隔和窗口长度；窗口太短噪声大，太长反应慢

**聚合与分组** ---- 使用 sum、avg、min、max、count、topk 按需要保留或丢弃标签；聚合会改变语义，先写清“每个结果代表什么”

**比例与错误率** ---- 用错误请求数除以总请求数，保持分子分母的标签维度可对齐；空数据、零分母和低流量要有明确展示与告警策略

**Histogram 分位数** ---- 用 histogram_quantile 配合桶速率估算 P50、P95、P99；分位数不是平均值，桶设计和聚合维度会影响解释

**时间函数与预测** ---- 认识 absent、changes、resets、predict_linear、deriv、delta 和时间偏移；预测适合容量提醒，不应替代真实故障信号

**Recording rules** ---- 将昂贵、常用或统一口径的查询预计算为新指标，降低面板和告警延迟；规则版本要评审，避免把错误口径固化成平台标准

## 第六站：Grafana 面板与信息设计

第六站轮到 Grafana 布置客厅。它最喜欢把十八张彩色图挂满墙，但优秀面板不是灯光秀，而是让值班员在几十秒内知道影响、范围、时间线和下一步。

**面板层次** ---- 先放 SLO、请求量、错误率、延迟和饱和度，再放实例、依赖和细节；用户看板与运维看板的目标不同，不要一张图服务所有人

**变量与下钻** ---- 用环境、区域、服务、实例和版本变量复用面板，链接到日志、追踪、主机和发布页面；变量取值要防止高基数与空结果

**时间范围与采样** ---- 默认时间窗口覆盖常见故障，支持发布前后对比；面板查询要考虑 step、分辨率、数据保留和大时间范围的成本

**图表选择** ---- 时间序列看趋势，Stat 看当前摘要，表格看排行，热力图看分布；图形类型服务于决策，不要为了看起来热闹而增加噪声

**注释与变更** ---- 在面板标记部署、配置、扩容、故障和维护事件；没有变更时间线的曲线，常常只能让大家一起猜

**权限与租户** ---- 用文件夹、数据源、团队、行级权限和只读角色隔离环境与业务；Grafana 的数据源凭据不应通过面板变量泄露

**面板即代码** ---- 用版本控制管理 Dashboard、数据源和告警规则，经过校验与评审发布；手工点击的生产面板迟早会变成“只有某个人看得懂”的遗迹

## 第七站：告警、Alertmanager 与 SLO

第七站是通知中心。告警像消防铃，响多了大家会拔电池，响少了又会错过火情；真正的目标不是制造更多红色，而是让有限的注意力在正确时刻流向正确的人。

**阈值与趋势告警** ---- 用静态阈值捕捉明确风险，用持续时间、变化率、预测和基线捕捉趋势；短暂尖峰是否告警要看用户影响与恢复能力

**告警标签与注释** ---- 给告警写严重级别、服务、环境、负责人、摘要、影响、运行手册和聚合键；标签用于路由，注释用于读者，二者不要混用

**Alertmanager 路由** ---- 学会分组、抑制、静默、路由、重复通知和接收器；部署、节点和服务告警要按责任边界路由，避免全员收到同一场烟花

**告警生命周期** ---- 关注 pending、firing、resolved、for、keep_firing_for 和数据缺失；Prometheus 重启、采集失败和目标消失的语义要提前测试

**SLO、SLI 与错误预算** ---- 以可用性、延迟、正确性和新鲜度定义 SLI，用目标形成 SLO，用剩余预算指导发布速度与风险；SLO 是决策工具，不是装饰指标

**多窗口多燃烧率** ---- 了解快速与慢速错误预算消耗的组合，平衡早发现与低噪声；告警复杂时先解释它保护的用户承诺

**通知可靠性** ---- 监控告警链路自身的采集、评估、路由、发送、接收和升级；告警系统失明时必须有备用路径与值班演练

## 第八站：日志、追踪与发布联动

第八站让几位侦探互换线索。指标先说“哪里不对”，日志补充“发生了什么”，追踪展示“哪一跳变慢”；再把发布版本贴上去，时间线才有机会从悬疑片变成纪录片。

**结构化日志** ---- 统一时间、级别、服务、环境、版本、请求 ID、trace ID、错误类型和安全脱敏；日志字段要稳定，不能每个服务都发明一套方言

**日志与指标关联** ---- 从错误率、延迟或队列告警下钻到对应服务、实例、版本与日志；避免把完整堆栈塞进指标标签

**分布式追踪** ---- 透传 trace context，观察入口、服务、队列、缓存和数据库跨度；采样策略要兼顾成本、错误保留和关键业务路径

**发布标记** ---- 将提交、镜像摘要、配置版本、迁移批次和发布事件写入指标、日志和面板注释；故障与变更的时间对齐往往比更复杂的查询更有用

**黑盒与白盒联动** ---- 黑盒确认用户路径，白盒解释组件内部；当两者结论不一致时，优先检查探测路径、缓存、区域与采样范围

**业务可观测性** ---- 为支付成功、订单延迟、库存一致性、消息年龄和数据新鲜度建立业务信号；平台指标正常而业务指标异常时，不能把问题标记成“无告警”

## 第九站：高可用、规模、资源与成本

第九站是监控系统的体检室。Prometheus 自己也会生病：采集太多、标签太花、查询太重、远程写入堵塞、磁盘太满，最后它可能比被监控对象更需要告警。

**高可用采集** ---- 了解双 Prometheus、去重、联邦、分片、集中远程写入和查询层的组合；高可用不仅是复制进程，还要避免重复告警与口径冲突

**采集规模** ---- 评估目标数、抓取间隔、每次样本量、标签基数、规则数量、查询并发和保留期；规模增长先治理数据模型，再堆机器

**查询与规则性能** ---- 用 recording rules、合理窗口、聚合前过滤、限制 dashboard 并发和分层数据源控制开销；慢查询需要找到高成本表达式，不是盲目加 timeout

**存储与保留** ---- 按故障响应、趋势分析、审计和合规设本地与长期保留；高精度短期数据与低精度长期数据可以分层，避免所有数据都永久保存

**远程系统与网络** ---- 关注 remote write 队列、重试、压缩、跨区流量、租户配额和回压；网络中断时定义丢弃、缓冲和恢复策略

**监控成本** ---- 成本来自采集器、存储、查询、日志、追踪、网络、Grafana 资源和人工值班；删除无行动价值的指标通常比优化一条查询更划算

**容量告警** ---- 为磁盘、WAL、内存、抓取失败、规则延迟、查询延迟和样本拒绝设置告警；监控平台的容量问题必须在它失明前暴露

## 第十站：安全、排障与演进

最后一站是监控员的职业道德课。监控系统拿着全公司的放大镜，既能看见秘密也能放大噪声；安全、权限、脱敏、证据保留和产品化都属于监控本身的可靠性。

**采集安全** ---- 为 scrape endpoint、exporter、remote write、Grafana 数据源和 Alertmanager 配置 TLS、认证与网络边界；不要为了方便把所有指标端点暴露到公网

**敏感数据治理** ---- 标签、日志、追踪和面板可能包含用户标识、令牌、路径和业务数据；定义脱敏、访问、保留、删除和审计规则

**排障顺序** ---- 先确认用户影响与时间范围，再看告警是否可信、目标是否采集、指标是否有数据、日志和追踪是否关联、最近是否发布；区分“系统坏了”和“监控看不见”

**监控自监控** ---- 监控 scrape failures、规则评估延迟、告警发送、数据缺失、远程写入、存储水位和查询错误；监控系统没有自监控，就像值班员没有手表

**运行手册与演练** ---- 每条重要告警都链接分层排查、缓解、升级、回滚和恢复步骤；定期模拟采集器、通知渠道、存储和区域故障

**从单体到平台** ---- 从单机 Prometheus + Grafana 起步，逐步加入服务发现、统一标签、日志、追踪、SLO、长期存储和多租户；每一步都以数据规模和行动需求为依据

**开放标准与迁移** ---- 理解 Prometheus exposition、OpenMetrics、OTel、远程读写和兼容查询；对外部平台保持可迁移的指标命名、资源模型和制品管理

## 通关标准

能为一个服务设计 RED、业务 SLI、运行时、依赖和发布指标，并控制标签基数；能解释 Prometheus pull、target、relabel、TSDB、WAL、remote write 与 exporter 的边界；能用 PromQL 写出错误率、速率、分位数、队列年龄和容量趋势查询；能制作一张面向值班的 Grafana 面板；能设计有路由、抑制、静默、运行手册和备用通知的告警；能把指标、日志、追踪、事件和发布版本串成故障时间线；能算清采集、存储、查询和人工响应的成本。

## 下一站去哪

把监控接到 Linux、Docker、Kubernetes 与 CI/CD，形成从主机、容器、集群到发布的统一信号；再进入云原生模式，学习如何把健康检查、SLO、降级和可观测性从运维补丁变成应用设计。

## 结语

好的监控不是把所有数据都留下，而是让重要问题更早、更准确、更少打扰地到达负责的人。先定义用户承诺和行动，再选指标、查询和图表；当告警能推动一次可靠的判断与恢复，Prometheus 和 Grafana 才真正完成了工作。
