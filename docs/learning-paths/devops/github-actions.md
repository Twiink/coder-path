# GitHub Actions 学习路线

GitHub Actions 是代码仓库里那位按事件上班的自动化管家：有人推送代码，它醒来跑测试；有人打标签，它开始打包发布；有人开 Pull Request，它端着检查清单来审核。它很灵活，也很容易被一份 YAML 养成“什么都做、哪里都能写”的巨型管家，所以学习重点是边界、权限、证据和可回滚。

这条路线从 Workflow、Job、Step 和 Runner 的关系开始，经过触发、上下文、缓存、矩阵、制品、Secrets、OIDC、自定义 Action、部署与观测。先学会一次任务如何被调度和隔离，再谈怎样让流水线更快、更便宜、更安全。

**推荐顺序** ---- 工作流模型与 Runner → 触发器与上下文 → Step、Job 与依赖 → 矩阵、缓存与制品 → 资源和并发调度 → Secrets、OIDC 与权限 → 测试和质量门禁 → 发布与部署 → 复用与自定义 Action → 可靠性、可观测性、成本与演进

## 第一站：Workflow、Job、Step 与 Runner

第一站先给自动化管家分配工牌。Workflow 是一趟完整流程，Job 是一间独立工作室，Step 是具体动作，Runner 是真正干活的机器；把它们混成“一个脚本”，出了问题就没人知道该找谁。

**Workflow** ---- 由事件触发的一份声明式工作流文件，表达触发条件、权限、并发、Job 与环境；文件本身是交付物，要经过代码评审和版本管理

**Job** ---- 一组在同一个 Runner 上执行的 Step，拥有独立工作目录和默认隔离边界；Job 之间不共享未声明的文件和进程

**Step** ---- 运行命令或调用 Action 的最小动作，前一步失败通常会阻止后续步骤；关键清理、上传日志或回收资源需要明确失败时是否仍执行

**Runner** ---- GitHub 托管 Runner 或自托管 Runner 执行 Job；运行环境、镜像、工具版本、CPU、内存、磁盘和网络出口都影响结果

**Action** ---- 可复用的步骤封装，可能是 JavaScript、Docker 或复合 Action；使用第三方 Action 前固定版本、查看权限和维护状态，不要让供应链替你写代码

**工作区与生命周期** ---- 理解 checkout、临时工作目录、环境变量、缓存目录、日志和 Job 结束后的清理；不要假设下一个 Job 会看到当前 Job 的文件

**最小工作流** ---- 能从检出代码、安装依赖、运行测试到上传结果讲清事件链；第一份工作流越小，后续定位越不容易变成 YAML 考古

## 第二站：触发事件、上下文与表达式

第二站的触发器像一位很爱看日历和通知的秘书。它会在 push、Pull Request、tag、手工点击或定时事件时敲门，但“什么时候触发”和“触发后允许做什么”必须分开设计。

**常见事件** ---- 掌握 push、pull_request、pull_request_target、workflow_dispatch、workflow_call、schedule、release、workflow_run 和 repository_dispatch 的边界；高权限事件尤其要理解不可信代码的风险

**分支与路径过滤** ---- 用分支、标签、路径和忽略规则减少无效运行；过滤条件要覆盖文档、依赖、配置和生成文件的影响，别因为省几分钟而漏掉关键检查

**手动与定时调度** ---- workflow_dispatch 适合带输入的人工流程，schedule 适合周期任务；定时任务可能延迟、重复或错过，任务本身要幂等并记录上次处理位置

**上下文 Context** ---- 理解 github、env、vars、secrets、inputs、matrix、needs、runner、job 和 steps 上下文；上下文值可能来自外部输入，进入命令时必须防止注入

**表达式与条件** ---- 掌握 success、failure、cancelled、always、contains、startsWith、fromJSON 等表达式的用途；条件越复杂越要拆成有名字的 Job 或脚本，避免一行谜语

**事件身份与权限** ---- 区分事件发起者、提交作者、触发工作流的令牌与审批人；不能根据用户名、分支名或提交信息直接授予部署权限

## 第三站：Job 依赖、矩阵与运行资源

第三站来到流水线的交通枢纽。Job 可以并行，也可以按依赖排队；矩阵像复制出一支测试小队，效率很高，但每个小队成员都要占 Runner、分钟数和缓存空间。

**needs 与 DAG** ---- 用 Job 依赖表达构建、测试、扫描、发布和部署顺序；有依赖才等待，没依赖就并行，别用一个巨型 Job 把所有阶段绑成单车道

**并行与矩阵** ---- 按操作系统、运行时版本、数据库版本或架构扩展测试；矩阵要限制维度、排除无效组合，并设置失败策略以避免一个实验版本拖垮全部反馈

**Runner 标签与调度** ---- 用 runs-on 选择托管或自托管 Runner，理解标签匹配、队列、可用区、架构和专用硬件；标签写得太宽会跑错环境，写得太窄会长期排队

**超时与取消** ---- 为 Job 与 Step 设置 timeout，利用并发组取消过时的同分支运行；取消策略要保护正在进行的生产部署和迁移

**环境变量与工作目录** ---- 区分工作流、Job、Step、Runner 和脚本级环境，了解默认 Shell、换行、路径和平台差异；脚本应显式指定关键工具版本与工作目录

**服务容器** ---- 用 service containers 提供数据库、缓存和消息服务，理解端口、健康等待、网络、数据清理和版本固定；测试依赖要尽量临时且可重复

**自托管 Runner** ---- 关注持久工作区、残留凭据、容器逃逸、网络权限、补丁、自动扩缩和任务隔离；不可信 Pull Request 不应在带生产凭据的常驻 Runner 上执行

## 第四站：缓存、制品与可复现构建

第四站是流水线仓库管理员。缓存喜欢把旧东西留着，制品负责把结果交出去；两者都很有用，但把缓存误当成制品，发布时就会发现“昨天的幽灵还在包里”。

**依赖缓存** ---- 缓存包管理器下载目录和工具目录，设计稳定键、操作系统、架构与锁文件哈希；缓存命中只能加速，不能成为构建正确性的前提

**缓存失效与污染** ---- 理解 restore key、缓存不可变、跨分支读取和缓存污染风险；依赖升级、编译器升级或安全修复后要主动失效旧缓存

**Artifacts** ---- 上传测试报告、覆盖率、日志、二进制和部署包，设置保留期与访问权限；制品应能关联提交、构建、工具链和签名

**依赖传递** ---- 通过 needs、artifact 下载和显式名称把构建结果传给下游 Job；不要依赖 Runner 工作区残留文件或隐式全局路径

**可复现构建** ---- 固定锁文件、基础镜像、Action 版本、编译器和时区，记录构建元数据；在不同 Runner 上重复构建，才能发现“只在某台机器成功”的幻觉

**测试结果与失败证据** ---- 即使测试失败也尽量保存报告、日志、崩溃转储和诊断信息；让失败可读，比只给一个红叉更接近工程质量

## 第五站：Secrets、OIDC 与供应链安全

第五站由安全管家接手。它最怕两件事：不可信代码捡到生产钥匙，以及可信流水线把钥匙打印在日志里；权限少一点，审计清楚一点，半夜就少一通电话。

**GITHUB_TOKEN 权限** ---- 在工作流和 Job 层显式设置 contents、pull-requests、packages、actions 等最小权限；默认权限不应靠平台历史设置猜测

**Secrets 与 Variables** ---- 区分机密 Secrets、非机密 Variables、环境级保护和组织级配置；秘密会被掩码但不是不可见，避免拼接、回显和写入制品

**环境审批** ---- 生产 Environment 可以配置保护规则、审批人和环境秘密；审批是人为闸门，仍需自动测试、变更记录和回滚路径

**OIDC 短期身份** ---- 用工作流身份向云平台换取短期凭证，按仓库、分支、环境和工作流声明限制信任；它能减少长期云密钥，但信任策略写错同样危险

**不可信输入与脚本注入** ---- Pull Request 标题、分支名、Issue 内容和提交信息都可能是外部输入；不要直接拼进 shell 命令或脚本，使用安全参数传递与白名单

**第三方 Action 供应链** ---- 固定 Action 到不可变提交或可信版本，审查维护者、权限、网络和 Dockerfile；依赖更新要有扫描、变更记录和回滚

**制品安全** ---- 生成 SBOM、扫描依赖与镜像、签名制品并在部署端验证；CI 通过不等于制品可以无条件进入生产

## 第六站：测试、质量门禁与开发反馈

第六站像一位不太会说好听话但很有用的审稿人。它不只问“测试有没有跑”，还问测试跑的是不是正确版本、失败有没有证据、质量门禁能不能阻止坏制品出门。

**分层测试** ---- 组合单元、静态检查、类型检查、集成、端到端、契约、安全和性能测试；快速反馈放前面，昂贵测试按风险与发布阶段安排

**依赖与服务隔离** ---- 固定依赖版本，使用服务容器或临时环境，准备初始化、迁移和清理；测试数据要隔离，不能让并行 Job 互相踩脚

**质量门禁** ---- 让测试、覆盖率、漏洞、格式、许可证和人工评审成为明确的阻断条件；门禁例外必须有期限、负责人和记录

**失败重试** ---- 只对确认的基础设施瞬态错误有限重试，不要重试断言失败、编译失败和权限错误；重试应暴露原始日志，否则流水线会学会掩盖问题

**变更影响与路径优化** ---- 使用路径过滤、依赖图或可选工作流减少无关运行，但关键共享库和工作流自身变更必须触发全量验证

**开发者体验** ---- 提供清晰的 Job 名、分组日志、失败摘要、链接和本地复现命令；最快的流水线不是最会跳过检查的，而是最早告诉你真正哪里坏了的

## 第七站：发布、制品与部署

第七站是发布台。构建完成只是包裹封好，发布还要核对版本、环境、审批、迁移、流量和回滚；Actions 可以按下按钮，却不能替你判断按钮是否该按。

**版本与制品映射** ---- 将提交 SHA、标签、构建号、镜像摘要、包校验和 SBOM 关联；部署只引用已验证制品，不在生产现场重新编译

**发布触发** ---- 区分分支构建、标签发布、Release、手动发布和上游工作流完成；生产发布应避免由任意分支的普通 push 直接触发

**环境分层** ---- 设计开发、测试、预发布、生产的变量、权限、网络和数据边界；环境名不能只是显示文字，它应真正影响授权与资源

**部署目标** ---- GitHub Pages、对象存储、虚拟机、容器仓库、Kubernetes、云平台和自托管服务的凭据与回滚方式不同；先选部署接口，再设计 Job

**滚动、蓝绿与金丝雀** ---- 发布 Job 负责交付制品，平台或脚本负责逐步切流、健康检查和自动回滚；观察错误率、延迟、业务指标与资源，而不只是命令返回 0

**数据库迁移** ---- 将扩展、回填、切换、收缩拆成兼容阶段，确保新旧应用短暂共存；失败时先保护数据，再决定回滚应用或前进修复

**回滚** ---- 保留上一个可用制品、配置与迁移策略，定义谁能触发、如何验证和何时停止回滚；回滚不是删除最新代码，而是恢复已证明可用的状态

## 第八站：复用、Reusable Workflow 与自定义 Action

第八站让自动化管家学会带徒弟。复用能减少复制粘贴，但抽象过度会让每个项目都要先读一部 YAML 史诗；好的复用隐藏重复，保留关键决策。

**Reusable Workflow** ---- 用 workflow_call 暴露输入、秘密、输出与权限，适合跨仓库共享完整流程；接口要版本化，调用方要能锁定版本并安全升级

**复合 Action** ---- 把一组 Shell 步骤封装成局部动作，适合仓库内重复逻辑；输入输出、Shell、平台差异和错误处理要明确

**JavaScript 与 Docker Action** ---- 了解运行环境、启动耗时、依赖打包、Node 版本和容器平台限制；只在复用价值明确时写自定义 Action，不要给一条命令建一座城

**输出与数据流** ---- 用 outputs 和 artifacts 传递结构化结果，避免通过日志解析状态；输出不要包含秘密，命名要稳定

**版本与兼容性** ---- 使用语义版本或提交固定引用，记录弃用字段、迁移方式和支持矩阵；复用组件的变更影响多个仓库，测试要覆盖调用方场景

**权限继承** ---- 复用工作流不会自动获得调用方想象中的权限；明确 `permissions`、环境保护和秘密传递，默认按最小能力设计

## 第九站：可观测性、可靠性与成本

第九站是流水线的值班室。它不会只盯着成功率，还会观察排队时间、执行时间、失败类型、重试次数和分钟数；因为一条“绿色但贵得离谱”的流水线，依然是生产问题。

**运行可观测性** ---- 记录 Workflow、Job、Step、提交、环境、Runner、制品和部署版本；保留失败日志、测试报告、审批记录和取消原因

**关键指标** ---- 关注触发到反馈的 Lead Time、队列时延、执行时长、成功率、重试率、变更失败率和恢复时间；按仓库、分支、Runner 与阶段分组观察

**失败分类** ---- 区分代码失败、依赖失败、Runner 异常、网络/服务限流、权限失败和供应链阻断；分类后才能决定修代码、重跑、扩容还是换依赖

**并发与取消** ---- 按分支、环境或部署目标设置 concurrency，取消过时验证但保护生产中的不可中断步骤；并发控制同时影响反馈速度、资源和成本

**Runner 资源** ---- 监测 CPU、内存、磁盘、网络、工具缓存和队列；自托管 Runner 要做补丁、隔离、自动清理和故障替换

**成本治理** ---- 通过路径过滤、合理矩阵、缓存、预装工具、按需 Runner、日志保留和制品生命周期控制费用；省钱不能以跳过安全与关键测试为代价

**恢复与重跑** ---- 设计幂等 Job、可重入部署、断点制品和人工重跑入口；重跑同一提交应得到可解释的结果，而不是依赖上次 Runner 恰好留下的文件

## 第十站：平台演进与边界

最后一站是自动化管家的职业规划。Actions 适合围绕 GitHub 事件快速组合流程，但不是万能调度器；当任务需要复杂队列、长期运行、专用网络或强隔离时，要把职责交给更合适的平台。

**适合的范围** ---- 代码检查、构建测试、制品打包、镜像发布、短流程部署、定时维护和仓库自动化是它的强项；任务应可重复、可观察、可安全重跑

**不适合的范围** ---- 长时间计算、强状态工作流、复杂数据管道、持续高吞吐构建、严格内网隔离或复杂多租户调度可能需要专用 CI、工作流引擎或云平台

**从脚本到平台** ---- 先统一命名、权限、制品和观测，再抽取复用工作流；平台标准化要保留例外通道，不能把所有团队塞进同一个模板

**版本与弃用治理** ---- 定期升级 Runner、Action、Node、基础镜像和工具链，跟踪弃用通知与安全公告；升级要分批、可回滚并保留兼容窗口

**灾备与供应商边界** ---- 保存关键制品、工作流定义、部署配置和恢复凭证；理解 GitHub 服务、Runner、云平台和外部仓库各自的可用性边界

## 通关标准

能独立设计一条从 Pull Request 检查到生产发布的工作流：说清触发事件、权限、Runner、Job 依赖、缓存、制品、审批、部署、健康检查与回滚；能用矩阵覆盖合理的平台组合而不造成资源浪费；能用 OIDC 和最小权限替代长期云密钥；能识别不可信输入与第三方 Action 风险；能从日志、测试报告、队列、指标和制品映射还原一次失败；能根据规模、隔离、成本和状态需求判断 Actions 与其他平台的边界。

## 下一站去哪

如果团队主仓库在 GitHub，继续把 Actions 与容器仓库、Kubernetes、云平台和监控接起来；如果需要 Runner、DAG、环境、资源组和多项目流水线的另一套模型，再学习 GitLab CI。

## 结语

GitHub Actions 的核心不是会写几段 YAML，而是能把一次变更变成有身份、有证据、有门禁、可回滚的交付过程。把权限和制品当成一等公民，把失败当成信息而不是噪声，流水线才会从“自动执行命令”进化成“自动守住质量”。
