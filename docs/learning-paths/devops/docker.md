# Docker 学习路线

Docker 是软件交付界那位爱整理行李的搬家师傅：应用、依赖、启动方式和一部分系统环境被装进镜像，到了另一台机器也尽量按同一套方式醒来。它并没有把 Linux 变没，而是把 Linux 的 namespace、cgroup、文件系统和网络能力包装成了更容易交付的工作流。

这条路线按“先理解运行时，再学构建与编排”的顺序展开。镜像解决交付一致性，容器解决进程生命周期，网络和卷解决边界问题，Compose 解决本地多服务，仓库与流水线解决发布；最后再判断什么时候应把调度交给 Kubernetes 或其他平台。

**推荐顺序** ---- 镜像与运行时 → 容器生命周期 → Dockerfile 与构建 → 网络 → 存储与状态 → Compose → 仓库与发布 → 安全与供应链 → 资源、性能与可观测性 → 可靠性、成本与演进

## 第一站：镜像、容器与 Docker Engine

第一站先认识 Docker 家庭成员。镜像是爱打包的静态成员，容器是出门上班的运行实例，Engine 则是那个负责把大家真正叫醒的管家；把三者混在一起，后面每个命令都会显得像玄学。

**镜像 Image** ---- 镜像是由多层只读文件系统与元数据组成的内容寻址对象；它描述文件、环境和默认入口，不等于一个正在运行的应用

**容器 Container** ---- 容器是镜像加可写层、进程、网络和资源约束的运行实例；容器删除后可写层消失，持久数据和配置必须放到明确的外部边界

**仓库 Registry** ---- Registry 保存、分发和鉴权镜像，镜像引用通常包含仓库、命名空间、名称和标签；标签便于人读，摘要才是不可变的交付凭证

**Docker CLI 与 Engine** ---- CLI 通过 API 与 Docker daemon 通信，daemon 负责镜像、容器、网络和卷；远程 Docker socket 本身就是高权限入口，不能随意暴露

**Containerd、runc 与 OCI** ---- 了解 Docker 常见的底层链路：Engine 调度 containerd，containerd 调用 OCI runtime，runc 根据 Linux 内核能力创建进程隔离；这解释了 Docker 与其他容器运行时为何能互操作

**安装与权限** ---- 区分 Docker Desktop、Linux Docker Engine、rootless 模式和云平台容器服务；加入 docker 组通常等价于获得主机级能力，开发方便与生产安全要分开评估

**第一次运行的事件链** ---- 理解 pull、解包、创建容器、挂载层、配置 namespace/cgroup、启动入口进程和发布端口的顺序；命令成功只说明容器被启动，不说明应用已经就绪

## 第二站：容器生命周期与运行边界

第二站的容器像一只很听话但记性不好的宠物：可以启动、停止、重启和检查，却不会替你永久保管文件。你要先把“进程活着”和“服务可用”分开，才能少被假绿灯骗到。

**创建、启动与退出** ---- 区分 `create`、`start`、`run`、`stop`、`kill`、`restart`、`rm` 和 `prune` 的生命周期含义；停止是给进程收尾时间，kill 是直接发送强信号

**入口与信号** ---- 理解 exec 形式和 shell 形式入口的差异，掌握 PID 1、信号转发和僵尸进程回收；应用要能接收 TERM 并优雅关闭，否则滚动发布会变成集体断电

**容器状态** ---- 查看 created、running、paused、restarting、exited、dead 等状态，结合退出码和日志判断原因；restart policy 能拉起进程，但不能修复持续崩溃、错误配置或坏数据

**环境与配置** ---- 用环境变量、只读挂载、启动参数和秘密管理注入配置；镜像应尽量保持可移植，环境差异放在运行时，不要把生产密钥烘进镜像

**检查与进入** ---- 用 inspect、logs、exec、top、events 和 stats 观察容器；`exec` 进去修改的内容只存在于当前容器层，修复应回到 Dockerfile、配置或源代码

**健康检查与就绪** ---- 区分进程存活、容器健康和业务就绪；健康检查要有超时、重试、启动宽限期和依赖边界，避免数据库尚未启动时把整个系统误判为故障

**资源约束** ---- 为 CPU、内存、进程数、块 I/O 和重启次数设置边界，理解硬限制、软限制、OOM kill 与宿主机资源争抢；容器没有设置限制，不代表它拥有无限资源

## 第三站：Dockerfile、层缓存与镜像构建

第三站是镜像厨师学校。Dockerfile 写得好，构建快、镜像小、漏洞少；写得差，构建上下文像把整个仓库搬进厨房，最后连 `node_modules` 都烤进了成品。

**基础镜像选择** ---- 比较官方镜像、distroless、slim、alpine 和企业基础镜像的兼容性、体积、补丁周期与调试能力；不要为了几 MB 盲选最小镜像，先验证 libc、证书、时区和诊断工具

**常用指令** ---- 理解 FROM、RUN、COPY、ADD、WORKDIR、ENV、ARG、EXPOSE、USER、ENTRYPOINT、CMD 和 HEALTHCHECK 的构建时与运行时语义；`EXPOSE` 只是元数据，不会自动开放端口

**构建上下文** ---- 用 `.dockerignore` 排除 Git 历史、依赖目录、构建产物、凭据和大文件；上下文会影响上传时间、缓存命中和秘密泄露风险

**层与缓存** ---- 每个变化的构建步骤会影响后续缓存；把稳定的依赖清单放在前面、变化频繁的源码放在后面，并理解缓存不能替代依赖锁定和可复现构建

**多阶段构建** ---- 在构建阶段保留编译器和测试工具，在运行阶段只复制产物；把编译环境与运行时分开，是瘦身、减小攻击面和降低拉取成本的共同手段

**构建参数与可复现性** ---- 区分 ARG、ENV、标签、摘要、时间戳和依赖锁文件；固定基础镜像摘要、记录构建元数据并尽量让同一源码得到可验证的同一产物

**非 root 与文件权限** ---- 创建专属用户、收紧目录权限、使用只读根文件系统并明确可写目录；镜像里的 root 不是“方便一点”，而是发生逃逸或漏洞时更大的爆炸半径

**构建检查** ---- 使用 lint、镜像历史、SBOM、漏洞扫描和体积分析检查 Dockerfile；不要靠删除包管理缓存掩盖真正的依赖设计问题

## 第四站：容器网络与服务发现

第四站的容器终于要交朋友了。默认网络像小区门禁，自定义网络像通讯录；IP 会换，服务名更稳定，端口映射也不是“容器内部端口自动变成公网端口”。

**网络命名空间** ---- 每个容器通常有独立网卡、路由表和端口空间；容器内监听端口只是本命名空间可见，外部访问要经过网络连接或端口发布

**bridge 与自定义网络** ---- 默认 bridge 适合简单实验，自定义 bridge 提供更清晰的隔离与内置名称解析；同一网络中的服务按名称通信，不应把动态容器 IP 写进配置

**端口发布** ---- 区分容器端口、宿主机端口、监听地址、NAT 和暴露范围；绑定到 localhost 与绑定到所有网卡的安全含义不同，开发机和服务器的默认策略也不同

**host、none 与其他模式** ---- 了解 host 网络减少隔离和 NAT，但会牺牲端口隔离；none 适合完全不需要网络的任务；模式选择应从延迟、隔离、可观测和安全需求出发

**DNS 与连接重试** ---- Compose 网络中的服务名解析会随容器变化，应用应处理启动顺序、DNS 短暂失败、连接超时和重连；`depends_on` 通常不等于“依赖已可用”

**代理、TLS 与出站网络** ---- 了解 HTTP 代理、企业根证书、出站白名单、DNS 解析器和 TLS 证书挂载；容器能访问互联网不代表它应该访问互联网

**网络排障** ---- 依次确认容器是否在同一网络、名称是否解析、端口是否监听、路由是否正确、宿主机策略是否放行，再看应用协议和认证；不要一上来重建所有容器

## 第五站：卷、挂载与有状态服务

第五站请数据管理员登场。容器可以随时换班，数据库却不喜欢被当成一次性纸杯；只要说不清数据放在哪里、谁能写、怎么备份，就还没有真正运行有状态服务。

**可写层的边界** ---- 容器可写层适合临时文件与运行变化，不适合数据库、上传文件和长期日志；容器重建、迁移或清理后，可写层不应承载业务真相

**命名卷 Volume** ---- Docker 管理卷的生命周期与挂载点，适合持久数据和跨容器复用；备份卷时要考虑一致性、权限、版本和恢复演练，而不是只复制某个目录

**绑定挂载 Bind Mount** ---- 将宿主机路径挂入容器，适合开发源码、明确配置和特定主机集成；它暴露宿主机路径与权限，生产使用要限制范围并优先只读

**tmpfs 与临时状态** ---- tmpfs 把数据放进内存，适合短期秘密、缓存或高速临时文件；重启即丢，且会消耗内存，不能把它伪装成可靠存储

**UID、GID 与挂载权限** ---- 容器用户和宿主机目录属主不一致时会 Permission denied；通过统一 UID、初始化权限、组权限或专门的卷驱动解决，不要直接把目录改成 777

**数据库与备份** ---- 容器化数据库仍要做一致性备份、日志归档、恢复验证、升级测试和磁盘监控；容器只改变运行方式，不会自动赠送高可用与数据安全

**卷驱动与外部存储** ---- 认识 NFS、云盘和第三方 volume plugin 的延迟、锁、可用区和故障边界；跨主机调度前先确认卷能否跟着工作负载移动

## 第六站：Docker Compose 与本地编排

第六站是多容器合租公寓。Web、API、数据库、缓存和观测组件各住一间房，Compose 负责写房屋平面图，但它不是生产级集群调度器，别让一份本地租约突然承担跨可用区的使命。

**Compose 模型** ---- 以 services、networks、volumes、configs 和 secrets 描述一组相关资源；文件应表达服务边界、依赖、端口、卷、环境与健康检查

**依赖与就绪** ---- `depends_on` 可表达启动依赖，但应用仍需等待、重试和健康判断；把“先启动”与“可接收业务流量”分开设计

**开发与测试环境** ---- 用 Compose 复现数据库、消息队列、对象存储模拟器和观测组件；开发覆盖挂载、测试数据初始化与隔离要清楚，避免本地卷污染下一次测试

**环境覆盖与配置校验** ---- 认识 `.env`、变量插值、多文件覆盖和 `config` 校验；把默认值、开发值和生产值分开，避免把本地调试配置悄悄带进发布

**网络、卷与日志管理** ---- 为服务定义专用网络和卷，限制不必要的端口，只让需要的服务互通；统一日志输出、轮转和清理策略，防止本地磁盘被数据库和调试日志瓜分

**Compose 的边界** ---- 它适合单机开发、集成测试和小型部署；需要多机调度、滚动升级、自动扩缩、故障转移和复杂权限时，应进入 Kubernetes、Nomad 或云容器平台

## 第七站：仓库、发布与 CI/CD

第七站来到镜像物流中心。镜像从“我电脑上的成品”变成“别人能拉取的发布物”后，就会遇到标签、权限、网络、架构和回滚这些现实问题，仓库不会替你记住谁改过什么。

**镜像命名与标签** ---- 用应用名、版本、Git 提交和构建目标组织标签；`latest` 适合演示，不适合作为可审计的生产部署凭证

**推送与拉取认证** ---- 了解 registry login、凭据存储、机器人账号、短期令牌和私有仓库权限；CI 中不要把长期密码散落在日志与环境变量里

**摘要与签名** ---- 用镜像 digest 固定内容，认识 cosign、签名、证明和供应链验证；“标签没变”不能证明内容没变，发布系统应验证来源与摘要

**多架构镜像** ---- 理解 amd64、arm64、manifest list 和跨架构构建；开发机能跑不代表目标节点能跑，构建矩阵和基础镜像都要覆盖真实平台

**构建缓存与制品流** ---- 在 CI 中复用 BuildKit 缓存，区分缓存、制品和正式发布镜像；缓存可丢，制品要可取，正式版本要可追溯

**发布与回滚** ---- 流水线应执行构建、测试、扫描、签名、推送和部署，记录源码到镜像的映射；回滚使用已验证的旧摘要，不现场重新构建“差不多的版本”

**网络与成本** ---- 关注镜像层大小、跨区域拉取、仓库存储、构建分钟数和带宽；瘦身不仅加快发布，也减少节点磁盘与供应链扫描成本

## 第八站：安全、隔离与软件供应链

第八站由安全审计员接管厨房。容器看起来轻巧，不代表里面没有危险；一层 root、一枚过期令牌、一个可写的 Docker socket，都足以让隔离墙显得很有幽默感。

**镜像来源与漏洞** ---- 使用可信基础镜像、固定版本、定期重建和漏洞扫描；漏洞扫描结果要结合可达性、运行时使用和修复窗口判断，不能只追求一个漂亮的数字

**最小权限运行** ---- 使用非 root 用户、只读根文件系统、丢弃不需要的 Linux capabilities、限制设备访问和进程数；按功能授予写目录与网络权限

**秘密管理** ---- 不把密码写入 Dockerfile、镜像层、Git 或构建参数；使用运行时 secret、外部密钥系统和轮换机制，并防止调试日志打印秘密

**Docker socket 风险** ---- 能访问宿主机 Docker socket 的容器通常能影响宿主机；需要构建时优先考虑 rootless、隔离构建器或专用构建服务

**隔离与逃逸边界** ---- 认识 namespace、cgroup、seccomp、AppArmor/SELinux、设备和内核共享的安全含义；容器不是硬件级隔离，强对抗场景要考虑虚拟机或沙箱运行时

**SBOM 与签名策略** ---- 生成软件物料清单，记录依赖、构建器、源码提交和签名；供应链安全要能回答“谁构建、用什么构建、产物是否被改过”

**运行时策略** ---- 监控异常进程、出站连接、文件改写、权限提升和加密挖矿；构建时安全与运行时安全是两道门，不能互相代班

## 第九站：资源、性能与可观测性

第九站是容器健身教练。它会把“容器很轻”改成更准确的说法：“容器的隔离开销通常较小，但资源仍来自宿主机，而且所有邻居都可能争抢同一块蛋糕。”

**CPU、内存与 I/O** ---- 查看容器级使用量、限制、节流、OOM、磁盘写入和网络流量；区分应用自身泄漏、容器限制过小、宿主机压力和邻居噪声

**启动与拉取性能** ---- 分析镜像层数量、层大小、解压时间、网络延迟、冷缓存和入口初始化；启动慢可能发生在拉镜像、挂载、进程启动或依赖连接，不要只测总耗时

**日志与事件** ---- 让应用把结构化日志写到 stdout/stderr，使用日志驱动或采集器转发；结合 `docker events`、inspect 和宿主机日志还原容器重启、网络变化与卷挂载事件

**指标与健康信号** ---- 关注容器重启次数、退出码、CPU throttling、内存工作集、文件描述符、连接数、请求延迟与错误率；容器指标要和应用指标对齐，不能只看“容器状态 Up”

**诊断工具** ---- 用 stats、top、inspect、exec、logs、events、宿主机 ps/ss/iostat 和应用探针组合定位；进入容器排查只是观察手段，最终修复应落在构建、配置或编排层

**资源配额与并发** ---- 为单容器和 Compose 服务设置合理上限，避免一个批处理任务吃光整台主机；并发、队列、连接池和进程数要一起设计

## 第十站：可靠性、成本与演进

最后一站讨论“Docker 化以后怎么办”。容器让交付更整齐，却没有消灭故障，只是把故障变得更适合自动化；如果每次异常都靠 `docker compose down`，那位搬家师傅会开始收取心理咨询费。

**单机可靠性** ---- 配置重启策略、健康检查、日志轮转、卷备份、主机补丁和磁盘水位；明确哪些故障可以自动恢复，哪些必须人工确认

**发布策略** ---- 选择停止替换、端口切换、蓝绿、金丝雀或外部负载均衡切流；数据库迁移要向前兼容，回滚应用时不能把数据格式一起打回过去

**多机调度边界** ---- Docker Engine 本身主要管理单机容器；Docker Swarm、Kubernetes、Nomad 与云容器服务才负责多节点调度、服务发现、滚动发布和故障转移，选择取决于规模与团队能力

**容量与成本** ---- 统计节点 CPU、内存、磁盘、镜像存储、构建缓存、仓库流量与日志费用；清理无引用镜像要先确认制品可恢复，不要用盲目 prune 代替生命周期管理

**灾备与数据恢复** ---- 备份卷、配置、镜像摘要、编排文件和外部依赖信息；在另一台干净主机上验证恢复，确保不是“备份存在但没人会用”

**从容器到平台** ---- 当你需要多副本调度、自动扩缩、服务发现、策略控制、渐进发布与跨节点存储时，进入 Kubernetes 和云原生模式；容器基础越扎实，平台抽象越不容易变成黑盒

## 通关标准

能解释镜像、容器、仓库、Engine、containerd、OCI runtime 与 Linux 隔离能力的关系；能写出小而可复现的 Dockerfile 并说明层缓存、多阶段、非 root 和健康检查；能为多服务 Compose 环境设计网络、卷、依赖和配置；能把镜像安全地构建、扫描、签名、推送并按摘要发布；能排查容器的启动、端口、DNS、权限、资源、日志和数据问题；能判断 Docker 单机、Swarm、Kubernetes 或托管容器服务的边界。

去 Kubernetes 学多节点的调度、声明式控制器、服务发现、滚动发布和资源治理；如果工作负载仍然是单机多服务，先把 Compose、镜像仓库和 CI/CD 做成稳定的交付链。

## 结语

Docker 的价值不是让命令变短，而是让“构建什么、运行什么、依赖什么、如何回滚”变得可描述、可复制、可审计。记住容器仍是 Linux 进程，数据仍需要备份，网络仍会超时，镜像仍要打补丁；带着这些现实感进入 Kubernetes，才不会把“容器能跑”误认为“系统可靠”。
