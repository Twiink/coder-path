# Redis 学习路线

Redis 是数据库世界里那位住在内存里的急性子管家：普通请求一敲门，它几乎立刻把结果递出来；但如果你把整栋楼的住户塞进一个 key，或者让一条 Lua 脚本霸占大厅，它也会把所有人一起晾在门外。它既能做缓存，也能做计数器、排行榜、队列、发布订阅和轻量状态存储，真正的难点是边界与可靠性。

这条路线从 key、数据结构和命令起步，逐步进入过期与淘汰、原子性、Lua、持久化、复制、哨兵、Cluster、缓存架构、分布式锁、限流、延时任务、底层编码、性能诊断、安全和生产取舍。Redis 的命令很容易记，难的是知道什么时候不能用某条命令，什么时候它根本不该承担数据库或消息系统的工作。

**推荐顺序** ---- 心智模型与连接 → key 与 String → Hash/List/Set → Sorted Set 与特殊结构 → Stream 与 Pub/Sub → 过期与内存淘汰 → 事务、脚本与原子性 → RDB/AOF 持久化 → 复制、哨兵与 Cluster → 缓存设计 → 锁、幂等、限流与延时任务 → 底层结构 → 性能与运维 → 安全、可靠性与架构

**这条线怎么用** ---- 每站都关注时间复杂度、内存成本、网络往返、失败重试、数据丢失窗口和故障恢复。Redis 的单条命令通常很快，但系统级的慢往往来自大 key、热 key、网络、持久化、复制或错误的业务假设。

## 第一站：先认识这位内存急件管家

第一站先给 Redis 贴好标签。它是单线程命令执行模型为核心的内存数据结构服务器，不是“永远不会丢数据的数据库”，也不是“加上 SETNX 就自动变成分布式协调系统”。

**Redis 的角色** ---- 区分缓存、临时状态、计数、队列、排行榜、会话、主数据和消息流；同一个 Redis 实例混装不同可靠性等级的数据，会让淘汰和恢复策略互相打架

**实例、逻辑数据库与 keyspace** ---- 理解 server、逻辑 DB、key、value、命令和客户端连接；逻辑数据库主要是命名空间，不提供真正的租户隔离、资源隔离或独立故障域

**RESP 与客户端** ---- 认识 RESP 协议、命令请求、批量参数、RESP2/RESP3 和驱动解码；网络往返、响应大小和客户端序列化经常比命令本身更耗时

**事件循环与命令原子性** ---- 理解命令在事件循环中串行执行，单条命令通常不会被其他命令插入；串行执行保证了简单原子性，但长命令会阻塞所有客户端

**连接与连接池** ---- 掌握 TCP、认证、连接复用、池大小、空闲、读写超时和断线重连；连接池过大可能造成连接风暴，过小则让请求在应用侧排队

**配置层级** ---- 区分启动参数、配置文件、CONFIG SET、运行时配置与重启后的持久配置；动态调整前要知道是否会在重启后丢失

**版本与客户端兼容** ---- 关注 Redis 版本、模块、协议、命令行为和客户端支持；不要因为本地能用一个新命令，就把所有生产节点当成同一版本

**本地实验环境** ---- 准备单节点、主从、哨兵和 Cluster 实验；为每个实验准备清理、重启、故障注入和数据校验方法

## 第二站：String、key 设计与基础原子操作

第二站认识最常用的 String。它看起来像一个小盒子，实际上能装文本、JSON、二进制、整数、位图和计数器；盒子越大，搬运、复制和删除越容易堵车。

**key 命名空间** ---- 设计业务前缀、租户、对象 ID、版本、环境和用途；统一命名让排查、批量迁移和权限审计有路可走

**key 长度与 value 大小** ---- 估算 key 元数据、网络传输、序列化、复制、持久化和删除成本；大 value 不只是占内存，还会长时间霸占事件循环

**GET/SET 与批量读写** ---- 掌握单值读写、MGET/MSET、NX/XX、GET 旧值、过期时间和返回结果；批量减少 RTT，但返回体太大时会把网络和客户端内存一起推高

**计数器** ---- 使用 INCR、INCRBY、DECR 和浮点增量做访问量、库存、版本和配额；计数器是原子操作，但跨 key 的业务判断仍需脚本或其他协调

**幂等写入** ---- 用业务请求 ID、SET NX、唯一值和结果缓存处理重复请求；网络超时后的重试必须区分“没执行”和“执行了但响应丢了”

**位图** ---- 用 SETBIT、GETBIT、BITCOUNT 和位运算表示签到、资格、日活或特征；位图节省空间，但索引语义、最大偏移和跨天清理要提前设计

**BITFIELD** ---- 了解在一个 String 中保存定宽整数、溢出策略和原子更新；它适合紧凑计数与状态，不适合让未来维护者猜位段布局

**范围与编码** ---- 认识 String 的整数编码、短字符串优化、二进制安全和追加/截取操作；频繁增长的 value 可能制造重新分配和内存碎片

**TTL 与读写语义** ---- 关注写入是否覆盖过期时间、更新后是否续期、读取是否刷新生命周期；缓存失效策略不能依赖“好像会自动续命”

**安全使用扫描** ---- 不用 KEYS 做线上全库扫描，改用 SCAN、批次和限速；扫描仍可能带来总成本，只是把阻塞变得更温和

## 第三站：Hash、List、Set——三位结构管家

第三站安排三位管家见面。Hash 擅长照看对象字段，List 喜欢排队，Set 负责去重；让它们做自己擅长的事，比把所有需求都序列化成一个 JSON 更省心。

**Hash** ---- 掌握 HSET、HGET、HMGET、HGETALL、HINCRBY、HDEL、HLEN 和 HEXISTS；局部读取与更新对象字段时，Hash 通常比整条 String 更节省网络

**Hash 的对象建模** ---- 适合用户资料、商品局部属性、购物车和分组计数；字段数量、字段长度和生命周期差异过大时要拆 key，避免形成大 Hash

**Hash 扫描与编码** ---- 大 Hash 使用 HSCAN 分批遍历，理解小对象紧凑编码、listpack 与哈希表的切换；HGETALL 是方便命令，不是大数据量的默认姿势

**List** ---- 掌握 LPUSH、RPUSH、LPOP、RPOP、LRANGE、LLEN、LINSERT 和阻塞弹出；List 适合简单队列、时间线和有限长度列表

**List 的边界** ---- 列表按顺序存储，不适合任意位置高频修改和无限增长；LRANGE、删除中间元素和大列表复制都可能带来线性成本

**阻塞队列** ---- 理解 BLPOP、BRPOP 等阻塞操作的连接占用、超时、断线和消息可靠性；弹出后消费者崩溃时，任务可能已经消失

**Set** ---- 掌握 SADD、SREM、SISMEMBER、SCARD、SMEMBERS、SPOP 和 SRANDMEMBER；Set 适合去重、标签、关注关系、资格判断和随机抽样

**集合运算** ---- 使用 SINTER、SUNION、SDIFF 处理共同关注、标签交集和差集；大集合运算会占用命令执行时间，结果集也可能很大

**遍历与集合大小** ---- 大 Set 使用 SSCAN，控制批次与并发；SMEMBERS、集合运算和删除大集合都要按元素数量评估

**结构选择** ---- 整体读写选 String，局部字段选 Hash，先进先出选 List，去重选 Set；结构不是越丰富越好，而是让业务操作接近数据形状

## 第四站：Sorted Set 与特殊数据结构

第四站让 Redis 端出排行榜。Sorted Set 同时记住成员和分数，能做排名、时间窗口和延时任务；但它不是万能的排序数据库，分数精度、成员数量和热点写入都要算。

**Sorted Set 基础** ---- 掌握 ZADD、ZRANGE、ZREVRANGE、ZRANGEBYSCORE、ZREM、ZINCRBY、ZRANK、ZSCORE、ZCARD 和 ZCOUNT

**排行榜** ---- 用分数排序、原子加分和排名查询构建积分榜、热榜与实时 TopN；并列、时间 tie-breaker、分数更新和分页规则要提前定义

**时间窗口** ---- 以时间戳作为 score，配合范围查询、清理和计数实现滑动窗口；时间精度、时钟回拨和同一毫秒内成员唯一性需要处理

**延时任务** ---- 用执行时间作为 score 保存到期任务；领取、确认、重试、超时和重复执行不能只靠“取出来再删”四个字解决

**跳表与哈希表** ---- 理解 Sorted Set 通常用跳表支持有序范围，用哈希表快速查成员分数；两种结构叠加意味着查询快，也意味着内存不便宜

**HyperLogLog** ---- 用 PFADD、PFCOUNT 和 PFMERGE 估算基数，如 UV 或独立设备数；它节省空间但只有近似结果，不能拿来结算钱

**Geospatial** ---- 了解 GEOADD、GEODIST、GEOSEARCH 等地理位置能力；距离模型、坐标顺序、精度和附近搜索规模必须经过业务验证

**Bloom/Cuckoo 等模块结构** ---- 认识布隆过滤器、布谷鸟过滤器、Count-Min Sketch、TopK 等概率结构的用途；它们用误判率换空间，不能把“可能存在”当作确定事实

**概率结构的治理** ---- 为误判率、容量、扩容、重建、删除能力和数据版本定义指标；概率数据结构适合拦截和统计，不适合做最终事实来源

## 第五站：Stream、Pub/Sub 与消息边界

第五站进入消息大厅。Pub/Sub 像广播站，听众不在线就错过；Stream 像带账本的传送带，能确认、重试和追踪，但仍不等于功能齐全的专业消息系统。

**Pub/Sub** ---- 掌握发布、订阅、模式订阅和频道管理；它适合实时通知、缓存失效广播和轻量聊天室，不提供离线补发、消费确认或历史回放

**Stream** ---- 理解追加消息、消息 ID、读取、阻塞读取和长度控制；Stream 适合把事件按顺序保存在 Redis 内并允许消费者稍后追赶

**消费者组** ---- 掌握创建组、组内读取、确认、pending entries、空闲时间和消费者状态；组内一条消息通常只交给一个消费者，但失败恢复需要显式处理

**Pending 与认领** ---- 识别未确认消息、消费者崩溃、超时消息和 XCLAIM/自动认领；认领前要有幂等处理，避免旧消费者与新消费者重复执行业务

**消息确认语义** ---- 区分已写入、已读、已处理、已确认和已归档；XACK 只是确认 Redis 层消费完成，不代表下游数据库事务已经提交

**重复、顺序与重试** ---- 设计事件 ID、去重表、重试次数、退避、死信和顺序键；“至少一次”系统必须接受重复处理

**Stream 长度与裁剪** ---- 通过最大长度、时间窗口和归档控制内存；裁剪过早会让恢复与审计失去事件，裁剪过晚会让内存成为定时炸弹

**Redis 作为队列的边界** ---- 任务量小、链路短、同栈轻量时可用 Stream；需要复杂路由、死信、优先级、海量堆积或严格投递保证时评估专业 MQ

**事件与缓存失效** ---- 用 Stream 或 Pub/Sub 广播变更时，消费者要处理断线、重复、乱序、版本和回放；缓存一致性不是发出一条通知就结束

## 第六站：过期、淘汰与内存管理

第六站由内存管理员接管。Redis 会让 key 过期，也会在内存不足时淘汰，但它不会替你判断“哪些数据绝对不能丢”；策略设置错了，系统会非常守规矩地丢掉不该丢的东西。

**EXPIRE 与绝对时间** ---- 掌握秒级/毫秒级过期、查询剩余时间、取消过期和按时间点设置；区分 key 不存在、没有 TTL 和已经过期的返回语义

**惰性删除与定期删除** ---- 理解访问时检查过期与后台抽样清理；过期 key 在一段时间内仍占内存是正常实现特征，不等于 TTL 失效

**过期与复制** ---- 了解主节点处理过期并将删除传播给副本的基本思路；副本读到的数据和过期时刻可能存在短暂差异

**maxmemory** ---- 为实例设置明确内存上限，给操作系统、fork、客户端缓冲区、复制缓冲和碎片预留余量；把上限设到物理内存头顶是给故障写邀请函

**noeviction** ---- 写入超过上限时返回错误，适合不能静默丢数据的场景；应用必须能处理写失败并有降级

**LRU 与 LFU** ---- 比较 allkeys-lru、allkeys-lfu、volatile-lru、volatile-lfu 和随机淘汰；LRU 看近期，LFU 看频率，选择要基于访问分布

**volatile 系列** ---- 只在有过期时间的 key 中淘汰；混存缓存与持久状态时容易出现“本来想淘汰缓存，却没有候选 key”的陷阱

**TTL 策略** ---- 对热点、冷数据、空值和不同业务设置不同 TTL；为批量写入增加随机抖动，避免大量 key 同时过期

**内存碎片** ---- 认识 used_memory、RSS、分配器碎片和主动碎片整理；频繁修改变长 value、批量删除和 fork 都可能扩大物理内存压力

**大 key 识别** ---- 关注大 String、大 Hash、大 List、大 Set、大 Sorted Set 和大 Stream；大小既按字节看，也按元素数量和一次命令工作量看

**淘汰与持久数据隔离** ---- 缓存实例、队列实例、锁实例和业务状态实例优先分离；不同可靠性和淘汰策略共用一池内存通常会互相污染

## 第七站：事务、Pipeline、Lua 与原子性

第七站讨论“几条命令能不能像一条命令一样行动”。MULTI/EXEC 让命令排队，Pipeline 减少往返，Lua/函数把判断与修改放进一次执行；三者都能提速，但用途并不相同。

**MULTI/EXEC** ---- 理解事务命令入队、执行顺序和 DISCARD；Redis 事务不提供传统数据库式的失败回滚，执行中出现运行时错误不能抹掉已经执行的命令

**WATCH** ---- 用乐观监视检测 key 被其他客户端修改的冲突；冲突后需要重读、退避和重试，且高竞争下可能造成重试风暴

**Pipeline** ---- 一次发送多条命令减少 RTT；Pipeline 默认不是事务，也不是原子执行，其他客户端命令可能穿插

**脚本原子性** ---- Lua 脚本在执行期间不会被其他命令插入，适合检查并修改、扣库存、限流和安全释放锁；脚本过长会阻塞整个实例

**脚本参数与 key 规则** ---- 明确通过 KEYS/ARGV 传入的 key 与参数，避免动态拼接和访问未知 key；Cluster 下脚本涉及的 key 通常必须落在同一 slot

**函数与脚本部署** ---- 认识脚本缓存、SHA、函数库、版本发布、回滚和重启后的加载；把业务逻辑放进 Redis 后，测试、发布和监控也要跟着搬进去

**原子性与持久性** ---- 命令执行原子不代表数据已经落盘、复制或被下游处理；把互斥、持久、可恢复和最终一致分开讨论

**错误处理** ---- 设计脚本参数校验、超时、失败返回、幂等、重试和日志；不要让客户端把所有脚本错误都当成“再试一次”

**命令时间复杂度** ---- 认识 O(1)、O(log N)、O(N) 和与返回结果相关的成本；一个复杂度为 O(N) 的命令在 N 很小时没问题，N 长大后就会成为线上主角

## 第八站：RDB、AOF 与持久化

第八站把内存里的东西送进保险柜。RDB 像定期拍快照，AOF 像持续记账；两者都能帮你恢复，却不能自动替你满足 RPO、RTO、异地灾备和误操作恢复。

**RDB 快照** ---- 理解手动/定时快照、文件紧凑、恢复快和时间窗口丢失；快照间隔决定崩溃后最多可能丢多少数据

**fork 与写时复制** ---- 了解后台保存通过 fork 产生子进程、父子共享页面并在写入时复制；内存越大、脏页越多，fork 和 COW 的峰值成本越明显

**AOF 追加日志** ---- 认识写命令追加、重启重放、文件增长和同步策略；AOF 记录的是逻辑操作，恢复速度和最终文件大小受写入模式影响

**fsync 策略** ---- 比较每次刷盘、每秒刷盘和交给操作系统；更强持久性通常换来更高延迟，选择要与 RPO 对齐

**AOF 重写** ---- 理解后台重写把历史命令压缩为当前状态，并在切换时合并增量；重写需要额外磁盘、内存和 I/O 余量

**混合持久化** ---- 了解用快照式内容缩短加载，再追加增量命令减少丢失窗口；混合方案仍需验证版本、文件完整性和恢复流程

**持久化与复制的区别** ---- 本地落盘解决单机重启的一部分风险，复制解决节点故障的一部分风险，备份解决逻辑错误与灾难的一部分风险；三者不能互相冒充

**备份保留与校验** ---- 保存多个时间点、异地副本、校验和与访问审计；备份文件能复制出来，不等于文件能恢复出正确数据

**恢复演练** ---- 演练 RDB 恢复、AOF 恢复、故障节点替换、数据校验、版本升级和应用切换；记录实际恢复时间和丢失窗口

**持久化取舍** ---- 纯缓存可接受重建和较小持久化投入，业务状态则需要更强日志、备份与恢复；先定义数据价值，再选 save、appendfsync 和备份频率

## 第九站：复制、哨兵与 Redis Cluster

第九站给 Redis 组建值班团队。主从复制解决数据跟随，Sentinel 解决主节点发现和切换，Cluster 解决水平分片；它们不是三个同义词，也不是部署后就会自动消除一致性问题。

**主从复制链路** ---- 理解主节点传播复制流、从节点接收并应用、复制偏移量和断线重连；异步复制意味着副本可能落后

**全量与增量同步** ---- 区分首次全量同步、断线后的部分同步、复制积压缓冲和重新生成快照；积压不足会把短断线升级成昂贵的全量同步

**副本读与陈旧数据** ---- 用副本分担读请求时，接受读旧数据、读后写不一致和切主期间的路由变化；强一致读要回主节点或另建确认机制

**Sentinel** ---- 理解监控、主观下线、客观下线、投票、故障转移和客户端发现新主；哨兵本身也要多实例、跨故障域和可观测

**quorum 与多数** ---- 区分判断下线所需 quorum、参与选举的多数和实际数据副本；数字写得漂亮不代表网络分区时一定安全

**旧主隔离** ---- 切换后阻止旧主继续接收写入，避免脑裂；客户端、代理、ACL、网络和基础设施要协同完成 fencing

**Cluster 哈希槽** ---- 理解固定数量 slot、CRC 哈希、节点负责 slot 和客户端重定向；Cluster 既分散容量，也要求应用接受路由和拓扑变化

**MOVED 与 ASK** ---- 认识槽位迁移期间的重定向、客户端自动跟随和缓存槽位失效；手写客户端时不要假设一个 key 永远在一台机器上

**Hash tag** ---- 用相同的标签让相关 key 落在同一 slot，支持多 key 原子操作；标签范围过大可能制造热点，范围过小又无法跨 key 协作

**Cluster 的多 key 限制** ---- 评估事务、脚本、集合运算、批量读写和跨 slot 查询；需要跨分片 JOIN 的需求通常说明数据模型或系统选型需要重新讨论

**扩容、缩容与 reshard** ---- 规划槽位迁移、带宽、内存、热点、回滚、客户端兼容和业务影响；扩容不是只添加几台机器

**选型路径** ---- 单机适合开发与小规模，主从加 Sentinel 适合单分片高可用，Cluster 适合容量或写入需要水平扩展；能不分片时先不分片

## 第十站：缓存设计与一致性

第十站处理 Redis 最常见的职业：给主数据库挡流量。缓存像门口的快递柜，速度很快，但里面的包裹可能过期、丢失或被别人先取走；必须定义真实来源和失效策略。

**Cache Aside** ---- 读时先查缓存，未命中再查主库并回填；写时先提交主库，再删除缓存，避免把失败的写入先放进缓存

**更新、删除与延迟双删** ---- 分析先删、后写、再删的竞态；延迟双删只能降低某些窗口，不能自动提供强一致

**缓存穿透** ---- 防止不存在的请求反复打主库；用参数校验、短 TTL 空值、布隆过滤器和访问限速组合处理

**缓存击穿** ---- 处理单个热点 key 过期瞬间大量回源；使用互斥重建、逻辑过期、后台刷新和本地缓存，控制只有少量请求回源

**缓存雪崩** ---- 避免大量 key 同时失效或 Redis 整体不可用；使用 TTL 抖动、多级缓存、限流、降级、预热、分批重建和高可用

**热点 key** ---- 识别一个 key 被极高频访问造成单线程、网卡或副本压力；通过本地缓存、拆分副本 key、请求合并和读路由分散热度

**缓存一致性等级** ---- 区分强一致、读己之写、会话一致、最终一致和允许陈旧；不同业务不要共用一个模糊的“缓存一致”

**失效通知** ---- 用消息、Keyspace Notifications、数据库 CDC 或应用事件传播失效；通知可能丢、重复或延迟，消费者仍需幂等和补偿

**缓存预热与冷启动** ---- 识别热点、批量回填、限速、失败重试和上线切流；预热脚本不能把主库在上线前先打倒

**缓存与主库故障** ---- 设计 Redis 不可用、主库不可用、缓存污染、回源失败和部分数据缺失时的降级；重试要有上限，否则缓存故障会放大主库故障

## 第十一站：分布式锁、幂等、限流与延时任务

第十一站是分布式现场。Redis 能提供很方便的互斥、计数和时间排序，但锁住一个 key 不等于锁住整个世界；租约、续期、栅栏令牌和业务幂等要一起出现。

**正确加锁** ---- 使用带唯一 token 的原子 NX 加过期时间写入；锁值标识持有者，过期时间限制进程崩溃后的永久占用

**安全释放** ---- 释放时比较 token 后再删除，避免旧持有者误删新持有者的锁；普通 DEL 不是安全释放协议

**租约与续期** ---- 处理业务执行时间超过 TTL 的情况；续期必须确认仍由自己持有，并设置最大租期，避免故障客户端永不归还

**锁不是幂等** ---- 分布式锁提供一段时间内的互斥，不保证请求只执行一次、消息不重复或结果不丢；业务仍需请求 ID、状态机和唯一约束

**锁不是共识** ---- 对需要强一致领导权、严格顺序和持久协调的场景，比较 ZooKeeper、etcd 或数据库方案；Redis 锁的安全边界必须写进设计

**Redlock 与多节点争议** ---- 了解多节点锁算法的假设、时钟、网络分区和实现复杂度；不要把它宣传成所有场景的绝对安全答案

**固定窗口限流** ---- 用计数器加过期时间实现最简单限流；窗口边界会产生突刺，适合粗粒度保护

**滑动窗口限流** ---- 用 Sorted Set 或 Stream 记录时间和请求，统计时间范围内的次数；精度更高，但内存与清理成本也更高

**令牌桶与漏桶** ---- 理解突发容量、平均速率、匀速处理和分布式计数；网关、服务本地和 Redis 限流要明确谁负责最后一道保护

**延时队列** ---- 用 Sorted Set 按执行时间索引任务，配合领取、确认、重试和幂等；需要严格投递、持久堆积和死信时换专业 MQ

**库存与配额** ---- 用原子计数或 Lua 完成检查和扣减，处理超卖、回滚、重复请求和过期订单；库存最终事实应由可信主库确认

## 第十二站：底层数据结构与事件循环

第十二站进入 Redis 的机械心脏。它之所以快，不只是“数据在内存里”，还因为对象编码、紧凑布局、事件循环和命令复杂度共同配合；每个快字后面都有一个内存账本。

**SDS** ---- 理解带长度、容量和二进制安全的动态字符串；预分配减少扩容，长度字段避免每次遍历，但大字符串仍然会带来复制和网络成本

**dict 哈希表** ---- 认识 keyspace 与 Hash 的哈希表、渐进式 rehash、扩容、缩容和哈希冲突；rehash 尽量分摊工作，但大批量操作仍可能产生抖动

**List 的 quicklist** ---- 理解现代 List 使用链表节点承载紧凑列表块，在指针与连续内存之间取平衡；中间插入、超长节点和范围读取仍需看复杂度

**listpack 与紧凑编码** ---- 了解小 Hash、Sorted Set 等结构使用紧凑连续编码节省内存；元素变大或变多后会切换到更通用的结构，阈值要用实际数据校准

**Set 的 intset** ---- 当集合成员全为整数且规模合适时，可用有序整数集合节省空间；插入非整数或规模增长后会切换为哈希表

**Sorted Set 的 skiplist** ---- 理解跳表层级、范围遍历、分数排序和与哈希表的组合；它用额外指针换取有序操作，不是“免费排序”

**对象编码变化** ---- 不要依赖某个旧版本的内部名称或固定阈值；升级前确认编码、模块和监控工具的兼容性

**事件循环** ---- 理解文件事件、时间事件、命令处理和客户端缓冲；一个阻塞命令会让所有连接共享它的等待

**I/O 线程** ---- 认识部分版本可用多线程辅助网络读写或协议处理，但命令执行的原子顺序模型仍是核心；I/O 线程不能修复大 key 和慢脚本

**内存分配器与碎片** ---- 了解 jemalloc 等分配器、RSS、空闲块、主动碎片整理和 fork 的额外内存；逻辑内存低不代表进程占用低

**时间复杂度与返回复杂度** ---- 读命令文档时同时看遍历量、结果集大小、元素移动和阻塞可能性；O(1) 也不保证网络响应小

## 第十三站：性能诊断与容量规划

第十三站是线上急救室。Redis 慢时，罪魁祸首经常不是某个神秘参数，而是一条看似方便的全量命令、一个异常大的 value，或一个把所有请求吸到同一台节点的热 key。

**基线指标** ---- 记录吞吐、p50/p95/p99、命令耗时、命中率、连接、网络、内存、复制延迟、持久化耗时和错误；没有基线就无法判断调优是否有效

**INFO** ---- 使用 memory、stats、clients、replication、persistence、commandstats 和 cpu 等信息定位方向；指标要与告警阈值和行动手册对应

**SLOWLOG** ---- 记录超过阈值的命令，关注大集合读取、复杂脚本、排序、阻塞弹出和批量删除；慢命令日志不包含完整业务上下文，需要与应用 trace 关联

**LATENCY 工具** ---- 观察事件循环延迟、fork、AOF、命令和操作系统抖动；延迟尖刺要结合持久化、内存、CPU 和网络时间线

**MONITOR 的边界** ---- MONITOR 能看实时命令但会显著增加开销，并可能泄露敏感参数；只在短时、低比例、隔离环境使用

**大 key 排查** ---- 结合 bigkeys、memory usage、抽样扫描、RDB 分析和应用指标识别大对象；排查工具本身也要限速，不能用诊断把实例再压一遍

**大 key 处理** ---- 拆分 Hash/List/Set、限制列表长度、分批遍历删除、使用异步删除、压缩 value 或改用对象存储；删除大对象本身也可能长时间占用资源

**热 key 排查** ---- 结合 LFU、代理统计、客户端埋点和访问日志定位单 key 热点；不要长期开启高开销观测命令

**热 key 处理** ---- 本地缓存、请求合并、key 分片、副本读、预热和过期抖动可以分担压力；写热点在拆分后要解决一致性和汇总

**Pipeline 与批量大小** ---- 用 Pipeline 减少 RTT，但控制命令数、响应大小、客户端缓冲和失败重试；一批太大时，延迟和内存会一起抬头

**连接与超时** ---- 设定连接、读、写、池等待和命令超时；无限等待会让应用线程堆积，过短则把正常抖动变成重试风暴

**容量规划** ---- 按 key 元数据、value、编码、索引/模块开销、复制缓冲、AOF/RDB、碎片、峰值 COW 和增长率预留空间；只算 value 是最常见的漏项

## 第十四站：安全、运维与可靠性

第十四站给这位急性子管家装上门锁和应急预案。Redis 暴露在公网、使用默认权限、备份无人恢复或磁盘没有余量时，速度越快，出事越快。

**认证与 ACL** ---- 使用 ACL 用户、命令类别、key pattern、只读权限和最小权限；不同服务、运维、备份、监控和发布身份分离

**网络与 TLS** ---- 限制 bind、端口、私网、网络策略和管理面访问；传输加密、证书校验和身份认证要同时配置

**危险命令治理** ---- 限制或重命名 FLUSHALL、FLUSHDB、CONFIG、DEBUG、MODULE、SHUTDOWN、MONITOR 等高风险能力；更重要的是避免把管理员凭据交给业务服务

**密钥与敏感值** ---- 不把密码、令牌、个人数据和长期密钥明文塞进没有访问控制的 key；缓存 TTL 也不是脱敏策略

**日志与审计** ---- 记录连接、认证失败、配置变更、危险命令、管理操作和数据访问；注意命令日志可能包含业务 payload

**客户端缓冲区** ---- 监控 query buffer、output buffer、复制缓冲、Pub/Sub 客户端和阻塞客户端；慢消费者会让内存从侧门逃走

**磁盘水位** ---- 为 RDB、AOF 重写、临时文件、日志、备份和恢复留出空间；磁盘满会同时破坏持久化、重写和故障处理

**升级与回滚** ---- 验证命令、协议、模块、持久化文件、客户端、复制和 Cluster 兼容性；滚动升级要先验证副本，再切主，最后观察应用

**故障演练** ---- 练习主节点宕机、Sentinel 切换、Cluster 节点丢失、网络分区、AOF 损坏、磁盘满、复制延迟和缓存重建

**数据恢复边界** ---- 区分缓存重建、RDB/AOF 恢复、误删回溯、Stream 回放和业务补偿；不同目标需要不同副本、备份与保留期

**监控与告警** ---- 关注内存、淘汰、命中率、命令延迟、blocked_clients、连接、复制状态、复制偏移、AOF/RDB、fork、磁盘和热点

## 第十五站：生产架构与系统边界

最后一站把 Redis 放回系统大图。优秀的 Redis 架构不是“所有问题都用 Redis”，而是把它放在合适的层：缓存加速、状态协调、轻量事件，或在清楚风险后承担有限的数据职责。

**主库与缓存分工** ---- 明确谁是事实来源、谁能丢、谁能重建、谁负责校验；缓存 key 里保存的不是业务真理，只是可失效的副本

**多级缓存** ---- 组合进程内缓存、Redis 和主数据库，设计版本、失效广播、回源、预热和一致性；多级缓存能降延迟，也会增加失效路径

**Redis 与数据库** ---- 处理双写、缓存旁路、CDC、Outbox、延迟双删、补偿和回填；不要在没有明确事务边界时宣称“缓存与数据库强一致”

**Redis 与消息系统** ---- 比较 Pub/Sub、Stream、专业 MQ 和日志系统在持久、重试、顺序、路由、堆积、消费组与死信方面的差异

**Redis 与分布式锁** ---- 让锁只保护短临界区，设置租约、唯一 token、续期边界、fencing 和降级；长事务、强一致领导权和跨区域协调要评估其他系统

**Redis Cluster 数据模型** ---- 设计 hash tag、key 共置、跨 slot 限制、热点分片、重分布和租户路由；Cluster 的槽位是架构约束，不是部署细节

**读写分离与副本** ---- 评估副本陈旧、网络分区、故障切换和路由；读多写少时复制有价值，但不是所有读都能安全下放

**租户与故障域** ---- 比较共享实例、共享 Cluster、独立实例和独立集群的隔离、成本、备份和爆炸半径；不同租户的热 key 不应互相拖垮

**容量与成本** ---- 估算内存、网络、CPU、磁盘、备份、跨区流量、复制、节点数量和运维复杂度；集群规模越大，拓扑和故障演练的成本越高

**替代方案判断** ---- 需要持久事务选择关系数据库，需要复杂消息投递选择 MQ，需要全文相关性选择搜索系统，需要强一致协调选择共识系统；Redis 可以参与，但不必独占

**毕业项目** ---- 做一个带缓存、排行榜、限流、幂等、延迟任务或 Stream 的服务，经历大 key、热 key、主从延迟、故障切换、备份恢复和缓存重建演练

## 通关标准

**基础通关** ---- 能解释 Redis 的内存模型、keyspace、String、Hash、List、Set、Sorted Set、Stream 与 Pub/Sub，并根据场景选择结构

**原子性通关** ---- 能区分单命令、MULTI/EXEC、WATCH、Pipeline、Lua/函数的保证，写出检查加修改的安全方案并说明失败语义

**缓存通关** ---- 能解释过期删除、淘汰策略、穿透、击穿、雪崩、热 key、大 key和缓存一致性，并为每类问题给出可观测的治理方式

**可靠性通关** ---- 能对比 RDB、AOF、混合持久化、复制、Sentinel 和 Cluster，明确 RPO、RTO、读旧数据和故障切换边界

**分布式通关** ---- 能设计带唯一 token、租约和安全释放的分布式锁，理解幂等、限流、延时任务、重复消费和 fencing

**性能通关** ---- 能根据复杂度、INFO、SLOWLOG、LATENCY、内存、网络、客户端和大/热 key 证据定位延迟，并控制 Pipeline 与连接池

**运维通关** ---- 能配置 ACL、TLS、监控、磁盘与内存告警，完成主从切换、Cluster 节点维护、备份恢复和故障演练

**架构通关** ---- 能根据数据价值、可重建性、一致性、吞吐、延迟、容量和团队能力决定 Redis 的职责与边界，并说明不用 Redis 的理由

## 下一站去哪

Redis 走到这里，已经从“会用几个命令”升级为“能把内存系统放进生产架构”。接下来可以按方向继续：

**PostgreSQL** ---- 深入事务、MVCC、复杂 SQL、索引、WAL、备份恢复和强一致主库

**MongoDB** ---- 学习文档建模、聚合、副本集、分片和半结构化数据的另一种取舍

**消息系统** ---- 对照学习专业队列的投递、重试、死信、顺序、堆积和消费语义

**分布式系统** ---- 继续研究共识、服务发现、限流、熔断、事件驱动和最终一致性

## 结语

Redis 最迷人的地方，是它把许多高并发模式压缩成了简单命令；最危险的地方，也是这些命令太简单，容易让人忘记背后的时间、内存、持久化和故障成本。

先把 key 和数据结构设计得克制，再理解事件循环、编码、过期、淘汰和持久化；先用证据处理大 key、热 key、复制延迟和缓存失效，再谈分片和分布式锁。等你能从一次延迟尖刺追到命令复杂度、事件循环、内存碎片、fork、网络和架构边界，也能在 Redis 故障后让业务有序降级——你学到的就不只是 Redis，而是如何让高速组件在可靠系统里保持分寸。
