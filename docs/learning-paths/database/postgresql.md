# PostgreSQL 学习路线

PostgreSQL 是数据库世界里那位穿着学者长袍、背着瑞士军刀的老教授：平时讲究标准与证据，真遇到复杂查询、地理数据、半结构化文档或并发冲突，又会从袖子里掏出一整套工具。它不只会保存表格，还能把 JSONB、全文检索、空间数据、向量、物化视图和自定义类型安排得井井有条。

这条路线从“能连上数据库”一路走到“能解释它为什么这样执行、如何恢复、怎样扩展”。先建立 PostgreSQL 的对象、类型和 SQL 心智模型，再进入 JSONB、索引、MVCC、VACUUM、WAL、复制、高可用与架构取舍。每一站都要同时问三个问题：它解决什么问题，付出什么成本，故障时谁会先露馅。

**推荐顺序** ---- 数据库心智模型 → 安装与对象 → 类型与建模 → SQL 基础 → 复杂查询 → JSONB 与半结构化数据 → 全文/空间/向量 → 索引 → MVCC 与锁 → 存储、VACUUM 与统计信息 → WAL、备份恢复 → 复制与高可用 → 性能与运维 → 分区、扩展与架构演进

**这条线怎么用** ---- 每站先理解概念，再用小规模数据观察结果；少背“永远这样”的口诀，多记录版本、数据分布、执行计划和恢复演练的证据。PostgreSQL 很愿意给你自由，但自由通常会附赠一个需要自己负责的边界。

## 第一站：先认识这位严谨的数据教授

第一站先不急着写复杂 SQL。PostgreSQL 的脾气来自它的分层：客户端连到服务器进程，服务器管理数据库对象，存储层负责页、版本与日志。把这些角色认错，后面遇到连接、锁或性能问题时就会像在错的办公室找人。

**数据库管理系统与实例** ---- 区分客户端、服务器进程、数据库集群、数据库、schema、表和存储文件；理解一个 PostgreSQL 集群可包含多个数据库，但普通 SQL 不能像某些数据库那样随意跨库 JOIN

**对象命名空间** ---- 掌握 database、schema、table、view、materialized view、sequence、function、type、extension、role 的关系；理解 public schema、search_path 和对象解析顺序

**OLTP 与 OLAP** ---- 区分事务系统的短查询、并发写入与强约束，以及分析系统的长扫描、聚合与并行；不要让一个报表查询把在线订单系统请去参加马拉松

**SQL 标准与 PostgreSQL 方言** ---- 知道 PostgreSQL 对标准 SQL 支持较完整，同时拥有 RETURNING、FILTER、LATERAL、DISTINCT ON、数组、范围类型等特色；写跨数据库应用时要主动标记方言边界

**一次请求的完整链路** ---- 串起 API、连接池、客户端驱动、PostgreSQL 后端进程、解析、规划、执行、WAL、提交和响应；接口慢可能是连接排队，也可能是锁、磁盘、网络或规划器选错了路

**数据生命周期** ---- 从建模、写入、读取、更新、归档、备份、恢复、审计到删除，理解字段的敏感级别、保留期限和恢复粒度会反过来约束设计

**版本与兼容性** ---- 关注服务器版本、客户端驱动、扩展版本、兼容性参数和升级路径；不要把“开发机能连上”误认为“生产升级可回滚”

**工具地图** ---- 认识 psql、图形客户端、迁移工具、EXPLAIN、pg_stat_statements、备份工具和监控系统的分工；工具负责照亮现场，不能替你判断现场

## 第二站：安装、连接与服务器地图

第二站把 PostgreSQL 请到本地。它不像一个只有开关的家电，更像一栋有门禁、住户、楼层和物业规则的公寓；端口能通只是走到了小区门口，认证、权限和 schema 还在里面排队。

**安装与发行方式** ---- 了解操作系统包、容器、源码、云托管和企业发行版的差异；掌握数据目录、日志目录、服务启动方式和初始化数据库集群

**连接参数** ---- 熟悉 host、port、database、user、密码、TLS、连接超时、应用名和客户端编码；为每类服务设置清晰的连接身份，方便审计与排障

**psql 基本能力** ---- 会使用库列表、切库、列出表、描述对象、显示扩展、查看当前连接和输出格式等元命令；宽表结果可用展开显示，避免横向滚动把问题藏起来

**PostgreSQL 后端进程模型** ---- 理解每个连接通常对应一个后端进程，连接数过多会带来内存、上下文切换和进程管理成本；连接池不是锦上添花，而是大型应用的基础设施

**配置层级与 GUC** ---- 区分 postgresql.conf、ALTER SYSTEM、数据库级、角色级、会话级和事务级参数；知道哪些参数可动态变更，哪些需要重启，哪些只影响当前会话

**pg_hba.conf 门禁** ---- 理解连接来源、数据库、角色、认证方法和规则从上到下匹配；规则写得太宽会让安全团队皱眉，写得太窄会让应用在凌晨学会拒绝访问

**角色与默认权限** ---- 认识 login role、group role、继承、SET ROLE、默认权限和对象所有者；创建对象的角色会影响后续迁移和运维，不要让个人账号成为生产表的唯一主人

**schema 与 search_path** ---- 用 schema 隔离业务、扩展、报表和临时对象；谨慎处理 search_path，避免同名对象劫持、迁移环境差异和权限绕过

**扩展安装** ---- 理解 extension 会创建类型、函数、操作符、索引支持或后台能力；扩展属于数据库运行时的一部分，必须纳入版本、备份和升级清单

## 第三站：类型、约束与表设计

第三站是地基施工。PostgreSQL 的类型柜子比普通工具箱更大，见到数组、范围或自定义类型时很容易兴奋地全搬回家；先看查询、约束和迁移成本，再决定要不要开新抽屉。

**整数、精确数与浮点数** ---- 区分 smallint、integer、bigint、numeric、real、double precision 的范围与精度；金额和可审计计算优先考虑 numeric，科学测量才考虑浮点误差

**文本与字符类型** ---- 掌握 text、varchar、char 的语义与实际代价；长度限制若是业务规则应使用约束表达，不要以为 varchar(n) 自动解决所有数据质量问题

**日期、时间与时区** ---- 理解 date、time、timestamp、timestamptz、interval；统一存储语义与展示时区，明确“当天”“月底”和夏令时在跨地区系统里如何定义

**标识符与自增** ---- 比较 identity、sequence、旧式 serial、UUID、自然键和组合键；关注生成并发、索引局部性、暴露业务量、迁移与跨库合并成本

**布尔、枚举、域与复合类型** ---- 了解 boolean、enum、domain、composite type 的适用边界；类型越贴近业务，约束越清楚，但迁移和跨系统交换也越需要计划

**数组与范围类型** ---- 掌握数组的存取、包含查询和索引边界，以及 int4range、daterange 等范围类型；时间区间、版本区间和排班冲突常常比两列起止时间更容易表达

**网络与几何类型** ---- 认识 inet、cidr、macaddr 和几何相关类型；IP 白名单、网段判断等需求不必退化成字符串拼接，空间业务则应尽早评估 PostGIS

**NULL 与三值逻辑** ---- 理解 NULL 不是零、空字符串或 false，并观察比较、聚合、唯一约束、排序和 JOIN 中的行为；“未知”也是一种结果，不能靠直觉代替

**主键、唯一与外键** ---- 掌握 PRIMARY KEY、UNIQUE、REFERENCES、ON DELETE/UPDATE 行为；约束是数据的最后一道门，应用校验只是前台提醒

**CHECK 与排他约束** ---- 用 CHECK 表达金额非负、状态合法等局部规则，用 exclusion constraint 表达时间区间不能重叠等高级完整性；能由数据库证明的规则不要只写在注释里

**生成列与默认值** ---- 区分默认值、生成列、触发器和应用计算；默认值适合创建时填充，生成列适合可重复推导，复杂副作用逻辑不要悄悄塞进表定义

**范式与反范式** ---- 认识函数依赖、重复组、更新异常、冗余和读性能；反范式必须配套写入策略、回填方式、校验机制与数据所有权

**软删除、审计与版本字段** ---- 评估 deleted_at、created_at、updated_at、revision、valid_from/to、操作者和来源字段；软删除会改变唯一约束、索引、查询默认条件与空间回收

**行宽、TOAST 与大字段** ---- 了解超长 text、bytea、JSONB 可能被移到 TOAST 存储；大字段设计会影响缓存命中、网络传输、备份和表膨胀，不要只盯着类型上限

## 第四站：SQL 基础与安全 CRUD

第四站让数据开始走动。PostgreSQL 的 SQL 语法看似温文尔雅，遇到空值、隐式类型、事务边界和错误恢复时却很有原则；写得出来只是入场券，写错时能及时失败才算基本功。

**SELECT 的逻辑顺序** ---- 建立 FROM、JOIN、WHERE、GROUP BY、HAVING、SELECT、DISTINCT、ORDER BY、LIMIT 的心智模型；理解书写顺序与逻辑执行顺序不同

**条件与类型转换** ---- 掌握比较、CASE、COALESCE、NULLIF、日期函数、显式转换和正则条件；避免依赖隐式转换，让索引、结果类型和跨版本行为更可预测

**INSERT、UPDATE 与 DELETE** ---- 明确过滤条件、影响行数、事务边界、审计字段和恢复方案；任何批量 UPDATE 都先在小范围验证，再扩大影响面

**RETURNING** ---- 使用写入后的返回结果拿到生成 ID、默认值、旧值或更新后的行；减少一次往返，但要控制返回列和结果集大小

**UPSERT 与冲突处理** ---- 理解 ON CONFLICT 的冲突目标、DO NOTHING、DO UPDATE 和并发语义；幂等写入不是把错误吞掉，而是定义重复请求应该得到什么结果

**事务控制** ---- 掌握 BEGIN、COMMIT、ROLLBACK、SAVEPOINT、自动提交、异常回滚和隐式提交边界；连接归还池前必须确认事务状态干净

**参数化查询** ---- 让值通过驱动绑定，动态表名、列名和排序方向通过白名单控制；不要把用户输入拼成 SQL 语法

**分页与稳定排序** ---- 区分 OFFSET 分页和基于游标/键集的分页，使用唯一的稳定排序键；深分页会让数据库先走过一大片无用数据

**DDL 与事务** ---- 了解 PostgreSQL 许多 DDL 可参与事务，但 DDL 仍可能持有强锁、重写表或制造长等待；“可回滚”不代表“没有代价”

**视图与权限边界** ---- 用视图封装稳定的数据访问和脱敏列；确认视图所有者、调用者权限、security definer 与 search_path 的安全边界

**结果集与应用映射** ---- 关注 numeric 精度、时间时区、数组、JSON、枚举、NULL、重复列名和大字段；数据库正确返回，不代表语言驱动会自动按业务语义接住

**错误与重试** ---- 区分唯一冲突、序列化失败、死锁、连接断开、超时和语法错误；只有明确可重试的错误才重试，重试次数、退避和幂等必须同时设计

## 第五站：连接、聚合与复杂查询

第五站是 SQL 的社交场。JOIN 连得好，数据会互相帮忙；JOIN 连得不好，结果集会像参加婚礼的亲戚一样成倍增长，最后谁都说不清到底在数什么。

**INNER、LEFT、RIGHT 与 FULL JOIN** ---- 理解每种连接保留哪一侧行，以及 NULL 补位的意义；实际设计通常优先使用 INNER 和 LEFT，但要能读懂其他形式

**ON 与 WHERE 的位置** ---- 特别关注外连接中的过滤条件；把右表过滤写进 WHERE，可能会把 LEFT JOIN 变成 INNER JOIN，SQL 不会替你报警

**结果集粒度** ---- 在写查询前说明“一行代表用户、订单还是订单商品”；聚合错误往往不是函数写错，而是粒度在中途悄悄变了

**聚合与 FILTER** ---- 掌握 COUNT、SUM、AVG、MIN、MAX、FILTER、GROUP BY 和 HAVING；FILTER 能让条件统计更清楚，但仍要处理 NULL 与重复行

**GROUPING SETS、ROLLUP 与 CUBE** ---- 生成多级小计、总计和多维汇总；理解它们对结果行标记、排序和报表消费端的影响

**子查询与 EXISTS** ---- 区分标量、集合、相关子查询、IN、EXISTS、NOT EXISTS，以及 NULL 造成的三值逻辑陷阱；选择可读且能被计划器有效处理的表达方式

**LATERAL** ---- 让右侧子查询引用左侧当前行，适合每个用户取最近订单、每个实体取 TopN 等场景；它很锋利，数据量大时必须用执行计划验证

**DISTINCT ON** ---- 用排序配合分组键取每组一条记录；语法短而有特色，但排序规则、并列处理和跨数据库迁移都要明确

**窗口函数** ---- 掌握分区、排序、窗口帧、ROW_NUMBER、RANK、DENSE_RANK、LAG、LEAD、NTILE 与窗口聚合；窗口计算保留明细行，GROUP BY 通常会改变粒度

**递归 CTE** ---- 处理组织树、菜单、评论、依赖和图状关系；设置终止条件、深度上限、路径与防环逻辑，别让递归把数据库带去无尽远足

**集合操作** ---- 理解 UNION、UNION ALL、INTERSECT、EXCEPT 的去重、列对齐、排序和类型兼容；不需要去重时优先避免无意义的排序

**数组与行类型查询** ---- 认识数组展开、行构造、记录比较和聚合为数组；这些能力很方便，但不要让复杂数组结构取代清晰的关联表

## 第六站：JSONB 与半结构化数据

第六站是 PostgreSQL 的魔术抽屉。JSONB 允许关系表临时穿上文档外套，但它不是“把 schema 丢进字符串里就天下太平”；抽屉越灵活，整理和索引越需要纪律。

**JSON 与 JSONB** ---- JSON 保留文本形态与键顺序，JSONB 解析后以二进制结构存储并适合查询索引；按写入成本、查询频率、保真要求和运维习惯选择

**对象与数组操作符** ---- 掌握取 JSON、取文本、路径取值、包含、键存在和数组展开等操作；区分返回 JSON 与返回文本，避免类型比较时出现“看起来一样”的误会

**JSONPath** ---- 了解 SQL/JSON 路径表达式、过滤、数组遍历和错误处理；复杂路径要评估可读性、索引支持和未来字段演进

**构造与修改** ---- 使用对象/数组构造函数、路径更新、合并和删除操作；频繁局部更新可能造成写放大，不能只看语句长度

**JSONB GIN 索引** ---- 理解通用倒排索引、不同 operator class、包含查询和键存在查询的适用范围；GIN 查询强不等于索引免费，写入和膨胀都要付账

**表达式索引** ---- 为常用 JSON 路径建立表达式索引，或将稳定字段提取为生成列；表达式必须与查询写法、类型和排序保持一致

**关系列与 JSONB 的边界** ---- 主键、外键、经常过滤、经常排序和需要强约束的字段优先关系化；弹性属性、原始 payload 和低频扩展字段才适合 JSONB

**JSONB 的 schema 治理** ---- 为必需键、类型、版本、大小、敏感字段和迁移方式建立约定；“无 schema”只是把审查责任从数据库搬到了团队

**数组、对象与去重** ---- 评估嵌套数组更新、重复元素、顺序语义和并发修改；需要独立生命周期、约束或高频关联的对象通常应该拆表

**JSONB 性能诊断** ---- 观察索引命中、返回文档大小、路径选择性、GIN 体积和更新频率；先用真实数据分布测试，再决定是否把它当文档库

## 第七站：全文、空间与向量工具箱

第七站里，PostgreSQL 终于把几件“通常要另请专家”的活也接了。它会搜索、算距离、比相似度，但不会因为工具齐全就替你判断业务规模；瑞士军刀也有刀刃长度。

**tsvector 与 tsquery** ---- 理解文档向量化、词元、词干、权重、查询组合和匹配操作；全文检索不是简单的字符串 LIKE，而是有语言规则的索引系统

**文本搜索配置** ---- 认识字典、解析器、停用词、语言配置、同义词和中文分词边界；多语言产品要按语言和数据分布验证，而不是只换一个配置名

**全文索引与排序** ---- 使用 GIN 加速匹配，用相关性函数做排序，用高亮函数服务展示；搜索结果正确性、相关性和更新延迟要一起验收

**pg_trgm** ---- 了解三元组相似度、模糊匹配、LIKE 和 ILIKE 的加速方式；适合短文本相似查找和中小规模模糊搜索，不等于完整搜索平台

**PostGIS 心智模型** ---- 认识 geometry、geography、坐标系、投影、空间关系、距离和 GiST/SP-GiST 索引；经纬度字符串不是空间模型，距离单位也不是天然的米

**空间数据边界** ---- 评估空间对象规模、坐标精度、空间连接、可视化和数据导入；复杂 GIS 分析应让专业扩展或专用平台承担

**pgvector** ---- 了解向量列、距离度量、精确/近似近邻索引和 embedding 生命周期；向量检索要同时考虑模型版本、维度、召回率、过滤条件和重建索引

**向量与关系过滤** ---- 设计租户、权限、时间、状态与向量相似度的组合查询；先验证过滤后检索还是检索后过滤的代价，避免把权限当成结果出来后的补丁

**专用系统的边界** ---- 轻量全文、空间和向量需求可由 PostgreSQL 承担；当相关性、吞吐、分布式索引或数据规模超出单库能力时，应拆分到专业系统

## 第八站：索引家族与执行计划

第八站是 PostgreSQL 的交通枢纽。它的索引方法比普通公路多：B-tree 是主干道，GIN 像倒排目录，GiST 像通用搜索树，BRIN 则像在超长铁路旁立一排里程牌。选错路，车还是会堵。

**B-tree** ---- 掌握等值、范围、排序、最小/最大值和多列索引；理解列顺序、等值与范围条件、NULL 排序和排序方向

**Hash 索引** ---- 了解等值查询场景、能力边界和为什么多数业务仍以 B-tree 为默认；少用不等于不认识，选型要有证据

**GIN** ---- 理解倒排结构、数组、JSONB、全文、pending list、写放大和维护成本；适合一个字段包含许多可检索元素的场景

**GiST 与 SP-GiST** ---- 认识通用搜索树、空间、范围、相似度和非均匀数据分割；索引方法与 operator class 搭配决定了它真正支持什么查询

**BRIN** ---- 为按时间或物理顺序增长的超大表保存块级摘要；体积小、维护轻，但依赖物理相关性，乱序数据会让它失去神气

**复合索引与 INCLUDE** ---- 设计查询前导列、排序列、覆盖列和更新代价；INCLUDE 可以减少回表，但会增大索引并影响写入和缓存

**部分索引** ---- 只索引活跃、未归档或满足稳定条件的行；谓词必须与查询条件匹配，数据分布变化后要重新评估收益

**表达式索引** ---- 为 lower、日期截断、JSON 路径或计算结果建索引；表达式的类型、函数稳定性和查询写法需要保持一致

**唯一索引与约束** ---- 区分索引和约束的职责；唯一、主键、排他约束还承担数据完整性，不能只把一个普通索引当成规则声明

**并发建索引** ---- 了解普通建索引的锁影响、CONCURRENTLY 的阶段与失败残留；大表线上变更要安排监控、重试和清理

**索引膨胀与 REINDEX** ---- 观察更新删除、死元组、页面利用率和索引大小；REINDEX、并发重建和 fillfactor 都要结合锁、空间和业务窗口选择

**EXPLAIN 的基本读法** ---- 读懂成本、估算行数、实际时间、扫描类型、连接节点、排序、物化和并行；计划不是 SQL 的装饰品，而是优化器对现实的猜测

**EXPLAIN ANALYZE 与 BUFFERS** ---- 通过真实执行比较估算与实际，观察共享命中、读盘、临时文件和循环次数；生产大查询使用前要评估副作用，因为它真的会执行

## 第九站：MVCC、事务与锁

第九站进入并发的地下室。PostgreSQL 不会粗暴地把读者赶出门，而是给不同事务安排自己的快照；但快照越长，旧版本越难清理，数据库也会开始记仇。

**元组版本** ---- 理解 UPDATE/DELETE 通常产生新旧元组版本，xmin、xmax、ctid 等隐藏信息参与可见性判断；旧版本不在逻辑查询里出现，不代表它没有物理成本

**快照与可见性** ---- 掌握事务快照、已提交事务、活动事务和版本可见性的关系；同一行在不同事务中看到不同版本，是 MVCC 的核心表现

**读已提交** ---- PostgreSQL 默认每条语句获取新快照；事务内两次查询可能看到不同结果，应用需要明确是否接受不可重复读

**可重复读** ---- 事务通常复用同一快照，普通读取保持一致；写入冲突和当前读仍可能失败，不能把它理解成无条件的时间旅行

**可串行化 SSI** ---- 通过检测危险的读写依赖结构阻止部分异常，并以 serialization failure 结束冲突事务；应用必须具备可重试的事务设计

**当前读与行锁** ---- 掌握 FOR UPDATE、FOR NO KEY UPDATE、FOR SHARE、FOR KEY SHARE 的差异；锁的目标、持有时间和索引路径都会影响并发

**表级锁** ---- 认识 ACCESS SHARE 到 ACCESS EXCLUSIVE 等模式及兼容关系；ALTER、TRUNCATE、VACUUM FULL 和某些重建操作可能阻塞大量业务

**谓词锁与 SSI** ---- 理解可串行化隔离下的读写冲突记录和内存压力；“没有锁住一行”不等于“没有留下并发约束”

**咨询锁** ---- 使用会话级或事务级 advisory lock 表达业务互斥，如单实例任务、迁移互斥和资源编排；它是协作工具，不是自动故障恢复

**死锁与阻塞** ---- 统一加锁顺序、缩短事务、避免事务中等待外部服务，并捕获死锁错误进行有限重试；死锁日志是证据，不是数据库在发脾气

**长事务** ---- 长时间未提交的事务会阻碍旧版本回收、延迟冻结、占用连接和放大复制延迟；监控事务开始时间、空闲事务和连接池归还状态

**隔离级别的业务选择** ---- 根据库存、余额、抢占、报表和批处理的异常容忍度选择隔离级别；不要把最高隔离级别当成万能性能保险

## 第十站：存储、VACUUM 与统计信息

第十站参观仓库内部。PostgreSQL 的 UPDATE 更像把旧货贴上“不可售”标签，再把新货放到货架上；清理、压缩、冻结和统计不及时，仓库不会立刻尖叫，却会越来越拥挤。

**Heap、page 与 tuple** ---- 理解表以页组织，页里存元组和空闲空间，索引指向堆表位置；页大小、行宽、随机访问和缓存命中最终会相遇

**TOAST** ---- 认识超长字段的外部存储、压缩与切片；TOAST 让行能住下大对象，但读取整行、备份和网络返回仍可能很贵

**FSM 与 visibility map** ---- 理解空闲空间映射和可见性映射如何帮助复用空间、跳过不必要扫描以及支持 index-only scan

**死元组** ---- UPDATE/DELETE 遗留的旧版本会占用表和索引空间；死元组率上升会拖慢扫描、增加膨胀并让统计信息落后

**VACUUM** ---- 清理可回收版本、维护可见性和推进冻结；普通 VACUUM 通常复用空间而不缩小文件，不能把它当成“压缩表”

**VACUUM FULL** ---- 通过重写表回收文件空间，但会持有强锁、需要额外空间并造成长时间影响；只有明确的空间回收需求才考虑

**ANALYZE** ---- 更新列分布、直方图、最常见值和相关统计，让规划器更接近现实；大表和偏斜字段可能需要按表或按列调整统计目标

**扩展统计信息** ---- 用多列依赖、组合最常见值和表达式统计帮助规划器估算相关条件；单列统计解释不了所有业务关联

**autovacuum** ---- 掌握触发阈值、worker 数、成本延迟、冻结阈值和按表调参；高更新小表常常需要比默认值更积极的清理

**HOT 更新** ---- 当更新不涉及索引列且页面有空间时，可在同页形成版本链，减少索引维护；fillfactor 是给未来更新预留座位

**事务 ID 回卷** ---- 32 位事务 ID 需要持续冻结，接近 wraparound 时会触发强制清理甚至威胁写入；冻结年龄是运维红线，不是学术名词

**膨胀治理** ---- 结合 pg_stat_user_tables、表/索引大小、死元组、长事务和磁盘水位判断问题；不要只看到文件大就直接 VACUUM FULL

## 第十一站：WAL、备份与恢复

第十一站是保险库。数据库真正可靠，不是因为它从没坏过，而是因为它能在断电、误删、磁盘故障和版本迁移后按目标时间回到可用状态。

**WAL 预写日志** ---- 理解修改先写 WAL、数据页随后落盘，以及 WAL 如何支持崩溃恢复；日志位置 LSN 是复制、归档和恢复链路的重要坐标

**WAL 段与 checkpoint** ---- 认识 WAL 文件、检查点、重放起点、脏页刷盘和恢复时间；检查点过于频繁会增加写放大，过于稀疏会拉长恢复

**wal_level 与归档** ---- 根据本地恢复、物理复制和逻辑复制目标选择日志级别；归档命令必须具备失败告警、幂等和远端保留策略

**逻辑备份** ---- 了解 pg_dump、pg_dumpall、对象依赖、并行导出/导入和跨版本迁移；逻辑备份可读性强，但大库恢复时间通常更长

**物理基础备份** ---- 使用 pg_basebackup 或合规的物理备份工具理解整集群复制、校验、压缩和恢复目录；物理备份与服务器版本、架构和扩展环境绑定更紧

**PITR 时间点恢复** ---- 用基础备份加连续 WAL 恢复到误删前、故障前或指定时间点；RPO 取决于日志是否完整，RTO 取决于恢复链路是否真正跑过

**备份一致性** ---- 明确在线备份的快照边界、正在提交的事务、复制槽和归档顺序；“文件复制完成”不等于“备份可恢复”

**恢复演练** ---- 定期验证整库、单库、单表、权限、扩展、应用连接、数据校验和切换流程；恢复演练是备份系统的考试成绩

**备份安全** ---- 为备份加密、限权、异地保存、生命周期管理、密钥轮换和脱敏；备份往往比在线库更完整，泄露后影响也更完整

**误操作修复** ---- 设计延迟副本、只读恢复环境、导出差异、逐步比对和回滚脚本；不要直接在生产恢复目录里凭感觉改数据

**WAL 保留风险** ---- 复制槽、长期断开的副本和归档失败会让 WAL 堆积并填满磁盘；监控槽位、归档延迟和 pg_wal 空间

## 第十二站：复制、连接池与高可用

第十二站把单机家庭升级成多节点社区。节点多了并不会自动产生秩序，大家还得决定谁能写、谁能读、谁落后了、谁可以接班，以及旧主什么时候必须闭嘴。

**物理流复制** ---- 理解主库发送 WAL、备库接收并重放的链路；异步复制有延迟和丢失窗口，同步复制以提交延迟换更强的数据保护

**同步级别** ---- 区分 remote_write、on、remote_apply 等确认语义；“副本收到”与“副本可读到”不是同一件事

**复制槽** ---- 用物理或逻辑槽位防止所需 WAL 被过早清理；槽位也可能因副本永久离线而拖垮主库，必须配置上限和告警

**级联与延迟副本** ---- 让备库继续向下游发送，减少主库网络压力；延迟副本可为误操作提供窗口，但会牺牲数据新鲜度

**逻辑复制** ---- 通过发布与订阅按表传输变更，适合选择性同步、跨大版本迁移和异构消费；DDL、序列、冲突和双向写入需要额外方案

**复制延迟** ---- 分析网络、WAL 生成、大事务、备库磁盘、回放锁、查询压力和长事务；读写分离前先决定业务能否接受读旧数据

**故障切换** ---- 设计探活、选主、隔离旧主、连接切换、未完成事务、数据校验和回切；自动 failover 不是魔法按钮，而是一套需要演练的状态机

**脑裂与 fencing** ---- 防止旧主在网络分区后继续写入；VIP、DNS、云实例电源、仲裁存储或控制平面都只是手段，关键是旧主确实不能继续服务

**Patroni、repmgr 与云托管** ---- 认识常见 HA 编排方案各自的选主、DCS、运维和故障边界；不要只看“能自动切换”，还要看升级、回滚和人工接管

**PgBouncer** ---- 理解会话级、事务级和语句级池化的差异；事务级池化能复用连接，但会限制临时表、会话状态和某些预备语句用法

**读写路由** ---- 把写请求、强一致读、普通读、延迟副本和故障降级分别建模；路由策略必须与业务的读后写一致性相配套

## 第十三站：查询优化、性能与容量

第十三站是性能诊断室。规划器不是算命先生，它只能依据统计、成本参数和现实资源做猜测；你要做的是给它更好的证据，而不是看到慢就把每个参数拧到最大。

**EXPLAIN ANALYZE 证据链** ---- 对比 estimated rows 与 actual rows，关注节点耗时、循环次数、过滤行、排序、哈希、临时文件和缓冲区；先定位瓶颈，再改 SQL 或索引

**扫描与连接节点** ---- 读懂 Seq Scan、Index Scan、Index Only Scan、Bitmap Heap Scan、Nested Loop、Hash Join、Merge Join；没有“全表扫描永远坏”，只有与选择性和数据规模不匹配

**统计信息与数据偏斜** ---- 识别统计过期、相关列、长尾分布、参数敏感和常量变化导致的计划差异；必要时提高列统计目标或使用扩展统计

**排序与哈希内存** ---- 理解 work_mem 通常按操作而非按连接只分配一次；盲目调大可能让并发查询同时申请过多内存并触发 OOM

**shared_buffers 与操作系统缓存** ---- 理解数据库缓存、OS page cache、effective_cache_size 和实际工作集的关系；配置不能脱离内存、并发、容器限制和磁盘

**并行查询** ---- 认识并行 worker、Gather、并行扫描/聚合/连接和启动成本；小查询不一定适合并行，大查询也可能受限于磁盘或锁

**JIT** ---- 了解 LLVM 即时编译对复杂表达式和长查询的潜在收益；编译开销会让短查询变慢，必须用基准验证

**pg_stat_statements** ---- 通过调用次数、总时间、平均时间、共享块、临时块和 WAL 统计定位最值得优化的 SQL；不要只盯着单次最慢

**等待事件与活动会话** ---- 结合 pg_stat_activity、wait_event、锁视图和应用请求 ID 判断是在 CPU、I/O、锁、客户端读取还是连接排队

**连接池与并发上限** ---- 让应用并发、池大小、数据库 max_connections、CPU、内存和下游容量相互匹配；连接越多不等于吞吐越高

**基准与回归** ---- 用接近生产的数据量、分布、并发、冷热缓存和事务比例做基准；记录 p95/p99、吞吐、错误、WAL、锁等待和资源水位

**容量规划** ---- 估算数据、索引、WAL、备份、临时文件、复制、连接和磁盘 IOPS 的增长；磁盘满会同时攻击写入、归档和恢复

## 第十四站：安全、运维与变更

第十四站负责把“能运行”送到“敢托付”。数据库管理员最怕的不是一个陌生命令，而是权限过宽、监控缺失、变更无回滚、日志泄露和凌晨才发现磁盘已经没有明天。

**最小权限** ---- 为应用读写、迁移、报表、备份、监控和管理员设置不同角色；避免业务连接使用超级用户或表所有者

**对象所有权与默认权限** ---- 规划迁移角色、运行角色、schema 所有者和未来对象权限；用默认权限减少新表上线后突然不可访问的事故

**Row-Level Security** ---- 用 RLS 按租户、用户或数据分类限制行可见性；审查 owner 绕过、BYPASSRLS、security definer 和连接池会话状态

**TLS 与认证** ---- 了解密码认证、证书认证、LDAP/外部认证、服务端证书和客户端校验；加密传输与身份确认是两件事，都不能省略

**日志体系** ---- 区分错误日志、连接日志、慢查询、审计、WAL 与应用日志；日志要能回答谁、何时、访问了什么、等待了谁，同时避免记录密码和敏感 payload

**监控指标** ---- 观察连接、事务年龄、锁等待、缓存命中、WAL、复制延迟、autovacuum、死元组、膨胀、磁盘和临时文件；每个指标都应有阈值后的动作

**DDL 与锁风险** ---- 识别表重写、默认值回填、索引创建、类型转换和外键校验的锁与耗时；大表变更要分阶段、可观测、可回滚

**迁移工具与发布顺序** ---- 采用向后兼容的扩展字段、双读/双写、回填、切换、清理顺序；数据库迁移不能脱离应用版本独自发布

**扩展与安全边界** ---- 审查扩展来源、超级用户权限、C 代码风险、升级兼容性和备份恢复；扩展不是装上就永远免费的插件

**故障排查顺序** ---- 先确认影响范围和当前错误，再看连接、锁、资源、计划、日志与最近变更；不要在证据不足时同时重启、调参和删缓存

**维护窗口** ---- 为 vacuum、reindex、分区切换、版本升级、恢复演练和证书轮换安排明确窗口与回退方案；维护不是“尽量不打扰”，而是把打扰控制在目标内

## 第十五站：分区、扩展与架构演进

最后一站是地图室。PostgreSQL 能从一台可靠的关系数据库成长为带空间、向量、逻辑复制和分区能力的平台，但每增加一层能力，也是在增加升级、监控和故障边界。

**范围分区** ---- 按时间、租户或数值范围组织大表，利用分区裁剪减少扫描并简化归档；分区键、边界、默认分区和未来分区必须有自动化维护

**列表与哈希分区** ---- 用 LIST 表达区域/类型，用 HASH 均匀分散数据；评估分区数量、跨分区查询、唯一约束与后续扩容

**分区生命周期** ---- 设计创建、预热、归档、detach、备份、删除和回收流程；时间分区的价值常常在于可控地丢弃历史，而不只是让查询更快

**分区索引与约束** ---- 理解本地索引、分区级约束、全局唯一性边界和维护成本；分区不是把所有索引问题自动复制成正确答案

**FDW 与外部数据** ---- 认识 foreign data wrapper、远端扫描、下推、事务和网络故障；远端表能被查询不代表它具备本地表一样的延迟与一致性

**分布式扩展** ---- 了解 Citus 等分布式方案的分布键、共置、重分布和跨节点查询代价；先证明单库和读写分离不够，再引入分布式复杂度

**多租户隔离** ---- 比较共享表加 RLS、按 schema、按 database、按实例的隔离、成本、备份和迁移；租户边界同时属于数据、权限和运维

**缓存与搜索协作** ---- 让 PostgreSQL 做可信来源，缓存承担短期热点，搜索承担相关性，消息系统承担异步传播；不要因为一个组件能做一点别人的工作就取消边界

**Outbox 与变更传播** ---- 处理“事务提交了但消息没发出”的间隙，使用 outbox、逻辑解码或 CDC 传递变更；消费者仍需幂等、重试、顺序和死信设计

**MySQL 迁移** ---- 重点比较大小写、identity/sequence、JSONB、时间类型、RETURNING、事务语义、索引方法、VACUUM 与复制；迁移应先做类型映射和数据校验，再做流量切换

**毕业项目** ---- 做一个带用户、订单或内容流的系统，经历建模、约束、复杂查询、JSONB、索引、并发冲突、备份恢复、复制延迟和一次可观测的线上变更

## 通关标准

**基础通关** ---- 能安装并连接 PostgreSQL，解释集群、数据库、schema、角色和 search_path，设计合理类型与约束，完成安全 CRUD、事务和稳定分页

**SQL 通关** ---- 能用 JOIN、聚合、FILTER、窗口函数、递归 CTE、LATERAL、DISTINCT ON 和 RETURNING 解决真实查询，并能说明结果集粒度

**扩展通关** ---- 能判断关系列与 JSONB 的边界，使用 GIN 或表达式索引；理解全文、空间、向量能力的适用场景与专用系统边界

**并发通关** ---- 能解释 MVCC、快照、隔离级别、行锁、表锁、咨询锁、长事务与死锁，并为序列化失败设计有限重试

**性能通关** ---- 能阅读 EXPLAIN ANALYZE 与 BUFFERS，解释统计信息、扫描、连接、work_mem、并行、索引膨胀和连接池对延迟的影响

**运维通关** ---- 能配置最小权限、TLS、日志和监控，处理 autovacuum、事务回卷、WAL 堆积、复制槽与磁盘水位，并完成恢复演练

**架构通关** ---- 能根据一致性、吞吐、延迟、规模、团队和故障目标选择单库、分区、复制、逻辑同步、缓存、搜索或分布式扩展，并说清回退路径

## 下一站去哪

PostgreSQL 走到这里，已经从“会写 SQL”变成了“能让数据可靠地活在系统里”。接下来可以按问题继续：

**Redis** ---- 去学习内存数据结构、缓存策略、持久化、分布式锁、限流和高并发访问

**MongoDB** ---- 去比较文档模型、嵌套数据、聚合管道、副本集和分片取舍

**消息系统** ---- 去理解 Outbox、重试、顺序、幂等、死信和最终一致性

**空间与向量应用** ---- 把 PostGIS 或 pgvector 单独做成一个可验证的业务项目，练习索引、召回、权限过滤和容量边界

## 结语

PostgreSQL 的魅力不在于“功能最多”这句宣传语，而在于它愿意把复杂问题拆成可验证的类型、约束、快照、索引、日志和扩展。它会允许你自由设计，也会要求你为每个自由承担可观察、可恢复、可迁移的责任。

先把数据模型和约束做对，再读懂执行计划；先学会 VACUUM、WAL 和恢复，再谈复制、分区和分布式。等你能从一条慢查询追到统计信息、索引、页面、锁和架构边界，也能把误删恢复到目标时间点——你学到的就不只是 PostgreSQL，而是一套可靠地与数据相处的方法。
