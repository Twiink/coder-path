# MongoDB 学习路线

MongoDB 是数据库世界里那位喜欢把行李装进文档的旅行家：用户资料、订单明细和内容元数据可以自然地住在同一个 BSON 文档里，字段还能随着产品迭代灵活增加。只是“灵活”不是“随便”，当文档膨胀、数组失控、索引过多或分片键选错时，这位旅行家会把账单连同查询延迟一起寄回来。

这条路线从文档模型和 CRUD 起步，逐步进入聚合管道、索引、单文档原子性、多文档事务、WiredTiger、副本集、分片、性能、备份、安全和架构取舍。MongoDB 的关键不是背一串 API，而是学会在嵌入与引用、灵活与约束、吞吐与一致性、单机与分布式之间做出有证据的选择。

**推荐顺序** ---- 文档数据库心智模型 → 安装与连接 → BSON 与建模 → CRUD 查询 → 聚合管道 → 索引 → 原子性与一致性 → WiredTiger 内部 → 副本集与高可用 → 分片 → 性能与容量 → 备份恢复与运维 → 安全 → 高级能力与架构演进

**这条线怎么用** ---- 每站都从访问模式出发：谁写、谁读、一次读多少、是否需要事务、数据怎样增长、故障后丢多少可接受。MongoDB 允许你不先画固定表结构，但不允许你不思考数据形状。

## 第一站：先认识这位文档旅行家

第一站先建立地图。MongoDB 不把世界切成传统的表和行，而是让文档、集合、数据库和节点各自扮演角色；如果把集合当成“永远不会变的大抽屉”，后面很快会发现抽屉里住着完全不同的生物。

**文档数据库与 BSON** ---- 区分 MongoDB 文档模型、BSON 二进制编码和关系数据库的表模型；理解嵌套对象、数组和类型信息如何贴近应用对象

**mongod、mongos 与驱动** ---- 认识数据库服务进程、分片路由进程、客户端驱动和连接池；查询从应用到节点的路径决定了延迟、路由与故障表现

**数据库、集合与文档** ---- 理解 database、collection、view、document、field、index、replica set 和 cluster 的层级；集合相当于同类文档的业务边界，而不是简单的“表改名”

**有 schema 与无固定 schema** ---- 了解 MongoDB 不强制所有文档字段完全一致，但生产系统仍然需要数据契约、版本字段和验证规则；没有强制 schema 不代表没有 schema

**嵌套数据的心智模型** ---- 把常一起读取、生命周期一致、规模可控的数据放进同一文档；把独立增长、频繁修改或需要跨实体复用的数据单独建模

**读写路径** ---- 串起驱动、连接池、mongos 或 mongod、查询规划、WiredTiger、journal、复制确认和响应；接口慢不一定是查询慢，也可能是连接、写关注或锁等待

**版本与兼容** ---- 关注服务器版本、驱动版本、Feature Compatibility Version、索引行为和命令弃用；升级要同时检查应用驱动、运维工具和备份格式

**工具地图** ---- 熟悉 mongosh、驱动、Compass 等 GUI、explain、profiler、currentOp、serverStatus、备份工具和监控；工具是望远镜，不能代替建模

## 第二站：安装、连接与客户端边界

第二站把 MongoDB 请进实验室。它看起来像启动一个服务，实际上还要处理认证、网络、连接池、读写偏好和超时；“本机能查到”只是数据库刚刚点亮了门牌。

**安装与部署方式** ---- 了解本地安装、容器、虚拟机、云托管和 Kubernetes 运营方式；记录数据目录、日志、配置、文件权限和服务启动方式

**连接串与拓扑发现** ---- 理解单节点、复制集、分片集群连接串、节点发现、TLS、认证数据库、读写超时和重试；让驱动知道拓扑，而不是把某个节点地址焊死

**连接池** ---- 掌握池大小、最小空闲、等待队列、连接寿命、心跳、连接超时和服务端连接上限；池过大时，所有请求都会一起冲向数据库门口

**mongosh 基础** ---- 会切换数据库、查看集合与索引、观察服务器状态、执行 explain 和查看当前操作；实验时保留数据生成和清理方式，避免手工操作无法复现

**读偏好** ---- 理解 primary、primaryPreferred、secondary、secondaryPreferred 和 nearest 的语义；读副本可能降低主节点压力，也可能读到旧数据

**写关注** ---- 掌握 acknowledged、w、majority、journal、wtimeout 等概念；写入返回成功的条件必须与业务对数据持久性的要求一致

**超时与重试** ---- 区分选择服务器、建立连接、发送查询、等待结果和提交事务的超时；开启重试写入或事务重试前，先确保操作具备幂等语义

**数据库与集合生命周期** ---- 理解隐式创建、显式创建、集合选项、视图、时间序列集合和删除对象的影响；对象变更要进入迁移和审计流程

**本地实验纪律** ---- 准备单节点和三节点复制集实验，制造网络抖动、进程重启、慢查询和回滚场景；不要把生产集群当成第一次故障演练的沙盒

## 第三站：BSON、约束与文档建模

第三站是 MongoDB 的建筑课。文档可以像公寓一样把相关房间放在一起，也可以像仓库一样堆到无法搬动；真正的设计从访问路径开始，而不是从“这个字段要不要嵌套”开始。

**BSON 类型** ---- 掌握 string、number、decimal、boolean、date、timestamp、binary、objectId、array、object、null、regular expression 和 min/max key 等类型的区别

**ObjectId** ---- 理解 ObjectId 的组成、生成位置、近似时间信息、排序特征和暴露风险；它适合默认标识，但不自动等于业务编号、全局有序 ID 或隐私安全

**数字类型与精度** ---- 区分 double、int32、int64 和 Decimal128；金额、计费、税率等需要精确小数的字段不要用浮点数侥幸过关

**日期与时间** ---- 统一 UTC 存储、业务时区展示和事件时间语义；注意 BSON Date 与应用语言日期类型之间的精度、时区和序列化差异

**缺失、null 与空数组** ---- 观察字段不存在、字段值为 null、空数组和空对象在查询、索引、聚合和更新中的不同结果；不要把“没有值”只设计成一种含义

**嵌入与引用** ---- 用嵌入支持一次读取和原子更新，用引用支持独立生命周期、无限增长和跨文档复用；两者也可以按读模型组合

**一对一与一对多** ---- 评估访问方向、文档大小、更新频率和权限边界；常用小对象可嵌入，增长无上限的子集合不要无脑塞进父文档

**多对多** ---- 比较双向数组、关联集合、冗余快照和聚合查询；关系两端都频繁增长时，引用与反向索引通常比互相复制更稳

**数组与数组索引** ---- 了解数组元素匹配、$elemMatch、位置更新和多键索引；数组越长，索引键越多，更新和写放大也会跟着长

**模式设计模式** ---- 练习 subset、bucket、computed、outlier、extended reference、polymorphic、schema version 和 archive 等模式；每种模式都要写清触发条件与回迁路径

**文档大小与嵌套深度** ---- 牢记单文档有大小边界，关注深层嵌套、单文档响应、更新复制和网络传输；大文档不是“少一次 JOIN”这么简单

**集合级 schema validation** ---- 使用 JSON Schema、验证级别与验证动作约束类型和必填字段；验证规则要配合历史文档、版本字段和迁移脚本

**唯一性边界** ---- 用唯一索引保护集合内唯一性，理解数组唯一、多租户唯一、软删除唯一和分片下唯一约束的限制

**命名与版本演进** ---- 统一字段风格、时间字段、状态、引用 ID、schemaVersion 和弃用字段；文档模型仍然需要向后兼容的发布顺序

## 第四站：CRUD、查询语义与安全边界

第四站让文档开始接受问讯。MongoDB 的查询很像对文档下达条件指令，但数组、缺失字段、正则和位置更新都可能偷偷扩大范围；每个更新都要知道自己会碰到多少份行李。

**查询过滤器** ---- 掌握等值、比较、逻辑、集合、存在、类型、元素匹配、文本与地理过滤；用明确条件限制扫描范围，避免把“方便查询”变成全库巡逻

**投影与返回大小** ---- 选择需要的字段，避免把大数组、原始 payload 和敏感字段无意返回；投影既影响网络，也影响是否能形成覆盖查询

**排序与限制** ---- 为排序提供索引和稳定的唯一补充键，组合 limit 控制返回规模；没有排序的结果顺序不能当业务顺序

**更新操作符** ---- 熟悉 set、unset、inc、mul、min、max、rename、currentDate、addToSet、push、pull、pop 和 bit 等操作的语义

**数组更新** ---- 理解 positional、filtered positional、arrayFilters、$each、$slice、$sort 和 $position；复杂数组更新要验证并发行为与索引变化

**替换文档与局部更新** ---- 区分 replaceOne 与 updateOne；替换会删除未包含的字段，局部更新更适合演进中的文档

**Upsert** ---- 设计过滤条件、默认字段、唯一索引和并发冲突；upsert 不是天然幂等，必须保证业务键和冲突处理正确

**findAndModify 类操作** ---- 使用带返回值和排序的原子读改写完成抢占、状态流转或队列领取；理解返回旧文档/新文档、未命中和并发竞态

**批量写入** ---- 了解 ordered 与 unordered、批量大小、失败项、部分成功和重试；批量能提高吞吐，但会放大单次请求的锁、日志和错误边界

**删除与归档** ---- 区分逐条删除、批量删除、软删除、TTL 过期和归档；大批删除要考虑复制、磁盘、索引、回滚和在线业务影响

**正则与全文查询** ---- 认识前缀正则可能利用索引，任意前缀模糊通常代价高；重度相关性搜索应评估专用搜索系统

**参数与注入防护** ---- 使用驱动的结构化查询，不把用户输入直接拼成操作符或字段路径；限制可用运算符、排序字段、正则长度和返回数量

**分页策略** ---- 比较 skip/limit 与基于索引键的范围分页；数据量大、翻页深或排序稳定性要求高时，优先使用键集分页

## 第五站：聚合管道与分析查询

第五站是 MongoDB 的流水线车间。每个文档像一件包裹，$match、$project、$unwind 和 $group 轮流加工；顺序不对，流水线就会先把全国货物拆开再问“有没有必要”。

**聚合管道心智模型** ---- 理解文档依次流经各 stage，前一站的输出是后一站的输入；先明确中间文档形状和粒度，再堆阶段

**$match 与早期过滤** ---- 尽量把可索引、可下推的过滤放在前面，减少后续内存、网络和 CPU；过滤条件要与数据权限同时设计

**$project、$set 与字段整形** ---- 控制输出字段、计算字段、脱敏字段和兼容字段；尽早丢弃无用大字段，但不要误删后续阶段还需要的键

**$unwind** ---- 将数组展开成多行，理解 preserveNullAndEmptyArrays、索引位置和结果集膨胀；一个超长数组可以瞬间把小查询变成长跑

**$group** ---- 掌握按键分组、计数、求和、最值、数组收集和去重；聚合内存、分组基数和排序方式决定性能

**$sort、$limit 与 TopN** ---- 让排序尽量走索引或在过滤后进行，先限制候选集；没有稳定排序键时，TopN 结果可能在数据变化后抖动

**$lookup** ---- 理解集合关联、pipeline lookup、相关变量、索引利用和结果数组；它能解决部分关联需求，但大量跨集合 JOIN 可能提示模型边界

**$facet** ---- 在同一批输入上生成多条子管道，适合列表与统计一起返回；facet 会共享输入成本，子管道多时要检查内存与延迟

**$bucket 与分箱** ---- 按价格、年龄、时间等区间统计分布；边界、空箱、时区和小数精度必须定义清楚

**$setWindowFields** ---- 做排名、累计、移动窗口和邻近记录分析；窗口排序与分区键要有索引或基准，避免把分析压力推回在线服务

**$graphLookup** ---- 遍历组织层级、推荐关系或依赖图；设置深度、过滤、防环与结果上限，图查询不应拥有无限假期

**$unionWith** ---- 合并不同集合或历史分区的结果；字段契约和排序需要统一，跨集合合并通常不如单一读模型简单

**$merge 与 $out** ---- 将聚合结果写入物化读模型、汇总表或临时集合；明确覆盖、更新、唯一键、失败恢复和重建策略

**聚合表达式与类型** ---- 处理日期、字符串、数组、条件、转换和 null；显式转换可以减少隐式类型带来的错误，但也可能增加 CPU

**聚合 explain 与内存** ---- 通过 explain 观察扫描、索引、文档数、阶段耗时和磁盘溢写；开启 allowDiskUse 只是把内存压力搬到磁盘，不是免费扩容

## 第六站：索引与查询规划

第六站是 MongoDB 的行李分拣中心。索引能让它快速找到目标包裹，也会让每次写入都多维护几条目录；目录越厚，搬家越慢。

**单字段索引** ---- 适合高频等值、范围、排序和存在查询；选择性、热度、返回比例与写入成本要一起评估

**复合索引与 ESR** ---- 按 Equality、Sort、Range 思考字段顺序，再结合真实查询形状；不是所有查询都能靠“高选择性列放第一”解决

**前缀规则** ---- 理解复合索引的前缀使用、跳列、排序兼容和多条件过滤；索引设计应围绕查询族，而不是围绕字段数量竞赛

**多键索引** ---- 了解数组字段如何产生多个索引键、一个索引的数组边界和嵌套数组限制；多键索引是数组的放大器，数据增长前要估算

**覆盖查询** ---- 让过滤和返回字段都能从索引取得，减少文档读取；覆盖索引可能很宽，写入和内存成本不能忽略

**唯一索引** ---- 保护单字段、复合字段和业务键唯一性；区分缺失字段、null、多租户、软删除和分片环境下的唯一范围

**部分与稀疏索引** ---- 只索引满足过滤条件或存在字段的文档；partialFilterExpression 通常更能表达业务条件，选择前要验证历史数据

**TTL 索引** ---- 自动清理会话、临时令牌、事件和日志；TTL 删除是后台行为，不保证精确到某一秒，也可能带来删除与复制压力

**文本与地理索引** ---- 了解 text、2dsphere 等索引的查询能力、语言配置、坐标语义和排序边界；复杂搜索、地理围栏和相关性需求要做专项压测

**哈希与通配索引** ---- 哈希适合特定等值与分片场景，通配索引适合字段路径多变的文档；灵活索引不能替代明确的高频查询设计

**隐藏与实验索引** ---- 利用隐藏索引评估计划影响，安全地观察删除候选；实验索引也会占空间、写入和构建资源

**索引构建与维护** ---- 关注在线构建、构建失败、磁盘临时空间、复制集滚动操作和版本差异；大索引不是点一下按钮就完成

**查询计划缓存** ---- 理解规划器、候选计划、统计、数据分布变化和计划缓存；参数和分布变化后，旧计划可能变成旧地图

## 第七站：原子性、事务与一致性

第七站讨论 MongoDB 的秩序感。单文档更新像一位很可靠的门卫，一次只守好一个房间；跨文档事务则是把多个房间绑在一次巡检里，安全性更强，成本也更高。

**单文档原子性** ---- 理解同一文档内的更新、数组修改和状态流转具有原子语义；优先通过合理嵌入把必须一起变化的数据放在一个原子边界内

**并发更新与条件保护** ---- 用版本号、状态条件、业务键和原子更新避免覆盖别人的修改；“先查再改”若不在同一原子操作里，容易留下竞态

**多文档事务** ---- 理解事务会话、开始/提交/回滚、读关注、写关注、快照和重试；事务不是把关系数据库完整搬进 MongoDB，而是有明确成本的补救工具

**事务限制与代价** ---- 关注事务时长、文档数量、锁、内存、日志、复制延迟和跨分片成本；长事务会让故障恢复和并发写入更难

**读关注** ---- 区分 local、available、majority、linearizable、snapshot 等语义的适用范围；“读到最新”需要明确对哪个拓扑、哪个时间点负责

**写关注与持久化** ---- 比较 w:1、majority、journal 与超时；多数确认增强数据保护，但会受最慢副本和网络影响

**读取偏好与陈旧数据** ---- 读副本能扩展读，但不能凭空消除复制延迟；为强一致读、报表读和可接受旧数据的读分别建策略

**因果一致性** ---- 认识会话、操作时间和读写依赖，保证相关操作的观察顺序；跨服务传播因果信息仍需应用设计

**可重试写入与提交** ---- 处理网络超时后的不确定结果，使用驱动重试能力和幂等业务键；不要把“客户端没收到响应”当作“服务器没执行”

**幂等与去重** ---- 用唯一索引、请求 ID、状态机、去重集合和结果记录处理重复请求；事务能保证原子，不会替你保证消息只来一次

**乐观并发与冲突** ---- 设计 compare-and-set、版本号、重试上限和用户可见冲突；高竞争资源适合短操作，避免用长事务霸占它

**一致性选择** ---- 根据支付、库存、配置、日志、社交关系和分析数据分别选择读写关注；统一套用 majority 或事务往往既浪费性能又没有解决真正问题

## 第八站：WiredTiger 与存储底层

第八站打开引擎机房。MongoDB 的 WiredTiger 会管理页面、缓存、压缩、检查点和多版本并发；它很勤快，但不负责把糟糕的数据形状和过多索引变成好设计。

**WiredTiger 的职责** ---- 区分 MongoDB 查询层、WiredTiger 存储引擎和操作系统文件系统；理解集合、索引、页面、缓存和日志的分工

**B-tree 与页面** ---- 认识集合与索引的树结构、页面分裂、局部性、随机写和范围扫描；高随机 ID、高更新字段和大索引会破坏缓存与写入局部性

**文档与记录存储** ---- 理解文档更新可能改变大小、触发移动、写入新版本和增加复制/日志成本；频繁增长的数组尤其需要单独估算

**WiredTiger cache** ---- 观察缓存上限、脏页、驱逐、读放大、写放大和操作系统缓存；把所有内存都交给数据库或把容器内存估错，都会导致惊喜

**压缩** ---- 了解集合与索引压缩对磁盘、CPU、缓存密度和恢复时间的影响；压缩不是越高越好，需按数据和 CPU 负载测量

**多版本并发** ---- 理解读写通过版本和时间戳减少互相阻塞，但旧版本仍需清理；长事务和慢读会增加存储压力

**Journal 与检查点** ---- 掌握日志写入、检查点、崩溃恢复和持久化确认的关系；journal 能减少崩溃丢失窗口，但不等于远端副本和异地备份

**Oplog** ---- 认识复制操作日志的大小、循环覆盖、时间窗口、写入速率和初始同步关系；oplog 太短会让断线副本不得不全量同步

**写放大** ---- 把更新文档、维护多条索引、写 journal、写 oplog、刷页和副本回放放在一张账上；一次业务写入可能远不止一次磁盘写

**文件空间与回收** ---- 区分逻辑删除、可复用空间、文件大小、压缩和重写；删掉数据不一定立刻把磁盘空间还给操作系统

**检查点与恢复时间** ---- 评估数据量、脏页、日志和磁盘吞吐对重启恢复的影响；恢复时间必须通过实际演练而不是想象得出

## 第九站：副本集与高可用

第九站组建 MongoDB 的值班队伍。主节点负责写，副节点保持追随；选举不是“谁声音大谁上”，而是心跳、投票、优先级、网络和数据状态共同决定谁能接班。

**副本集角色** ---- 理解 primary、secondary、arbiter、hidden、delayed 和 priority 0 成员；不同角色解决不同的读扩展、灾备、投票或隔离需求

**心跳与选举** ---- 认识成员探活、选举超时、投票、优先级、step down 和新主选出；应用必须接受主节点变化和短暂不可写窗口

**Oplog 复制链路** ---- 串起主节点写入 oplog、从节点拉取、应用、确认和延迟；复制延迟可能来自网络、磁盘、锁、长操作和副节点负载

**多数与数据保护** ---- 用多数投票和多数写关注理解“可选主节点”和“已确认数据”的关系；节点数量、故障域和部署区域决定多数的实际意义

**初始同步** ---- 了解全量拷贝、索引构建、oplog 追赶和失败重试；大数据集初始同步会占用源节点、网络、磁盘和副本资源

**回滚** ---- 认识主节点切换后未被多数确认的写入可能回滚；业务必须有幂等键、审计和回滚数据处理，而不是只期待数据库替你修业务

**延迟副本** ---- 让特定副本故意落后，用作误删或错误发布的恢复窗口；它不能承担实时读，且落后期间需要监控磁盘与 oplog

**隐藏副本与备份副本** ---- 用 hidden、priority 0 和 tags 隔离报表、备份或灾备流量；副本成员仍会消耗网络、存储和回放资源

**读偏好与标签路由** ---- 让地理就近、专用报表、灾备流量按标签选择节点；读副本扩展不等于读一致性自动升级

**故障切换与应用重连** ---- 设计驱动拓扑发现、重试、连接池清理、写入幂等、超时和告警；切主后旧连接不会自动变成健康连接

**跨区域副本** ---- 评估跨地域延迟、投票配置、写关注、带宽、数据驻留和故障域；把所有投票节点放在同一机房，灾难时会一起下班

## 第十站：分片、路由与水平扩展

第十站进入分布式迷宫。MongoDB 分片能把数据拆到多个 shard，但 mongos、配置服务器、分片键、chunk、balancer 和跨分片查询会同时加入会议；扩展的是容量，增加的也是运维责任。

**分片集群组件** ---- 理解 shard 副本集、mongos、配置服务器副本集、分片元数据和客户端路由；应用通常只看 mongos，但故障边界并没有消失

**分片键选择** ---- 从基数、频率、单调性、查询路由、写热点、租户边界、扩容和生命周期判断分片键；分片键选错后，硬件和中间件只能帮你更快地踩坑

**范围分片** ---- 适合范围查询和局部性，但可能产生热点与不均衡；需要观察 chunk 分布、边界、写入时序和迁移开销

**哈希分片** ---- 让写入更均匀，代价是范围查询被打散、路由和排序更复杂；均匀不等于高效，仍要看访问模式

**复合分片键** ---- 用前导等值、范围、租户或时间组合查询和分布；既要保证路由选择性，也要避免低基数字段制造热点

**Chunk 与迁移** ---- 了解 chunk 分裂、balancer、迁移、临时空间、网络压力和对在线业务的影响；大文档、长事务和 jumbo chunk 会让迁移卡住

**分片查询路由** ---- 区分 targeted query 与 scatter-gather；没有分片键条件的查询可能访问所有 shard，结果归并与延迟随节点数增长

**跨分片聚合与排序** ---- 理解局部聚合、全局归并、分页、排序、lookup 和 facet 的分布式代价；“查询能跑”不代表“查询能稳定跑”

**分片下的唯一性** ---- 认识唯一索引通常需要包含分片键，跨分片全局唯一性需要额外建模；业务唯一约束必须在设计期验证

**分片事务** ---- 了解跨分片事务的协调、网络往返、锁和失败重试成本；优先让事务边界与分片键共置

**在线重分片与扩容** ---- 设计添加 shard、迁移数据、热点观察、容量余量、限速、回滚和验证；扩容不是只改一个数字

**区域与租户分片** ---- 用 zone/标签把租户、地域或合规数据放到指定故障域；隔离规则要与备份、权限和灾备一起验收

## 第十一站：性能、索引与查询诊断

第十一站是性能体检室。MongoDB 会把查询计划写给你看，但它不会替你解释为什么数据量变了以后计划突然换人；要把计划、数据分布和资源曲线放在一起看。

**explain 三种视角** ---- 区分 queryPlanner、executionStats 和 allPlansExecution；关注 winning plan、候选计划、实际文档数、索引键数和返回数

**计划健康信号** ---- 识别 COLLSCAN、FETCH 放大、扫描键远大于返回文档、内存排序、阻塞、散射查询和低选择性索引；别把“用了索引”当作性能证明

**查询与索引对齐** ---- 以高频过滤、稳定排序、范围、投影和数据生命周期设计索引；重复索引、重叠索引和只服务一次的索引都在收租

**深分页与范围分页** ---- skip 越深，数据库通常要跳过越多结果；使用索引上的最后一个键、唯一 tie-breaker 和方向一致的范围条件

**大结果集** ---- 使用 limit、批量游标、投影和流式消费控制网络与客户端内存；一次返回一百万文档不是接口，是搬家公司的紧急订单

**聚合性能** ---- 前置过滤、减少字段、控制 unwind、避免高基数 group、利用可下推索引并评估磁盘溢写；对在线请求设置明确的资源上限

**写入吞吐** ---- 对比单条、批量、有序/无序写入、索引数量、写关注、journal、磁盘和副本延迟；吞吐提升必须以错误与持久性目标不变为前提

**连接与线程** ---- 监控连接池等待、服务端连接数、并发查询、线程、锁和网络；盲目增大连接池会把排队从应用挪到数据库

**Profiler 与慢查询** ---- 使用数据库 profiler、慢查询阈值、currentOp、日志和采样观察现场；生产开启详细诊断要控制采样比例和敏感信息

**serverStatus 与 FTDC** ---- 关注 opcounters、wiredTiger cache、tickets、page faults、connections、network、repl、metrics 和 locks；指标要能对应容量或故障动作

**内存与磁盘** ---- 区分 WiredTiger cache、文件系统缓存、索引工作集、脏页、磁盘延迟和临时文件；内存不足时先找工作集和大索引，不要只加连接

**热点与大文档** ---- 识别热集合、热分片键、热文档、大数组、大索引和单分片流量；通过拆文档、重做分片键、缓存或读模型分散压力

**基准与回归** ---- 用真实基数、数组长度、冷热比例、读写比、复制拓扑和并发压测；记录 p95/p99、吞吐、复制延迟、磁盘和错误率

## 第十二站：备份、恢复与日常运维

第十二站是灾难预演厅。副本集解决可用性，备份解决误操作、逻辑损坏和整个故障域消失；副本里已经同步了错误，所以“有副本”不等于“有后悔药”。

**备份目标** ---- 先定义 RPO、RTO、恢复粒度、保留期、合规地域和可接受停机；备份策略的第一行不是工具名，而是损失上限

**逻辑备份** ---- 理解 mongodump/mongorestore 的适用规模、元数据、索引、并行、版本和一致性边界；逻辑备份便于迁移，但大集群恢复耗时可能很长

**文件系统快照** ---- 评估存储快照的一致性、锁定/协调、加密、跨区域复制和恢复依赖；快照速度快，不代表应用和 oplog 时间线自动完整

**连续时间点恢复** ---- 使用全量备份与 oplog 归档恢复到误删前的时间点；确认归档完整、时钟、顺序、权限和恢复环境可用

**恢复演练** ---- 定期演练整集群、单数据库、单集合、单文档抽取、索引重建、用户权限和应用切换；恢复脚本没人跑过，就只是漂亮的愿望

**校验与数据一致性** ---- 对比文档数、关键业务聚合、抽样哈希、时间窗口和引用关系；恢复成功要有数据正确性证据，不只是进程启动成功

**滚动维护** ---- 规划副本成员重启、索引构建、配置变更、补丁升级和扩容顺序；先从隐藏或低优先级成员开始，观察复制与选举

**版本升级与 FCV** ---- 区分二进制升级与兼容性版本切换，先验证驱动、索引、聚合、备份和回滚；不要把数据库升级当成一个只换镜像的动作

**磁盘与容量** ---- 监控数据文件、索引、journal、oplog、临时空间、快照和备份占用；磁盘水位不仅影响写入，也影响迁移、重建和恢复

**集合维护** ---- 理解 validate、compact、collMod、重建索引和删除历史的风险；需要重写或长时间独占资源的操作必须安排窗口

**故障排查** ---- 按影响范围、最近变更、连接、锁、复制、分片路由、磁盘、慢查询和数据完整性顺序取证；先保护现场，再做修复动作

**变更记录** ---- 记录版本、参数、索引、分片键、备份验证、故障切换和恢复演练结果；没有时间线的事故，只能靠记忆互相指认

## 第十三站：安全、治理与数据边界

第十三站给文档旅行家办护照。灵活的字段让产品迭代很快，也容易让敏感数据、任意查询和租户边界在不知不觉中混进同一间房。

**认证** ---- 了解 SCRAM、X.509、外部认证和认证数据库；认证只回答“你是谁”，不回答“你能看哪些集合”

**授权与 RBAC** ---- 使用内置角色、细粒度权限、自定义角色和最小权限；应用账号、迁移账号、备份账号、只读账号和管理员账号分离

**网络隔离** ---- 配置 bind、私网、TLS、网络策略、防火墙和管理面隔离；不要把数据库端口暴露在公共网络里再寄希望于复杂密码

**传输与静态加密** ---- 评估 TLS、磁盘加密、密钥管理、备份加密和密钥轮换；加密要覆盖在线数据、日志、快照和备份副本

**字段级保护** ---- 识别应用层加密、客户端字段级加密、可查询加密与脱敏的取舍；加密会影响索引、排序、聚合、密钥轮换和排障

**审计与访问记录** ---- 记录身份、来源、集合、操作、失败和敏感访问；审计日志也包含敏感信息，必须限制读取与保留

**查询注入** ---- 防止用户输入变成任意操作符、正则、字段名、排序或 JavaScript 表达式；对过滤结构、返回字段、limit 和超时设白名单

**租户隔离** ---- 比较共享集合、租户字段、独立集合、独立数据库和独立集群的权限、索引、备份与爆炸半径

**数据保留与删除** ---- 设计 TTL、归档、合规删除、备份保留和恢复后再删除；在线删除不等于所有备份副本立刻消失

**扩展与脚本边界** ---- 审查服务器端脚本、模块、外部工具和管理权限；越强的执行能力，越需要更窄的安装和运行边界

**稳定 API 与契约** ---- 对外暴露的查询能力、字段格式和错误语义要稳定；数据库内部字段不应未经治理直接成为公共 API

## 第十四站：高级能力与生产架构

最后一站把 MongoDB 放回整套系统。它可以做文档主库、事件源旁边的读模型、时间序列仓库或搜索入口，但“能做”不等于“应该独自承担所有角色”。

**Change Streams** ---- 监听集合、数据库或集群变更，构建缓存失效、搜索同步、审计和异步投影；处理 resume token、断线重连、重复事件、顺序和权限

**时间序列集合** ---- 理解时间字段、元数据、桶化、压缩、保留期和查询模式；时间序列设计要从采样频率、设备数、标签基数和保留周期倒推

**GridFS** ---- 了解大文件分块、元数据、下载流、删除一致性和备份；它适合需要 MongoDB 访问控制与元数据关联的文件场景，不等于通用对象存储

**搜索与向量能力** ---- 评估 MongoDB 内置或云平台搜索、向量检索、同步延迟、索引资源和权限过滤；重度搜索需求要比较专用搜索引擎的成本与收益

**Outbox 与事件驱动** ---- 在同一文档或事务内记录业务变更与待发送事件，再由消费者投递；消息重复、乱序、重试和幂等仍需应用负责

**缓存协作** ---- 让 MongoDB 做可信来源，缓存承载热点；设计失效、穿透、击穿、预热、回源限流和最终一致性，不要把缓存当第二主库

**读模型与物化结果** ---- 用聚合写入汇总集合、按页面组织文档或按租户拆读模型；读模型需要重建、回放、版本与校验能力

**关系数据库对比** ---- 文档天然嵌套、读模型稳定、迭代快且跨实体事务少时 MongoDB 更顺手；强约束、多表分析、复杂跨实体事务和统一报表可能更适合关系数据库

**从关系库迁移** ---- 先梳理表关系、访问路径、事务边界、唯一约束和报告需求，再决定嵌入、引用、冗余与校验；迁移不是把每一行改成一份 JSON

**从 MongoDB 拆分** ---- 当文档过大、跨实体写入频繁、查询越来越像 JOIN、索引不可控或事务边界不断扩大时，评估关系化、读写分离或专用系统

**故障域与降级** ---- 为主节点不可用、副本延迟、mongos 故障、分片迁移、磁盘不足和缓存失效设计超时、限流、只读、降级与人工开关

**容量与成本** ---- 估算文档增长、索引倍数、复制副本、分片、备份、网络、跨区流量和恢复空间；云上账单通常会奖励那些提前算过的人

**毕业项目** ---- 做一个内容、设备或订单系统，经历文档建模、schema validation、聚合、索引、复制集、故障切换、备份恢复、分片模拟和一次数据模型迁移

## 通关标准

**基础通关** ---- 能解释 BSON、ObjectId、集合、文档、连接池、读偏好和写关注，完成安全 CRUD，并能说清缺失字段、null 与数组的区别

**建模通关** ---- 能根据访问模式决定嵌入或引用，处理一对多、多对多、无限增长、版本演进、软删除、唯一性和文档大小边界

**查询通关** ---- 能写出带稳定排序、范围分页、数组过滤、批量写入和幂等 upsert 的查询，并能限制返回字段、结果集和用户输入

**聚合通关** ---- 能用 match、project、unwind、group、lookup、facet、窗口、图遍历和 merge 组织真实报表，并能解释中间粒度与内存代价

**性能通关** ---- 能阅读 explain，识别 COLLSCAN、低选择性、索引不匹配、深分页、大文档、热点和 scatter-gather，并用基准验证修改

**并发通关** ---- 能解释单文档原子性、多文档事务、读写关注、因果一致性、可重试写入、回滚和幂等；知道什么时候不该上事务

**运维通关** ---- 能搭建复制集，解释选举、oplog、延迟、初始同步和回滚；能制定备份、PITR、升级、监控与恢复演练方案

**架构通关** ---- 能根据数据形状、查询路由、规模、租户、合规、团队和故障目标选择单机、复制集、分片、缓存、搜索或关系数据库，并说明退出路径

## 下一站去哪

MongoDB 学到这里，已经从“会存 JSON”走到了“能设计文档系统并承担生产责任”。接下来可以按方向继续：

**PostgreSQL** ---- 对照学习强约束、复杂 SQL、MVCC、VACUUM、JSONB、空间与向量扩展

**Redis** ---- 学习内存数据结构、缓存一致性、持久化、分布式锁、限流和高并发访问

**搜索系统** ---- 深入倒排索引、相关性、分词、向量检索与搜索数据同步

**消息与流处理** ---- 继续研究 Change Streams、Outbox、重复消费、重试、顺序和最终一致性

## 结语

MongoDB 最值得学习的不是“没有表结构”，而是它迫使你从访问模式、文档生命周期和故障边界出发设计数据。嵌入让一次读取更自然，引用让无限增长更可控；灵活 schema 让迭代更快，也把治理、校验和迁移责任交给了团队。

先把文档形状和索引做对，再理解 WiredTiger、oplog、复制集和分片；先练会 explain、备份恢复与幂等，再谈跨分片事务和高并发。等你能解释一次慢查询为什么从索引走到了全库扫描，也能把误删恢复到目标时间点——你学到的就不只是 MongoDB，而是面向访问模式设计可靠数据系统的方法。
