# Codex MCP 兼容集成学习路线

这一页讲的是兼容集成，而不是重新发明一套“Codex 专属 MCP”。如果现有系统仍依赖旧的 MCP Server 入口，应把它看成迁移与兼容边界：先确认现有客户端为什么需要它，再评估 Codex SDK、App Server 与通用 MCP 客户端的组合。

前置建议先看 [MCP 协议](/learning-paths/ai/claude-mcp) 的 Host、Client、Server、Tools、Resources 和传输模型，再看 [Codex SDK / App Server](/learning-paths/ai/codex-platform) 的任务与工作区边界。本页不把历史命令当成长期 API，具体入口以当前官方文档为准。

这条线按 **兼容层定位 → 现状盘点 → 权限迁移 → 协议与事件 → 错误恢复 → 验证与发布 → 何时移除** 推进。

## 第一站：先分清兼容层解决什么

欢迎来到兼容层的旧火车站。这里的老线路还能把客户端送到 Server，但站牌、闸机和广播可能已经是上一代的；第一关不是让火车开起来，而是确认它为什么还值得开。

**兼容入口** ---- 解决旧客户端、旧启动方式或旧协议之间的连接问题；它不是新项目默认的架构，也不自动获得更高权限

**通用 MCP** ---- 负责工具和资源的发现、描述、调用与传输；宿主、Agent 和服务端仍各自承担会话、模型、权限和执行职责

**Codex 平台** ---- 更关注编码 Agent 的任务、工作区、文件修改、命令执行、审批与验证；MCP 可以提供工具，但不是 Codex 运行时的全部

**迁移目标** ---- 目标应是能力、权限、事件和审计可解释，而不是“旧客户端还能连上”；能连上一个过宽权限的 Server，属于负分通关

**重点在这** ---- 将兼容层作为有边界、可观察、可回滚的过渡组件，而不是永远没人负责的地下管线

## 第二站：盘点现有集成

第二站是资产盘点室。桌上摊着客户端、Server、启动命令、凭证和权限清单；很多“协议不兼容”最后会露出真相：只是某个工作目录和环境变量在偷偷串门。

**客户端清单** ---- 记录每个 MCP Client、宿主应用、版本、用户范围和调用场景；同名客户端可能拥有完全不同的审批与文件能力

**Server 清单** ---- 盘点 Server、工具、资源、启动方式、传输、环境变量、凭证、工作目录和外部依赖

**工具与资源清单** ---- 区分可写工具、只读工具、敏感资源、动态资源和废弃能力；按实际调用频率和业务价值排序

**权限清单** ---- 明确文件目录、命令、网络、数据库、第三方 API、租户和用户范围；把隐含在宿主进程里的权限单独写出来

**运行证据** ---- 保存调用轨迹、错误、耗时、重试、审批和最终结果；没有现状基线，就无法证明迁移后变好

**重点在这** ---- 盘点的产出是一张“客户端—Server—工具—权限—审计”关系图，而不是一份启动命令收藏夹

## 第三站：迁移工具、权限与配置

第三站是闸机改造现场。旧入口最容易把“能连上”误装成“什么都能做”，现在要把工作区、命令、资源和审批一项项写成明文规则。

**工作目录** ---- 为每个任务指定最小工作区；防止通过相对路径、符号链接或路径穿越访问不相关项目

**命令策略** ---- 把允许命令、参数、网络和资源额度写成白名单或明确的审批规则；“终端工具”不是一张无限期通行证

**工具命名** ---- 只读、写入、删除和执行工具在名称、描述与 UI 上清楚分级；高风险工具要求确认并记录批准者

**资源权限** ---- 文档、数据库记录、代码仓库和密钥按用户、租户、项目与环境隔离；Server 返回资源前再次检查权限

**配置迁移** ---- 将启动参数、环境变量、端点、认证和超时显式版本化；敏感值进入密钥管理，不写进仓库或普通日志

**回滚策略** ---- 迁移期间保留旧入口的隔离副本与关闭开关；回滚也必须遵守新的权限边界，不能把旧漏洞原样请回来

**重点在这** ---- MCP 的连接成功只说明协议握手成功，不说明工具调用安全

## 第四站：协议、事件与错误路径

第四站是故障演习场。正常返回只是晴天彩排，真正的演出在断连、版本变化、工具消失和 Agent 取消时；兼容层要学会报站，而不是突然关灯。

**能力协商** ---- 理解 Server 声明工具、资源、提示与其他能力的过程；Client 要能处理能力缺失和版本不匹配

**调用关联** ---- 为任务、会话、工具调用和审批保留关联 ID；并行调用时尤其不能依赖时间顺序猜结果归属

**传输与断连** ---- 区分本地进程传输与远程 HTTP 传输的生命周期、认证、超时和重连行为；断连后要明确任务继续、暂停还是取消

**工具不存在** ---- Client 发现工具名变化、Server 未启动或能力未声明时，应返回可诊断错误并走降级，不要无限重试

**协议错误** ---- 区分 JSON-RPC 或传输错误、schema 错误、工具业务错误、权限拒绝和模型决策错误；每类错误的责任方不同

**取消与幂等** ---- 取消工具调用时查询副作用状态；写操作使用幂等键，避免重连或重试造成重复提交

**重点在这** ---- 事件和错误是兼容层的主要产品；只测试“算出 3×3”证明不了集成能跑长任务

## 第五站：验证、观测与发布

第五站是验收大厅。旧入口和新集成要用同一组任务比一场：功能、权限、事件和恢复都得过关；“以前好像能用”不是测试报告，是候车室传闻。

**功能回归** ---- 覆盖工具发现、参数校验、资源读取、写操作审批、错误回填、并行调用与最终结果

**权限回归** ---- 以不同用户、租户、目录、环境和审批状态测试；确保不应访问的资源在 Client、Server 与宿主各层都被拒绝

**编码 Agent 回归** ---- 使用只读搜索、受控修改、测试运行和差异报告任务，比较修改范围、测试结果、工具轨迹与恢复行为

**运行观测** ---- 记录连接成功率、工具耗时、错误类别、重试、审批等待、资源访问、任务成本与断连恢复

**安全审计** ---- 审查 Server 依赖、凭证、日志、网络、文件和命令权限；将第三方 Server 当作可执行供应链组件管理

**灰度发布** ---- 先让低风险、只读任务使用新路径，再逐步开放写操作；保留开关、版本与回滚证据

**重点在这** ---- 兼容迁移的验收标准是“功能相当或更好、权限更清楚、失败更可恢复、审计更完整”

## 第六站：何时保留，何时移除

第六站是退役办公室。兼容层可以暂住，但不能永久占着生产房间不交房租；要给它设保留条件、迁移指标和明确的下线日期。

**可以暂留** ---- 旧客户端无法短期升级、业务仍依赖旧入口，且 Server 能被隔离、限权、审计和回滚

**应当替换** ---- 新平台已支持更清晰的 SDK/App Server 边界，旧入口隐藏权限、事件不足、版本停滞或难以修复安全问题

**应当移除** ---- 没有真实调用、只有历史配置、无法确认凭证归属，或兼容层权限无法收紧；删除前先确认没有隐形消费者

**退出清单** ---- 通知消费者、迁移配置、停止新接入、观察调用下降、撤销凭证、下线 Server、保留审计与恢复文档

**重点在这** ---- 迁移的终点不是“旧命令换成新命令”，而是系统已经不再依赖不可解释的隐式权限

## 通关标准

能画出现有 Host、Client、Server、工具、资源和权限边界；能把兼容入口迁移到受控的 MCP 或 Codex 平台集成；能处理版本变化、断连、工具缺失、取消、重复提交和审批；能用固定任务与审计记录证明迁移后的能力和风险。

## 结语

兼容层的使命不是证明老入口永远正确，而是让系统有一条安全的过桥路线。盘点、限权、回归、灰度和下线都做完，它才算完成任务；否则只是把旧问题贴了一张新标签。

迁移时记住一句话：能连接是起点，能解释、能审计、能回滚才是终点。旧火车可以退休，线路图和事故记录要留下。
