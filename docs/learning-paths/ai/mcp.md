# MCP（模型上下文协议）学习路线

MCP（Model Context Protocol）是一套连接 AI 应用、工具和数据源的开放协议。它解决的是“能力如何被发现、描述、连接和调用”，不是“模型如何变聪明”，也不是“权限如何自动正确”。可以把它想成 AI 的 USB-C：接口统一了，插上什么设备仍然要看设备本身、供电和使用权限。

前置建议先掌握 [模型 API 通用原理](/learning-paths/ai/model-api-overview) 的工具调用边界，再看 [Agent 基础](/learning-paths/ai/agent-basics) 与 [Agent 开发](/learning-paths/ai/agent-development) 的循环、权限和观测。本页关注协议心智、Server 设计、客户端接入与生产治理。传输、鉴权和 SDK 细节以当前官方规范与实现文档为准。

这条线按 **架构 → Tools/Resources/Prompts → 连接与能力协商 → Server 设计 → Client 与 Agent 接入 → 安全 → 调试与测试 → 发布治理** 推进。

## 第一站：Host、Client 与 Server

欢迎来到 MCP 的码头。Host 是港口，Client 是调度员，Server 是一艘艘装着工具和资料的船；先分清谁负责靠岸、谁负责卸货、谁负责批准，后面才不会让一条船自己决定海关规则。

**Host** ---- 运行 AI 会话、用户界面和整体权限策略的宿主应用；它可以是桌面应用、IDE、编码 Agent 或自研服务

**Client** ---- Host 内部负责连接某个 Server、协商能力、转发调用和处理结果的组件；一个 Host 可以管理多个 Client 连接

**Server** ---- 对外暴露工具、资源或提示模板的能力提供方；Server 不应因为被 AI 调用就获得比宿主明确授予更多的权限

**模型与 MCP 的关系** ---- 模型通常看到由 Client 整理后的工具或资源信息，模型提出调用意图，Client/Host 决定是否执行；MCP 不替代模型 API 的函数调用机制

**本地与远程连接** ---- 本地 Server 常由宿主启动并通过进程通信连接，远程 Server 则需要网络、鉴权、超时、重连和租户隔离；两者的信任边界不同

**重点在这** ---- MCP 是能力连接层；模型、执行策略、用户身份、审批、审计和业务状态仍然属于宿主或应用

## 第二站：三类原语

第二站是三扇门：Tools 让模型动手，Resources 让模型读资料，Prompts 让团队复用工作话术。门牌挂错，模型就会拿“读表结构”的钥匙去开“删数据”的门。

**Tools** ---- 可执行的动作，通常带参数并可能产生副作用；查询、计算、写文件、发消息和执行任务都属于这一类

**Resources** ---- 可按 URI 或其他标识读取的只读数据；文件、文档、表结构、配置或报告适合用资源表达，便于发现、引用和按需读取

**Prompts** ---- 可复用的提示模板或工作流入口；适合把团队的代码审查、排障和报告格式固化，而不是把业务权限藏在模板里

**工具与资源的分界** ---- “读表结构”更像资源，“执行查询”更像工具；动作是否有副作用、数据是否需要按需读取，是判断的关键

**结果与来源** ---- 工具结果要包含足够的状态、来源和错误信息；资源要保留 URI、版本、权限和新鲜度

**重点在这** ---- 原语是产品语义，不是三个不同颜色的按钮；先确定谁负责什么，再决定如何暴露

## 第三站：连接、握手与能力协商

第三站是握手大厅。Client 和 Server 要先报姓名、版本和会什么，再决定能不能合作；只会复制配置而不懂能力协商，就像拿着旧地图去找新码头。

**初始化** ---- Client 与 Server 建立连接后交换协议版本与能力；双方应处理版本不匹配、能力缺失和未知字段

**能力声明** ---- Server 表明支持哪些工具、资源、提示或通知，Client 据此决定如何展示和调用；声明不等于调用授权

**工具发现** ---- Client 获取工具名称、描述、输入 schema 和必要元数据；发现后应缓存或刷新，但不能绕过服务端每次执行的授权

**资源发现** ---- 了解资源列表、URI、模板、订阅或变更通知等概念；资源很多时需要分页、过滤、权限与新鲜度策略

**传输生命周期** ---- 处理启动、就绪、请求、响应、通知、错误、关闭和重连；长任务不能只靠一个同步响应承载

**配置管理** ---- Server 的启动命令、环境变量、端点、凭证、工作目录和超时都应版本化；配置文件不是安全审计的替代品

**重点在这** ---- “能发现工具”只证明目录可见；“能安全执行”还要经过身份、范围、参数和业务状态检查

## 第四站：Server 设计与工具契约

第四站进入工具铸造厂。每个工具都要有说明书、参数表和保险丝；代码写得再多，如果模型不知道何时使用，人类不知道会造成什么后果，仍然只是一个很忙的黑箱。

**内聚边界** ---- 一个 Server 围绕清晰领域组织工具与资源；文件、数据库、工单和发布能力不必为了“少配置一项”塞进同一个万能 Server

**工具描述** ---- 写清何时使用、何时不要使用、输入含义、输出形状、错误和限制；描述既是模型路由信号，也是文档与安全评审入口

**输入 schema** ---- 用类型、必填项、枚举、范围、格式和默认值约束参数；schema 之后仍要做身份、业务和资源级校验

**返回契约** ---- 区分给模型看的摘要、给用户看的产物、给系统保存的元数据和给审计记录的证据；一份返回值不一定适合所有消费者

**错误设计** ---- 返回模型可理解的错误码、原因、是否可重试和建议动作；内部堆栈进入日志，不要把服务器内部地图递给模型

**幂等与超时** ---- 写操作需要幂等键、重复检测和补偿；外部 API、数据库和命令执行都要有超时与资源限制

**重点在这** ---- Server 的质量不在“暴露了多少工具”，而在“工具能否被正确选择、可靠执行、清楚失败”

## 第五站：Client 与 Agent 接入

第五站是工具分发中心。Server 有什么不等于模型都该看到什么；Client 要按任务、用户和风险筛选能力，不能把整座工具仓库倒进模型的背包。

**工具筛选** ---- 按任务、用户、项目、风险和租户只暴露必要工具；工具越多，模型路由越难，提示词和评估成本也越高

**调用回路** ---- 模型提出调用意图，Client 聚合参数并做初步校验，Host/服务端执行，再将结果按关联 ID 回填；最终答案仍需要业务验收

**工具错误** ---- 区分 Server 不可用、schema 错误、权限拒绝、业务不存在、限流和暂时性网络失败；错误类别决定重试与降级

**并行调用** ---- 独立查询可并行，写操作和有依赖的动作要串行；并行结果保留调用 ID、来源和失败状态，不能按返回先后猜顺序

**动态能力** ---- 工具或资源可能随会话、权限和版本变化；刷新能力时要处理删除、重命名和兼容期，不能让模型继续调用幽灵工具

**框架集成** ---- LangChain、LlamaIndex 和自研 Agent 都可以把 MCP 能力包装成工具或资源；框架帮你接线，不替你做权限与审计

**重点在这** ---- Client 是连接器和策略执行点；“模型能看到”与“模型能调用”应当是两个经过控制的状态

## 第六站：安全、权限与供应链

第六站是安全海关。MCP Server 可能摸到文件、数据库、网络和业务 API，一张配置单写宽了，影响就不是“回答有点跑偏”，而是整艘船开进了不该去的港口。

**最小权限** ---- 为每个 Server、工具、用户、租户、目录、数据库和网络设置最小范围；只读优先，写入按风险逐项开放

**路径与查询安全** ---- 文件工具限制根目录并防止路径穿越；数据库使用只读账号、表白名单、行数限制、查询超时和结果脱敏

**审批与人工确认** ---- 删除、发送、付款、发布、执行命令和修改生产资源等动作要求明确确认；审批记录要包含动作、参数、范围和批准者

**提示词注入** ---- 用户内容、网页、文档和工具结果都可能夹带伪指令；外部内容作为数据处理，不能因为来自“可信 Server”就自动升级

**远程鉴权** ---- 远程连接需要身份、凭证、加密传输、过期、轮换、租户和重放保护；连接成功不能替代每次工具调用的授权

**供应链** ---- 审查 Server 作者、源码、依赖、更新、发布来源和权限；第三方 Server 拥有什么权限，实际上就拥有什么风险

**审计与数据保留** ---- 记录连接、工具、参数摘要、资源范围、结果状态、审批和错误；敏感内容按保留期限脱敏或删除

**重点在这** ---- MCP 安全的三根支柱是最小权限、人工确认和完整审计；协议本身不是护身符

## 第七站：调试、测试与发布

第七站来到质检码头。一次成功调用只是船顺利靠岸，不代表风浪、断线、越权和重复装卸都能处理；协议、业务和宿主策略要一起演练。

**Inspector 与协议调试** ---- 使用官方或社区 Inspector 类工具查看能力、请求、响应、通知和错误；将最小复现保存为可重复测试

**Server 单元测试** ---- 单独测试 schema、参数校验、权限、超时、幂等、错误码、脱敏和返回结构；不依赖模型也能证明基础安全

**Client 集成测试** ---- 测试发现、能力刷新、工具筛选、并行调用、结果回填、断连、重连、取消和版本不匹配

**Agent 轨迹测试** ---- 固定任务集比较工具选择、参数、步骤、停止、越权拒绝和最终答案；不要只测试“工具返回 200”

**故障注入** ---- 模拟 Server 未启动、网络超时、空结果、坏 schema、权限拒绝、重复请求和部分失败；每种故障都有明确用户体验

**发布策略** ---- Server 版本、工具 schema、权限、依赖和配置一起发布；先只读灰度，再逐步开放写操作，保留回滚与撤销凭证

**重点在这** ---- 调试工具证明“协议能通”，回归与审计证明“系统能用且可控”，两者缺一不可

## 第八站：生态与治理

先使用可信的现成 Server 做连接、权限和审计练习，再自研一个小而内聚的 Server。推荐项目：只读代码仓库或文档 Server，支持搜索、读取、来源引用和明确的访问范围。

**生态选型** ---- 按来源可信度、权限范围、维护状态、依赖、数据流向和可观测性选 Server；“一键安装”不等于“一键合规”

**组织治理** ---- 建立 Server 清单、负责人、版本、权限、数据分类、升级窗口、审计保留和下线流程；工具生态越大，目录治理越重要

**交付证据** ---- 能解释 Host、Client、Server 和三类原语；能实现或配置一个受控 Server；能完成发现、调用、错误、取消与重连；能为文件、数据库和写操作设计权限、审批、审计与回滚

## 通关标准

能解释 Host、Client、Server 与 Tools、Resources、Prompts 三类原语；能实现或配置一个受控 Server；能处理发现、能力协商、调用、错误、取消、重连与版本变化；能为文件、数据库和写操作设计权限、审批、审计和回滚。

## 结语

MCP 让工具连接像 USB-C 一样方便，但方便只解决了“插得上”，没有替你回答“谁能插、能读什么、能写什么、出了问题谁负责”。协议是桥，权限和审计才是桥上的护栏。

先做一个只读、内聚、可观测的 Server，再逐步开放写操作。等你能解释每次调用的来源、范围、结果和失败，MCP 才真正从配置技巧变成工程能力。
