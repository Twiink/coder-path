# 模型 API 通用原理学习路线

模型平台的名字会换，SDK 的方法名会换，但应用层反复遇到的问题很稳定：输入怎么组织、输出怎么验证、工具怎么执行、失败怎么恢复、成本怎么解释。本页把这些问题整理成一层供应商无关的心智模型，学完再去看 OpenAI、Claude、Gemini 或本地推理页，会少很多“这个参数到底是谁家的”式迷路。

这是一页路线图，不是某个 SDK 的 API 手册。目标是设计一层可替换的模型适配边界，让业务依赖能力契约，而不是依赖供应商响应对象。

这条线按 **请求与消息 → 内容与上下文 → 流式与结构化 → 工具与事件 → 可靠性与成本 → 适配层与评估 → 平台分支** 推进。

## 第一站：请求与消息模型

欢迎来到模型 API 的装配车间。这里有消息、内容块、工具和响应四类零件，供应商会不断换包装；先学会认螺丝和扳手，才不会换一家 SDK 就把整间屋子拆了重装。

**系统指令** ---- 放置稳定的角色、规则、边界、工具说明与输出约束；动态的用户数据不要误塞进长期规则，权限信息也不应只写在提示词里

**用户与助手消息** ---- 多轮对话通常由应用维护历史并按顺序回传；要区分用户原文、模型历史回答、工具结果和系统级消息，避免不同信任级别混成一锅

**内容块** ---- 文本、图片、文件、工具调用、工具结果和平台扩展字段都可能成为一次消息的一部分；适配层应保留语义，不要为了统一而把多模态内容压扁成字符串

**请求上下文** ---- 模型、指令、历史、检索材料、工具定义、用户权限和响应格式共同消耗输入预算；上下文越长不代表答案越好，相关性与排列顺序同样重要

**能力矩阵** ---- 为每个后端记录是否支持视觉、流式、结构化输出、工具调用、批处理、缓存、长上下文和取消；“请求能发出去”不等于“能力真的兼容”

**请求标识** ---- 为用户请求、模型调用、Agent 运行和工具调用分别保留可关联的 ID；没有关联 ID，出了问题就只能靠时间戳猜谜

**重点在这** ---- 先定义内部消息与响应契约，再写平台适配器；供应商的原始字段保留在边界内，业务只消费经过归一化的字段

## 第二站：上下文与 Token 预算

第二站是上下文仓库。模型的工作台不是无限大的，历史、工具说明和资料都来抢位置；把整间仓库塞进去看似勤快，实际是在让模型玩“找出最重要那张便签”。

**上下文窗口** ---- 关注输入与输出的总限制、工具定义占用、历史增长和平台差异；窗口再大也需要任务级预算，否则长对话会慢慢吞掉延迟和费用

**历史管理** ---- 短对话可以完整保留，长对话需要滑动窗口、摘要、关键信息提取或外部存储；摘要必须可验证，不能把关键约束总结成“用户大概想要点什么”

**内容排序** ---- 将高优先级指令、问题、证据、工具结果和补充材料分层组织；检索内容、网页内容和用户内容属于不可信数据，不能通过排版偷偷升级成系统规则

**Token 记账** ---- 分开记录输入、输出、缓存命中、工具结果和 Embedding 用量；平均成本会掩盖少数失控任务，最好同时看 P50、P95 与单任务上限

**裁剪与压缩** ---- 先删除重复内容和无关工具，再做摘要或上下文压缩；压缩后保留来源、时间、权限和不确定性，短并不等于完整

**缓存前缀** ---- 稳定的系统提示、工具定义、长文档或示例可按平台能力使用缓存；缓存要考虑 TTL、数据新鲜度、租户隔离和失效策略

**重点在这** ---- 上下文工程的目标是让模型在正确时间看到最少但足够的信息，而不是追求“把窗口填满”

## 第三站：流式与结构化输出

第三站是双轨质检线。前端想先看到字，业务系统想等一份完整、可验证的货单；两条轨道要分开，否则用户刚看到“成功”，数据库还在等半截 JSON 拼完。

**增量事件** ---- 流式响应可能包含文本片段、工具调用片段、状态变化、警告、完成原因和用量；适配层应归一化事件类型，同时保留供应商原始事件供排障

**最终结果** ---- 只有收到明确完成状态并通过校验，才把响应标记为业务成功；连接中断时展示过的半截文字不能自动变成已落库的答案

**结构化契约** ---- 用 JSON Schema、平台原生结构化能力或工具参数表达字段、类型、枚举和必填关系；schema 是接口契约，不是事实正确性的证明

**解析与校验** ---- 解析器负责语法，程序负责类型、范围、权限、业务不变量和事实核验；失败时记录 schema 版本、模型版本和响应摘要，便于回归定位

**部分结果** ---- 流式 JSON、表格和列表可能长期处于未闭合状态；界面可以展示草稿，写库、发消息或触发下一步必须等待最终验证

**取消与恢复** ---- 用户取消、客户端断连、服务超时和后端主动终止都要有明确状态；如果之前已经触发副作用，需要查询执行状态或走补偿流程

**重点在这** ---- “看得到”与“已完成”是两个状态；前端体验、业务提交和审计记录不应共享一个模糊的成功标记

## 第四站：工具调用与 MCP 边界

第四站是工具闸机。模型可以提出“我要查库、发信、改文件”，但闸机只认身份、范围和审批，不认自信语气；执行、鉴权、超时和审计都要由服务端看守。

**工具定义** ---- 包含名称、用途、参数 schema、返回形状、限制和失败方式；描述是模型的路由信号，也是人类评审权限边界的入口

**调用意图** ---- 模型返回工具名称、参数和关联 ID；适配层要处理参数缺失、额外字段、重复调用、并行调用与模型选择不存在工具等异常

**执行边界** ---- 服务端重新校验参数、用户身份、租户、资源范围和业务状态；工具输出再回填模型前也要做长度限制、脱敏和不可信内容标记

**副作用分级** ---- 查询、计算和草稿生成通常风险较低；写数据库、发消息、删文件、付款、执行命令和发布代码需要幂等、确认、审计或人工接管

**循环控制** ---- 为一次任务设置最大步数、总预算、单工具超时、重复调用检测和整体 deadline；模型说“任务完成”只能作为候选状态，不能单独作为证明

**MCP 的位置** ---- MCP 统一工具与资源的发现、描述和传输；它可以成为适配层上的连接方式，但不替代业务权限、审批、沙箱、审计和数据隔离

**重点在这** ---- 把“模型想做什么”和“系统允许做什么”分成两道门；第一道由模型提出，第二道由程序决定

## 第五站：可靠性、错误与成本

第五站来到故障维修间。模型调用是会堵车的网络服务，不是永不抛错的本地函数；把限流、参数错、业务拒绝和用户取消混成“再试一次”，很快就会修出一张巨额账单。

**错误分类** ---- 区分参数错误、认证失败、限流、服务过载、网络中断、超时、解析失败、内容安全拒绝和业务工具错误；不同类别对应不同提示、重试与降级路径

**重试与退避** ---- 只重试有机会恢复的错误，使用指数退避、抖动、上限和请求关联 ID；写操作要用幂等键或明确禁止自动重试

**超时与 deadline** ---- 连接超时、读取超时、工具超时和整个任务 deadline 分层设置；单个工具无限等待会把线程、连接和用户耐心一起锁死

**降级路径** ---- 可切换轻量模型、只读模式、固定模板、缓存结果、人工接管或明确拒答；降级要告诉用户当前能力边界，不能悄悄返回看似正常的低质量结果

**模型路由** ---- 把分类、抽取、改写、复杂推理和高风险任务分配给不同模型；路由规则要可解释、可回归，不能只靠一个模型判断“该用哪个模型”

**并发与队列** ---- 实时短请求适合同步或流式，长任务进入队列并提供状态查询；并发上限同时受模型配额、数据库连接、工具吞吐和内存约束

**成本预算** ---- 按租户、用户、任务、模型和步骤统计 token 与工具成本；设置单次、每日和月度预算，预算耗尽要暂停或降级

**重点在这** ---- 可靠性不是“模型永远成功”，而是失败时系统仍然可解释、可恢复、可审计

## 第六站：适配层、评估与发布

第六站是兼容性考场。“两个平台都能回答”只是签到，真正的考试还要比质量、延迟、成本、工具轨迹和失败方式；否则只是把供应商名字换了，脾气一点没测。

**内部接口** ---- 统一调用入口、消息类型、响应状态、事件、工具意图、用量与错误；平台专属能力以扩展字段或显式能力声明暴露，不要假装所有后端完全一样

**配置与密钥** ---- 模型路由、温度、输出上限、超时、重试和端点通过配置管理；密钥只在服务端，日志和追踪中不得泄露密钥或敏感输入

**回归数据集** ---- 覆盖正常请求、边界输入、长上下文、结构化失败、工具失败、拒答、安全注入和多语言场景；固定样例才让平台切换可比较

**质量指标** ---- 按任务选择正确率、字段准确率、答案相关性、忠实度、引用正确性、工具选择率和人工通过率；不要只看一个综合分数

**运行指标** ---- 记录首 Token 延迟、完整响应延迟、P95、错误率、重试次数、缓存命中、token 与单任务成本；质量下降时才能判断是模型、提示词还是下游变慢

**灰度与回滚** ---- 新模型、适配器或提示词先按小流量发布，对比固定任务与线上样本，再逐步放量；保留旧版本和配置，避免升级变成单向旅行

**重点在这** ---- 供应商可替换不代表答案完全一致；适配层的价值是控制变化范围、提供比较证据，而不是抹平真实差异

## 通关标准

能用一套内部契约接入两个模型后端；支持多轮消息、流式文本、结构化结果和工具调用；能归一化错误与用量；能处理取消、超时、限流、schema 失败和工具失败；能用固定任务集解释一次平台切换对质量、延迟和成本的影响。

## 结语

模型 API 的表面是一个请求，底下却连着消息、上下文、事件、工具、错误、预算和权限。掌握通用原理，就不会因为某家平台把按钮挪了位置，便宣布自己的 AI 生涯也跟着迁移失败。

先做一层薄而清楚的适配，再去拥抱平台特色。能解释一次请求发生了什么、失败了什么、花了多少钱、下一步如何恢复，才算真正掌握模型 API。
