# OpenAI / Responses API 学习路线

本页把 OpenAI 的 Responses API 当作“模型平台适配”的一个实现来学习。重点不是背某个 SDK 方法名，而是理解一次响应如何承载文本、结构化结果、工具调用、文件或其他内容，以及这些事件如何进入你的应用状态机。

前置建议先看 [模型 API 通用原理](/learning-paths/ai/model-api-overview)。通用概念已经在那里讲过，本页专门整理 OpenAI 平台上值得核对的能力边界、学习顺序和工程习惯。平台参数会更新，具体模型与限制以官方文档和你的回归集为准。

这条线按 **Responses 心智模型 → 输入与输出 → 流式事件 → 结构化输出 → 工具调用 → 会话与状态 → 生产封装 → 评估与迁移** 推进。

## 第一站：Responses 的位置与心智模型

欢迎来到 Responses 的中央车站。这里进出的不是一条孤零零的字符串，而是消息、内容块、工具请求和状态事件组成的整列火车；先学会看站牌，才不会把“需要工具”误当成“任务完成”。

**统一响应入口** ---- 将文本、结构化结果、工具请求和元数据放在同一次运行的统一容器里；业务代码应消费内部事件，不要把平台响应对象一路传到前端

**输入与输出的关系** ---- 输入包含指令、用户内容、历史、工具和附加材料，输出可能需要继续驱动工具或生成最终消息；一次 API 请求不一定等于一次完整业务任务

**模型能力差异** ---- 不同模型对长上下文、视觉、工具、结构化输出、推理与成本的支持不同；先建立能力矩阵，再决定默认模型与降级模型

**服务端边界** ---- API Key、工具执行、文件权限、用户身份和业务数据都留在服务端；浏览器只拿到经过筛选的结果和必要的流式事件

**重点在这** ---- Responses API 是一次运行的承载层，不是完整 Agent；任务状态、权限和业务完成条件仍由你的应用负责

## 第二站：输入、消息与内容

第二站是行李安检口。文本、图片、文件、历史和工具结果都能上车，但来源不同、可信度不同；不贴标签的行李，迟早会混进系统规则的车厢。

**指令层级** ---- 分清系统级规则、开发者约束、用户请求和外部资料；用户与文档可以提供任务材料，但不能覆盖权限、审计和安全规则

**多模态内容** ---- 了解文本、图片、文件和结构化内容的组合方式；先做格式、大小、清晰度、脱敏和可读性检查，再交给模型判断

**文件与检索材料** ---- 大文件可以通过平台能力或应用侧 RAG 进入流程；要记录文件版本、来源、权限和过期时间，不能把“模型读过”当作“用户有权读”

**历史与状态** ---- 多轮对话需要明确保存哪些消息、摘要哪些内容、何时过期；会话标识应与用户和租户绑定，不能只拿一个全局线程 ID 解决所有问题

**输出文本** ---- 文本适合聊天、解释和草稿，但不适合直接驱动数据库或工作流；后续动作应依赖结构化结果与程序校验

**重点在这** ---- 先画输入的信任分层，再决定提示词怎么写；内容来自哪里，往往和内容写了什么同样重要

## 第三站：流式事件与运行生命周期

第三站是事件调度室。流式输出像列车逐节进站，文本、工具、审批和完成状态各有时刻表；少处理一个事件，前端就可能欢呼“到了”，后台却还在半路。

**增量文本事件** ---- 用于即时渲染和用户体验；前端显示的内容应与服务端最终保存的完整结果分离

**工具事件** ---- 工具调用可能分多段到达，应用要按调用 ID 聚合名称与参数，完成后再执行；不能把未完成的参数当成真实请求

**运行状态** ---- 区分开始、进行中、需要工具、需要确认、完成、失败、取消和超时；状态机比一个布尔值“is_done”更能解释长任务

**取消与断连** ---- 用户关闭页面不代表服务端副作用自动撤销；取消前后都要查询工具执行状态，并为不可撤销动作设计补偿或人工确认

**用量与审计** ---- 最终事件或响应元数据中记录模型、输入输出 token、请求 ID、完成原因和错误；流式连接中断时也要保存已知部分

**重点在这** ---- UI 的“正在输入”、模型的“还在运行”和业务的“已经完成”是三个不同状态，别让它们共用一个 loading 图标解决人生大事

## 第四站：结构化输出

第四站是票务窗口。自由文本像广播稿，结构化输出才是能被闸机读取的车票；目标是可校验、可追踪，不是拜托模型在末尾画几对花括号。

**Schema 设计** ---- 先定义字段职责、类型、枚举、必填关系、不确定状态和拒答状态；允许模型表达“不知道”通常比逼它填一个猜测更安全

**原生结构化能力** ---- 平台支持 schema 约束时优先使用，并记录模型能力与限制；不同模型对复杂嵌套、数组和边界枚举的支持可能不同

**解析与服务端校验** ---- 语法解析通过后，继续检查权限、范围、业务不变量、引用和事实；模型产出的 JSON 仍是外部输入，不是可信数据库记录

**失败恢复** ---- 解析失败时可重试、缩小 schema、补充约束或转人工；不要无限修复，也不要把修复后的结果绕过审计直接提交

**结构化与流式** ---- 界面可以展示部分字段，业务触发要等待完整对象；对象需要版本号，便于 schema 演进和历史数据迁移

**重点在这** ---- schema 解决“长什么样”，程序校验解决“能不能用”，业务规则解决“做了是否合理”

## 第五站：工具调用与 Agent 循环

第五站来到工具调度台。模型可以提出“请查一下订单”，但真正去查谁、能不能查、查完是否发信，要由服务端调度；它递来的只是申请单，不是站长印章。

**工具定义** ---- 名称、描述和参数 schema 要具体，写明何时用、何时不用、返回什么和有哪些限制；工具描述同时服务模型路由与人类评审

**执行与回填** ---- 服务端按调用 ID 执行工具，重新做鉴权和参数校验，把结构化结果或可读错误回填；不要将内部堆栈、密钥或无关数据原样暴露给模型

**只读与写操作** ---- 查询、计算和草稿工具可先自动执行；发信、下单、删除、改库、执行命令和发布代码必须有权限、幂等、确认或人工审批

**循环上限** ---- 设置最大工具步数、总 token 预算、单步超时、重复调用检测与整体 deadline；最终答案必须满足业务验收条件，不能只看模型是否停止调用

**工具错误** ---- 将可恢复网络错误、参数错误、权限拒绝和业务不存在区分回填；模型可以换策略，但不能通过重试绕过权限

**MCP 连接** ---- MCP 可以把外部工具和资源接入 Agent，但具体执行与授权仍在应用侧；协议解决连接问题，不自动解决安全问题

**重点在这** ---- 先做一个两工具的可回放循环，再扩展多 Agent；工具数量越多，路由、权限和评估矩阵越容易失控

## 第六站：会话、状态与长任务

第六站是行李寄存处。短对话可以下车即忘，真实任务却要保存进度、工具结果、用户确认和产物；平台会话和业务状态不是同一个行李牌，别拿错了。

**对话历史** ---- 明确由平台保存、由应用保存还是两者协作；要能裁剪、摘要、删除和按租户隔离，避免历史无限膨胀

**任务状态** ---- 把计划、已完成步骤、待确认动作、失败原因和产物位置保存为结构化状态；不要只把状态藏在一段自然语言摘要里

**长任务** ---- 分钟级任务应进入队列或后台 worker，前端通过状态查询、事件流或回调获取进度；不要让一个 HTTP 请求永远等 Agent 醒悟

**幂等与恢复** ---- 工具调用和任务提交要有幂等键；服务重启后能从检查点恢复，或明确回滚到安全状态

**成本与上下文** ---- 按任务阶段裁剪历史和工具结果，稳定内容考虑缓存；为高风险或高成本任务设置预算与人工接管

**重点在这** ---- 平台会话解决“模型看见什么”，应用状态解决“业务已经做了什么”；两者都要有来源和生命周期

## 第七站：生产封装与安全

第七站是运营控制室。先把限流、错误、权限和审计接好，再考虑加第十个酷工具；模型输出、用户输入、文件和工具结果都要先过安检。

**客户端封装** ---- 统一超时、限流、指数退避、取消、请求追踪、错误分类和用量记账；平台变更只改适配层

**数据边界** ---- 只发送完成任务所需的最少数据，日志脱敏，按租户隔离会话、文件、检索结果和工具权限；敏感业务先核对平台数据政策

**提示词注入** ---- 用户、网页、文件和工具返回都可能包含伪指令；把外部内容明确标记为资料，并在工具执行前重新校验权限与参数

**输出安全** ---- 对个人信息、密钥、内部链接、危险命令和越权建议做过滤或人工复核；安全拒绝需要可解释的用户体验

**观测与告警** ---- 记录调用、事件、工具、耗时、token、错误、预算和用户取消；建立限流、成本失控、重复调用与异常输出告警

**重点在这** ---- API 能力越强，应用护栏越不能省；把“模型很聪明”当作安全策略，是把门锁交给门口的海报

## 第八站：评估、迁移与练习项目

第八站是毕业专列。做一个工单分流助手：先输出结构化分类，必要时调用只读查询工具，再生成带依据的回复；错误参数、超时、重复提交、空结果和越权请求，都是列车员故意放上的考题。

**质量评估** ---- 比较分类准确率、字段完整率、引用正确率、工具选择率和人工通过率；不同任务不要被一个总分掩盖

**效率评估** ---- 比较首 Token、完整响应、工具轮数、输入输出 token、缓存命中和单任务成本；质量提升若需要十倍成本，要把取舍写出来

**适配回归** ---- 用相同输入测试另一家平台或另一模型，比较文本、结构化结果、工具轨迹和失败行为；记录能力差异，不强行追求完全相同的句子

**最小复现** ---- 为每个失败案例保留输入、平台、模型、提示词版本、工具版本和响应摘要；最小复现比“线上偶尔不对”更能推动修复

**交付证据** ---- 能完成一次流式调用、一次 schema 约束调用和一次完整工具循环；能解释响应生命周期、权限边界与成本来源；能在不改业务流程的情况下切换后端

## 通关标准

能完成一次流式调用、一次 schema 约束调用和一次完整工具循环；能解释输入、事件、响应生命周期、权限边界与成本来源；能处理超时、限流、取消、工具失败和结构化失败；能在不改业务流程的情况下切换后端。

## 结语

Responses API 的价值像一个现代车站：文本、工具、结构化结果和流式事件可以从同一套调度体系出发。但车站只负责调度，不负责替你确认乘客有没有票、行李是否危险、列车是否真的到站。

先把事件、状态、权限和验证做稳，再把 Agent 和更多工具接上。会发请求只是起点，能把一次运行讲清楚、停得下来、换得了后端，才算真正掌握这条路线。
