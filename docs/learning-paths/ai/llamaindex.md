# LlamaIndex 框架学习路线

LlamaIndex 专注于让 LLM 访问、索引和理解你的数据。如果说 LangChain 更像组件编排工具房，LlamaIndex 更像知识数据管道：它关心数据从哪里来、如何解析成节点、怎样建立索引、如何检索、如何合成答案，以及这些过程如何被评估。

前置建议先读 [RAG 系统](/learning-paths/ai/rag-systems) 了解检索增强的原理，再看 [向量数据库](/learning-paths/ai/vector-databases) 的存储与选型。本页讲 LlamaIndex 的抽象地图和学习顺序，不把版本敏感的导入路径当成长期知识；具体 API 以当前官方文档为准。

这条线按 **数据抽象 → 摄取管道 → 索引与存储 → 查询引擎 → 后处理与 Agent → 评估 → 生产治理 → 生态组合** 推进。

## 第一站：Document、Node、Index 与 Query

欢迎来到 LlamaIndex 的图书馆。Document 是原书，Node 是切下来的章节，Index 是目录，Query 是前台检索员；先认清谁负责搬书、谁负责找书，后面就不会把目录当答案交出去。

**Document** ---- 一份原始资料及其来源、作者、时间、权限和版本；元数据不是装饰，它决定过滤、引用与删除能否可靠

**Node** ---- 可被索引和检索的内容单元，包含文本、元数据与节点关系；节点大小、重叠与父子关系直接影响召回和回答上下文

**Index** ---- 组织节点的索引结构；向量索引适合语义召回，摘要或列表型索引适合小规模全局阅读，选型由问题形态决定

**Retriever** ---- 根据问题取回候选节点；top-k、阈值、元数据过滤、混合检索和后处理决定“模型看到什么”

**Response Synthesizer** ---- 将检索到的节点合成为回答或结构化结果；合成模式影响上下文使用方式、延迟、成本与可追溯性

**Query Engine** ---- 对外提供查询入口，组合索引、检索、后处理和合成；它是数据问答服务的边界，不应吞掉权限与业务校验

**Chat Engine** ---- 在查询之上维护多轮上下文与追问；对话记忆仍要有生命周期、租户隔离与摘要策略

**重点在这** ---- LlamaIndex 的核心不是“一个 query 方法”，而是从数据到证据再到答案的一条可替换管道

## 第二站：数据摄取与解析

第二站是资料入库处。加载器能打开 PDF，只能说明门开了，不代表标题、表格、页码和权限没有在搬家时掉进纸箱缝里；数据先整理，检索才有体面可言。

**数据连接器** ---- 了解本地文件、网页、云盘、知识库、数据库、API、代码仓库和消息系统等来源；选择连接器时同时看增量、删除和权限能力

**解析质量** ---- 关注 PDF 版面、扫描 OCR、表格、页眉页脚、代码块、链接、编码、图片和多栏布局；解析错误会在检索与生成阶段层层放大

**Document 元数据** ---- 记录来源 URI、标题、页码、时间、作者、租户、部门、文档版本和访问级别；元数据要能随节点继承并参与过滤

**去重与版本** ---- 对重复文件、不同版本、撤回内容和内容指纹建立规则；知识库最危险的不是没有新内容，而是旧内容删不干净

**增量摄取** ---- 只处理新增、修改和删除的内容，避免每次全量重算 Embedding；增量失败要可重试，索引更新要有状态记录

**数据血缘** ---- 能从答案节点追到原始文档、解析版本、切分策略、Embedding 模型和索引版本；没有血缘就很难解释答案为何变化

**重点在这** ---- 先让数据可解析、可追踪、可删除，再谈“更聪明的检索”

## 第三站：切分、Embedding 与存储

第三站是切书与建库工坊。切得太碎，章节失忆；切得太大，检索员抱着整本书喘气。chunk 没有宇宙标准，文档结构和问题类型才是裁缝尺。

**NodeParser** ---- 按句子、段落、标题、Markdown、代码、页面或语义切分；保留层级、邻接和来源关系，避免上下文被切碎

**父子节点** ---- 小节点用于精确召回，大节点用于恢复完整语境；父子关系能缓解“找得准”和“读得全”的矛盾

**Embedding 模型** ---- 将节点与问题映射到向量空间；关注多语言、领域术语、维度、输入长度、批量成本和版本

**索引重建** ---- 更换 Embedding 模型、维度、归一化或关键切分策略后，通常需要重建索引；旧向量不能因为“看起来也是数字”就继续混用

**Storage Context** ---- 管理文档、节点、索引、向量库和持久化；生产环境要把索引版本、备份、恢复和一致性写进运维流程

**外部向量库** ---- 原型可使用本地存储，生产按规模、过滤、事务、托管、备份和运维选择 pgvector、Qdrant、Milvus、Weaviate 等；选型见 [向量数据库](/learning-paths/ai/vector-databases)

**重点在这** ---- 索引是数据资产，不是一次性构建脚本；它需要版本、更新、删除、回滚和质量基线

## 第四站：查询引擎与响应模式

第四站来到阅览室。检索决定把哪几本书放上桌，后处理决定擦掉多少灰，合成器负责写读书报告；先看清三位馆员的分工，再相信 Query Engine 的默认菜单。

**相似度 top-k** ---- 控制候选数量与上下文噪声；k 太小容易漏证据，k 太大增加成本和冲突，需要用评估集调参

**元数据过滤** ---- 按时间、部门、文档类型、项目、租户和权限缩小范围；过滤必须由服务端校验，不能完全依赖模型解析

**相似度阈值** ---- 低于阈值时返回无相关结果或转人工；阈值应在真实数据上校准，不同领域与模型不能直接照搬

**响应合成** ---- 了解紧凑合并、逐块精炼、树状摘要、引用回答等策略；文档规模、问题类型、延迟和成本共同决定选择

**追问改写** ---- 对“那它多少钱”一类没有主语的追问，先结合历史改写为完整问题再检索；改写结果要保留原意与权限范围

**子问题与路由** ---- 复杂问题可拆成多个子查询，或按知识域路由到不同索引；拆分后要处理部分失败、重复证据与最终汇总

**引用与拒答** ---- 保存节点来源、页码、版本和片段；证据不足时明确不知道，不能让合成器用流畅语言填补空洞

**重点在这** ---- Query Engine 不是自动正确答案机，它只是把数据、召回与生成组织到了一起；质量仍由评估决定

## 第五站：高级检索、后处理与数据 Agent

第五站是高级检索实验室。重排、父子节点、多查询和路由都是新设备，但每加一台机器都要回答“它修复了哪次翻车”，否则只是给图书馆添了一排会发光的架子。

**Node Postprocessor** ---- 通过阈值、去重、元数据、时间和自定义规则清理候选；后处理过度会把关键限定条件一起删掉

**Rerank** ---- 先用便宜召回取得候选，再用交叉编码器或模型重排；比较精度提升与额外延迟、成本

**句子窗口与自动合并** ---- 小句命中后带回邻近句子或父节点；适合既要精确定位又要完整语境的长文档

**多查询与 HyDE** ---- 通过问题扩展、同义改写或假设答案提升召回；同时监控查询漂移、成本和错误放大

**Router Query Engine** ---- 按问题选择向量、关键词、SQL、知识图谱或不同知识库；稳定规则优先，模型路由要有默认与拒答分支

**SubQuestion Query Engine** ---- 将复合问题拆成可验证子问题后分别查询；最终汇总要保留每个子答案的证据与失败状态

**数据 Agent** ---- 将 SQL、API、文档或图谱查询封装为受控工具；只读账号、表白名单、行数限制与结果校验不可省

**Agent 工具化** ---- 将 Query Engine 暴露给 Agent，让 Agent 决定何时检索；明确工具描述、权限、超时与引用回传

**重点在这** ---- 高级检索不是组件越多越强，而是每个组件都能在失败样例上证明自己的价值

## 第六站：评估与可观测性

第六站是图书馆质检处。默认链路很快能说话，但“能回答”距离“答得对”还有一张借阅单；检索、生成、引用、延迟和成本要分别验收。

**检索评估** ---- 测召回率、命中率、上下文精确性、排序质量和无结果率；先确认正确证据是否进入候选集

**生成评估** ---- 测答案相关性、忠实度、完整性、引用准确性、拒答质量与格式有效率；RAG 的幻觉要与检索漏召回区分

**固定数据集** ---- 用人工问答、生产失败样本、边界问题和合成样本构建 golden 集；每次改切分、Embedding、检索或模型都跑回归

**LLM 评审** ---- 可用强模型做批量评分，但要控制偏差、标准漂移、隐私和成本；关键任务配人工复核与规则校验

**Trace 与回调** ---- 记录摄取、解析、Embedding、检索、后处理、合成、模型、token、引用与耗时；最终答案之外的中间轨迹才是调试线索

**失败分类** ---- 将解析失败、索引缺失、权限过滤、召回不相关、生成不忠实、引用错误和服务超时分别统计

**重点在这** ---- 可观测性回答“发生了什么”，评估回答“做得好不好”；两者一起才有调优闭环

## 第七站：生产工程与生态组合

第七站是馆长办公室。生产环境要处理更新、权限、并发、成本和回滚；LlamaIndex 可以管理书和检索，但身份、审批和交付不能让它顺便代签。

**多租户隔离** ---- 在摄取、索引、检索、缓存、引用与日志各层带上租户边界；只在回答末尾过滤已经太晚

**更新与删除** ---- 用文档 ID、内容指纹和索引版本管理 upsert、删除、重建与回滚；删除必须能验证向量与缓存均已失效

**缓存** ---- 对 Embedding、检索、查询和模型结果分别设计缓存；缓存键要包含模型、索引、权限和数据版本

**并发与超时** ---- 为加载、Embedding、向量库、重排与生成设置并发和 deadline；长文档处理进入队列，避免阻塞在线请求

**数据安全** ---- 文档、节点、引用、追踪和缓存都可能包含敏感信息；脱敏、访问控制、留存和删除流程要与业务一致

**框架组合** ---- 可让 LlamaIndex 负责数据接入与检索，让 LangChain/LangGraph 或自研编排负责 Agent 与工作流；边界清楚比争论谁更全重要

**版本与迁移** ---- 锁定核心包、集成包、Embedding、向量库驱动和模型版本；升级前阅读迁移说明并跑固定数据集

**重点在这** ---- 框架帮你降低管道搭建成本，不能替你定义数据质量、权限和上线标准

## 通关标准

能用多格式资料完成摄取、解析、切分、Embedding、索引持久化、检索、引用和查询；能解释 Document、Node、Index、Retriever、Query Engine 与合成器的关系；能配置元数据过滤、父子节点、重排与增量更新；能用检索/生成两类指标定位失败；能把查询引擎安全地接成 Agent 工具。

## 结语

LlamaIndex 的魅力是把“从文件到答案”的许多搬运活整理成了图书馆流程，但它不会替你决定哪本书可信、谁有借阅证、旧版本何时下架。默认值适合开馆，评估和治理才适合迎接读者。

先用小数据跑通，再用真实问题调切分、召回、重排和引用。能说清一条答案来自哪份资料、哪个节点、哪个版本，才算真的学会了这间图书馆。
