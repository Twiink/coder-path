# LangChain 框架学习路线

LangChain 是一套把模型、提示词、工具、检索和 Agent 组装起来的应用框架。它像一间零件很多的工具房：螺丝刀、扳手、自动门和会写诗的电钻都有，但不会因为工具房很大，房子就自动盖好。

这份路线是**学习指引和知识索引**，不是 API 说明书，也不是把官方文档重新抄一遍。每一站只回答三件事：要认识哪些概念、它们之间怎么接、继续深入时应该去哪里。具体类型、参数、代码和完整案例，放到后续学习笔记中展开。

学习 LangChain 的总原则是：先理解 LLM 调用、工具循环、检索和状态，再学习框架的抽象；先用小链路验证每个组件，再把它们装进 Agent。否则很容易出现“代码能跑，自己不知道为什么”的框架魔法秀。

## 第一站：LangChain 的位置与生态地图

第一站先不急着导入任何类，先把地图摊开。LangChain 不是一个单独的包名就能概括的世界，它由核心抽象、模型集成、社区组件、Agent 编排和可观测平台共同组成。地图看懂了，遇到导入路径变化时才不会像在机场找错航站楼。

**LangChain 的职责边界** ---- 负责把模型、提示词、工具、检索和执行流程组合起来；它不替你决定业务规则、权限模型、数据质量和上线标准

**LangChain 与裸 SDK** ---- 裸 SDK 适合理解底层请求和极小应用，LangChain 适合组件较多、需要统一接口或持续编排的系统；两者不是信仰战争，复杂度才是裁判

**LangChain 与 LangGraph** ---- LangChain 提供较高层的 Agent 与组件抽象，LangGraph 更适合显式状态、分支、循环、持久化、中断和长流程；遇到状态机问题就别让一条链假装自己是图

**LangChain 与 LangSmith** ---- LangSmith 负责追踪、调试、数据集、评估和线上观测；没有运行轨迹的 Agent，出了问题只能对着最终答案进行考古

**核心包与集成包** ---- 认识 `langchain`、`langchain-core`、模型供应商集成包、社区集成包、文本切分包和 LangGraph 的职责边界；包拆分是为了降低耦合，不是为了给开发者增加寻宝游戏

**模型集成生态** ---- 了解 OpenAI、Anthropic、Google、开源模型、本地推理、数据库、向量库和第三方工具的适配方式；统一接口很有用，但不能抹平模型能力、上下文、工具和计费差异

**Python 与 JavaScript/TypeScript 生态** ---- 对比两套生态在导入路径、类型系统、异步模型、运行时和示例组织上的差异；学习概念可以共用，复制代码却常常会复制出一只不一样的 bug

**当前 API 与历史 API** ---- 识别旧式 Chain、Memory、AgentExecutor 与现代 Runnable、`create_agent`、Middleware、LangGraph 的关系；会迁移比会背旧教程更重要

**版本管理与文档导航** ---- 学会区分概念文档、集成文档、API Reference、迁移指南和示例仓库；版本快速演进时，搜索到一篇旧教程不等于找到真理

**重点在这** ---- 先建立“组件层、编排层、观测层”的三层心智模型；以后每看到一个新类，都先问它属于哪一层、解决什么边界问题

## 第二站：消息、模型与上下文

第二站来到模型调用的码头。模型看到的不是你的业务对象，而是消息、内容块、工具描述和上下文。消息排错了，模型就会像收到了错寄的快递：东西都在，但用途完全不对。

**消息角色** ---- 掌握 system、human/user、ai/assistant、tool 等角色及其边界；角色不是装饰标签，它会影响上下文语义、工具回填和多轮对话结构

**消息内容块** ---- 认识文本、图片、文件、工具调用、工具结果、推理相关内容和供应商扩展字段；多模态应用不能把所有内容都粗暴塞成一段字符串

**消息元数据** ---- 关注响应 ID、token 用量、模型信息、响应原因、请求标识和供应商原始字段；业务需要统一字段，排障又不能把原始信息全部丢掉

**Chat Model 与普通 LLM** ---- 区分面向消息的对话模型和面向单字符串的传统补全模型；现代 Agent 通常围绕消息与工具调用工作，但遗留系统仍可能使用旧接口

**统一调用协议** ---- 掌握 `invoke`、`ainvoke`、`stream`、`astream`、`batch`、`abatch` 等调用形态；单次、异步、流式和批量不是同一个按钮换颜色，而是不同的运行约束

**模型参数** ---- 认识模型标识、温度、最大输出、停止条件、超时、重试、随机种子、响应格式和供应商特有参数；参数应按任务管理，不要把一套“玄学旋钮”复制到所有模型

**模型能力声明** ---- 识别是否支持工具调用、结构化输出、视觉输入、流式、批量、缓存、推理参数和多模态；“接口能调用”不等于“能力完全兼容”

**模型绑定与配置** ---- 学习 `bind`、运行时配置、可配置模型、模型替换和供应商参数透传；适配层要暴露稳定能力，不能为了统一而把最有价值的特性藏进地下室

**Token 与上下文预算** ---- 关注输入、输出、工具定义、历史消息、检索内容和缓存前缀共同占用的预算；Agent 变慢变贵，很多时候不是模型突然变笨，而是上下文偷偷长胖

**模型响应生命周期** ---- 了解开始、增量事件、工具调用、工具结果、最终响应、异常和取消等阶段；后续的流式 UI、日志和重试都依赖这张生命周期图

**重点在这** ---- LangChain 的模型抽象主要统一调用方式，不保证统一模型行为；必须把“框架契约”和“模型能力差异”同时写进学习笔记

## 第三站：提示词模板与上下文组装

第三站是提示词工坊。这里学习的不是“把语气写得像魔法学校”，而是让提示词成为可测试、可复用、可版本化的输入构造器。字符串拼接能跑起来，但也很容易把历史消息、用户内容和系统规则炖成一锅粥。

**ChatPromptTemplate** ---- 学习消息模板、变量占位、系统指令、用户消息和示例消息的组合方式；模板的价值是让输入结构可见、可复用、可检查

**MessagesPlaceholder** ---- 为历史消息、工具结果、Agent 草稿和动态上下文预留插槽；多轮 Agent 不应靠手工在字符串里挖隧道

**PromptTemplate 与聊天模板** ---- 理解字符串模板和消息模板的适用边界；简单摘要可以用字符串，工具 Agent 通常需要明确的消息角色

**模板格式化器** ---- 认识 f-string、mustache、Jinja2 等格式化方式及其转义风险；模板越灵活，注入、缺变量和审计难度也可能越高

**部分变量与动态变量** ---- 学习固定系统提示、运行时用户输入、工具说明、日期、租户信息和权限上下文的分层注入

**Few-shot 示例** ---- 掌握静态示例、动态示例选择、示例压缩、相似度选择和示例质量评估；示例不是越多越强，太多只是给 token 账单办健身卡

**提示词组合与复用** ---- 认识模板组合、共享片段、版本管理、环境变量、远程提示词和提示词注册；通用规则与业务规则要有清楚的所有权

**上下文工程** ---- 学习如何组织指令、历史、检索内容、工具说明、用户资料、约束和输出格式；Agent 质量常常败在上下文布局，而不是败在“模型不够聪明”

**不可信内容隔离** ---- 将用户输入、网页、文档、工具结果和系统指令分层标记；外部内容应该作为数据进入上下文，不能偷偷升级成项目经理

**提示词调试** ---- 使用模板渲染检查、变量缺失检查、输入快照、版本对比和 LangSmith Playground；先看模型实际收到什么，再讨论它为什么答错

**重点在这** ---- 把提示词看成输入程序，把上下文看成数据结构；好的提示词工程不是辞藻比赛，而是边界设计

## 第四站：Runnable 与 LCEL

第四站进入 LangChain 的流水线车间。Runnable 是许多组件共同遵守的运行协议，LCEL 则是把这些组件组合成流程的声明式方式。它像传送带，但传送带也会把错误稳定地传到终点，所以每个工位都要能单独验货。

**Runnable 核心协议** ---- 认识输入、输出、配置、调用、流式、批量和异步等统一接口；统一协议让模型、提示词、解析器和自定义步骤能够互相拼接

**RunnableSequence** ---- 理解顺序执行与前一步输出传给后一步的关系；适合提示词→模型→解析器等线性流程

**RunnableParallel** ---- 认识并行分支、结果聚合、并发限制和失败传播；“同时查多个来源”很适合并行，但下游服务不一定喜欢突然被集体点名

**RunnablePassthrough** ---- 保留原始输入并继续传递；在组装上下文时常用来同时保留问题、检索结果和中间字段

**RunnableLambda** ---- 将普通函数接入 Runnable 协议；自定义函数很方便，但函数中的副作用、异常和类型边界不能因为套了 Runnable 外壳就隐身

**RunnableBranch** ---- 按条件选择不同分支；适合路由、降级和不同任务类型，但条件规则稳定时应优先使用确定性代码

**RunnableAssign 与字段组合** ---- 学习在保留原输入的同时增加计算字段、重命名字段和整理中间结构；字段形状清楚，链路才不会变成字典考古现场

**RunnableMap 与输入映射** ---- 认识同一输入如何映射到多路组件，以及字典输入如何参与组合；这部分是 LCEL 可读性与可调试性的基础

**with_config 与运行配置** ---- 掌握 tags、metadata、run name、回调、并发度、递归限制、可配置字段和请求级追踪信息；配置是运行时控制面，不是随手塞参数的抽屉

**with_retry 与 with_fallbacks** ---- 学习可重试错误、退避、备用模型、备用链和降级输出；重试不可恢复的参数错误，只会让错误更有耐心

**with_types 与输入输出契约** ---- 为 Runnable 标注输入输出类型，帮助编辑器、测试和团队理解数据流；类型声明不是运行时校验，外部数据仍需要真正验证

**流式组合** ---- 了解哪些组件可以逐步产出、哪些组件必须等完整结果、解析器如何处理增量文本；一条链支持 `stream` 不代表每一站都能丝滑打字

**批量与异步组合** ---- 学习批量调用、异步并发、完成即返回、取消、超时和背压；吞吐提升的另一面是限流、内存和故障放大

**get_graph 与链路检查** ---- 了解如何查看 Runnable 组合出的图、节点和数据流；可视化不是为了截图发朋友圈，而是为了发现字段丢失和分支走错

**LCEL 与显式编排的边界** ---- 线性、可组合、可测试的流程适合 LCEL；复杂状态、循环、暂停、恢复和长时间任务应转向 LangGraph

**重点在这** ---- LCEL 解决“组件怎么连”，不解决“业务应该怎么决策”；先画输入输出，再选择组合器，别让一根 `|` 负责整个系统的命运

## 第五站：输出解析与结构化结果

第五站来到输出质检处。模型喜欢写文章，业务系统喜欢对象；两者见面时必须经过解析、校验和失败处理。把模型输出直接当数据库记录，是让生产事故提前预约座位。

**StrOutputParser** ---- 认识文本输出的统一提取、空结果、停止原因和流式拼接；最简单的解析器也要处理模型没有按预期结束的情况

**JSON 与结构化解析** ---- 学习 JSON 解析、字段缺失、额外字段、类型错误、嵌套结构和部分输出；“看起来像 JSON”离“可以安全入库”还有一段路

**Pydantic、Zod 与标准 schema** ---- 认识 Python、TypeScript 和 JSON Schema 生态中的结构化契约；路线页只记类别，具体字段校验在学习笔记中展开

**with_structured_output** ---- 学习让模型按 schema 产出结构化结果的现代方式，以及不同模型对原生结构化能力的支持差异

**ProviderStrategy 与 ToolStrategy** ---- 理解原生结构化输出与工具策略之间的取舍；平台支持时优先原生能力，不支持时再用工具或解析策略兜底

**OutputFixing 与重试解析** ---- 认识解析失败后的修复、重新请求、错误回填和重试次数；修复机制只能处理格式问题，不能把错误事实变成正确事实

**结构化结果的语义校验** ---- 区分 schema 校验、业务规则校验、权限校验和事实核验；字段类型正确，不代表内容有道理

**结构化流式输出** ---- 关注增量 JSON、未闭合结构、事件边界和最终对象确认；界面可以展示半成品，系统入库要等验收通过

**解析失败的可观测性** ---- 记录模型、提示词版本、schema 版本、原始响应摘要、重试次数和最终状态；否则每次失败都只能靠“再跑一次看看”祈祷

**重点在这** ---- 结构化输出的目标是可验证，不是让模型戴上一顶 JSON 帽子；最终边界永远由程序校验守住

## 第六站：工具系统与函数调用

第六站是 Agent 的工具柜。工具让模型从“会说”走向“能请求动作”，但模型只负责提出意图，真正的执行、鉴权、审计和副作用控制仍属于应用。给模型一把锤子之前，先确认它不会顺手拆了承重墙。

**Tool 的组成** ---- 掌握名称、描述、参数 schema、返回值、错误、元数据和执行函数；工具描述是模型的使用说明，也是模型的路由信号

**`@tool` 与自定义工具** ---- 认识装饰器、函数工具、结构化工具、类工具和底层工具接口；快捷写法适合原型，复杂权限和生命周期需要更明确的实现

**args_schema 与参数校验** ---- 关注必填、可选、枚举、范围、格式、默认值和业务级校验；schema 是第一道门，不是最后一道门

**工具描述设计** ---- 写清什么时候用、什么时候不用、参数含义、权限边界、返回格式和失败方式；描述含糊，模型就会开始自由发挥产品经理人格

**ToolCall 与 ToolMessage** ---- 理解模型发出的调用意图、调用 ID、参数、执行结果和回填关系；工具循环的关联键必须可靠，否则多个工具并行时会演成群聊事故

**工具错误处理** ---- 认识异常转消息、可重试错误、不可重试错误、用户可见错误和内部审计错误；错误应该帮助模型调整策略，而不是把堆栈日志念给用户

**工具运行时上下文** ---- 学习如何传递用户、租户、权限、请求 ID、数据库连接和运行状态；上下文要按范围注入，不能把所有内部对象都塞给模型

**状态与存储注入** ---- 了解工具如何读取 Agent 状态、运行时上下文和长期存储；工具需要的数据应显式声明，隐藏的全局变量迟早会出来串门

**返回值与 artifact** ---- 区分给模型看的文本、给用户看的文件或结构化产物、给系统保存的元数据；一份结果不一定适合所有消费者

**工具调用策略** ---- 掌握自动选择、强制调用、禁止调用、单工具和多工具并行；工具越多，路由越难，先做工具分组和粗路由通常更稳

**确定性工具与 Agent 工具** ---- 计算、校验、权限判断、数据库过滤等能用普通代码完成时不要交给模型；模型擅长处理不确定语言，不擅长替你维护业务不变量

**内置、社区与自研工具** ---- 了解搜索、计算、文件、数据库、浏览器、代码执行、邮件和业务 API 等类别，以及依赖来源和供应链风险

**MCP 工具接入** ---- 理解 LangChain 如何把 MCP Server 暴露的工具接入 Agent；MCP 解决连接与发现，不替代你的权限、审批、审计和沙箱

**重点在这** ---- 工具设计的核心不是“能不能调”，而是“谁能调、何时能调、调错怎么办、调完谁负责”；工具文档和安全策略要一起写

## 第七站：Agent、Middleware 与决策循环

第七站进入 Agent 控制室。Agent 的骨架通常是“模型决策 → 工具执行 → 结果回填 → 再决策”，但生产系统还要加入停止条件、权限、人工确认、错误恢复和状态持久化。没有刹车的自动驾驶，名字再智能也只是移动的风险。

**Agent 的最小循环** ---- 掌握输入、模型决策、工具调用、工具结果、最终回答和结束条件；先把循环画出来，再学习框架帮你省掉哪些胶水代码

**`create_agent`** ---- 认识当前高层 Agent 入口、模型、工具、响应格式、检查点和中间件配置；它适合快速得到可用骨架，但复杂流程仍需要下潜到图编排

**模型节点与工具节点** ---- 理解模型负责选择下一步，工具负责执行外部动作，状态负责在节点间传递；把三者混在一个函数里，测试和审计都会变得很有创意

**停止条件** ---- 学习没有工具调用时结束、达到最大步数、达到 token 预算、超时、用户取消、错误阈值和人工终止；“模型说完成了”不能单独作为完成证明

**递归与循环限制** ---- 关注 recursion limit、重复工具调用、相同参数重试和工具结果导致的自激循环；Agent 最擅长的事情之一，就是很有礼貌地重复犯错

**Middleware 总览** ---- 认识在模型前后、工具前后和 Agent 生命周期中插入逻辑的方式；中间件适合横切能力，业务主流程仍应保持可读

**模型前置与后置处理** ---- 学习动态系统提示、上下文裁剪、请求改写、输出检查、模型路由和结果后处理；前后钩子是控制面，不是藏逻辑的阁楼

**工具前置与后置处理** ---- 关注参数校验、权限判断、脱敏、确认、审计、结果清洗、重试和工具失败降级；任何副作用工具都应该在执行前有门，在执行后有账

**动态模型与动态工具** ---- 按任务、权限、预算、租户、上下文或风险等级选择模型与工具；动态能力越强，测试矩阵越大，不能只测“默认用户”

**Guardrails** ---- 了解输入护栏、输出护栏、工具护栏、内容安全、格式约束和越权检测；Guardrail 是安全网，不是把不安全设计包装成安全设计

**Human-in-the-loop** ---- 掌握 interrupt、审批、拒绝、修改参数、恢复执行和审批记录；发邮件、删数据、改代码、付款等动作不应靠模型一句“我确认过了”

**Handoff 与多 Agent 协作** ---- 理解一个 Agent 把任务交给另一个 Agent、共享上下文或只传递必要信息的方式；交接不是把所有聊天记录复制三份

**Supervisor 与 Agent-as-tool** ---- 学习管理者、专职 Agent、路由器、聚合器和工具化子 Agent 的组合；角色划分要减少复杂度，而不是把一个问题拆成十个互相甩锅的问题

**重点在这** ---- Agent 不是“调用一个高级 API”，而是一个受约束的决策循环；可控性来自状态、权限、停止条件和观测，而不是来自提示词里的祈祷

## 第八站：LangGraph、状态与持久化

第八站下潜到 LangGraph。只要流程出现共享状态、条件分支、循环、暂停、恢复、长任务或多人协作，就需要把流程画成图。图不是为了显得复杂，而是为了让复杂度别躲在黑箱里。

**StateGraph** ---- 认识状态、节点、边和图的基本组成；图的价值是把流程控制显式化，让每一步都能单独检查

**State Schema** ---- 设计消息、任务状态、检索结果、审批状态、错误、预算和产物等字段；状态不是“把所有变量丢进字典”，而是系统的工作记忆契约

**节点函数** ---- 学习节点如何读取状态、返回状态更新、处理异常和保持幂等；节点应聚焦一个动作，别把整个工作流塞成一颗巨型洋葱

**普通边与条件边** ---- 理解固定流转、条件路由、成功/失败分支和循环回边；路由条件最好来自明确状态，不要让流程控制完全依赖自然语言

**Send 与动态扇出** ---- 认识把一个任务拆成多个并行子任务、分别执行后再聚合的模式；扇出需要考虑顺序、限流、部分失败和结果去重

**Command 与控制流更新** ---- 学习一次操作如何同时更新状态并决定下一步；控制流和数据更新靠得太近时，要特别注意可读性和重放行为

**子图 Subgraph** ---- 将复杂流程拆成可复用模块，并理解父图与子图的状态边界；子图不是把文件夹换成函数名，而是要有清楚输入输出

**Checkpointer** ---- 掌握检查点、线程 ID、状态快照、恢复、重试和故障后继续执行；长任务没有检查点，服务重启一次就像把小说撕掉最后三章

**Interrupt 与恢复** ---- 理解节点暂停、等待用户或审批、保存状态、恢复命令和恢复后的幂等执行

**Durable Execution** ---- 关注持久执行、任务重放、外部副作用、幂等键和崩溃恢复；能恢复不等于可以重复扣款，副作用必须单独设计

**时间旅行与调试** ---- 了解状态快照、轨迹回放、节点级重跑和分支调试；这类能力适合解释“Agent 到底在哪一步决定走歪了”

**长流程与后台任务** ---- 学习队列、超时、取消、租约、心跳、断点恢复和用户查询进度；短请求能跑通，不代表长任务可以直接搬进生产

**重点在这** ---- LangGraph 的深层知识是“状态如何演进、失败如何恢复、副作用如何保证一次性”；节点和边只是这套思想的可视化外衣

## 第九站：记忆、上下文与会话状态

第九站研究 Agent 的记忆。记忆不是把历史消息无限保存，而是决定什么该保留、什么该摘要、什么该检索、什么该删除，以及谁有权看到它。记性太差不行，记性太好也可能变成合规部门的噩梦。

**短期记忆** ---- 认识当前线程、对话历史、任务进度和检查点；短期记忆服务于一次会话或一项任务，不等于用户永久档案

**长期记忆** ---- 了解用户偏好、事实、任务经验和组织知识的持久化方式；长期记忆必须有来源、置信度、更新时间、删除和纠错策略

**消息窗口** ---- 学习完整历史、滑动窗口、按 token 裁剪、按重要性保留和按消息类型过滤；砍掉最早消息很简单，砍掉最不重要消息才是工程

**摘要记忆** ---- 关注增量摘要、分层摘要、摘要质量、事实漂移和摘要版本；摘要是有损压缩，不要把它当成完美录像

**消息删除与脱敏** ---- 处理敏感信息移除、用户请求删除、租户隔离、保留期限和日志同步；“从上下文删了”不代表它从系统所有副本消失

**Checkpointer 与会话线程** ---- 理解 Agent 状态如何按 thread 保存、读取、恢复和并发访问；会话 ID 的设计直接影响数据隔离

**Store 与长期存储** ---- 认识命名空间、键、版本、检索、更新和并发写入；长期存储要像数据库一样治理，而不是一个会无限膨胀的抽屉

**记忆检索** ---- 学习关键词、向量、时间、重要性、用户确认和混合检索；能找到不等于应该使用，记忆还需要权限与相关性判断

**上下文与状态的区别** ---- 状态是流程运行中的共享数据，上下文是当前调用可见的信息，长期存储是跨任务持久化的数据；三者混用，最终谁都不知道这句话从哪里来的

**多租户与隐私** ---- 关注租户命名空间、用户授权、数据隔离、访问审计、加密、删除和跨区域存储；记忆功能上线前先问“谁能读到”，再问“能记住什么”

**重点在这** ---- 记忆设计的目标不是让 Agent 什么都记住，而是让它在正确的时间看到正确的最少信息

## 第十站：RAG 与检索组件链

第十站进入知识库工厂。LangChain 的 RAG 组件很多，但 RAG 的上限通常不是某个类名，而是数据清洗、切分、召回、权限、引用和评估。把一堆文档塞进向量库，不叫知识工程，最多叫文档搬家。

**Document 对象** ---- 掌握正文、来源、页码、标题、时间、租户和自定义 metadata；metadata 是过滤、引用、审计和问题定位的地基

**Document Loader** ---- 了解 PDF、网页、Markdown、Office、数据库、云盘、代码仓库和自定义数据源的加载方式；加载成功不代表文本结构没有被破坏

**解析与清洗** ---- 关注 OCR、表格、页眉页脚、代码块、链接、重复内容、编码、段落层级和文档版本；垃圾进，精致的向量也只能产出垃圾

**Text Splitter** ---- 学习递归字符、按标题、按 Markdown、按代码、按 token、语义切分和父子文档策略；切分粒度要由检索任务验证，不能迷信一个固定数字

**Embedding 接口** ---- 认识文本向量、多语言、维度、批量、模型版本、归一化和重建索引；embedding 模型变了，旧向量通常不能假装没事继续混用

**VectorStore** ---- 了解写入、更新、删除、相似度搜索、过滤、命名空间、持久化和索引生命周期；向量库是存储系统，不是自动替你理解业务语义的仙人

**Retriever** ---- 掌握检索器接口、top-k、分数阈值、过滤器、空结果和召回元数据；检索器的输出质量决定后续模型有没有值得阅读的材料

**相似度与 MMR** ---- 理解相似度召回、最大边际相关、去重和多样性；最相似的五段可能只是同一句话的五个分身

**混合检索** ---- 组合关键词、全文、向量、字段过滤和业务规则；精确 ID、错误码和专有名词常常需要关键词检索帮忙

**多查询与查询改写** ---- 学习把用户问题改写成多个检索问题、补充同义词和澄清歧义；改写可能提升召回，也可能把原问题改到亲妈不认识

**Parent Document Retriever** ---- 先用小块定位，再返回更大的父文档上下文；解决精确召回与完整语境之间的拉扯

**MultiVectorRetriever** ---- 了解一份文档如何拥有摘要、假设问题、图片描述和正文等多个向量表示；索引结构越丰富，更新和删除也越需要治理

**Contextual Compression** ---- 在召回后进一步压缩、过滤或提取与问题相关的内容；减少上下文噪声，但要防止把关键限定条件一起压掉

**Reranker** ---- 认识二阶段检索、交叉编码器、模型重排和成本延迟权衡；向量召回负责找候选，重排负责把候选重新排队

**Ensemble 与路由检索** ---- 学习多个 retriever 融合、按问题类型路由、按文档域选择知识源；不是所有问题都应该打遍整个知识库

**Self-query 与结构化过滤** ---- 将自然语言中的时间、部门、标签和权限转换为 metadata 过滤；过滤条件必须由程序校验，不能让模型凭空扩大查询范围

**SQL、图谱与非向量检索** ---- 了解数据库查询、知识图谱、代码搜索、时间序列和 API 检索何时比向量更合适；RAG 不等于“凡事先 embedding”

**索引管道** ---- 掌握增量同步、删除、去重、版本、重建、回滚、失败重试和数据血缘；知识库最难的往往是“旧内容真的被删掉了吗”

**权限感知检索** ---- 在检索前、检索中和检索后都检查租户、用户、文档和字段权限；答案引用了不该看的资料，生成得再流畅也属于安全事故

**引用与可追溯性** ---- 保留来源、页码、片段、版本和检索分数；引用不是在回答末尾贴一个链接，而是让答案和证据能互相对上号

**RAG 评估** ---- 分别评估召回率、精确率、上下文相关性、答案忠实度、引用正确性、延迟和成本；只看最终回答，无法知道问题出在检索还是生成

**重点在这** ---- RAG 是“数据管道 + 检索系统 + 上下文组装 + 生成验证”的组合工程；LangChain 负责帮你接组件，不替你定义知识质量

## 第十一站：多 Agent 与复杂工作流模式

第十一站来到协作办公室。多 Agent 有时能解决职责隔离和并行任务，有时只是把一个能读懂的函数拆成五个会互相发消息的部门。先证明单 Agent 不够，再引入组织架构。

**Router** ---- 按意图、领域、权限、语言或任务类型把请求路由到不同链或 Agent；路由优先使用稳定规则，模型路由要有默认分支和拒答路径

**Supervisor** ---- 由一个管理 Agent 选择、调用和汇总多个专职 Agent；要控制上下文传递、工具权限、循环次数和汇总偏差

**Handoff** ---- 一个 Agent 将任务和控制权交给另一个 Agent；交接协议要定义输入、输出、失败责任和用户可见状态

**Agents as tools** ---- 将子 Agent 封装成上层 Agent 可调用的工具；上层只看到清晰能力，子 Agent 内部可以拥有独立工具和状态

**Fan-out / Fan-in** ---- 将任务并行分发给多个节点，再合并结果；要学习并发上限、部分失败、超时、结果排序和重复消除

**Map-Reduce** ---- 对多个文档或任务分别处理，再进行汇总；适合可拆分的数据流，不适合强依赖前一步决策的流程

**Plan-and-Execute** ---- 先生成计划，再执行步骤并允许重规划；计划必须可验证、可修订、可终止，不能只是漂亮的待办清单

**Reflection 与 Evaluator-Optimizer** ---- 用评估器检查输出，再让生成器改进；要控制反思次数和评估标准，避免 Agent 对着自己写的作文互相鼓掌

**Researcher-Writer-Critic** ---- 研究、写作和审查分工；注意信息来源、引用保留、事实冲突和最终责任归属

**子图与层级 Agent** ---- 将复杂领域拆成可组合图或子 Agent；边界越清楚，越容易分别测试和替换

**并行与串行的取舍** ---- 独立任务可并行，有依赖的任务必须串行；并行不是免费的速度按钮，它会放大配额、成本和故障数量

**多 Agent 失败模式** ---- 认识循环交接、上下文膨胀、重复劳动、责任漂移、汇总幻觉和错误扩散；复杂度增长通常比 Agent 数量更快

**重点在这** ---- 多 Agent 的核心是组织边界和信息流，不是 Agent 数量；能用确定性工作流解决的事情，不要先建一个“AI 集团”

## 第十二站：流式、异步、批量与运行时控制

第十二站负责让系统跑得稳、跑得快、跑得像个服务。开发环境里一条链慢一点只是心情问题，生产环境里则会变成队列、费用和用户耐心的三重审判。

**消息流式输出** ---- 学习文本增量、消息事件、工具调用事件、最终状态和前端渲染边界；显示得早不等于完成得早

**更新流与事件流** ---- 认识按状态更新、按消息增量、按自定义事件和按节点事件观察 Agent；不同流模式服务于不同 UI、日志和监控需求

**自定义事件** ---- 让检索进度、工具进度、审批状态和业务阶段对外可见；事件命名要稳定，否则前端会追着后端的心情改代码

**同步与异步** ---- 区分阻塞调用、异步调用、异步生成器、线程池和真正的非阻塞 I/O；把同步函数套上 async 外套，不会自动变成异步高手

**批量调用** ---- 学习批量输入、批量 embedding、批量评估、批量生成和完成即返回；批量适合离线任务，不一定适合有强顺序依赖的 Agent

**并发控制** ---- 关注 max concurrency、信号量、供应商配额、数据库连接池、向量库吞吐和下游限流；并发开大之前，先确认下游没有在角落里冒烟

**取消与超时** ---- 为用户取消、请求超时、节点超时、工具超时和整体 deadline 建立边界；取消之后的副作用要能查询和补偿

**重试与退避** ---- 区分网络错误、限流、服务端错误、参数错误、解析错误和业务错误；重试策略需要幂等性、上限和抖动

**缓存** ---- 认识模型缓存、提示词缓存、embedding 缓存、检索缓存和业务结果缓存；缓存命中要考虑数据新鲜度、权限和失效策略

**Token 与预算控制** ---- 按用户、租户、任务、模型和 Agent 步骤统计成本；预算耗尽时要有降级、暂停或转人工，而不是默默继续烧钱

**背压与队列** ---- 了解流式消费者变慢、任务排队、消息积压、优先级和死信；实时体验与吞吐之间永远存在账单

**重点在这** ---- 流式解决体验，异步解决等待，批量解决吞吐，队列解决峰值；不要用其中一个概念替代另外三个

## 第十三站：LangSmith、追踪与评估

第十三站安装系统的“黑匣子”。Agent 的最终答案只是表面，真正需要观察的是提示词、模型、工具、检索、状态变化、耗时、token 和失败节点。没有 trace 的调试，基本等于只看电影结尾猜凶手。

**Trace、Run 与 Thread** ---- 理解一次请求、一次组件执行和一组多轮会话之间的关系；层级关系清楚，才能从最终回答钻回具体工具调用

**Projects 与环境隔离** ---- 区分开发、测试、预发布和生产项目；环境隔离是避免测试数据和生产报警互相串门的第一步

**Tags、Metadata 与运行命名** ---- 为模型版本、提示词版本、租户、场景、实验组和发布批次增加检索字段；没有标签的日志，数量越多越像一座没有门牌号的城市

**模型与工具轨迹** ---- 观察每次模型输入输出、工具选择、参数、结果、重试、耗时和状态更新；Agent 的“为什么”通常藏在这些中间步骤里

**敏感数据与脱敏** ---- 规划 API Key、个人信息、业务机密、工具参数和检索文档在 trace 中的处理；可观测性不能成为数据泄露的另一条高速公路

**Dataset** ---- 将人工样例、历史生产样本、失败案例和合成案例整理成可重复运行的数据集；评估的第一步是定义什么叫“好”

**Offline Evaluation** ---- 在上线前做基准比较、单元评估、回归评估、回放和模型/提示词对比；每次改模型都应该有证据，而不是靠“感觉这次更聪明”

**Online Evaluation** ---- 在生产流量上监控异常、质量趋势、安全问题、格式错误和用户反馈；线上评估要控制采样、成本和隐私

**Evaluator 类型** ---- 认识人工评审、代码规则、LLM-as-judge、成对比较、组合评分和轨迹评估；主观质量适合模型评审，硬规则能抓格式、权限和数值错误

**Agent 轨迹评估** ---- 评估工具选得对不对、参数是否正确、步骤是否过多、是否越权、是否在正确时机停止；只评最终文本会漏掉大量过程问题

**RAG 评估** ---- 分别评估检索相关性、上下文覆盖、答案忠实度、引用准确性和拒答质量；要定位到底是“没找到”还是“找到了但没用好”

**提示词与实验管理** ---- 管理模板版本、模型版本、工具版本、实验配置和数据集版本；可复现比某次跑出高分更重要

**OpenTelemetry 与外部观测** ---- 了解如何把 LangChain/LangGraph 运行轨迹接入统一观测体系；平台可以替换，trace 语义和业务指标不能丢

**重点在这** ---- 可观测性回答“发生了什么”，评估回答“做得好不好”；二者缺一，Agent 只能靠运气上线

## 第十四站：测试、可靠性与生产工程

第十四站给 Demo 办理生产许可证。LangChain 能帮你快速搭骨架，但可靠性、权限、成本和发布策略仍需要工程团队负责。框架不会自动替你值夜班，这一点它和大多数同事一样。

**组件单元测试** ---- 单独测试提示词渲染、解析器、切分器、检索器、工具函数和路由条件；每个组件都能独立验收，组合出错时才有抓手

**Fake Model 与 Fake Tool** ---- 用可控响应替代真实模型和外部服务，测试错误、重复调用、工具参数和边界状态；确定性测试是 Agent 质量的地基

**集成测试** ---- 验证真实模型适配、向量库、MCP、数据库、队列和检查点协作；集成测试要管理凭证、成本、数据清理和失败重试

**Golden Dataset 回归** ---- 对固定样例比较输出、工具轨迹、引用、延迟和成本；模型更新后先跑回归，再让新模型进入生产

**属性与不变量测试** ---- 检查权限不越界、输出 schema 始终有效、工具调用有上限、状态可恢复和敏感字段不出现在日志中；这些规则比某一句回答更值得自动化

**故障注入** ---- 模拟限流、超时、断网、空结果、脏文档、错误参数、检查点损坏和重复恢复；系统只在晴天工作，不能叫可靠

**幂等与副作用** ---- 为发消息、写数据库、创建资源、提交代码和付款等操作设计幂等键、去重和补偿；Agent 重试时尤其要把“执行一次”说清楚

**降级与兜底** ---- 规划备用模型、只读模式、固定模板、人工接管、空结果回复和服务不可用提示；降级路径要比主路径更容易理解

**权限与隔离** ---- 控制模型、工具、用户、租户、文件、网络、数据库和工作区边界；代码执行与浏览器自动化要默认视为高风险能力

**提示词注入与数据污染** ---- 防范网页、文档、工具结果和用户输入诱导 Agent 改变规则；检索内容和工具结果一律按不可信数据处理

**密钥与隐私** ---- 密钥只在服务端、日志脱敏、外部数据最小化、租户隔离、删除流程和保留期限都要有明确设计

**依赖与供应链** ---- 锁定 LangChain 核心包、集成包、模型 SDK、向量库驱动和 MCP Server 版本；社区工具不是因为名字里有“tool”就自动可信

**部署与扩缩容** ---- 关注无状态 API、检查点存储、队列、worker、连接池、并发、冷启动、健康检查和滚动升级

**重点在这** ---- Agent 的生产质量由失败路径决定；先把“模型答错、工具失败、服务超时、用户取消、权限不足”写进测试，再谈 Demo 有多惊艳

## 第十五站：版本迁移、选型与源码阅读

第十五站是毕业前的装备整理。LangChain 变化快不是秘密，真正危险的是项目同时混着新旧抽象，团队每个人都在使用不同年代的教程，最后连错误消息都开始考古。

**旧式 Chain 到 Runnable** ---- 了解 LLMChain、SequentialChain 等历史抽象如何迁移到 Runnable/LCEL；重点理解数据流，不要只做机械替换

**旧式 Memory 到状态与持久化** ---- 对比传统 Memory 类、消息历史包装器、Agent checkpointer 和长期 store；不同记忆解决不同生命周期，不能把所有“记住”都叫 Memory

**旧式 AgentExecutor 到现代 Agent** ---- 理解黑盒循环、显式图、`create_agent`、Middleware 和自定义 LangGraph 的边界；迁移目标是获得可控性，不是换一个更长的导入路径

**集成包拆分与导入路径** ---- 关注核心包、供应商包、社区包、文本切分包和 LangGraph 的版本配合；升级时记录变更范围，避免全仓库盲目改名

**配置与序列化** ---- 认识 Runnable 配置、可序列化组件、环境变量、远程提示词和部署配置；本地能运行的对象不一定适合跨进程或跨版本保存

**向后兼容与弃用** ---- 关注 deprecation warning、迁移指南、版本锁定、兼容矩阵和上游 release note；警告不是装饰，它常常是未来构建失败寄来的明信片

**裸 SDK、LangChain、LangGraph 的选择** ---- 简单调用选裸 SDK，组件化链路选 LangChain，复杂状态工作流选 LangGraph；不要为了一个模型调用引入一座框架城堡

**LangChain 与 LlamaIndex 的选择** ---- LangChain 更偏组件编排与 Agent，LlamaIndex 更偏数据连接、索引和检索；实际项目可以组合，边界要由主要问题决定

**源码阅读顺序** ---- 先读核心消息、Runnable、工具和 Agent 抽象，再读一个具体模型集成与一个具体检索器；不要从整个仓库第一行开始挑战自己的耐心

**源码阅读重点** ---- 观察输入输出协议、回调传播、错误处理、异步实现、序列化、配置合并和版本兼容；这些地方决定框架的真实行为

**官方示例与最小复现** ---- 每学一个新能力都保留一个最小实验，并记录依赖版本、输入、输出和失败现象；最小复现是开发者对抗“我这里怎么不一样”的护身符

**重点在这** ---- 框架学习的终点不是记住更多类名，而是能在抽象失效时下潜到协议层，在抽象过重时安全地退回裸 SDK

## 通关标准

**新手能把积木摆稳** ---- 能说清模型、提示词、Runnable、工具、检索和 Agent 的关系；能搭一条可追踪的“提示词→模型→结构化输出”链，遇到导入错误不会立刻给整个项目举行告别仪式

**初级开发者能做出工具 Agent** ---- 能定义有 schema 和权限边界的工具，跑通工具调用循环、错误回填、停止条件和基础流式输出；知道模型提出调用，不等于模型真的执行了调用

**中级开发者能驾驭状态与 RAG** ---- 能用 LCEL 组织可测试链路，用 LangGraph 表达分支、循环、检查点和人工确认；能设计一条包含切分、召回、过滤、重排、引用和评估的 RAG 管道

**高级开发者能让系统经得住折腾** ---- 能处理多 Agent、动态路由、异步并发、取消、重试、幂等、权限、注入、成本、版本迁移和故障恢复；还能解释为什么某些地方根本不该使用 Agent

**工程负责人能做出取舍** ---- 能在裸 SDK、LangChain、LangGraph、LlamaIndex 和自研编排之间做出有证据的选择；能用 trace、dataset 和评估结果推动迭代，而不是用会议音量替代指标

## 结语

LangChain 的价值是把重复的 LLM 应用工程工作拆成可组合的组件；它的提醒则是：抽象越方便，越要知道抽象背后发生了什么。把 Runnable 当函数管道，把 Agent 当受约束的循环，把 RAG 当数据与检索系统，把 LangGraph 当状态机来理解，你就不会在版本升级时只剩下一句“昨天还能跑”。

学会 LangChain，不是为了永远住在 LangChain 里，而是为了能在需要时快速组装、准确调试、谨慎上线，并在框架不合适时体面地离开。工具可以换，工程判断力最好别换。
