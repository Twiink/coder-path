# Claude API 使用学习路线

Claude 是 Anthropic 的模型平台，常被用于长文本、代码、写作、多轮工具任务和视觉理解。学习它的重点不是背模型家族的宣传语，而是掌握 Messages API、内容块、工具使用、长上下文、缓存和安全边界，再用自己的任务集决定它是否适合项目。

前置建议先看 [模型 API 通用原理](/learning-paths/ai/model-api-overview)。本页聚焦 Claude 的平台心智模型；具体模型名、上下文上限、价格和数据政策会变化，上线前必须核对官方文档并跑回归集。

这条线按 **模型选型 → Messages 与内容块 → 长上下文 → Prompt Caching → Tool Use → 视觉与结构化 → 工程治理 → 场景评估** 推进。

## 第一站：模型选型与能力矩阵

欢迎来到 Claude 的模型集市。Haiku 像跑腿小哥，Sonnet 像靠谱主力，Opus 像请来的资深顾问；先看任务需要谁，别让跑腿小哥去做架构答辩，也别让顾问替你做字符串清洗。

**能力分层** ---- 通常可以把模型按速度与成本、均衡能力、复杂推理分层；分类、抽取和路由不必默认使用最强型号，难题也不要为了省钱硬塞给最小型号

**任务匹配** ---- 长文档、代码修改、复杂推理、创意写作、摘要、结构化抽取和视觉分析的要求不同；为每类任务保存少量真实样例再做选择

**上下文与输出** ---- 关注上下文容量、最大输出、工具数量、视觉输入、流式和批处理支持；“能放进去”不代表模型能稳定关注到每个角落

**版本锁定** ---- 生产环境记录可复现的模型版本、提示词版本和参数；别让上游自动换模型后，线上质量突然开始写现代诗

**降级路线** ---- 为限流、预算耗尽或强模型不可用准备轻量模型、固定模板、只读模式或人工接管；降级能力也要加入评估集

**重点在这** ---- 默认用均衡型号跑通闭环，再用数据决定升档或降档；模型选择是工程实验，不是品牌投票

## 第二站：Messages API 与内容块

第二站是消息码头。文本、图片、文件和工具结果都要按内容块装船，角色和顺序就是航线；货物放错舱，最后只能对着一条漂亮但不靠岸的回答发呆。

**系统提示** ---- 将稳定的角色、规则、边界、输出要求和工具约束放在独立系统上下文；用户资料、外部文档和权限事实仍要由程序控制

**用户与助手消息** ---- 多轮请求由应用维护历史，保持角色顺序与工具回填关系；历史中的旧回答不是永远正确，重要业务状态应单独保存并校验

**内容块** ---- 文本、图片、文件、工具调用和工具结果可以组合在消息中；适配层要保留内容类型、来源和关联 ID，不要把它们全压成字符串

**最大输出** ---- 明确设置输出预算，并把长任务拆成阶段或交给后台执行；输出越长，延迟、费用和被截断的概率一起上升

**流式响应** ---- 识别增量文本、内容块开始/结束、工具事件和最终停止原因；前端渲染与服务端持久化要分别判断成功

**服务端代理** ---- API Key 只留在服务端，前端通过自己的接口获取经过筛选的结果；文件、工具和会话权限也在服务端执行

**重点在这** ---- Claude 的消息结构是应用状态的一部分；每次请求前都能回答“模型看到了什么、哪些内容来自外部、哪些规则不可覆盖”

## 第三站：长上下文与多轮设计

第三站进入长文本图书馆。Claude 能搬来整份合同、手册和代码变更，但“书架大”不代表模型自动找到重点；章节、证据、预算和定位都要提前贴好索引。

**整读与 RAG** ---- 文档较小且需要全局理解时可以整读；知识库大、内容频繁更新或权限复杂时用 RAG；混合策略通常比二选一更实用

**文档布局** ---- 保留标题、页码、段落、表格边界和来源信息；把整份资料拼成无标题长字符串，会让模型和人类一起玩寻宝游戏

**问题定位** ---- 长文任务先让模型定位相关章节或列出依据，再要求生成结论；引用页码、段落或文件版本，便于人工复核

**多轮历史** ---- API 本身不替你理解业务状态；应用要决定保留原文、摘要、关键事实和工具结果哪些部分，并按用户/租户隔离

**上下文压缩** ---- 删除重复工具结果、旧草稿和无关历史，摘要时保留数值、约束、来源和未解决问题；压缩错误会比超长更难排查

**长任务状态** ---- 研究、代码审查和多步工具任务应保存检查点、预算、待办与已确认动作；不要把所有状态寄托在一段自由文本里

**重点在这** ---- 长上下文减少切分损失，却增加成本与注意力管理；先做证据定位和预算，再把窗口当成能力使用

## 第四站：Prompt Caching 与成本控制

第四站是缓存仓库。相同的系统提示、工具说明和长文档不用每次全价搬家，Prompt Caching 可以帮你省力；但缓存不是保险箱，更不是替业务状态记账的管家。

**稳定前缀** ---- 把跨请求不变的内容放在前面，变化快的用户问题和工具结果放在后面；前缀一致性越高，缓存越容易命中

**适用场景** ---- 长系统提示、多工具 Agent、重复审阅同一份文档和批量处理同一套规则通常更值得缓存；短请求命中缓存的收益可能不值得增加复杂度

**缓存生命周期** ---- 关注 TTL、命中条件、计费规则、模型差异、失效策略与数据新鲜度；缓存命中不应绕过租户权限或删除要求

**缓存与多轮** ---- 可以缓存稳定文档和工具定义，但变化中的会话状态要保持清晰；不要为了命中率把用户私密信息拼进跨租户共享前缀

**成本账本** ---- 记录缓存写入、缓存读取、普通输入、输出、模型和任务类型；以真实流量计算节省，而不是只看单次 API 价格

**重点在这** ---- 缓存优化的是重复输入；上下文裁剪、模型路由和任务拆分仍然是控制成本的第一层

## 第五站：Tool Use 与 Agent 循环

第五站来到工具码头。Claude 会把“想查订单”写成一张工具单，但接不接单、查谁的订单、查完能不能发信，仍由你的服务端盖章；模型的请求不是权限通行证。

**工具定义** ---- 通过名称、描述和输入 schema 说明能力；描述要写清何时使用、何时禁止、参数含义、返回形状和权限限制

**工具调用块** ---- 模型返回工具名称、输入与调用 ID；服务端先聚合并校验完整参数，再决定是否执行

**工具结果块** ---- 执行结果、可读错误和来源信息回填模型；工具结果中的网页或文档内容要标记为不可信资料，不能覆盖系统规则

**工具分级** ---- 查询、计算和草稿生成可自动执行；发信、删改数据、执行命令、提交代码和付款需要确认、权限、幂等与审计

**循环停止** ---- 没有下一次工具请求、达到最大步数、超预算、超时、用户取消或人工拒绝时停止；模型宣称完成只是候选信号

**错误恢复** ---- 区分网络重试、参数修正、权限拒绝和业务不存在；让模型换策略，不让它靠重复请求撞穿安全门

**重点在这** ---- Tool Use 是“提出动作”，不是“获得权限”；每次执行都要回到服务端的身份、范围和业务状态检查

## 第六站：视觉、文件与结构化结果

第六站是视觉展厅。截图、图表和扫描件都能进场，但低清图片、糊掉的表格和没脱敏的合同不会因为模型会看就自动变清白；先布展，再请评审。

**图像输入** ---- 关注分辨率、裁剪、方向、文字大小、格式和压缩；先去除无关或敏感区域，减少成本也减少模型被噪声带跑

**文档与表格** ---- 让模型知道页面、表头、行列和图注关系；表格提取必须用程序校验数值，不能因为答案排版整齐就当作计算正确

**视觉任务流程** ---- 将观察、定位、分析、结论和不确定性分开；要求模型指出依据位置，便于人工复核

**结构化输出** ---- 用 schema 或输出工具约束分类、抽取和风险清单；服务端继续检查字段、范围、权限和业务规则

**缺失与不确定** ---- schema 应允许“无法判断”“资料不足”和“需要人工确认”；逼模型填满所有字段，是制造幻觉的快捷方式

**重点在这** ---- 多模态输入增加了信息渠道，也增加了隐私、成本和校验面；输入先治理，输出再自动化

## 第七站：可靠性、安全与平台治理

第七站是安全城门。Claude 自带一部分安全守卫，但限流、超时、越权、注入和敏感数据仍要你自己巡逻；把平台安全当全部安保，等于只装门牌不装门锁。

**错误与重试** ---- 对限流、过载、网络中断和暂时性服务错误使用有限退避；参数错误、权限拒绝和内容政策拒绝通常不应盲目重试

**并发与队列** ---- 为同步请求、流式任务和批处理分别设置并发与超时；长文档和 Agent 任务应有队列、状态查询和预算

**提示词注入** ---- 用户内容、网页、文档和工具结果都可能包含伪指令；分层传递外部资料，并在工具前后重新检查权限与参数

**数据政策** ---- 了解 API 数据保留、训练使用、区域、企业配置和敏感数据要求；合同与平台设置应由组织的合规流程确认

**日志与脱敏** ---- 保存模型、提示词版本、调用轨迹、token、延迟、错误和工具摘要；对个人信息、密钥、源代码和文档内容做最小化与脱敏

**评估与回滚** ---- 模型、提示词、缓存策略和工具变更都跑 golden 集；保留旧版本，质量下降时能快速切回

**重点在这** ---- 安全、成本和质量不是上线后的补丁，而是 Claude 适配层的一部分

## 第八站：场景练习

建议做三个由浅入深的项目：长文档审阅器、带只读工具的客服助手、带引用和人工确认的代码审查器。每个项目都记录模型、输入、输出、工具、错误、token、延迟和人工结论。

**长文档项目** ---- 使用结构化文档、证据定位、引用、上下文预算与缓存；测试跨页问题、表格、缺失信息和超长输入

**工具助手项目** ---- 实现工具定义、调用回填、错误重试、循环上限、权限和转人工；测试重复调用、越权参数和工具超时

**模型比较** ---- 与另一平台或另一档模型使用同一组任务对比；报告质量、成本、首 Token、完整延迟和失败类型

**交付证据** ---- 能完成基础多轮与流式调用；能解释内容块与长上下文；能使用缓存或其他手段控制重复输入；能完成 Tool Use 循环和结构化输出；能处理限流、超时、注入、隐私与回滚

## 通关标准

能完成 Claude 的多轮与流式调用；能解释消息内容块、长上下文、缓存和 Tool Use；能用结构化结果接入业务；能处理限流、过载、超时、注入、隐私、工具越权和模型回滚；能用固定任务集比较质量、成本与延迟。

## 结语

Claude 的强项像一间很大的工作室：长文档能摊开，代码能细看，工具能接上。但工作室越大，整理、权限和成本管理越不能靠“应该没事”。

把内容块、缓存、工具和评估这几根梁搭好，你得到的就不只是一次漂亮回答，而是一套能被复用、能被审计、能在换模型时保持体面的应用能力。
