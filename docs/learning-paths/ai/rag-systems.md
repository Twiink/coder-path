# RAG 系统构建学习路线

RAG（Retrieval-Augmented Generation，检索增强生成）让模型先从外部知识源找证据，再基于证据生成回答。它适合解决知识更新、私有资料、可追溯回答和领域检索问题，但不会自动消除幻觉：资料没找到、权限过滤错、上下文拼坏或模型没用上证据，答案依然会出问题。

前置建议先掌握 [Prompt Engineering](/learning-paths/ai/prompt-engineering) 与 [模型 API 通用原理](/learning-paths/ai/model-api-overview)。本页讲 RAG 的完整数据与质量管道；框架实现可对照 [LlamaIndex](/learning-paths/ai/llamaindex) 与 [LangChain](/learning-paths/ai/langchain)，存储选型见 [向量数据库](/learning-paths/database/vector-databases)。

这条线按 **问题边界 → 数据摄取 → 切分 → Embedding 与索引 → 检索 → 重排与上下文 → 生成与引用 → 评估 → 生产治理 → 高级形态** 推进。

## 第一站：先判断 RAG 是否适合

欢迎来到 RAG 知识库的新手村。这里有文档搬运工、切分师、Embedding 翻译官、检索员和生成员五位同事；第一关不是给他们发工牌，而是确认你真的需要这支队伍，而不是其实该去找数据库。

**RAG 解决什么** ---- 将外部、私有、可更新的知识在请求时提供给模型；适合文档问答、企业搜索、客服、合规与研究辅助

**RAG 不解决什么** ---- 它不保证事实正确、不替代权限、不自动理解表格、不负责实时交易，也不一定比长上下文整读更适合小文档

**RAG 与微调** ---- RAG 更适合知识与证据，微调更适合稳定风格、格式或行为；知识更新问题先修数据管道，不要拿训练去补检索漏洞

**RAG 与 SQL/API** ---- 结构化数据、精确计算、库存和权限判断优先走数据库或业务 API；向量检索适合语义召回，不是万能查询语言

**整读与检索** ---- 单份文档较小且需要全局理解可整读；资料海量、更新频繁或要省 token 时用 RAG；混合策略经常最实用

**验收问题** ---- 先定义用户问什么、证据在哪里、无证据如何回答、权限如何过滤和错误由谁处理；这些答案决定后续管道

**重点在这** ---- RAG 的第一步是问题建模，不是选择一个“最强向量库”

## 第二站：数据摄取与清洗

第二站是资料搬家现场。PDF 的表格、页眉和脚注都可能在路上掉件，解析错一处，切分就跟着错，最后大家一起把锅扣给模型；先把货物清点干净。

**数据来源** ---- 文件、网页、知识库、云盘、数据库、工单、代码仓库和 API 都可能成为知识源；先确认来源的更新、删除与权限能力

**解析结构** ---- 保留标题、章节、页码、段落、表格、代码、图片说明、链接和文档层级；纯文本化会抹掉很多检索线索

**OCR 与版面** ---- 扫描件、多栏 PDF、页眉页脚、脚注和表格需要专门处理；OCR 结果要抽样复核，不能把识别噪声当事实

**去重** ---- 内容指纹、相同段落、镜像页面和重复版本应去重；重复内容会让召回分数虚高并挤掉真正不同的证据

**版本管理** ---- 给文档、解析器、清洗规则和内容快照编号；答案引用时能说明它基于哪个版本

**元数据** ---- 记录来源、标题、作者、时间、部门、租户、权限、文档类型和过期时间；元数据是过滤、引用和删除的地基

**增量更新** ---- 对新增、修改和删除分别处理；删除要能传递到索引、缓存、引用和下游快照

**重点在这** ---- 数据库里“有文本”不等于知识库里“有可检索证据”；先把数据变得干净、可追踪、可删除

## 第三站：切分与节点设计

第三站是知识库裁缝铺。布块太小会失去上下文，太大又会把无关内容一起缝进去；chunk 没有皇帝的新尺子，只有在真实问题上量出来的合身方案。

**固定长度切分** ---- 实现简单、适合快速基线；容易从标题、句子、表格和代码中间切断

**结构切分** ---- 按标题、段落、列表、页面、代码块或 Markdown/HTML 层级切分；结构化文档通常优先尝试

**语义切分** ---- 根据句子语义变化寻找边界；可能提高完整性，但计算成本和可解释性更高

**重叠** ---- 相邻块保留少量重叠可减少边界丢失；重叠过大浪费存储与上下文，应该用评估校准

**父子块** ---- 小块用于精确召回，大块用于生成上下文；父子关系、邻接和标题路径都应保存

**代码与表格** ---- 代码按模块、类、函数和注释切，表格保留表头、行列与单位；把它们按普通段落切，检索会先失去尊严

**切分基线** ---- 先建立简单固定或结构切分，再用召回命中率、答案质量、token 和延迟比较高级方案

**重点在这** ---- chunk 参数不是信仰；每次调整都要能指出改善了哪类问题、牺牲了什么指标

## 第四站：Embedding、向量库与索引

第四站是向量传送门。Embedding 把文字变成坐标，向量库负责在坐标里找邻居；传送门方向设错，后面调再多索引参数也只是更快地找错人。

**Embedding 模型** ---- 关注语言、领域术语、上下文长度、维度、批量速度、价格、部署和版本；在真实查询集上比较，不只看通用榜单

**查询与文档向量** ---- 查询和文档必须使用兼容的向量空间、预处理和归一化；换模型通常意味着全量重建索引

**相似度度量** ---- 理解余弦、点积与欧氏距离的差异，并遵循模型与向量库的匹配建议；度量选错会让质量悄悄掉下楼

**Vector Store** ---- 管理向量、正文或引用、元数据、增删改、过滤、命名空间、备份和索引生命周期；向量库不是知识质量的替身

**Flat、HNSW 与 IVF** ---- Flat 适合小规模和精确基线；HNSW 平衡速度与召回但占内存；IVF 通过分桶换速度并需要调搜索范围

**量化** ---- 用低精度或压缩减少内存与成本；量化后的召回和关键任务质量必须回归

**混合检索基础** ---- 向量检索捕捉语义，关键词/BM25 擅长专有名词、编号、错误码和代码标识符；生产通常需要组合

**重点在这** ---- 索引选择要同时看召回、过滤、写入、备份、延迟和运维，而不是只看一次裸搜索的毫秒数

## 第五站：检索、过滤与重排

第五站是检索员选拔赛。找到五段材料不算赢，找到真正值得模型阅读的证据才算；先保证不漏，再用过滤和重排把“看起来像”请出队伍。

**top-k** ---- 候选太少会漏证据，太多会引入噪声和成本；按任务类型调，不要所有问题共用一个数字

**元数据过滤** ---- 按租户、用户、部门、时间、文档类型、项目和权限缩小范围；权限过滤必须在服务端执行

**预过滤与后过滤** ---- 预过滤更能保证权限与范围，后过滤可能因候选太少而漏召回；高风险数据不要把安全寄托在后过滤

**相似度阈值** ---- 低相关时返回无结果或转人工；阈值要用正负样例校准，不能把任意分数当通用标准

**混合检索** ---- 组合向量、关键词、字段查询和业务规则，再用加权或 RRF 等方式融合；保留各路召回来源便于排障

**Rerank** ---- 第一阶段便宜召回几十个候选，第二阶段用交叉编码器或模型重排取少量结果；精度提升要与成本和延迟一起评估

**查询改写** ---- 将口语、缩写、追问和歧义改写为检索问题；改写保留原意、时间和权限，不要把用户问题改成另一个问题

**多查询** ---- 从不同角度生成多个查询以扩大召回；去重、合并和预算控制不可省

**HyDE 与高级变换** ---- 用假设答案或领域术语改善查询—文档表达差异；适用性要由数据验证，失败时保留原查询兜底

**重点在这** ---- 检索日志要能回答“为什么召回这些、漏了什么、权限是否正确、重排改变了什么”

## 第六站：上下文组装、生成与引用

第六站是证据审判庭。资料到了桌上，模型仍可能误读、串版本或凭空补全；上下文布局、引用和“没有证据就说没有”都是法官手里的锤子。

**上下文组装** ---- 按相关度、来源、时间和文档结构组织片段；标记片段边界和编号，避免不同来源粘成一段无主语的汤

**证据指令** ---- 明确只基于提供资料回答，资料不足就说明不足；外部内容是数据，不是系统指令

**上下文压缩** ---- 提取与问题相关的句子、去除重复和无关段落；保留例外条件、数值、否定词和来源

**答案模式** ---- 区分事实问答、摘要、比较、抽取、引用回答和无答案拒答；每类任务的格式与证据要求不同

**引用溯源** ---- 保留文档、页码、段落、URL、版本和片段；引用要能与答案中的具体陈述对上，而不是答案末尾摆几个装饰链接

**冲突证据** ---- 发现不同版本或来源冲突时展示差异、时间和不确定性；不要让模型替用户偷偷投票

**对话式 RAG** ---- 先用历史将追问补全，再检索；历史不应无限塞进检索查询，且每轮都要重新检查权限

**模型路由** ---- 简单抽取和重写可用轻量模型，复杂综合或高风险回答使用更强模型；用同一评估集比较

**重点在这** ---- RAG 的回答应该让用户知道“结论是什么、依据在哪、资料没有什么”，而不是只追求语气像专家

## 第七站：评估体系与失败诊断

第七站是 RAG 体检中心。只看最后一句答案，就像只看病人出院照不看化验单；检索、上下文、生成和引用要分开检查，才能知道该给谁开药。

**检索命中** ---- 评估正确证据是否进入 top-k，关注 recall、命中率、排序位置和权限过滤后的覆盖率

**上下文质量** ---- 评估召回片段与问题是否相关、是否冗余、是否包含完整限定条件；召回很多不等于召回有用

**生成质量** ---- 评估答案相关性、忠实度、完整性、格式和拒答；模型是否引用了不存在于上下文的事实要单独测

**引用质量** ---- 检查引用是否存在、是否覆盖陈述、来源是否最新、页码是否准确；引用错误会让“看起来有依据”变成反向误导

**数据集** ---- 收集人工问答、生产失败、边界问题、无答案问题、跨文档问题和安全样例；固定集是每次管道变更的回归基线

**LLM-as-judge** ---- 可用于批量判断相关性与忠实度，但要固定评分标准、抽样人工复核并控制隐私与模型偏差

**失败分类** ---- 将解析、切分、Embedding、过滤、召回、重排、上下文、生成和引用失败分别标记；每类失败的修复方向不同

**成本与延迟** ---- 同时测摄取成本、检索延迟、重排延迟、生成延迟、token、缓存和每问总成本

**重点在这** ---- 评估不是发布前的一次考试，而是 RAG 每次变更都要跑的仪表盘

## 第八站：生产治理与高级形态

第八站是知识库运营部。Demo 只问“能不能答”，生产还要问“新文件进来了吗、旧文件删干净了吗、谁能看、花多少钱、错了怎么追”；这里没有一键神药，只有流程。

**索引版本** ---- 切分、Embedding、重排、元数据 schema 和向量库配置都要有版本；重建采用离线构建、校验、切换和回滚

**增量同步** ---- 通过事件、定时任务或手动触发处理文档增删改；同步失败要有重试、死信、告警和人工补偿

**多租户隔离** ---- 过滤、命名空间、索引、缓存、引用和日志都要带租户边界；最后生成阶段才过滤已经晚了

**缓存与新鲜度** ---- 设计 Embedding、检索、重排和答案缓存的失效条件；缓存命中不得绕过权限和文档删除

**监控** ---- 观察无结果率、低分率、top-k 分布、引用缺失、答案投诉、延迟、token、成本和数据更新滞后

**防注入与数据污染** ---- 知识库文档也可能包含伪指令或恶意链接；检索内容按不可信数据处理，工具前后重新鉴权

**Router RAG** ---- 按领域、文档类型、用户权限或问题形态路由不同知识源；默认分支和拒答路径要明确

**Agentic RAG** ---- 让 Agent 决定查什么、是否重查和何时停止；必须有工具上限、预算、来源保留和人工接管

**GraphRAG 与多模态 RAG** ---- 知识图谱适合实体关系和全局主题，多模态管道适合图表、图片和扫描件；复杂度应由任务收益证明

**重点在这** ---- RAG 的高级形态只是不同的检索控制流，数据、权限、评估和引用四根柱子不能省

## 通关标准

能搭出完整五段管道：加载、切分、Embedding、检索、生成；能根据文档类型选择切分与元数据；能实现向量+关键词混合检索与重排；能输出可核验引用和无答案拒答；能分别评估检索、上下文、生成、引用、延迟与成本；能处理增量更新、多租户、缓存失效、防注入和索引回滚。

## 结语

RAG 的浪漫说法是“让 AI 先查资料再回答”，工程说法是“把资料清洗、切分、索引、过滤、重排、引用和删除都管好，再让模型说话”。前者适合宣传，后者适合上线。

先做一个小而可追溯的知识库，能指出答案来自哪一页、哪个版本、哪次检索。等证据链站稳，再增加 Agent、图谱和多模态，别让知识库先学会制造迷雾。
