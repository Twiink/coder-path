# 向量数据库学习路线

**向量数据库存储的不是文字,是"语义"**:它存 **Embedding 向量**(文本/图片/音视频经模型映射成的"语义指纹"),并按**相似度**检索——能搜"意思相近"而不仅是"字面相同"。它是 **RAG(检索增强生成)、语义搜索、推荐、去重与多模态检索**的核心基础设施,也是 2023 年 AI 浪潮里最热闹的赛道之一(FAISS/Chroma/pgvector/Milvus/Qdrant/Pinecone……)。**先摆正认知**:它不是"数据库界的革命",而是"**擅长相似检索的专用存储**"——事务、复杂查询还是交给关系库;它常与主库并行(业务数据在 PostgreSQL,向量副本在向量库/或直接 pgvector 同库)。框架接入见 [RAG](/learning-paths/ai/rag-systems) 与 [LlamaIndex](/learning-paths/ai/llamaindex),本页讲原理与选型。

这条线按 **概念基础 → 相似度与 ANN → 索引类型 → 工程操作 → 产品家族与选型 → 高级话题 → 应用** 推进。

## 第一站:概念基础——向量与相似度

**Embedding 是什么**:把文本/图片映射成**高维向量(数百到数千维)**,关键性质:**语义相近的内容,向量在空间中距离也近**("苹果"和"iPhone"的向量比和"香蕉"近?实际:苹果-水果 vs 苹果-公司 的歧义由上下文决定——embedding 质量决定检索质量)。**三个相似度度量(按库选对)**:①**余弦相似度(文本检索事实标准**:只比方向不比长度,对 embedding 范数差异不敏感);②**点积**(向量归一化后与余弦等价;FAISS 的 IP metric 常用);③**欧氏距离(L2)**(比绝对距离——某些模型/场景更合适);**选错度量 = 检索质量莫名下降**(多数库默认余弦,改用前看 embedding 模型的推荐度量)。**为什么不能靠暴力比对**:1000 万条 × 1536 维的线性扫描在毫秒级要求下不可行——所以向量库的核心是 **ANN(近似最近邻)**:**"足够好、足够快"的近似**是这门技术的灵魂——索引与精度/速度/内存的三角权衡贯穿本页。

## 第二站:索引类型——选型的第一知识

**索引家族(面试必考,理解 trade-off)**:①**Flat(暴力全量)**:精确但慢——小数据集(几万条)/高精度要求/建立质量基线用;②**IVF(倒排文件)**:先聚类(如 1000 桶)分桶,搜索只进最近的几个桶——**快很多,召回略降**;训练(聚类)需要数据,nprobe 参数(查几个桶)调速度与召回;③**HNSW(分层小世界图,当前主流默认)**:构建多层图,搜索从高层粗跳到低层精搜——**召回/速度/内存三者的最佳平衡,内存占用高**(图结构常驻);参数:M(每节点连接数)、efConstruction/efSearch(构建与搜索的候选队列——越大越准越慢);④**PQ(乘积量化)**:把向量切段各自聚类,用"簇中心 ID"压缩存储(内存可降 10 倍+)——**精度换空间,大库标配**;**生产组合拳:IVF-PQ / HNSW-PQ**(图/倒排负责"快",量化负责"省")——**千万级以上、内存紧张时的标准姿势**;**量化变体**:标量量化(int8)比 PQ 简单粗暴、常用作第一档压缩。**选型经验**:起步数据小直接 Flat/HNSW;预计百万级用 HNSW(内存够)或 IVF-PQ(内存紧);量化后**务必用你的数据压测召回率**再上线。

## 第三站:工程操作——CRUD 之外的门道

**基本操作**:upsert(写入带 id+向量+payload)、按 id 删除/更新、相似搜索(top_k)。**Metadata 过滤(生产第一能力)**:**向量相似 + 标量条件 一起查**("在 2024 年合同里找语义最像的")——实现方式三种:**pre-filter(先按条件过滤再向量搜索:结果精确但可能慢/过滤后数据太少)**、post-filter(先搜 top-k 再滤:**快但可能滤完不够 k 条——漏召回**)、库内优化(如 Qdrant 的过滤感知搜索:兼顾两者)——**选库时"过滤性能"是比"裸向量速度"更重要的指标**(真实业务全是带条件的搜索);**多租户隔离**也靠过滤(tenant_id 必带——**忘了过滤 = 数据串租户**)。**批量与吞吐**:批量 upsert(比单条快一个量级)、写入时关刷新/合并段(类 ES 思路,批量导入完再建索引)、并发读。**持久化与备份**:纯内存索引(FAISS/部分 HNSW)要自己管理落盘与加载;**重启恢复**(WAL/快照)与备份策略是选型问题(自管 vs 托管库);**增量更新**:upsert 对 ANN 索引的代价(删除是"标记墓碑"、图结构增量插入会劣化——**定期重建索引(如每周)是常规运维**,批量导入比持续小写入对索引更友好)。

## 第四站:产品家族速览——各怀绝技

**按形态分三类**:①**库(嵌入你的应用,非独立服务)**:**FAISS(Facebook/Meta 开源:性能天花板、索引类型最全——但它只是索引库:持久化/过滤/多租户要自己造,适合懂行的自建)**;Chroma(本地轻量、开发者友好——**原型与教学首选**,生产慎用);②**扩展(挂靠现有库)**:**pgvector(PostgreSQL 扩展——事务、SQL、过滤、备份全继承;中小规模 RAG 的"最优解"之一,少一个组件少一份运维)**、Elasticsearch 的 dense_vector(已有 ES 生态要混合检索时——见 [Elasticsearch](/learning-paths/middleware/elasticsearch))、Redis(轻量场景);③**专用数据库(独立服务,大规模/生产)**:**Qdrant(Rust,性能好、过滤能力强、易自托管——社区口碑与易用性佳)**、**Milvus(分布式云原生架构:十亿级、分片与多副本——大规模检索的事实标准之一)**、Weaviate(混合搜索+GraphQL 原生)、Pinecone(全托管 SaaS:零运维、自动扩缩——不想碰运维的团队)。**选型决策树**:原型 → Chroma/FAISS;已有 PostgreSQL → pgvector(先跑通再考虑迁移);已有 ES → 其向量能力;数据百万级以内+要控制 → Qdrant 自托管;**千万级/分布式 → Milvus;要托管省心 → Pinecone/Qdrant Cloud**;**最终用你的数据压测**(召回@10、P95 延迟、成本),别信榜单与博客。

## 第五站:高级话题

**①降维**:PCA 把 1536 维压到 256/512——省内存提速,**精度损失明显,先用 embedding 模型自带的低维输出(很多模型支持 matryoshka 降维,比事后 PCA 好)**;**②量化压缩(成本优化主流)**:int8 标量量化(存储降 4 倍,精度微损)+ PQ(更高压缩)——**"先量化跑通,精度不够再升档"是省钱路线**;③**混合检索(向量 + 全文 BM25)**:语义 + 关键词互补(专有名词/代码靠关键词)——库原生 hybrid(Qdrant/Weaviate/ES)或自融合(RRF 倒数排名融合最稳,见 [RAG](/learning-paths/ai/rag-systems) 混合检索节);④**分片与副本**:专用库的横向扩展(按 id 分片/副本容错——Milvus 的架构);⑤**冷热与成本**:热数据内存索引、冷数据量化/磁盘;⑥**一致性**:向量库与源库的同步(业务数据删了向量库还留着——**删除同步是 RAG 数据治理常被忽略的一环**,靠应用双写/事件驱动)。

## 第六站:应用场景与学习路径

**核心场景**:①**RAG**(检索增强生成——向量库在其中的角色就是"存储与召回",完整方法论见 [RAG 系统](/learning-paths/ai/rag-systems));②**语义搜索**(站内搜索/企业搜索:混合检索已经是标配);③**去重与聚类**(相似内容合并:新闻/商品去重——向量相似度阈值);④**推荐**("相似商品":以物品向量找近邻);⑤**多模态**(图片/文本同一向量空间(CLIP 类模型)——图搜文、文搜图);⑥异常检测(离群向量)。**学习路径**:先在 Chroma/pgvector 上手(插入→搜索→过滤 半小时跑通)→ 用 RAG 框架把它接进问答(见 [LlamaIndex](/learning-paths/ai/llamaindex))→ 理解索引(Flat→HNSW→量化,自己数据压测召回)→ 生产化(过滤/批量/持久化/监控)→ 按规模选型。**配套必学**:Embedding 模型怎么选(决定检索质量上限——开源 BGE/M3E(中文)/闭源;评估同 [RAG](/learning-paths/ai/rag-systems) 评估章)。

## 通关标准

能独立做到:解释 Embedding 与余弦相似度,并在给定模型时说出该用哪种度量;画出 Flat/IVF/HNSW/PQ 的 trade-off 并给出"百万级内存紧张"的推荐组合;实现带元数据过滤的检索并解释 pre/post-filter 的漏召回风险;根据"数据量/是否已有 PG/运维预算/是否要混合检索"给出选型并说出理由;用自己数据跑过召回@10 与延迟压测——向量数据库主线通关。

向量数据库是"AI 应用的水管":不性感,但 RAG/语义搜索全靠它。学它的正确姿势是**原理(ANN/索引)与工程(过滤/量化/选型)并重**——网上教程总在比"哪个库好",而真正的分水岭是:你懂不懂 HNSW 的参数、会不会量化、敢不敢用真实数据压测。把本页的选型树和 [RAG](/learning-paths/ai/rag-systems) 的评估方法组合起来,你就能为任何"语义检索"需求给出有依据的架构,而不是追着新库跑。下一步:回 [RAG](/learning-paths/ai/rag-systems) 把向量库放进完整管道,或学 [LlamaIndex](/learning-paths/ai/llamaindex) 的开箱即用。
