# 向量数据库学习路线

向量数据库保存 Embedding 向量与元数据，并按相似度召回内容。它是 RAG、语义搜索、推荐、去重和多模态检索的重要基础设施，但不是“懂语义的万能数据库”：事务、复杂业务规则和权威事实仍应由关系库或业务服务负责。

前置建议先读 [RAG 系统](/learning-paths/ai/rag-systems) 了解向量库在完整管道中的位置，再看 [LlamaIndex](/learning-paths/ai/llamaindex) 或 [LangChain](/learning-paths/ai/langchain) 的接入方式。本页重原理、权衡、过滤和运维，不绑定某个产品版本。

这条线按 **向量与相似度 → ANN 索引 → 元数据与 CRUD → 产品形态 → 混合检索 → 压缩与扩展 → 评估与运维 → 选型项目** 推进。

## 第一站：Embedding 与相似度

欢迎来到向量数据库的坐标城。Embedding 把句子变成坐标，数据库负责给邻居排队；但如果地图画歪了，后面把快车换成高铁，也只是更快地把你送到错误街区。

**Embedding** ---- 将文本、图片或其他内容映射为高维向量，使相似内容在空间中更接近；质量取决于模型、数据、语言、领域与预处理

**查询与文档空间** ---- 查询向量与文档向量必须来自兼容的模型、版本、归一化和预处理；更换模型通常需要重建索引

**余弦相似度** ---- 比较向量方向，常用于语义文本检索；适用性要遵循 Embedding 模型的建议与真实测试

**点积** ---- 计算向量内积，归一化后可与余弦相近；索引库的 metric 配置要与训练和预处理匹配

**欧氏距离** ---- 比较绝对空间距离，在某些模型或数值场景适用；不能因为某个库默认它就直接使用

**向量维度** ---- 维度影响存储、计算、索引与质量；更高维不是自动更准确，先看模型输出与任务回归

**重点在这** ---- 向量库只能在 Embedding 建立的空间里做近邻搜索；如果空间没有表达你的业务语义，换索引救不了它

## 第二站：精确搜索与 ANN 索引

第二站是索引赛车场。百万个向量不可能每次都挨个握手，于是 Flat、IVF、HNSW 和量化选手登场；它们比的不是谁最会喊快，而是谁在速度、召回和内存之间少撒谎。

**Flat** ---- 全量计算，结果精确，适合小数据、质量基线和高精度对照；规模变大后延迟线性增长

**IVF** ---- 先把向量分桶，查询只搜索部分桶；训练与桶数、搜索范围、更新和召回之间需要调参

**HNSW** ---- 用分层图快速探索近邻，通常在速度与召回间平衡较好；构建、内存和动态更新成本要关注

**PQ** ---- 将向量压缩为量化编码以节省空间；适合大规模或内存紧张场景，但需要验证召回与关键任务质量

**混合索引** ---- IVF-PQ、HNSW 结合量化等方案可以同时追求速度与空间；组合越复杂，调优、重建与故障恢复越需要工程化

**参数调优** ---- 记录索引参数、数据规模、硬件、召回率、P95 延迟与内存；不要只在玩具数据上调出漂亮数字

**重点在这** ---- ANN 的“近似”不是缺陷，而是可调的工程预算；生产要知道你为多少速度牺牲了多少召回

## 第三站：写入、更新、删除与过滤

第三站是数据库办事大厅。用户很少只说“找最像的五条”，通常还会附带租户、日期、部门和权限；不会过滤、删除和隔离，向量库就会把隔壁家的文件热情递过来。

**记录结构** ---- 一条记录通常包含 ID、向量、正文或引用、元数据、版本与时间；正文和权威业务数据可放主库，向量库保存必要副本

**Upsert** ---- 通过稳定 ID 写入或覆盖向量与元数据；设计重复写入、并发更新和失败重试的语义

**删除** ---- 文档撤回、租户删除和权限变化要同步删除或标记向量、缓存与索引；“主库删了”不等于检索结果立即消失

**Metadata Filter** ---- 按租户、用户、部门、日期、类型、项目和版本过滤；过滤条件由服务端构造或校验，不能完全信任模型

**Pre-filter** ---- 先按条件缩小候选再做向量搜索，范围与权限更清晰；过滤过窄时需要处理结果不足

**Post-filter** ---- 先取近邻再过滤，简单但可能过滤后没有足够结果，造成漏召回；高风险隔离不应只依赖它

**批量写入** ---- 批量 Embedding 与 upsert 通常比逐条写更高效；导入、刷新与索引构建要考虑一致性与恢复

**重点在这** ---- 过滤性能和删除语义往往比裸向量速度更影响生产质量；忘记 tenant_id 是最短的安全事故路线

## 第四站：产品形态与选型地图

第四站是产品相亲角。每个向量库都说自己又快又稳，但真正要问的是：你有多少数据、已有哪套基础设施、谁来运维、怎么备份、预算多少；榜单不能替你值夜班。

**嵌入式索引库** ---- 适合单机实验、离线任务和完全自管；持久化、过滤、服务、多租户和备份需要自己负责

**轻量本地存储** ---- 适合教学、原型和小规模应用；上线前确认并发、升级、备份和权限能力是否足够

**关系库扩展** ---- 已有 PostgreSQL 时可用 pgvector 等方案复用事务、SQL、权限与备份；规模和检索吞吐到达边界后再评估专用库

**搜索引擎向量能力** ---- 已有全文检索、字段过滤和日志生态时可考虑；混合检索与运维统一通常是主要收益

**专用向量数据库** ---- 适合需要独立扩展、过滤、分片、副本和向量特性的团队；要评估部署、升级、监控和数据迁移

**托管服务** ---- 省去部分运维并支持弹性，但要核对数据区域、成本、锁定、网络、权限、备份与供应商故障策略

**选型维度** ---- 数据量、增长速度、向量维度、更新频率、过滤复杂度、召回目标、P95、并发、托管预算和团队技能共同决定答案

**重点在这** ---- 先用最少组件跑通并测量，再在真实瓶颈出现时迁移；少一个无必要的分布式系统，通常就是少一份夜间报警

## 第五站：混合检索与高级召回

第五站是检索双打赛。向量选手擅长“意思差不多”，关键词选手擅长“这个编号一个字不能错”；生产队伍通常要让它们搭档，再请时间和权限当边裁。

**BM25 与全文** ---- 适合专有名词、错误码、型号、代码标识符和精确短语；它与向量召回是互补，不是替代

**结果融合** ---- 通过分数归一化、加权或 RRF 等方式合并多路结果；保留来源和原始分数，便于解释融合结果

**过滤与路由** ---- 先按问题领域、时间、租户、权限或文档类型选择搜索空间；分区越清晰，候选越少，错误也越容易定位

**多向量** ---- 一份文档可以为标题、摘要、正文、图片说明或假设问题建立多种表示；更新、删除和引用要能追溯到同一原文

**重排** ---- 向量或关键词先召回候选，再用交叉编码器或模型按查询相关性重排；向量库常负责召回，重排通常在上层完成

**MMR 与去重** ---- 在相关性之外增加多样性，避免 top-k 全是同一段话的不同切片；多样性过高也可能漏掉关键重复证据

**重点在这** ---- 先做可解释的多路基线，再逐步增加重排和多向量；高级检索必须用失败样例证明价值

## 第六站：压缩、扩展与一致性

第六站是运维健身房。原型只问“搜得到吗”，生产会追问“存得下吗、写得快吗、旧数据删了吗、挂了能回来吗”；索引也要参加耐力训练。

**标量量化** ---- 用低精度保存向量，通常比复杂压缩更容易落地；先测精度与过滤行为，再追求更高压缩

**降维** ---- 模型原生支持的可伸缩维度通常比事后粗暴降维更可控；任何降维都要跑自己的召回回归

**分片与副本** ---- 关注数据分布、查询路由、故障转移、重平衡与一致性；分布式不是把数据切开就完成了

**写读一致性** ---- 文档更新后，主库、Embedding、向量索引、缓存与引用可能短暂不同步；明确最终一致窗口与用户体验

**索引重建** ---- 大量删除、模型升级、切分变化和碎片积累可能需要重建；采用新旧索引并行、校验后切换并保留回滚

**备份恢复** ---- 备份向量、元数据、索引配置、Embedding 版本与源文档关系；只备份裸向量，恢复后可能无法解释来源

**冷热分层** ---- 热数据使用低延迟索引，冷数据使用压缩或磁盘方案；查询路由、迁移与新鲜度要有明确规则

**重点在这** ---- 生产向量库的核心资产是“向量 + 元数据 + 来源 + 版本 + 可恢复流程”，不只是一个大数组

## 第七站：评估、监控与安全

第七站是指标体检室。P95 很漂亮但召回了错误租户，仍然是医疗事故；召回、权限、新鲜度、延迟和成本必须一起量，不能只给速度拍写真。

**召回指标** ---- 评估 recall@k、命中率、排序位置、过滤后覆盖率和无结果率；使用人工标注或可靠的 golden 查询集

**延迟指标** ---- 看 P50、P95、P99、并发、冷启动、写入和索引构建时间；平均延迟容易把长尾藏起来

**更新指标** ---- 观察摄取滞后、删除生效时间、失败重试、重复写入和索引重建进度；知识新鲜度是 RAG 的产品指标

**成本指标** ---- 记录存储、内存、Embedding、读写、备份、网络和托管费用；按租户或项目核算，避免“大库很便宜”的错觉

**权限安全** ---- tenant_id、资源级 ACL、命名空间、过滤器和缓存键必须一致；检索结果返回前再次检查权限

**数据治理** ---- 删除、保留、脱敏、区域、日志与引用策略覆盖向量、正文、元数据和备份；向量也可能泄露敏感语义

**故障演练** ---- 测试节点故障、索引损坏、备份恢复、网络中断、写入重复和过滤错误；恢复时间与数据丢失窗口要可量化

**重点在这** ---- 把向量库当生产存储治理，而不是把它当一块永不坏的缓存

## 第八站：应用项目

建议做一个带权限的知识库检索基准：使用同一批文档与查询，比较 Flat、HNSW、量化、向量检索、关键词检索和混合检索，报告召回、P95、内存、成本与更新行为。

**基础练习** ---- 完成向量写入、相似搜索、稳定 ID 更新、删除和元数据过滤；为无结果与错误参数写测试

**进阶练习** ---- 加入混合召回、重排、引用、租户隔离和增量更新；对比不同索引参数的质量与延迟

**生产练习** ---- 做一次索引版本切换与恢复演练；验证删除、缓存失效、备份和权限在故障后仍然成立

**交付证据** ---- 能解释 Embedding、距离度量、Flat、IVF、HNSW 与量化；能实现带过滤的检索并说明预/后过滤风险；能按规模、已有基础设施、数据边界和运维预算做选型；能用真实数据报告 recall@k、P95 和成本

## 通关标准

能解释 Embedding、距离度量、Flat、IVF、HNSW 与量化；能实现带过滤的检索并说明预/后过滤风险；能按规模、已有基础设施、数据边界和运维预算做选型；能用真实数据报告 recall@k、P95、内存和成本。

## 结语

向量数据库像 AI 应用的地下水管：平时不抢镜，堵了、串租户或停水时全公司都能记住它。真正的能力不是会调用一次相似搜索，而是知道它为什么召回、如何过滤、怎样更新、坏了怎么恢复。

先用小数据跑出基线，再用真实查询调索引、混合检索和过滤。别被“毫秒级”迷住，能把正确资料在正确权限下稳定送到模型面前，才是向量库的毕业照。
