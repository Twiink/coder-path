# AI Agent 开发进阶学习路线

[AI Agent 基础](/learning-paths/ai/agent-basics) 讲清了模型、工具、状态和循环；这一页解决“怎么把它做成生产系统”。重点是工具契约、工作流、状态恢复、评估、安全、部署和成本，而不是再堆一层听起来很聪明的提示词。

Agent 框架和平台迭代很快，本页优先讲工程模式。裸 SDK、LangChain、LangGraph、MCP、各家 Agent SDK 都可以替换，超时、权限、幂等、评估和审计这些老朋友不会因为换了名字就消失。

这条线按 **调用工程化 → 工具工程 → 工作流编排 → 状态与记忆 → RAG → 评估 → 部署观测 → 安全 → 进阶架构** 推进。

## 第一站：把模型调用工程化

欢迎来到 Agent 的工程训练营。新兵先学会把一次模型调用安全送达：有超时、有账单、有追踪、还能取消；别刚学会喊“调用工具”就让它连续跑十圈马拉松。

**客户端封装** ---- 统一端点、模型、消息、超时、取消、重试、错误分类、请求 ID 和用量；供应商 SDK 不应渗透到业务层

**流式输出** ---- 区分文本增量、工具事件、状态事件和最终结果；前端可以先显示，业务入库必须等完成与校验

**结构化输出** ---- 用 schema、解析器和服务端验证约束分类、计划、工具参数与最终报告；格式通过不代表事实正确

**错误分类** ---- 区分参数、认证、限流、过载、网络、超时、解析、安全拒绝和业务错误；重试与降级要按类型处理

**异步与并发** ---- 模型调用和工具调用多为 I/O；使用异步、并发上限、取消、背压和连接池，但先确认下游能够承受

**用量记账** ---- 每次调用保存模型、输入输出 token、缓存、耗时、任务类型和错误；Agent 的成本通常藏在循环次数里

**重点在这** ---- 把模型当不稳定的外部服务，而不是一个永远成功的本地函数

## 第二站：工具工程与执行边界

第二站是工具铸造厂。每把工具都要有名字、说明书、保险丝和责任人；工具越多不一定越能干，可能只是让模型在工具架前选择困难症发作。

**单一职责** ---- 一个工具完成一个可命名、可测试的动作；复杂业务流程拆成由代码控制的步骤，不要让一个万能工具吞掉所有责任

**描述即路由** ---- 说明何时用、何时不用、参数含义、返回形状、错误和限制；模型靠描述选择工具，人类靠描述做审查

**参数 schema** ---- 约束类型、必填、枚举、范围、格式与默认值；schema 之后继续做用户、租户、资源和业务状态校验

**执行包装器** ---- 统一超时、重试、日志、结果截断、脱敏、错误码和追踪；工具内部异常不能直接变成用户堆栈

**只读与写入** ---- 查询、计算和草稿是低风险类别；写库、发信、下单、删除、执行命令和发布要有确认、幂等与审计

**幂等** ---- 为会创建或修改资源的动作设置幂等键、去重和查询状态；模型重试不是罕见事件，是设计前提

**结果契约** ---- 区分模型摘要、用户产物、业务状态和审计证据；超长结果应分页、摘要或按需读取

**重点在这** ---- 工具层决定 Agent 的真实上限；模型可以建议，执行器才是最后的门卫

## 第三站：工作流与编排

第三站进入交通指挥中心。红绿灯、金额校验和权限判断别交给一位语言模型临时发挥；确定的路写死，真正需要判断的岔路再请模型上岗。

**Pipeline** ---- 固定的数据处理、分类、检索、校验和模板回复用线性流程；简单、便宜、容易测试

**状态图** ---- 有分支、循环、暂停、恢复、审批或长任务时显式建模节点、边和共享状态；状态图比一段超长 prompt 更可维护

**自由 Agent 循环** ---- 适合工具不固定、任务开放、需要动态选择下一步的场景；必须加入步数、预算、超时和重复检测

**路由** ---- 按意图、领域、权限、风险或成本选择流程与模型；稳定规则优先代码，模型路由需要默认与拒答分支

**计划—执行** ---- 先生成有限计划，再执行和验证；计划允许重排，但不要每个小动作都全量重规划

**并行与汇总** ---- 独立检索、评审和子任务可并行；汇总时处理部分失败、重复、冲突、排序和证据保留

**多 Agent** ---- 只有当角色权限、上下文或专业边界确实需要隔离时使用；否则单 Agent 加好工具通常更简单

**重点在这** ---- 编排解决信息流与控制流，不负责替你定义业务真相

## 第四站：状态、记忆与长任务

第四站是长任务车站。列车可能断网、晚点、换司机甚至重启，但到站时系统仍得知道哪些货已经卸下；状态要记录事实，不要只保存模型上次的工作感言。

**会话状态** ---- 保存近期消息、摘要、用户问题和工具结果；有过期、删除和租户隔离策略

**任务状态** ---- 保存目标、计划、步骤、审批、失败、产物和当前节点；结构化字段供程序判断，原始轨迹供审计

**长期记忆** ---- 只写入值得长期复用且经过筛选的事实、偏好或经验；敏感信息、错误结论和短期噪声不应自动永久化

**检查点** ---- 在关键节点保存可恢复状态、版本、输入摘要和副作用状态；恢复前确认工作区、权限和外部资源仍有效

**队列与 worker** ---- 分钟级任务进入后台队列，支持状态查询、事件、重试、取消和死信；不要让 HTTP 请求一直等

**补偿与回滚** ---- 取消或失败后查询已执行的副作用，执行补偿或进入人工处理；文件和数据库操作也需要恢复策略

**重点在这** ---- 会话记录“模型看到了什么”，任务状态记录“业务做了什么”，两者都要能解释和恢复

## 第五站：RAG 与外部知识整合

第五站是知识仓库。RAG 是一把好用的扳手，却不是能拧所有螺丝的万能锤；订单、库存和精确统计有自己的工具，别让向量检索去兼职财务。

**上下文注入** ---- 每轮把相关资料放入上下文，适合知识问答和证据密集任务；要控制长度、权限与引用

**检索工具** ---- 将知识库作为 Agent 工具，允许它决定何时查、查什么和是否重查；适合知识只是任务一部分的流程

**结构化查询** ---- 订单、库存、财务和统计优先使用数据库或业务 API；精确计算不要交给向量近邻

**权限感知检索** ---- 按用户、租户、项目、时间和文档权限过滤；工具结果回填前后都要检查，不要最后才过滤

**引用与版本** ---- 保留来源、页码、文档版本、时间与片段；证据不足时拒答或转人工

**检索评估** ---- 分开测召回、相关性、重排、答案忠实度、引用准确性、无答案和成本；详见 [RAG 系统](/learning-paths/ai/rag-systems)

**重点在这** ---- RAG 提供证据，Agent 决定是否使用证据；权限和数据质量不能由模型兜底

## 第六站：评估与回归

第六站是期末考场，而且监考老师会看草稿。Agent 偶尔答对不算满分：它可能选错工具、越权、绕远路，还顺手花掉十倍 token；过程轨迹也要交卷。

**Golden 数据集** ---- 覆盖正常、边界、无答案、冲突、长上下文、工具错误、注入、权限与取消；从真实失败样本持续补充

**任务成功率** ---- 目标达成、验收通过、需要人工返工和回归缺陷是核心指标；让“成功”有可观察定义

**轨迹指标** ---- 工具选择、参数正确率、步骤数、重复调用、停止时机、权限拒绝与验证完整度；轨迹比最终文字更能揭露问题

**质量评审** ---- 人工、规则、LLM-as-judge、成对比较和业务指标组合使用；高风险结果不只依赖模型评审

**在线反馈** ---- 观察重问、编辑、转人工、投诉、任务取消、审批拒绝与实际业务结果；用户点赞只是一个信号

**回归门禁** ---- 修改模型、提示词、工具、检索、状态或框架后跑固定任务；质量下降、成本超标或安全失败应阻止发布

**重点在这** ---- 评估不是给 Agent 颁奖，而是尽早告诉你它在哪些边界会犯错

## 第七站：部署、监控与成本

第七站来到生产车间。模型、工具、队列、状态和追踪要像流水线一样接好；在线请求、流式任务和离线批处理不能都挤在同一个小窗口里排队。

**同步接口** ---- 适合短请求，设置整体 deadline、并发与输出上限；超时要返回可理解状态

**流式接口** ---- 适合聊天和长回答，事件要可重放或可恢复；工具和审批状态也要对前端可见

**异步任务** ---- 适合长研究、代码修改、批量文档和多步工作流；提供任务 ID、状态、进度、取消与结果领取

**监控指标** ---- 任务成功率、P50/P95、工具错误率、循环步数、token、单任务成本、队列、人工接管和安全事件

**模型路由** ---- 简单分类、抽取和路由用轻量模型，复杂推理用强模型；路由本身要有回归和预算

**缓存与批量** ---- 对稳定提示、Embedding、检索和重复任务缓存；离线评估与生成使用批处理；缓存要包含权限和版本

**灰度与熔断** ---- 新模型或新工具按比例放量；连续错误、成本异常或安全风险触发熔断与降级

**重点在这** ---- Agent 的成本方差比普通请求大，必须按任务设置预算，而不是只看月度平均数

## 第八站：安全纵深

第八站是安全闸门。Agent 一句话就可能触发多次调用、改数据甚至发邮件，因此每道门都要查身份、范围和审批；“模型说它很确定”不是门禁卡。

**提示词注入** ---- 用户输入、网页、文档和工具结果都可能包含伪指令；外部内容当数据，执行前重新鉴权

**最小权限** ---- 工具白名单、资源范围、数据库只读、文件目录、网络隔离、租户过滤和模型配额由程序强制

**审批** ---- 删除、付款、发信、改库、执行命令、发布和外部联网按风险要求确认或人工接管

**沙箱** ---- 模型生成的代码与命令隔离执行，限制网络、文件、时间、CPU、内存和凭证；浏览器自动化同样视为高风险

**数据保护** ---- 日志、trace、记忆、检索、工具结果和缓存都可能含敏感数据；脱敏、加密、保留与删除策略要一致

**供应链** ---- 锁定模型 SDK、框架、MCP Server、工具依赖和容器镜像；第三方工具需审查源码、发布和权限

**重点在这** ---- Prompt 是护栏的一层，不能代替权限、沙箱、审计和人工确认

## 第九站：进阶架构

第九站是高级工坊。只有单 Agent 加工作流真的遇到瓶颈，才请监督者、子图、事件驱动和长时记忆来帮忙；否则容易把一个函数扩建成一家公司。

**事件驱动 Agent** ---- 用事件总线连接任务、工具、审批和状态更新；关注顺序、重复、幂等、死信与可观测

**层级 Agent** ---- 让上层负责路由与汇总，下层负责窄领域能力；传递最少必要上下文，明确失败责任

**Agent-as-a-tool** ---- 将稳定的子 Agent 封装为上层工具；接口、预算和权限比子 Agent 的内部 prompt 更重要

**长时记忆** ---- 将稳定事实、经验和任务记录分别存储，支持过期、修正、删除和权限；“记得越多”不等于“更有帮助”

**多模态 Agent** ---- 将视觉、音频、文档和工具事件纳入同一状态模型；输入质量、成本和安全边界更复杂

**代码 Agent** ---- 文件、搜索、测试和命令形成工具链；最小工作区、差异审阅、测试证据与回滚是核心

**交付证据** ---- 能从裸 SDK 或轻量框架交付一个可暂停、可恢复、可评估的业务 Agent；有工具契约、权限、预算、日志、golden 集、故障测试和明确降级；能解释为什么某一步应该用代码而不是模型

## 通关标准

能把一个 Agent 做成可上线的服务：调用有超时、重试、取消、记账和追踪；工具有 schema、权限、幂等和审计；工作流有状态、队列、检查点、人工接管和降级；评估覆盖最终答案、工具轨迹、成本、延迟与安全边界。

## 结语

生产 Agent 的高级感，不在于它能说多少漂亮话，而在于它能把失败分门别类：该重试的重试，该停下的停下，该找人的找人。把模型、工具、状态和队列接起来只是施工，真正的工程师还要给每条路装路牌、护栏和回头路。

先把一个真实流程做稳，再增加自治和多 Agent。能用指标证明它更快、更准、更省或更安全，才值得把下一块积木放上去。
