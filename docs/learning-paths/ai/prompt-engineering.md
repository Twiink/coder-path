# Prompt Engineering 学习路线

Prompt Engineering（提示工程）不是给模型施法，而是把任务、上下文、约束和验收方式写成模型能稳定执行的输入。它既服务聊天，也服务 RAG、结构化抽取、工具调用和 Agent；真正成熟的提示词会被版本化、测试和观测，而不是躺在某人的收藏夹里等下一次复制粘贴。

前置不强制，但建议同时了解 [模型 API 通用原理](/learning-paths/ai/model-api-overview)。本页重方法与判断，不堆“万能咒语”；模型行为会变，任何技巧都要在自己的任务集上验证。

这条线按 **任务定义 → 指令结构 → 示例 → 上下文工程 → 结构化输出 → 推理与工具 → 注入防御 → 评估迭代 → 场景模板** 推进。

## 第一站：先把任务说清楚

欢迎来到 Prompt 的新手村。村里没有一句“万能咒语”，只有任务、上下文、约束和验收四位村民；你不说清楚要去哪里，模型就会很有礼貌地带你绕远路。

**目标** ---- 用一个可验证的动词描述任务，如分类、抽取、比较、改写、规划或审查；“帮我优化一下”没有验收边界

**输入** ---- 说明材料来源、格式、范围、时间、语言和缺失情况；让模型知道哪些是原始资料，哪些是背景说明

**受众** ---- 指定读者、专业程度、使用场景与风险等级；给工程师、客户和审计人员的同一答案不应共用一套表达

**约束** ---- 写明长度、格式、禁用内容、证据要求、工具权限和不确定时的动作；约束要能被程序或人工检查

**成功标准** ---- 定义正确、完整、相关、忠实、安全、可读或可执行中的优先级；优先级冲突时模型才知道听谁的

**失败路径** ---- 规定资料不足、字段缺失、无法判断、工具失败、冲突证据和不安全请求如何处理；没有失败路径，模型就会自己编一个

**重点在这** ---- 一个好的 prompt 先像任务单，再像文案；任务单越清楚，模型越少靠猜

## 第二站：指令结构与消息层级

第二站是提示词建筑工地。系统规则住顶楼，用户任务住客厅，网页和文档是戴访客证的资料；楼层不分，网页就可能穿着系统指令的外套来当物业经理。

**系统规则** ---- 放角色、目标、边界、原则、输出契约和安全红线；稳定规则与用户临时要求分离

**用户任务** ---- 放本次问题、具体材料和期望动作；避免让用户输入覆盖权限、审计和系统级约束

**上下文材料** ---- 用明确标签区分文档、网页、检索结果、工具返回和用户内容；外部内容只提供证据，不拥有控制权

**优先级** ---- 处理规则冲突时说明系统、开发者、用户和资料的优先次序；模型可能理解错，程序仍需执行硬权限

**分段与标题** ---- 用短段、标题、编号和字段名组织复杂任务；结构是给模型的导航，也是给人类审阅的目录

**指令位置** ---- 将关键规则放在稳定且醒目的位置，长材料中间可重复简短提醒；重复不是越多越好，要避免互相矛盾

**重点在这** ---- Prompt 的版式不是审美问题，而是信任边界和注意力管理问题

## 第三站：Few-shot 与示例设计

第三站是示例训练场。模型很会学样子，三个好例子能胜过十个糊涂例子；坏示范越多，它越认真，认真得让人想把训练场的门锁上。

**Zero-shot** ---- 模型已擅长的翻译、摘要和常见分类先直接描述任务；省 token，也更容易发现真正缺什么

**Few-shot** ---- 用少量输入—输出对齐自定义格式、领域口径、风格和边界；示例要和真实输入保持结构一致

**边界示例** ---- 加入空值、冲突、拒答、长输入、相似类别和恶意材料；只给完美样例会让模型误以为世界没有坑

**示例选择** ---- 静态任务可固定示例，领域变化大时按相似度或任务类型动态选择；动态选择本身也需要测试与权限控制

**示例压缩** ---- 删除重复说明，保留能改变决策的差异；示例太多会占上下文并放大错误

**示例版本** ---- 记录示例来源、任务版本、模型和评估结果；示例变了，prompt 行为可能跟着变

**重点在这** ---- 示例不是模型的“参考答案仓库”，而是决策边界的可视化样本

## 第四站：输出格式与结构化结果

第四站是输出质检线。自由文本像会即兴发挥的实习生，schema 像表格和工牌；让模型输出 JSON 只是让它戴上帽子，不代表它真的填对了表。

**格式选择** ---- 根据下游选择文本、表格、枚举、对象、列表或工具参数；能用有限枚举解决，就不要让模型自由写同义词

**字段定义** ---- 说明字段含义、类型、是否必填、空值、不确定和拒答状态；字段名相似时给出区别与边界

**原生 schema** ---- 平台支持结构化输出时优先使用；不支持时可用工具策略、解析器和有限重试，但要接受可靠性差异

**程序校验** ---- 语法、类型、范围、权限、业务不变量和事实引用逐层验证；通过 JSON 解析不等于可以直接入库

**格式失败** ---- 记录模型、prompt、schema、原始响应摘要和重试次数；修复格式错误时不要掩盖事实错误

**可演进性** ---- 给 schema 版本，允许新增字段和未知值，定义旧数据迁移；不要让某次 prompt 的临时字段成为永久接口

**重点在这** ---- prompt 负责表达期望，程序负责守住契约；模型不是数据库事务

## 第五站：推理、分解与自检

第五站是推理迷宫。复杂任务可以拆路标、设检查点、做自检，但别要求模型把每一段内心戏都搬上台；生产系统更需要能验证的中间产物，而不是一部长篇独白。

**任务分解** ---- 把研究、比较、计算、写作和审查拆成可验收步骤；步骤之间有依赖时明确输入输出

**结构化推理** ---- 要求模型给出假设、证据、结论、风险或检查清单等可审阅字段，而不是依赖一段不可验证的长篇思考

**计划与执行** ---- 先生成有限计划，再允许根据工具结果修订；计划必须有预算、停止条件和失败路径

**自检** ---- 让模型检查遗漏、冲突、格式、引用和约束；自检不是事实证明，关键任务仍要用程序或人工验证

**多次采样** ---- 高价值、低容错任务可以让模型独立生成多个候选并比较；成本会成倍增加，只在指标证明值得时使用

**批评与修订** ---- 用评估标准驱动修改，限制轮数与输出长度；没有明确标准的“再润色一次”只是把账单润色得更长

**重点在这** ---- 不追求让模型写出越长的思考，而是让每一步都能被检查、被停止、被替换

## 第六站：上下文工程与 RAG

第六站是上下文仓库。模型不缺字，缺的是相关、可信、在权限范围内的那几箱材料；把整座仓库倒进 prompt，只会让它在纸箱里寻找重点。

**资料筛选** ---- 只注入完成任务所需的内容；无关材料越多，模型越难找到真正证据

**检索上下文** ---- 给每段材料附来源、时间、页码、版本和权限；明确“只基于资料回答，资料没有就说没有”

**上下文排序** ---- 将问题、关键证据、补充证据、历史和输出要求分层；对长材料先定位再回答

**上下文压缩** ---- 摘要、去重、裁剪和父子片段可以节省预算；压缩不能删掉限制条件、例外和证据来源

**对话记忆** ---- 区分短期历史、长期事实、任务状态和偏好；记忆写入要有规则，读取要有权限

**外部内容隔离** ---- 网页、PDF、代码和工具返回都可能夹带指令；给它们加数据边界，不能直接拼成高优先级规则

**重点在这** ---- Prompt 是上下文的编排器；[RAG 系统](/learning-paths/ai/rag-systems) 负责检索与证据工程，二者不是互相替代

## 第七站：工具调用与 Agent 提示

第七站是工具训练场。Prompt 一旦能影响发邮件、改数据和执行命令，就从作文课升级成驾驶课；要教它能力、权限、刹车和回报，不能只教它说“请放心”。

**工具目录** ---- 描述工具用途、参数、返回、限制和禁止场景；工具越多，越需要分组或路由

**选择规则** ---- 说明何时调用、先后顺序、何时不要调用和结果不足怎么办；不要只列工具名字让模型自行猜业务流程

**行动确认** ---- 对发送、删除、修改、付款、发布和执行命令等副作用要求确认；确认不能只写在 prompt 中，还要由程序拦截

**结果回填** ---- 将工具状态、来源、错误和不可信标记回传；不要把工具堆栈或未经脱敏的数据库结果直接展示

**停止条件** ---- 任务完成、预算耗尽、最大轮数、超时、用户取消、权限拒绝和人工接管都要明确；模型“觉得完成”不够

**错误策略** ---- 教模型区分重试、换参数、换工具、请求用户补充和转人工；连续失败时必须停止

**重点在这** ---- Agent prompt 只能指导决策，不能授予权限；真正的安全门在工具服务端

## 第八站：注入防御与安全提示

第八站是安全演习场。注入者不会乖乖写“我是恶意指令”，它可能藏在网页、PDF、代码注释和工具结果里；一句“不要上当”挡不住一整套输入与权限问题。

**直接注入** ---- 用户要求模型忽略规则、泄露系统提示或越权操作；按信任层级处理，拒绝覆盖系统与权限

**间接注入** ---- 网页、文档、邮件、代码注释和工具结果中藏着伪指令；外部内容一律作为数据，执行动作前重新鉴权

**数据外泄** ---- 防止模型复述密钥、个人信息、内部提示、其他租户文档和工具返回；日志与最终输出都要脱敏

**工具越权** ---- 不让 prompt 成为唯一权限控制；服务端按用户、租户、资源、动作和环境再次校验

**输出安全** ---- 对危险命令、恶意链接、违法建议、敏感字段和未经证实的结论设拦截、标记或人工复核

**对抗测试** ---- 用改写、编码、长文夹带、角色扮演、工具返回注入和跨轮诱导测试；记录成功率与误报率

**重点在这** ---- 提示词是安全控制面的一部分，但不是安全边界本身；最小权限、沙箱和审计才是硬护栏

## 第九站：评估、实验与迭代

第九站是实验室。Prompt 改一句，模型可能变聪明，也可能顺手变贵、变慢或忘记拒答；先写假设、固定样例和指标，别用一张漂亮截图替代实验报告。

**黄金数据集** ---- 覆盖正常、边界、缺失、冲突、注入、长文本和多语言样例；小而真实比大而空泛更有用

**指标设计** ---- 按任务测正确率、字段准确率、相关性、忠实度、格式通过率、拒答质量、工具选择和人工通过率

**成对比较** ---- 同一输入对比旧 prompt 与新 prompt，记录胜负、差异和失败类型；不要只挑新版本表现好的截图

**规则评估** ---- 用程序检查格式、数值、引用、敏感信息、权限和工具上限；硬规则能抓住模型评审容易放过的问题

**LLM 评审** ---- 适合批量判断主观质量，但要固定标准、控制偏差、抽样人工复核并保护数据

**线上反馈** ---- 结合点赞、重问、转人工、编辑幅度、任务完成和投诉；用户行为是信号，不是绝对真值

**版本实验** ---- 同时记录 prompt、模型、工具、检索、参数、数据集和时间；否则实验结果不可复现

**重点在这** ---- 迭代闭环是“提出假设 → 固定样例 → 改一件事 → 跑评估 → 观察副作用 → 记录结论”

## 第十站：场景模板与通关标准

第十站是场景副本。工单、文档问答、代码审查、客服和数据助手各有怪物；先用 zero-shot 探路，再根据失败样例加结构和约束，别一开局就背满一整套咒语。

**抽取模板** ---- 明确字段、证据、缺失状态、歧义和 schema；先校验数据，再进入业务流程

**摘要模板** ---- 指定受众、范围、重要性排序、事实边界与未决事项；摘要不能把不确定结论写成定论

**分析模板** ---- 规定假设、证据、计算、风险、反例和建议；需要数字时让程序计算或复核

**代码模板** ---- 给出仓库范围、修改边界、验证要求和输出格式；不要让模型直接拥有提交或发布权限

**研究模板** ---- 规定来源质量、引用、时间范围、冲突处理和停止条件；搜索结果不是事实本身

**交付证据** ---- 能为一个真实任务写出清晰目标、上下文分层、示例或 schema、失败路径和安全边界；能用固定数据集比较版本；能解释一次改动带来的质量、成本和延迟变化

## 通关标准

能为真实任务写出清晰目标、上下文分层、示例或 schema、失败路径和安全边界；能用固定数据集比较版本；能解释一次改动带来的质量、成本、延迟和副作用变化；能让 prompt 与程序校验、权限和评估形成闭环。

## 结语

Prompt Engineering 不是把一句话磨成“神谕”，而是把任务写得清楚，把资料摆得正确，把失败安排好，再用数据验证效果。模型越聪明，越值得给它一份清楚的工作说明书。

先从一个真实任务开始，只改一件事，只看一组指标。等你的 prompt 能被复用、被测试、被回滚，它就不再是个人魔法，而是团队真正能继承的工程资产。
