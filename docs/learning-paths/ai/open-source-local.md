# 开源模型与本地推理学习路线

开源模型与本地推理的价值在于数据边界、可控性、离线能力、定制空间和长期成本；代价是模型文件、硬件、推理服务、升级、监控、评估和供应链都要由团队负责。它不是“下载一个模型然后免费得到云 API”，更像是自己养一只不会主动报销显卡的基础设施宠物。

前置建议掌握 [模型 API 通用原理](/learning-paths/ai/model-api-overview)、[RAG 系统](/learning-paths/ai/rag-systems) 的评估思路和基本部署能力。本页不绑定某个运行时或模型品牌，具体硬件兼容与部署命令应以当前项目文档为准。

这条线按 **模型家族与任务 → 权重与许可 → 硬件 → 推理运行时 → 量化 → 服务化 → 适配与微调 → 评估治理 → 上线运维** 推进。

## 第一站：模型家族与任务匹配

欢迎来到本地推理牧场。这里不只有模型，还有显卡、驱动、权重、许可和电费几位会定期来收租的 NPC；第一关先挑对坐骑，别看排行榜顺眼就把整套马具买回家。

**基础模型与指令模型** ---- 基础模型适合继续训练，指令模型适合对话、抽取和工具任务；先确认模型训练目标，再决定能否直接服务用户

**通用、代码与推理模型** ---- 通用模型适合文本与多语言，代码模型偏向程序理解与生成，推理模型可能以更高延迟换复杂问题能力；不要让“参数更多”替代任务匹配

**多模态模型** ---- 关注文本、图片、音频、视频输入与输出的实际支持，以及本地运行时是否完整实现；模型卡片里的能力不一定等于服务接口里的能力

**语言与领域覆盖** ---- 用自己的中文、英文、术语、代码、长文档和拒答样例测试；小语种与专业领域不要只凭通用榜单推断

**质量与成本** ---- 比较准确率、结构化成功率、幻觉、拒答、首 Token、完整延迟、吞吐、显存和每请求成本；至少保存一组可重复的基准数据

**重点在这** ---- 先定义“不合格是什么”，再选择模型；本地推理的第一项产出应是选型报告，不是一个孤零零的聊天窗口

## 第二站：权重、许可与供应链

第二站是模型海关。权重、代码、数据、适配器和依赖各自带着许可证护照；“能下载”不等于“能商用”，更不等于“能放心放进公司仓库”。

**权重格式** ---- 了解模型权重、配置、分词器、量化文件和适配器各自的职责；缺一项可能导致无法加载或输出异常

**模型许可** ---- 核对商业使用、再分发、衍生模型、地域、用户规模和署名要求；“开源”在不同项目里可能代表不同程度的开放

**模型卡片** ---- 阅读训练数据说明、已知限制、偏见、安全风险、上下文长度、推荐硬件和评估方式；卡片是上线前的安全说明书

**来源与校验** ---- 固定下载源、版本、哈希、配置和分词器；避免从不明镜像下载能执行或会被加载的模型相关文件

**依赖供应链** ---- 审查运行时、容器、插件、远程代码、第三方 tokenizer 与自定义算子；本地服务减少外部数据发送，却可能增加本地依赖风险

**重点在这** ---- “能下载”不等于“能合法、可复现、可审计地上线”

## 第三站：硬件与资源预算

第三站来到显卡健身房。模型要占显存，KV cache 要占显存，并发还要排队占显存；先算体重和训练计划，再决定单机、容器还是托管。

**显存与内存** ---- 估算权重、KV cache、运行时工作区、批处理和并发共同占用；“模型文件大小”只是显存预算的开场白

**上下文长度** ---- 上下文越长，KV cache 越大，延迟与显存压力也越高；把用户需要的最大长度与理论上限分开规划

**吞吐与延迟** ---- 区分首 Token 延迟、单请求生成速度、并发吞吐和尾延迟；聊天体验与离线批处理的最优硬件可能完全不同

**CPU、GPU 与专用芯片** ---- 关注算子支持、内存带宽、驱动、编译链和容器兼容；本地服务最怕“开发机能跑，部署机只会发热”

**资源隔离** ---- 为模型进程、文件、网络、临时目录和用户任务设置边界；代码 Agent 或工具 Agent 不能默认拥有宿主机的全部能力

**重点在这** ---- 选硬件时同时看质量、吞吐、利用率、能耗、维护和故障恢复；只看显卡价格通常会漏掉最贵的运维账单

## 第四站：推理运行时与服务形态

第四站是发动机维修铺。运行时负责把权重变成可调用服务，启动参数只是仪表盘上的旋钮；真正要学的是加载、生成、批处理、并发和故障恢复。

**本地进程** ---- 适合单人实验、离线任务与快速基准；生命周期简单，但共享、鉴权、监控和并发能力需要自行补齐

**容器化服务** ---- 将模型、运行时、驱动和配置打包以便复现；要管理镜像体积、硬件透传、健康检查、优雅退出和滚动升级

**统一 HTTP 接口** ---- 对外提供消息、流式、结构化结果、工具意图、模型信息与用量契约；让业务沿用 [模型 API 通用原理](/learning-paths/ai/model-api-overview) 的内部接口

**批处理与连续批处理** ---- 离线生成适合批处理，交互场景可合并并发请求提升利用率；吞吐提升要同时观察首 Token 与尾延迟

**队列与伸缩** ---- 长任务进入队列，按显存和模型类型分派 worker；排队、取消、重试和死信都需要可观测

**重点在这** ---- 运行时是基础设施，不是业务逻辑；业务只依赖稳定适配层，才能更换本地后端或回到云端

## 第五站：量化、精度与上下文

第五站是模型瘦身营。量化能让模型少吃显存，但也可能顺手减掉一点准确率；没有评估的量化，只是把质量问题藏进显卡背后，等上线再出来吓人。

**权重量化** ---- 了解不同位宽对显存与质量的影响，以及离线量化和加载时量化的差异；不要只比较文件大小

**量化类型** ---- 区分权重、激活、KV cache 与混合量化；不同层对精度敏感度不同，实际收益要用目标模型与任务测量

**校准数据** ---- 量化校准集应覆盖真实语言、术语、代码和长度分布；数据过于简单会让线上质量出现“突然变笨”的惊喜

**上下文与 KV cache** ---- 长上下文和高并发会显著增加缓存占用；应按场景设置最大长度、批大小和并发上限

**精度回归** ---- 比较抽取字段、工具参数、引用、拒答、数学、代码测试与长文一致性；平均分掩盖不了关键任务退化

**重点在这** ---- 量化目标不是“最小文件”，而是在质量底线内获得更好的单位成本吞吐

## 第六站：适配、结构化输出与工具

第六站是适配训练场。本地模型通常能聊天，真正绊脚的是工具格式、结构化输出、多轮模板和停止条件；它会说话不代表它会按你的业务协议办事。

**消息模板** ---- 核对分词器与模型要求的系统、用户、助手和工具消息格式；模板错了，模型会像收到一封没有主题的工作邮件

**结构化结果** ---- 使用 schema 约束、有限枚举、解析器和服务端校验；本地模型更需要“解析失败时怎么办”的明确路径

**工具调用** ---- 训练过工具格式的模型通常更容易稳定调用，但仍要在服务端做参数、权限、超时和副作用控制

**RAG 接入** ---- 将本地模型放在生成层，检索、引用、权限与评估保持独立；模型小不代表知识库可以不做质量治理

**云本地切换** ---- 适配层统一消息、流式、结构化、工具、错误与用量；能力差异通过能力矩阵和降级策略表达

**重点在这** ---- 本地模型最重要的不是“聊天像不像云端”，而是能否在你的业务协议中稳定完成任务

## 第七站：微调与定制（可选分支）

第七站是训练实验室。微调不是入场券，而是后续加点；先排除数据、检索、提示词和工具的问题，别用一轮训练去治疗一个本来应该修配置的感冒。

**提示与检索优先** ---- 知识更新、引用错误和权限问题通常由数据管道解决；不要用训练去修本应由系统规则解决的缺陷

**参数高效微调** ---- 了解 LoRA、Adapter、量化微调和全量训练的资源与发布差异；适配器本身也要记录基座版本与许可

**训练数据** ---- 关注任务定义、输入输出质量、去重、泄露、边界样例和拒答样例；数据少而准通常比堆大量噪声更有价值

**训练与评估隔离** ---- 训练集、验证集、测试集和线上 golden 集分开；不要用训练数据证明模型已经学会

**回滚与组合** ---- 记录基座、适配器、分词器、量化和推理配置；不同适配器组合可能互相影响，发布前要逐项评估

**重点在这** ---- 微调改变模型行为，不能自动改变事实来源、权限和安全边界

## 第八站：评估、监控与安全上线

第八站是运维夜班室。服务上线不是毕业，而是开始值班；硬件、运行时、量化、并发和版本任何一个打喷嚏，质量和延迟都可能跟着感冒。

**离线质量集** ---- 覆盖正常任务、长上下文、多语言、结构化输出、工具调用、拒答、注入、代码与边界输入；固定集用于版本回归

**在线指标** ---- 监控首 Token、完整延迟、吞吐、P95、显存、队列、错误、取消和质量抽样；本地服务还要记录硬件温度与利用率等运维信号

**数据与日志** ---- 最小化保存输入输出，脱敏个人信息和业务机密；本地部署不意味着内部员工都可以看全部 prompt

**安全隔离** ---- 模型生成的代码、命令、文件操作和浏览器动作在沙箱与白名单内执行；模型服务与宿主机、密钥和生产网络分离

**升级与回滚** ---- 版本、权重、运行时、驱动、量化和配置一起发布；保留上一版本与基准结果，质量或稳定性下降时快速切回

**成本核算** ---- 把硬件折旧、能耗、存储、运维、人力和云端备援计入每请求成本；“没有 API 账单”不等于“零成本”

**重点在这** ---- 本地推理的交付标准是可复现、可观测、可回滚和可解释，不是“我的电脑能跑”

## 通关标准

完成一个只读内部文档问答服务：支持本地与云端模型切换，记录检索质量、首 Token、完整延迟、吞吐、显存和每次请求成本；为模型升级保留 golden 集、版本清单和回滚方式。

你应能解释权重、运行时、服务层与业务适配层的边界；根据质量、延迟、数据合规和运维成本做选型；完成至少一种量化回归；处理结构化失败、工具调用、取消、超时、越权和模型升级。

## 下一站去哪

**想做本地知识库** ---- 去 [RAG 系统](/learning-paths/ai/rag-systems)，让本地模型接上检索、引用和评估

**想让模型调用工具** ---- 去 [Agent 开发](/learning-paths/ai/agent-development)，测试工具格式、循环、权限和成本

**想比较云端与本地** ---- 回到 [模型 API 通用原理](/learning-paths/ai/model-api-overview)，用同一适配层做质量与延迟对照

**想继续训练模型** ---- 在本地基线稳定后，再研究微调、数据构造、评估与模型许可

## 结语

本地推理的浪漫版本是“没有 API 账单，数据也不出门”；工程版本是“显存、驱动、权重、许可、吞吐、电费和回滚都有人负责”。后一个版本听起来没那么诗意，却能让服务活得更久。

先把一个小模型稳定跑起来，再逐步提高上下文、并发和质量。能复现、能观测、能升级、能回滚，你才是真正拥有了模型，而不是暂时借住在一条启动命令里。
