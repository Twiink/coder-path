# AI Agent 基础学习路线

Agent（智能体）不是“会聊天的模型”换了个名字，而是一个围绕目标运行的决策循环：模型理解任务、选择下一步、请求工具、观察结果、更新状态，直到满足停止条件。模型负责提出意图，程序负责执行、权限、状态和结果验证。

前置建议先掌握 [Prompt Engineering](/learning-paths/ai/prompt-engineering) 与 [模型 API 通用原理](/learning-paths/ai/model-api-overview)。本页只讲通用骨架，不绑定某个 Agent 框架；理解循环后再看 [LangChain](/learning-paths/ai/langchain)、[Agent 开发](/learning-paths/ai/agent-development) 和 [自主 Agent](/learning-paths/ai/autonomous-agents)。

这条线按 **Agent 心智模型 → 消息与上下文 → 工具调用 → 状态与记忆 → 规划与反思 → 工作流与多 Agent → 安全与评估 → 最小项目** 推进。

## 第一站：Agent 是什么

欢迎来到 Agent 新手村。村门口有四位 NPC：模型是会出主意的军师，工具是长着手脚的打工人，状态是负责记账的管家，控制流则拿着哨子喊“到此为止”。先认清这四位，Agent 的魔法就会变成工程。

**模型** ---- 负责理解目标、判断下一步、选择工具、生成计划和表达结果；模型不会自动访问你的数据库、文件或网络

**工具** ---- 将搜索、计算、查询、写入、代码执行和业务 API 暴露为受控能力；工具的权限与实现由程序掌握

**状态** ---- 保存当前问题、历史消息、任务进度、工具结果、用户确认和中间产物；状态不是一段无限增长的聊天记录

**控制循环** ---- 让模型决策、工具执行、结果回填和再次决策按有限步骤运行；循环必须有停止、错误和取消路径

**Chatbot 与 Agent** ---- Chatbot 主要生成回复，Agent 还要围绕目标采取行动并观察结果；两者可以共享模型，但控制面不同

**工作流与 Agent** ---- 固定步骤、业务规则和权限判断优先写成确定性代码；开放决策、自然语言理解和工具选择才适合交给模型

**重点在这** ---- Agent = 模型决策 + 工具执行 + 状态 + 控制流；缺一个，系统可能只是聊天、脚本或一段没有刹车的循环

## 第二站：消息、上下文与 System Prompt

第二站来到 Agent 的记忆旅馆。模型每轮能看到哪些消息，决定它是记得任务，还是像刚睡醒一样把用户再问一遍；房间分错，会议纪要就会互相打架。

**消息角色** ---- 区分系统规则、用户任务、助手历史、工具调用和工具结果；不同角色有不同信任级别

**System Prompt** ---- 规定角色、目标、能力边界、工具使用、输出格式、拒答和安全规则；不能替代程序权限

**任务上下文** ---- 将目标、约束、用户资料、相关文档、已完成步骤和待办事项结构化；动态资料与稳定规则分开

**上下文窗口** ---- 历史、工具定义、检索内容和输出共同消耗预算；长任务需要滑动窗口、摘要、关键信息提取或外部存储

**摘要记忆** ---- 适合保存阶段结论、决策、未解决问题和下一步；摘要必须保留数值、来源、限制与不确定性

**短期与长期** ---- 短期记忆是当前会话，长期记忆可以是用户偏好、事实、文档或任务记录；长期记忆写入与读取都需要规则和权限

**重点在这** ---- Agent 质量常常不是败在模型能力，而是败在上下文塞了太多、太旧、太杂或不该看的内容

## 第三站：工具调用循环

第三站是工具集市。模型可以指着天气 API 和数据库说“我想用这个”，但真正搬货、开门和刷卡的人还是程序；先用两个工具练循环，别一上来就给它整座城的钥匙。

**工具契约** ---- 工具包含名称、描述、参数 schema、返回结构、错误与限制；描述要写清何时使用与何时禁止

**模型意图** ---- 模型返回要调用的工具、参数和关联 ID；这只是请求，不是执行结果，更不是权限批准

**服务端执行** ---- 程序重新校验身份、租户、资源、参数和业务状态，再决定是否执行；模型生成的参数不能直接写库

**结果回填** ---- 把成功数据、来源、状态和可读错误回传模型；外部网页、文档和 API 响应要标记为不可信内容

**多工具顺序** ---- 有依赖的动作串行，独立查询可以并行；并行调用要按 ID 聚合，不能按返回先后猜结果归属

**写操作** ---- 发信、删改、付款、提交代码和执行命令需要确认、幂等、审计、沙箱或人工接管；只读工具也要限制范围

**循环上限** ---- 设置最大步数、单步超时、总预算、重复调用检测和整体 deadline；达到上限要总结进展或转人工

**重点在这** ---- 模型只负责“想做什么”，程序负责“是否允许、如何执行、执行后发生了什么”

## 第四站：状态与记忆设计

第四站进入记忆仓库。这里有会话、任务、用户偏好和知识库四个货架，保质期各不相同；把它们全塞进一个箱子，隐私、成本和调试会一起申请加班。

**会话状态** ---- 保存近期消息、当前用户问题、工具结果和对话摘要；适合多轮交互，通常有过期时间

**任务状态** ---- 保存目标、计划、已完成、待办、失败、审批和产物；适合长任务与断点恢复

**用户记忆** ---- 保存明确值得复用的偏好或事实；写入前要判断敏感性、准确性、有效期与用户是否知情

**知识库** ---- RAG 存储可检索的文档与事实，不等于用户记忆；详见 [RAG 系统](/learning-paths/ai/rag-systems)

**状态存储** ---- 小型原型可内存保存，生产通常需要数据库、缓存或检查点；存储要考虑一致性、加密、删除与备份

**状态压缩** ---- 原始轨迹用于审计，摘要用于当前决策，结构化字段用于程序判断；三者不必互相替代

**重点在这** ---- 记忆的目标不是让 Agent 什么都记住，而是让它在正确时间看到正确的最少信息

## 第五站：规划、反思与停止

第五站是计划室，墙上贴满了“下一步做什么”。计划写得越长不代表越聪明，有时只是把迷路路线画得更精致；先让代码处理确定的路口，再把不确定的岔路交给模型。

**直接循环** ---- 简单任务边做边决策，反馈快、状态少、成本低；先用它建立基线

**Plan-and-Execute** ---- 先拆任务和依赖，再逐步执行；计划要能重排、取消、验证和在预算耗尽时收尾

**动态重规划** ---- 工具结果、用户补充或失败可能改变计划；允许局部修订，不要每一步都把全世界重新计划一遍

**反思** ---- 用检查清单审查遗漏、事实、格式、引用或测试；反思不能替代外部验证，且必须限制轮数

**自我修订** ---- 生成—批评—修订适合写作、代码和结构化结果；记录每轮成本与收益，避免模型对自己的草稿举行无限表扬大会

**停止条件** ---- 业务验收通过、无工具请求、达到步数、预算、时间、错误阈值、用户取消或人工拒绝都可以终止

**重点在这** ---- 设计“什么时候停”与设计“下一步做什么”同样重要；自主但不停机，只是更贵的死循环

## 第六站：工作流与多 Agent

第六站来到 Agent 办公楼。这里可以安排路由员、监督者和多个专员，但别为了一个查天气任务成立董事会；只有职责、权限或上下文真的需要隔离，才值得招新同事。

**确定性 Pipeline** ---- 固定的分类、检索、模板回复和校验优先用代码串接；稳定流程不必请模型担任骰子

**状态机与图** ---- 有分支、循环、暂停、恢复、人工确认和长任务时，用显式状态图表达；状态边界比提示词里的“请记住”可靠

**Router** ---- 按意图、领域、权限或风险将任务分给不同链或 Agent；规则稳定时优先代码，模型路由要有默认与拒答分支

**Supervisor** ---- 管理 Agent 选择和汇总子 Agent；需控制上下文传递、循环、工具权限与汇总偏差

**Handoff** ---- 将任务与控制权交给另一个 Agent；交接应包含输入、输出、失败责任和用户可见状态

**并行协作** ---- 独立研究、检索或评审可并行；共享写操作与有依赖任务应串行并使用隔离状态

**重点在这** ---- 多 Agent 的核心是信息流和责任边界，不是 Agent 数量；能用一个 Agent 和一条工作流解决，就别先建一个 AI 部门

## 第七站：安全、观测与评估

第七站是城门和质检站。Agent 可能把一句“帮我处理一下”放大成十次查询、一次写库和一封邮件，所以安全员和验收官必须从第一天上岗，不能等系统闯祸后再补招聘。

**提示词注入** ---- 用户、网页、文档和工具结果都可能包含伪指令；外部内容作为数据，不能覆盖系统规则

**权限最小化** ---- 工具白名单、只读账号、文件目录、命令白名单、网络隔离和租户过滤由程序执行

**人工确认** ---- 删除、付款、发信、发布、改库和高风险命令需要明确审批；审批记录要能追溯

**执行沙箱** ---- 模型生成的代码、命令和浏览器操作在隔离环境运行，限制时间、网络、文件和资源

**轨迹观测** ---- 记录模型决策、工具、参数摘要、结果、状态、token、耗时、重试与停止原因；最终回答不够解释 Agent 行为

**任务评估** ---- 测任务成功率、工具选择、参数、步数、越权拒绝、答案质量、成本和延迟；固定 golden 集用于回归

**重点在这** ---- 可观测性告诉你发生了什么，评估告诉你做得好不好，权限告诉你允许做什么；三者缺一不可

## 第八站：最小项目

建议项目：做一个客服或内部数据助手，只提供天气、知识库检索和只读订单查询三个工具。要求有消息历史、工具循环、错误回填、最大步数、权限、日志和无答案兜底。

**基础交付** ---- 能画出模型、工具、状态、控制循环；能手写一个工具调用与回填流程

**进阶交付** ---- 支持摘要记忆、结构化结果、工具错误、超时、重复调用和用户取消；保存可回放轨迹

**安全交付** ---- 为每个工具写权限范围与风险等级；写操作需要确认，外部结果按不可信数据处理

**评估交付** ---- 用固定样例报告成功率、工具准确率、步数、token、延迟和失败类别；模型说完成不能代替测试

**交付证据** ---- 能独立实现一个会调用两三个工具的 Agent；解释短期/长期记忆、规划/反思与工作流边界；为超时、限流、注入、越权、预算耗尽和人工接管设计路径

## 通关标准

能从零画出模型、工具、状态和控制循环；能实现工具定义、参数校验、结果回填、停止条件和错误处理；能区分会话、任务、用户记忆与知识库；能为超时、限流、提示词注入、越权、预算耗尽和人工接管设计可验证路径。

## 结语

Agent 的本质没有那么神秘：模型负责想一想，工具负责动一动，状态负责记一记，控制流负责在它准备无限循环时吹哨。真正难的不是让它动起来，而是让它知道什么时候该停、哪些事不能做、做完如何证明。

先做一个小 Agent，把每一次调用和失败都看懂；等它能稳定完成任务，再给它更多工具和更长的腿。会拆边界、会设护栏、会看证据，你就已经从“会调模型”走进了 Agent 工程的大门。
