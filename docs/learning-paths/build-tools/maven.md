# Maven 学习路线

Maven 是 Java 世界那位穿着西装、手里拿着项目清单的总管：项目结构、依赖、编译、测试、打包和发布，都喜欢按既定流程排队。它看起来像 XML 很多，实际上真正要学的是 **项目对象模型（POM）+ 生命周期 + 插件 + 仓库** 这套构建心智。Maven 不负责替你写业务，但会在你忘记提交测试、依赖版本打架或“本地能跑、CI 不行”时，准时敲门。

这是一条独立的 Maven 学习地图，从第一个项目走到多模块、依赖治理、可复现构建、发布与持续集成。每一站同时覆盖日常最常用的能力、容易漏掉的边界和值得深挖的机制；路线尽量少放代码，把注意力留给构建为什么这样工作。

路线按 **项目模型 → 生命周期 → 依赖与仓库 → 插件 → 多模块 → 测试质量 → 打包发布 → 可复现构建 → CI 与诊断 → 生产治理** 推进。

## 第一站：项目模型与第一个构建

欢迎来到 Maven 的登记处。POM 是项目的身份证，坐标是它的住址，生命周期是办事流程；先把这三样认全，后面看到一长串 XML 就不会像在机场找错登机口。

**POM 与项目坐标** ---- 理解 `groupId`、`artifactId`、`version` 如何唯一定位构件，掌握 `packaging`、属性、依赖和构建配置各自的职责

**约定目录结构** ---- 熟悉 `src/main`、`src/test`、资源目录、测试资源和 `target` 产物目录；约定的价值是让工具、IDE 和新同事少问几次“代码到底放哪儿”

**Maven Wrapper** ---- 使用项目锁定的 Maven 版本，让团队和 CI 不必依赖每台机器的全局安装；Wrapper 文件要审查来源并纳入版本控制

**常用命令语义** ---- 分清清理、编译、测试、打包、验证、安装和部署分别做到哪一步；命令不是咒语，阶段顺序才是它的语法

**构建输出** ---- 认识编译产物、测试报告、源码包、文档包和临时目录，建立“源代码、构建中间物、发布构件”三类边界

**重点在这** ---- 先能从 POM 推断项目身份、默认目录、构建入口和最终产物，再谈插件调优；否则只是给 XML 戴了一副很贵的眼镜

## 第二站：生命周期与构建阶段

第二站进入 Maven 的流水线车间。生命周期像传送带，阶段像工位，插件目标才是真正拧螺丝的人；你执行某个阶段，前面的工位通常也会顺手跑完。

**Clean、Default 与 Site 生命周期** ---- 了解清理、主构建和站点文档三条生命周期的边界，知道同名阶段为何不是同一条传送带

**阶段与目标** ---- 区分生命周期阶段和插件 goal，理解插件如何绑定到 `compile`、`test`、`package`、`verify` 等阶段；阶段只定时机，goal 才负责干活

**默认绑定** ---- 认识 Java 项目从资源处理、编译、测试到打包的默认绑定，知道改变 `packaging` 会改变默认流水线

**验证阶段** ---- 把集成测试、质量门禁、签名检查和自定义验证放在 `verify` 等合适位置；不要让“打包成功”冒充“可以发布”

**跳过与失败策略** ---- 理解跳过测试、跳过测试编译、失败即停和继续构建的差异；临时跳过是诊断工具，不能变成团队的永久性逃生门

**生命周期扩展** ---- 了解插件绑定、执行顺序、继承和覆盖，遇到构建行为异常时能追溯“哪个插件在什么时候做了什么”

**重点在这** ---- 会画出一次构建的阶段流和插件流，能解释为什么某个检查发生在打包前或打包后，而不是只记住一串命令行参数

## 第三站：依赖管理与版本冲突

第三站是 Maven 的仓库调解室。依赖会自己带朋友来，传递依赖会带朋友的朋友来；你要学会让它们登记、分组和按规则解决冲突，别让一棵依赖树长成热带雨林。

**依赖坐标与范围** ---- 掌握编译、运行时、测试、提供和系统等依赖范围，理解它们如何影响类路径、打包内容和传递关系

**传递依赖** ---- 从依赖树理解“我没声明却出现了它”的来源，学会用依赖树定位引入路径和不必要的重量

**版本冲突** ---- 理解 Maven 的冲突调解、就近原则和显式声明，知道“构建通过”不代表运行时拿到的版本就是你想要的版本

**依赖管理与 BOM** ---- 使用父 POM、属性和 `dependencyManagement` 统一版本；理解 BOM 只管理版本，不会凭空替你添加依赖

**排除与替换** ---- 谨慎使用 exclusions、直接依赖和版本覆盖，记录为什么排除；把冲突压下去而不解释原因，只是把雷埋得更深

**可选依赖与 API 暴露** ---- 区分实现依赖、对外 API 依赖、可选能力和运行时插件，避免库把不该暴露的类型带进消费者世界

**重点在这** ---- 看到依赖冲突能回答来源、选择结果、运行时风险和长期治理方案，依赖树不再是一串看完就忘的缩进

## 第四站：仓库、镜像与构件解析

第四站来到 Maven 的物流中心。中央仓库、私服、本地缓存和镜像各有岗位；下载慢时别先怀疑网速，可能是仓库在和你玩“我明明有但就是不给你”。

**本地仓库** ---- 理解本地缓存、坐标目录、失败缓存和更新策略，知道清理缓存为什么有时有效、有时只会让构建重新排队

**远程仓库与私服** ---- 区分中央仓库、企业仓库、代理仓库和宿主仓库，理解依赖下载与内部构件发布的不同路径

**镜像与认证** ---- 配置镜像、凭据、服务器 ID 和仓库权限；凭据不能硬编码进 POM，也不要把生产仓库密码当调试日志打印

**快照版本** ---- 理解 `SNAPSHOT` 的更新语义、缓存时间和不稳定边界；快照适合协作中的开发构件，不适合承担可追溯发布的身份证

**构件完整性** ---- 认识校验和、签名、元数据和下载来源，建立对供应链的基本信任验证意识

**离线与代理环境** ---- 了解离线构建、预热缓存、网络代理、证书和仓库不可用时的失败表现，为受限网络准备可解释的恢复路径

**重点在这** ---- 能从“找不到依赖、下载很慢、版本不更新、CI 认证失败”反推出仓库链路，而不是反复删除本地目录祈祷

## 第五站：插件与构建逻辑

第五站是 Maven 的工具间。插件是会干活的工匠，但工匠太多、版本太旧、配置互相覆盖时，POM 就会开始写长篇连续剧。

**核心插件族** ---- 认识编译器、资源、Surefire、Failsafe、JAR、WAR、Shade、源码和 Javadoc 等常用插件的职责边界

**插件版本锁定** ---- 显式管理插件版本和配置，避免不同 Maven 环境因默认插件漂移而产生不同结果

**编译与工具链** ---- 配置 Java 版本、编码、模块路径、编译参数和 Toolchains，区分“本机 JDK 版本”和“项目目标 JDK 版本”

**测试插件分工** ---- 理解 Surefire 适合单元测试、Failsafe 适合集成测试的命名与阶段约定，避免把所有测试塞进一个慢而模糊的阶段

**插件执行顺序** ---- 关注同阶段的执行顺序、继承覆盖、配置合并和默认值，诊断“配置写了但没有生效”时先看执行模型

**自定义插件边界** ---- 知道什么时候复用现有插件，什么时候写脚本或插件；构建逻辑越像业务程序，越需要测试、版本和文档

**重点在这** ---- 能阅读一段插件配置并说清触发阶段、输入、输出、失败条件与副作用，构建文件终于不再是一座会自动长大的迷宫

## 第六站：多模块与项目边界

第六站把一个项目拆成一群互相认识但不互相乱串门的模块。多模块不是目录变多，而是边界、依赖方向、构建顺序和发布节奏都变得可管理。

**聚合与继承** ---- 区分聚合 POM 负责一起构建、父 POM 负责共享配置；两者经常同居，但不是同一个人

**模块声明与反应堆** ---- 理解模块发现、依赖排序、部分构建和反应堆行为，知道为什么改一个库模块会触发下游模块重建

**父子配置** ---- 组织属性、插件管理、依赖管理和公共检查，避免父 POM 变成“所有团队决定都塞进去”的巨型抽屉

**依赖方向** ---- 让领域、基础设施、接口和应用层保持清晰依赖，识别循环依赖与过度共享；构建工具能排序模块，却不能替你修好架构

**部分构建** ---- 使用按项目选择、包含依赖和排除依赖等方式缩短反馈，确认局部构建没有偷偷绕过必要验证

**版本发布策略** ---- 选择统一版本、独立版本或发布列车，处理模块间版本一致性、回滚和兼容窗口

**重点在这** ---- 能判断一个模块该拆还是不该拆，能解释拆分带来的构建速度、复用性、发布复杂度和认知成本

## 第七站：测试、质量与安全门禁

第七站是构建流水线的体检室。编译器只能证明代码语法能接受，测试、静态分析和依赖扫描才会继续追问“行为对不对、有没有旧漏洞、能不能放心交付”。

**单元与集成测试分层** ---- 配置测试目录、命名、分类和生命周期，让快速反馈与真实依赖测试各司其职

**覆盖率的正确位置** ---- 接入 JaCoCo 等覆盖率工具，关注未覆盖的风险路径和断言质量，不把百分比当成唯一成绩单

**静态分析** ---- 集成 Checkstyle、SpotBugs、PMD、编译器告警和架构规则，把风格、缺陷和设计约束放进构建反馈

**依赖漏洞扫描** ---- 使用依赖审计、版本升级和许可证检查，区分可利用漏洞、误报、运行时路径和修复优先级

**质量门禁** ---- 让测试、覆盖率、静态分析、漏洞等级和构件签名成为发布条件；门禁太松是摆设，太乱则是团队每天绕路的收费站

**测试数据与秘密** ---- 防止测试把真实凭据、生产数据和个人信息打进日志或构件，使用隔离环境与可撤销凭据

**重点在这** ---- 质量检查要能阻止高风险构件流出，又不能把每次本地改字都变成半小时的等待比赛

## 第八站：打包、发布与供应链

第八站是构件出库处。JAR、WAR、源码包和文档包是不同商品，发布到仓库后就会被别人依赖；版本一旦发出去，时间机器可没有 Maven 插件那么好用。

**打包形态** ---- 分清普通 JAR、可执行 JAR、WAR、依赖聚合包和分发压缩包，理解类路径、资源路径与启动方式的差异

**资源与配置** ---- 处理资源过滤、环境配置、编码、占位符和运行时注入，避免把环境秘密烘焙进不可逆的发布构件

**发布到仓库** ---- 掌握发布元数据、源码包、Javadoc、版本策略和仓库权限，区分本地安装、内部发布和正式发布

**签名与校验** ---- 为构件建立签名、校验和、来源记录和可追溯版本，供应链安全不靠“这个包看起来很眼熟”

**兼容性承诺** ---- 评估二进制兼容、源代码兼容、依赖升级和弃用策略；版本号不是装饰，而是对消费者的承诺书

**回滚与撤回** ---- 设计坏版本隔离、修复版本、仓库策略和消费者迁移，尽量不删除已经被使用的正式构件

**重点在这** ---- 能把一次构建从源码追踪到可验证构件，知道谁构建、用什么依赖、在哪发布、如何回滚

## 第九站：可复现构建与性能

第九站请构建系统做一次体检：同一提交在不同机器上应该尽量产出同样的结果，速度优化也应该有数据，不是靠“我感觉删掉这行会快”。

**可复现构建** ---- 固定 Maven、JDK、插件和依赖版本，处理时间戳、文件顺序、环境变量和本地路径差异

**构建缓存意识** ---- 识别本地仓库缓存、编译增量、CI 缓存和远程缓存各自能保证什么，避免缓存旧产物掩盖真正失败

**并行构建** ---- 了解多模块并行的收益、资源竞争、非线程安全插件和共享目录风险；快车道也要有交通规则

**构建剖析** ---- 使用构建日志、时间统计和插件诊断定位慢点，区分下载慢、编译慢、测试慢、打包慢和外部服务慢

**环境隔离** ---- 通过容器、工具链和 CI 镜像统一运行环境，减少“某位同事电脑上有一个神秘 JAR”的民间传说

**升级策略** ---- 分阶段升级 Maven、JDK、插件和依赖，保留构建基线与回滚点，避免一次升级把所有变量拧到最大

**重点在这** ---- 性能优化最终要回答节省了多少时间、牺牲了什么确定性、失败是否更难诊断，而不只是终端上的秒数变小

## 第十站：CI、故障诊断与生产治理

最后一站来到发布控制室。这里的 Maven 不只是执行命令的工具，而是从提交到构件的证据链；它要能失败，也要能告诉人为什么失败。

**CI 流水线分层** ---- 组织快速检查、单元测试、集成测试、打包、扫描、签名和发布，按反馈速度与风险安排顺序

**构建日志** ---- 保留版本、环境、依赖解析、测试摘要和构件信息，避免只留下一个“退出码 1”让值班同事猜谜

**常见故障分类** ---- 从目录、JDK、网络、仓库、依赖冲突、插件、测试、权限和资源耗尽等方向建立排查树

**构建权限** ---- 让 CI 使用最小仓库权限、短期凭据和隔离账号，发布权限与普通验证权限分开

**升级与弃用** ---- 关注 Maven、插件、JDK、仓库和依赖的生命周期，建立升级窗口、兼容性验证和安全响应流程

**构建治理** ---- 维护父 POM、版本策略、质量门禁、构件保留、许可证和审计记录，让规则能被解释、被执行、被修改

**重点在这** ---- 生产级 Maven 项目应当可构建、可测试、可审计、可复现、可发布、可回滚；只会执行 `mvn package` 还只是拿到了车间门票

## 通关标准

**Maven 新手能跑通项目** ---- 能读懂 POM、目录、坐标和生命周期，能定位编译失败、测试失败与依赖下载失败的基本方向。

**初级 Java 开发者能管依赖** ---- 能处理范围、传递依赖、版本冲突、插件配置和常见测试阶段，不再靠复制别人的父 POM 过日子。

**中级工程师能维护多模块** ---- 能设计模块边界、统一版本、配置质量门禁、发布内部构件，并让 CI 给出可信反馈。

**高级工程师能治理供应链** ---- 能推动可复现构建、漏洞扫描、签名、权限隔离、性能基线和升级策略，让构建系统经得起夜间告警。

## 结语

Maven 的魅力不在于 XML 写得多，而在于它把“一个项目如何被可靠地变成构件”这件事说得很清楚。先理解模型，再配置插件；先保证能复现，再追求跑得快；先让失败有证据，再谈自动发布。等你能从一条 CI 日志还原构建经过，Maven 就不再是那个爱缩进的总管，而是团队共同遵守的工程记忆。
