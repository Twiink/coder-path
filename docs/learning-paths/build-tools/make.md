# Make 学习路线

Make 是 Unix 世界那位年纪很大、脾气很直的构建老兵：它不关心你用了什么 IDE，只看目标文件、依赖文件和时间戳。1970 年代的工具，至今仍能在 C/C++ 项目、系统源码、部署脚本和各种开源仓库里突然探头。它的语法不算现代，思想却极其现代：**把工作描述成依赖图，只重做真正需要重做的部分**。

这是一条独立的 Make 学习地图，从第一个 Makefile 走到模式规则、自动依赖、并行构建、可移植脚本、复杂项目治理与工具选型。每一站都兼顾常用规则、冷门坑位和底层机制；示例只用文字和关键词说明，避免让 Tab 字符成为本路线唯一的主角。

路线按 **依赖图 → 变量 → 规则 → 组织 → 依赖生成 → 并行 → Shell 边界 → 项目治理 → CI → 构建生态** 推进。

## 第一站：目标、依赖与增量构建

欢迎来到 Make 的档案室。目标是要交付的文件，依赖是它需要的材料，配方是加工步骤；Make 不会因为你看起来很忙就重做一切，它先检查时间戳再决定谁该上班。

**规则三件套** ---- 理解目标、前置依赖和配方，建立“声明依赖关系，而不是罗列命令”的心智模型

**时间戳判断** ---- 掌握目标不存在、依赖更新和目标早于依赖时的重建规则，知道增量构建为何快，也知道它为何会被错误时间戳骗过

**默认目标** ---- 认识第一个目标、默认入口、聚合目标和目标选择，给项目安排一扇清晰的正门

**伪目标** ---- 使用 `.PHONY` 表示清理、测试、安装等不对应真实文件的动作，避免同名文件让 Make 误以为工作已经完成

**目标图** ---- 把编译、链接、打包和部署看成有向无环图，识别循环依赖与隐含顺序；Make 会报循环，但不会替你做架构咨询

**重点在这** ---- 能从一组文件推断哪些会被重建，并解释为什么“只改一个头文件”可能牵动半个项目

## 第二站：变量与自动变量

第二站来到 Make 的小算盘旁。变量负责去重，自动变量负责在规则执行时递上当前目标和依赖；写得好是模板，写得坏是美元符号迷宫。

**变量展开时机** ---- 区分递归展开、简单展开、条件赋值和追加，理解定义时展开与使用时展开带来的差异

**命令行覆盖** ---- 设计编译器、编译选项、链接选项和输出目录变量，允许 CI 或开发者安全地覆盖默认值

**自动变量** ---- 掌握目标名、第一个依赖、全部依赖、新依赖和模式茎等上下文变量，知道它们只在规则配方中有意义

**变量作用域** ---- 了解全局、目标专属、模式专属、环境变量和命令行变量之间的优先级，避免某个环境变量悄悄接管构建

**函数与列表** ---- 使用文件匹配、替换、过滤、排序、去重和路径处理函数，理解 Make 的字符串世界本质上是列表世界

**递归展开陷阱** ---- 识别自引用、空变量、空格、转义美元符号和意外 shell 展开，别让一个变量在日志里变成一位失忆演员

**重点在这** ---- 能判断变量何时求值、由谁覆盖、最终展开成什么，并能让一个 Makefile 在不同编译器和平台上保持可读

## 第三站：模式规则与隐含规则

第三站是规则裁缝店。模式规则用一个模板服务一群文件，隐含规则是 Make 自带的旧经验；经验可以复用，但关键处要知道它到底套了哪件外套。

**模式规则** ---- 理解 `%` 模式、目标与依赖的茎、单目标与多目标规则，用一条规则覆盖同类源文件

**静态模式规则** ---- 在已知目标集合上应用模式，兼顾模板复用与目标边界，避免通配符把不该编译的文件也拎进来

**隐含规则链** ---- 了解 Make 如何尝试内置规则、推导中间目标和选择配方，遇到“它怎么自己编译的”时能还原原因

**显式规则优先** ---- 在关键目标上写清依赖和命令，掌握覆盖、取消和替代内置规则的方式

**自动变量组合** ---- 用目标目录、依赖目录和路径变换组织多目录项目，让规则不依赖当前工作目录的幸运位置

**规则冲突** ---- 识别多个模式匹配、重复目标、不同配方和覆盖规则引起的警告与不确定性

**重点在这** ---- 会在简洁与明确之间取舍：重复少一点很好，但让构建行为需要考古就得不偿失

## 第四站：包含、条件与项目组织

第四站给 Make 搭办公室。一个小 Makefile 可以一页讲清楚，项目一大就会需要配置、平台、模块和自动生成文件；这时最怕的是“每个目录都有一位自己的 Make 老板”。

**文件包含** ---- 使用 include 拆分编译选项、平台配置、公共规则和自动依赖，理解被包含文件缺失时的软失败与硬失败

**条件判断** ---- 按操作系统、编译器、调试模式和工具可用性切换配置，避免把平台差异散落到每条命令里

**目标参数化** ---- 设计 all、clean、test、install、package、format 和 lint 等公共目标，保持入口稳定、职责清晰

**递归 Make** ---- 理解子目录递归调用的便利与缺陷，识别并行、错误传播、变量传递和依赖图被切断的问题

**非递归组织** ---- 了解在一个顶层 Makefile 中维护完整依赖图的思路，知道什么时候它比递归调用更可靠

**生成配置** ---- 处理平台检测、版本信息、编译数据库和构建元数据，区分生成源码、生成配置与临时文件

**重点在这** ---- 项目拆分要服务于依赖图和团队协作，不要因为目录多就自动复制十份“进入子目录再 make”的咒语

## 第五站：头文件与自动依赖

第五站是 C/C++ 构建的侦探科。源文件改了容易发现，头文件改了却可能影响几十个目标；如果依赖没记全，Make 会自信地交付一份旧程序。

**头文件依赖** ---- 理解源文件、直接头文件、间接头文件与目标文件的关系，知道时间戳只在依赖图完整时才可靠

**编译器生成依赖** ---- 使用编译器选项生成依赖文件，并在构建中包含它们，避免手写头文件清单随项目一起腐烂

**依赖文件缺失** ---- 处理第一次构建、清理后构建、生成失败和空依赖文件，保证自动包含不会让新环境直接摔倒

**生成文件顺序** ---- 规划生成头文件、代码生成器和编译任务的关系，防止并行构建时“文件还没出生，编译已经来催”的竞态

**接口与实现边界** ---- 通过头文件依赖观察模块耦合，识别一个小改动触发大量重编译的结构性原因

**重点在这** ---- 能让增量构建在头文件、生成代码和清理重建场景下都正确，速度建立在依赖事实而不是运气上

## 第六站：Shell、命令与跨平台边界

第六站是 Make 的外交部。Make 负责调度，Shell 负责执行；两个脾气不同的角色住在同一个配方里，换平台时最容易互相甩锅。

**配方执行模型** ---- 理解每行命令的 shell 边界、工作目录、错误码和回显行为，知道为什么上一行的变量不会自动活到下一行

**Shell 选择** ---- 处理 POSIX Shell、Bash、PowerShell 和 Windows 环境差异，声明必要假设，避免把个人终端习惯伪装成项目标准

**错误传播** ---- 使用严格错误策略、命令前缀和显式检查，让失败及时中断；沉默失败是构建系统最会演的假笑

**环境变量** ---- 区分 Make 变量、Shell 变量、导出变量和命令行变量，防止路径、代理、编译器和秘密被意外覆盖或泄露

**路径与空格** ---- 处理绝对路径、相对路径、空格、通配符和特殊字符，理解跨平台路径规范化的边界

**命令注入风险** ---- 不把不可信输入直接拼进 Shell 命令，限制下载、发布和部署目标，构建脚本也属于软件供应链的一部分

**重点在这** ---- 能说清一条命令由谁解释、在哪执行、失败如何返回、跨平台会不会变形

## 第七站：并行构建与竞态

第七站给 Make 装上多车道。并行构建能把等待时间压下去，但它不会自动把隐藏依赖变成显式依赖；没有依赖关系的任务同时跑，正是它的工作方式。

**并行执行** ---- 了解并行参数、作业槽位、负载和输出交错，先保证依赖图完整再提高并发

**独立目标** ---- 区分可以并行的目标与必须排序的目标，识别共享目录、共享生成文件和共享临时文件带来的冲突

**顺序约束** ---- 使用有序前置依赖表达真正的顺序要求，避免把“看起来先写在上面”当作同步机制

**竞态诊断** ---- 复现偶发失败、删除构建目录重跑、降低并发并对照日志，定位隐式依赖与不安全脚本

**输出管理** ---- 让并行日志可读、临时产物隔离、失败目标可追踪，减少“十个命令一起吵架，只听见一个错误”的体验

**性能边界** ---- 评估 CPU、磁盘、网络、链接器和测试资源，知道并发开到最大不一定是最快

**重点在这** ---- 并行不是开关，而是对依赖图质量的考试；越能并行，越说明边界说得越清楚

## 第八站：测试、安装与发布目标

第八站是 Make 的服务台。`all` 只是入口，`test` 负责信心，`install` 负责落地，`package` 负责交付；目标命名要让人能猜到动作和副作用。

**测试目标** ---- 组织单元测试、集成测试、静态检查和覆盖率目标，区分快速反馈与昂贵验证

**安装目标** ---- 处理头文件、库、二进制、配置和文档的安装路径，支持 DESTDIR 等暂存方式，避免测试时直接污染系统

**清理目标** ---- 区分 clean、distclean、maintainer-clean 等清理级别，明确哪些文件可重建、哪些生成物可能包含用户数据

**打包目标** ---- 组织归档、版本信息、校验和、符号文件和发布清单，确保包内路径和来源可追溯

**开发与发布模式** ---- 区分调试、发布、分析、交叉编译和 sanitizer 配置，避免把优化选项与诊断选项搅成一锅汤

**安装安全** ---- 限制安装路径、权限、脚本副作用和网络下载，审查发布目标是否会执行不必要的特权操作

**重点在这** ---- 能从一个目标名判断它会生成什么、写到哪里、是否可重复执行、失败后如何清理

## 第九站：CI、可复现与故障排查

第九站让 Make 走进 CI。自动化环境没有你的别名、缓存和“上次留下的那个目录”，所以它会诚实地暴露构建脚本的所有小秘密。

**干净构建** ---- 在干净工作区、固定工具链和隔离缓存中验证完整构建，避免本机遗留文件提供虚假成功

**工具链锁定** ---- 记录编译器、链接器、SDK、Shell 和关键工具版本，识别环境漂移造成的差异

**构建日志** ---- 保留命令、版本、配置、依赖摘要、失败目标和产物清单，让退出码背后有完整故事

**故障分类** ---- 从目标缺失、规则匹配、变量展开、头文件依赖、Shell 错误、权限、网络和并行竞态建立排查顺序

**可复现构建** ---- 控制时间戳、路径、文件排序、区域设置和随机生成信息，尽量让同一提交产生可比较的产物

**CI 安全** ---- 对下载工具、编译脚本、环境变量、缓存和发布凭据使用最小权限，禁止把秘密回显到日志

**重点在这** ---- 能从一段 Make 日志还原目标图、变量值和执行命令，并能在不删光所有缓存的情况下定位根因

## 第十站：Make 与现代构建生态

最后一站是工具选型室。Make 是优秀的依赖图老兵，但它不必负责所有事情；CMake、Ninja、Bazel、Meson 或语言专用工具各有舒适区。

**Make 的适用范围** ---- 适合小型项目、Unix 工具链、胶水任务、源码阅读和已有生态维护，理解它的低依赖与高透明度优势

**CMake 与生成器** ---- 认识 CMake 负责描述项目，Make 或 Ninja 负责执行，区分配置阶段、生成阶段和构建阶段

**Ninja 与执行性能** ---- 理解 Ninja 的窄职责、快速调度和与 IDE/生成器的关系，知道它为什么常被放在后端而不是手写入口

**大型构建系统** ---- 了解 Bazel、Buck、Meson 等在远程缓存、沙箱、可复现和多语言项目上的取舍，不把规模问题硬塞进一个 Makefile

**迁移边界** ---- 根据项目规模、语言、平台、团队、缓存、IDE 和发布需求决定继续维护还是迁移，并保留可验证的过渡路径

**重点在这** ---- 会用 Make 不等于必须永远用 Make；懂得依赖图、执行模型和迁移成本，才是真正掌握构建工具

## 通关标准

**Make 新手能看懂规则** ---- 能读懂目标、依赖、配方、变量和伪目标，完成编译、测试与清理。

**初级工程师能维护项目** ---- 能写模式规则、自动生成头文件依赖、处理配置和常见 Shell 边界。

**中级工程师能解决并行问题** ---- 能维护多目录构建、设计完整依赖图、诊断竞态并支持 CI 与交叉编译。

**高级工程师能做工具决策** ---- 能比较 Make、CMake、Ninja 与大型构建系统，围绕正确性、性能、可复现和团队成本做选择。

## 结语

Make 的语法像老式工具箱，规则却像一张清晰的地图：目标在哪里、依赖是什么、哪一步需要重做，一目了然。先把依赖图画对，再谈并行和缓存；先让失败诚实，再谈自动发布。等你能让一个跨平台项目在干净环境中稳定构建，Make 这位老兵就不再只是“会写 Tab 的人”，而是你理解所有现代构建系统的第一位教练。
