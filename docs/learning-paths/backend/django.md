# Django 学习路线

Django 是 Python 后端的全家桶：路由、视图、ORM、模板、表单、认证、Admin 和安全防护都已经在厨房里摆好了。它不是只递给你一把螺丝刀，然后让你自己寻找剩下的墙；它更像先给你一套能住人的房子，再带你理解每根承重墙为什么这么放。内容管理、电商后台、企业系统、SaaS 和数据驱动的 Web 应用，都很适合从 Django 起步；极致实时或极致高并发场景，则要把异步、任务队列和其他服务一起纳入设计。

这条路线是**指引和索引**，不是 API 字典，也不是把整本教程压缩成一页。每一站只负责告诉你应该建立什么心智模型、要覆盖哪些常用与不常用的知识、应该继续向哪些深层问题追问。后续学习笔记可以按这些关键词展开，但路线页先保持独立、清爽，不把读者直接拽进链接迷宫。

路线按 **项目与环境 → URL 与视图 → 模板与静态资源 → 模型与 ORM → 表单与校验 → 认证与 Admin → API → 中间件与状态 → 安全 → 异步与任务 → 测试与调试 → 部署与性能** 推进。

## 第一站：项目结构与开发环境

欢迎来到 Django 的项目新手村：manage.py 是村口传令官，settings.py 是总管家，app 是各自负责一块业务的施工队。先把项目、应用、配置和依赖的边界画清楚，后面才不会把所有东西都塞进一个“临时先用着”的文件里，最后临时用了三年。

**Python 环境与依赖** ---- 掌握虚拟环境、解释器版本、依赖安装、依赖锁定和可重复构建；开发机能跑不等于换台电脑也能跑

**项目与应用的区别** ---- 理解 project 负责全局配置与入口，app 负责一组可复用的业务能力；一个项目可以有多个 app，但 app 之间不该互相偷拿对方的抽屉钥匙

**项目初始化** ---- 熟悉项目创建、应用创建、开发服务器、第一次请求和基础目录；开发服务器只用于开发，不是线上迎宾员

**命令行工作流** ---- 覆盖项目检查、交互式 Shell、数据库迁移、超级用户、静态资源收集、测试和数据导入导出等常用命令；命令不是背诵题，而是每个阶段的排障入口

**配置主干** ---- 建立 INSTALLED_APPS、MIDDLEWARE、DATABASES、TEMPLATES、静态资源、媒体文件、认证模型、调试模式和允许主机之间的关系

**配置分层** ---- 将密钥、数据库连接、第三方服务和环境差异放到环境变量或分环境配置中；不要让生产密码跟着代码一起旅行

**应用注册与启动顺序** ---- 了解应用配置、应用加载、信号注册、迁移发现和 URL 入口；很多“明明写了却没生效”的问题，本质是启动阶段没走到那里

**目录组织** ---- 认识模型、视图、表单、管理后台、模板、静态资源、迁移和测试的常见边界；目录结构要帮助定位问题，而不是考验考古能力

**开发与生产的差异** ---- 区分开发服务器与生产服务器、本地数据库与生产数据库、调试日志与结构化日志；本地方便的默认值，到了线上可能变成小型事故

**重点在这** ---- Django 的约定优于配置，不是让你停止思考，而是先沿着稳定约定建立项目骨架，再把真正有必要的差异显式写出来

## 第二站：URL、请求与视图

第二站来到 Django 的交通局：URLconf 是路牌，视图是调度员，request 带着乘客进站，response 负责把结果送回去。先理解请求如何找到代码，再讨论函数视图、类视图和业务分层；不然路由表很快会长成一张谁也不敢改的地铁图。

**URLconf 匹配** ---- 掌握路径、包含、动态参数、路径转换器、匹配顺序和命名空间；URL 是外部契约，不是散落在模板和 JavaScript 里的字符串

**反向解析** ---- 理解路由命名、反向生成和模板中的地址解析；路由调整时，调用方应该跟着契约走，不要全项目搜索字符串祈祷遗漏得少一点

**请求对象** ---- 覆盖请求方法、查询参数、路径参数、表单数据、请求头、Cookie、Session、上传文件和请求体；先分清数据从哪里来，再谈怎么使用

**响应对象** ---- 认识 HTML、JSON、重定向、文件、流式响应、响应状态码、响应头和缓存控制；返回结果不仅是“把数据发出去”，还要表达这次请求发生了什么

**函数视图** ---- 理解函数视图、模板渲染、重定向、JSON 返回、快捷查询和装饰器；简单流程用函数表达往往最直白，不必为了显得高级而套三层抽象

**类视图** ---- 认识基础类视图、模板视图、列表视图、详情视图、创建视图、更新视图和删除视图；先理解生命周期，再决定哪些行为适合配置、哪些行为应该覆写

**Mixin 组合** ---- 学习登录要求、权限要求、通用查询和表单处理等 mixin 的职责与顺序；mixin 是积木，不是把十个不相干的业务规则叠成一座塔

**错误与边界** ---- 处理 404、403、405、500、空结果、失效请求和异常页面；错误反馈要让用户能理解，也要让日志留下可以排查的上下文

**视图与业务分层** ---- 让视图负责协调请求和响应，复杂业务下沉到模型方法、服务层或领域函数；一个视图同时管支付、库存、邮件和权限时，它已经该减肥了

**请求生命周期** ---- 串起 URL 匹配、中间件、视图、模板或序列化、响应返回的完整链路；知道请求走过什么，比只会背某个装饰器更能排查问题

**重点在这** ---- URL 是应用的外部入口，视图是协议适配层；两者都应该清楚、可测试、可替换，而不是成为所有业务逻辑的集散地

## 第三站：模板、静态文件与页面输出

第三站进入 Django 的页面剧场：模板负责排练视图，继承负责搭舞台，静态文件负责灯光，自动转义则像门口的保安。页面能显示只是起点，真正要学的是数据边界、复用方式和浏览器拿到资源时发生了什么。

**变量与表达式** ---- 掌握模板变量、属性访问、默认值、空值行为和上下文范围；模板适合表达展示，不适合偷偷长出一套业务规则

**标签体系** ---- 覆盖条件、循环、地址、静态资源、CSRF、包含、上下文绑定、循环信息和空列表分支等常用能力；标签越方便，越要知道它不该承担什么

**过滤器** ---- 了解日期、长度、默认值、转义、截断、连接、自定义过滤器和过滤器链；过滤器适合轻量展示变换，不应该变成藏起来的服务层

**模板继承** ---- 用基模板、区块和子模板组织页面骨架；布局应该集中维护，不要每个页面复制一份 header，等第八份出现时才开始怀疑人生

**包含与片段复用** ---- 用包含拆分导航、表格、分页、提示和表单片段，理解上下文传递与局部复用的边界；复用片段要有稳定输入，不要依赖一堆隐形全局变量

**上下文处理器** ---- 理解公共数据、当前用户、站点配置等信息的注入方式；全局数据要克制，否则每个模板都背着一整个数据库结果集

**自动转义与安全输出** ---- 认识自动转义、可信 HTML、富文本清洗和禁用转义的风险；“这段内容来自自己的数据库”不是 XSS 豁免证

**静态资源** ---- 区分样式、脚本、图片、字体与用户上传媒体，掌握开发期查找、生产收集、缓存命名和部署路径；静态资源应该像货物，不该像每次请求临时现做的手工艺品

**媒体文件** ---- 理解用户上传、文件名、大小、类型、存储后端、访问权限和删除策略；用户文件不是静态资源，也不能因为开发环境能访问就默认线上会替你保存

**模板性能** ---- 关注模板内重复查询、N+1、分页、片段缓存、响应体积和渲染时间；模板只是最后一棒，慢通常在更早的数据准备阶段就决定了

**重点在这** ---- 模板层要让页面结构清晰、输出安全、资源可部署；复杂逻辑回到 Python 层，安全边界则要在模板和后端两边同时守住

## 第四站：模型、迁移与 ORM

第四站来到 Django 的数据库心脏：模型是领域对象的蓝图，迁移是数据库的版本记录，QuerySet 是一张尚未真正执行的购物清单。ORM 会帮你省掉大量 SQL，但不会替你决定数据边界、索引和事务；它只是把犯错的姿势变得更优雅。

**模型与字段地图** ---- 覆盖文本、数字、时间、布尔、邮箱、URL、UUID、JSON、文件和自定义字段等常见与特殊类型；路线只建立分类和选择意识，具体类型的细节留给学习笔记

**字段约束** ---- 理解默认值、可空、表单可空、唯一性、选项集合、数据库索引、展示名称和可编辑性；数据库约束和表单约束不是一回事，不能只在页面上假装认真

**模型元数据** ---- 关注默认排序、表名、联合约束、条件约束、索引、权限名称和模型展示信息；让数据库结构服务于查询与业务，而不是只追求模型类看起来短

**关系建模** ---- 掌握一对多、多对多、一对一、反向关系、自定义关联表和关联字段；先说清关系的拥有者、生命周期和删除语义，再决定字段写法

**删除策略** ---- 理解级联删除、禁止删除、置空、置默认和自定义处理的业务后果；级联很方便，但可能一口气带走一整串你以为只是“删一条记录”的数据

**迁移工作流** ---- 建立“改模型、生成迁移、检查迁移、执行迁移、发布迁移”的完整心智模型；迁移是版本化的数据库变更，不是开发者手写 SQL 后留下的一张便签

**迁移进阶** ---- 了解数据迁移、可逆迁移、空迁移、迁移依赖、迁移合并、历史模型状态和大表变更风险；能生成迁移只是入门，能安全发布迁移才算进入生产世界

**QuerySet 惰性** ---- 理解查询条件如何累积，以及遍历、切片、计数、长度和列表转换何时触发数据库访问；惰性不是不执行，只是晚一点执行

**查询表达式** ---- 覆盖双下划线条件、与或非组合、数据库端字段计算、条件表达式、子查询、存在性判断和窗口函数；先学会读查询意图，再追求写法短

**聚合与注解** ---- 区分整表聚合与逐行派生值，理解分组、连接、空值、重复计数和聚合结果的业务含义；能算出来不代表算对了

**事务与并发** ---- 掌握原子事务、锁、隔离级别、唯一约束、乐观更新、悲观锁和幂等；“正常情况下不会同时发生”不算并发策略

**查询性能** ---- 认识单值关系预加载、多值关系预取、只取需要的列、批量读写、分页和迭代器；列表页性能的第一课，是别让 20 条数据发出 21 次查询

**索引与查询计划** ---- 学习索引的选择性、联合索引顺序、排序与范围条件、慢查询和数据库执行计划；索引不是越多越好，每个索引都会给写入和存储收账单

**原生 SQL 边界** ---- 理解什么时候 ORM 足够、什么时候需要原生查询、参数绑定和数据库特性；原生 SQL 是工具，不是 ORM 写不出来时的情绪出口

**重点在这** ---- ORM 的高级能力不在于把 Python 写得像 SQL，而在于能从数据模型、查询计划、事务和业务一致性一起做判断

## 第五站：表单、校验与用户输入

第五站来到表单质检车间：用户输入像刚从野外回来的包裹，必须验收、清洗、分类，不能因为浏览器已经校验过一次就直接放进数据库。Django Form 负责把输入变成可信的业务数据，ModelForm 帮你减少重复劳动，但不会替你决定权限。

**表单结构** ---- 掌握字段、标签、控件、初始值、帮助文本、必填状态和显示顺序；表单不仅是 HTML 外壳，也是输入契约

**绑定状态** ---- 区分未绑定表单、绑定表单、初始数据、提交数据和文件数据；什么时候应该回显，什么时候应该清空，决定了用户体验是否像在和一个有记性的系统打交道

**校验生命周期** ---- 理解字段校验、单字段清洗、跨字段清洗、复用验证器、整体校验和清洗后数据；校验要靠近数据边界，但跨字段规则也要有清晰归属

**错误反馈** ---- 设计字段错误、非字段错误、错误顺序、用户提示和模板展示；错误信息是用户体验的一部分，不是调试时顺便打印一下

**ModelForm** ---- 理解模型到表单的字段映射、字段白名单、保存过程、延迟保存和自定义保存逻辑；自动生成不等于自动安全

**批量赋值边界** ---- 明确哪些字段允许用户提交，哪些字段只能由服务端决定；价格、归属、审批状态和权限字段不能因为表单少写几行就开放编辑

**FormSet 与 InlineFormSet** ---- 处理同一页面多条记录和父子记录编辑，关注删除标记、数量限制、重复数据、事务边界和错误展示

**文件上传** ---- 覆盖请求文件、大小、类型、文件名、内容验证、存储后端、访问权限和恶意内容；扩展名看起来像图片，不代表内容真的像图片

**表单视图** ---- 理解 POST/Redirect/GET、成功跳转、失败回显以及通用创建、更新、删除视图的生命周期

**服务端校验** ---- 前端校验负责及时反馈，后端校验负责真正守门；任何来自浏览器的数据都应当被视为不可信输入

**重点在这** ---- 表单不是 HTML 的装饰层，而是输入校验、数据清洗、错误反馈和权限边界组成的小型应用协议

## 第六站：认证、权限与 Admin

第六站进入 Django 的身份管理所：认证回答“你是谁”，权限回答“你能做什么”，Admin 则像一间已经装修好的内部运营办公室。它们都很省时间，但省下来的时间应该拿去设计边界，而不是把 Admin 当成面向所有用户的产品界面。

**用户模型选择** ---- 尽早决定默认用户、自定义用户和 Profile 扩展的边界，理解用户模型替换的迁移成本；项目上线后再换身份模型，通常是给自己安排一场长途搬家

**认证流程** ---- 掌握登录凭证校验、登录态建立、登出、会话失效、密码修改、密码重置和登录失败处理

**密码安全** ---- 理解密码哈希、迭代成本、升级策略、泄露后的处置和多因素认证的扩展方向；密码不是拿来加密后放数据库的纪念品

**视图保护** ---- 使用登录要求、权限要求、用户组和对象权限保护资源；隐藏按钮不是权限控制，服务端拒绝才是

**模型权限与分组** ---- 认识新增、修改、删除、查看等默认权限，理解用户权限、用户组、对象级权限和业务角色的差异

**会话与 Cookie** ---- 关注登录态、会话过期、Cookie 安全属性、跨站行为、并发登录和多设备策略；“记住我”背后是生命周期和风险取舍

**Admin 注册** ---- 掌握模型注册、列表字段、过滤、搜索、只读字段、字段分组、关联编辑和批量操作等后台能力

**Admin 业务化** ---- 为内部运营设计搜索、过滤、批量处理、审计信息和误操作保护；后台好用不等于可以绕过所有业务规则

**Admin 与 C 端边界** ---- Admin 适合内部管理和运营，不适合直接当作面向客户的产品；客户流程需要自己的视图、权限、错误反馈和体验设计

**认证异常** ---- 处理过期会话、禁用用户、权限变化、并发请求、重置链接和登录失败限速；身份系统最怕的是“偶尔能绕过去”

**重点在这** ---- 身份、权限、会话和后台管理是四个相关但不同的问题；把它们分开建模，系统才不会出现“能登录所以什么都能做”的惊喜

## 第七站：Django REST Framework 与 API

第七站来到 API 车站：Serializer 是检票口，ViewSet 是调度台，Router 自动铺轨，权限和限流负责防止整辆车被陌生人开走。DRF 让 Django 很适合前后端分离，但“能返回 JSON”只是 API 的幼儿园阶段，契约、错误、权限、分页和版本才是成年人的账单。

**API 的请求与响应** ---- 建立资源、动作、状态码、请求体、响应体、请求头和错误结构的整体概念；API 不是把 HTML 标签换成 JSON 就毕业

**序列化与反序列化** ---- 理解数据输出、输入校验、字段转换、嵌套关系、只读字段和写入边界；输出模型与输入模型不一定应该长成同一张脸

**模型序列化** ---- 了解模型字段映射、关联对象、批量数据、创建更新流程和自定义校验；自动映射节省时间，但暴露哪些字段仍由你负责

**函数 API 与类 API** ---- 对比函数式接口、APIView、通用视图和 ViewSet 的职责与适用场景；抽象不是越多越好，关键是团队能预测它会怎么工作

**路由与资源动作** ---- 理解路由注册、标准增删改查、自定义动作、嵌套路由、资源命名和 URL 版本；自动生成的路由很快，但业务动作仍然要清晰

**验证与错误格式** ---- 统一字段错误、业务错误、资源不存在、权限失败、限流和服务器异常的表达；错误结构也是前端和其他服务依赖的契约

**认证与权限** ---- 覆盖会话认证、令牌认证、JWT、全局权限、视图权限、对象权限和自定义权限；默认收紧，再按资源开放

**过滤、搜索与排序** ---- 设计过滤字段、搜索范围、排序白名单和查询组合；允许客户端排序不代表允许它把数据库所有列都拿来试

**分页与限流** ---- 理解页码、偏移、游标等分页思路，以及匿名用户、登录用户和敏感接口的限流策略；列表接口没有边界，数据量一上来就会给自己发加班邀请

**接口版本与兼容** ---- 认识路径版本、请求头版本、字段新增、字段弃用、兼容窗口和迁移通知；版本不是复制一份目录就结束，而是长期维护承诺

**接口文档与契约** ---- 描述输入、输出、认证、错误、示例和废弃状态，理解文档、测试和实现之间的同步关系；联调不应该靠两边各自猜测

**API 分层** ---- 让接口层负责协议协调，序列化层负责输入输出，服务层负责复杂业务；一个方法塞满查询、授权、发邮件和事务时，已经不是简洁了

**重点在这** ---- API 的核心不是把页面换成 JSON，而是建立稳定、可验证、可授权、可演进的服务契约

## 第八站：中间件、信号、会话与缓存

第八站是请求生命周期的后台机房：中间件像一串关卡，信号像广播，session 像用户寄存柜，缓存像快速取件柜。它们都很方便，也都容易变成隐式魔法；越是全局生效的能力，越要让执行顺序和失效方式可追踪。

**中间件顺序** ---- 理解请求从上到下、响应从下到上的执行顺序，掌握安全、会话、认证、CSRF、通用处理和消息等内置能力的职责

**自定义中间件** ---- 用于计时、请求上下文、响应头、审计和统一处理；中间件适合横切关注点，不适合藏一段只有某个页面需要的业务

**信号机制** ---- 认识保存前后、删除前后、请求异常等信号和接收器注册方式，理解隐式触发对调试、事务和测试的影响

**信号的边界** ---- 信号适合缓存失效、审计、轻量关联创建等解耦场景；核心业务流程、支付状态和复杂联动尽量显式调用，不要让数据变化偷偷召唤半个系统

**Session 与消息** ---- 掌握会话数据、过期时间、消息提示和登录态的存储语义；会话不是数据库替代品，大对象和高频数据别住进去

**Cookie 与跨站行为** ---- 理解 HttpOnly、Secure、SameSite、CSRF Cookie 和站点边界；浏览器自动携带 Cookie 的便利，也意味着你必须认真设计跨站请求

**缓存层级** ---- 区分整页缓存、模板片段缓存和低级缓存接口，理解 key、过期、主动失效、缓存穿透、击穿和雪崩

**Redis 与分布式部署** ---- 了解本地内存缓存与 Redis 的差异，理解多进程、多实例环境下缓存、会话和锁为什么不能只放在单机内存里

**缓存一致性** ---- 处理写入、读取、更新、删除、并发失效和热点数据；缓存不是数据库的第二个自我，失效策略必须先于缓存代码出现

**邮件与外部服务** ---- 认识超时、重试、失败记录、幂等和异步化边界；请求里直接等待第三方服务，用户会被迫陪它一起思考人生

**文件存储** ---- 理解本地存储、对象存储、存储后端、文件清理和访问权限；文件生命周期要和业务删除策略一起设计

**重点在这** ---- 全局机制的价值是统一处理横切问题，风险是行为变得隐形；使用它们时必须能回答“什么时候执行、谁触发、如何失效、怎么测试”

## 第九站：安全与生产边界

第九站进入 Django 的城墙：框架默认帮你挡住不少攻击，但默认安全不是免死金牌。CSRF、XSS、SQL 注入、点击劫持和密码哈希都有现成机制，真正的难点是别在自定义响应、原生 SQL、文件上传和部署配置里亲手把城门打开。

**威胁建模** ---- 从用户、管理员、第三方服务、浏览器、数据库和部署环境出发，识别资产、信任边界、攻击面和失效后的影响

**CSRF 防护** ---- 理解令牌、中间件、模板表单、异步请求头和 API 场景下的认证选择；关闭 CSRF 不是修复跨域问题，而是把问题改名

**XSS 与输出** ---- 掌握模板自动转义、富文本清洗、可信 HTML 和用户内容展示策略；任何“这段 HTML 看起来没问题”的判断都应该有明确的信任来源

**SQL 注入** ---- 优先使用 ORM 参数化查询，理解原生 SQL、动态排序和条件拼接的风险；数据库查询能跑不等于输入边界安全

**点击劫持与安全响应头** ---- 认识安全中间件、框架选项、内容类型保护、点击劫持防护、HSTS 和内容安全策略的作用与部署条件

**生产配置检查** ---- 关闭调试模式、限制允许主机、启用安全 Cookie、配置 HTTPS、代理头和环境变量；上线前要把配置当成代码审查

**认证与授权边界** ---- 每个写操作都要重新检查对象权限、资源归属和状态流转；前端隐藏入口只是体验，后端拒绝才是安全

**文件与反序列化** ---- 校验上传大小、类型、内容与访问权限，谨慎处理不可信序列化数据和外部回调；用户上传目录不是代码执行游乐场

**依赖与密钥** ---- 固定并审查依赖版本，及时处理安全更新，密钥只从安全配置注入；日志也不能把 token、密码和完整个人数据当纪念品保存

**API 跨域与限流** ---- 精确配置跨域来源、认证方式、CSRF 策略、登录限速、接口限流和重放风险；星号是省事的符号，不是安全架构

**安全测试与响应** ---- 覆盖越权、未登录访问、错误信息泄露、上传绕过、限流失效和依赖漏洞；发现问题后还要有隔离、修复、通知和复盘流程

**重点在这** ---- Django 的安全能力要理解原理、确认配置、覆盖测试；安全不是某个中间件的单项成绩，而是数据从输入到存储再到输出的完整链路

## 第十站：异步、任务队列与实时通信

第十站是 Django 的交通升级站：WSGI 适合经典请求响应，ASGI 让异步和长连接有了入口，任务队列负责把重活搬到后台，Channels 则让 WebSocket 不再需要你从零造一座桥。先分清“请求内异步”和“请求外任务”，不要看到 async 就把所有函数都换装。

**WSGI 与 ASGI** ---- 理解同步服务器、异步服务器、请求生命周期和部署方式的差异；Django 可以接入异步能力，但不代表所有依赖都会自动变成异步

**异步视图** ---- 了解异步视图、阻塞库、事件循环、同步桥接和线程池；同步文件操作、数据库调用和第三方 SDK 在异步链路里需要明确隔离

**异步 ORM 边界** ---- 认识 ORM 的同步与异步调用方式、事务限制和同步桥接的代价；把同步代码包起来不等于它突然拥有了异步性能

**任务队列模型** ---- 理解消息代理、任务消费者、结果存储、任务重试、失败任务和定时调度之间的关系；任务队列不是把函数换个名字就自动可靠

**任务设计** ---- 为邮件、报表、图片处理、通知和重计算设计幂等、超时、重试、死信与失败记录；非幂等任务重试前要先算账

**事务与任务** ---- 理解数据库提交和异步任务发送的先后关系，必要时使用事务提交后的回调；别让 worker 比数据库更早收到“这条记录已经存在”的消息

**定时任务** ---- 认识定时调度、重复执行、时区、任务锁和错过执行窗口；定时任务最可怕的不是没跑，而是悄悄跑了三遍

**实时通信** ---- 掌握 Consumer、路由、连接生命周期、频道层、Redis 群组广播和断线重连的基本模型

**轮询、SSE 与 WebSocket** ---- 比较三种实时方案在连接、方向、代理、扩容、断线和消息可靠性上的差异；实时不是任何地方都保持连接，而是业务确实需要及时推送

**异步可观测性** ---- 为任务记录追踪标识、状态、耗时、重试次数、失败原因和人工重放入口；后台任务没有页面可点，更需要日志告诉你它去了哪里

**重点在这** ---- 异步的价值是合理安排等待与工作，不是给代码增加几个 await；先判断任务是否应离开请求，再选择 ASGI、队列或实时通信方案

## 第十一站：测试、调试与质量反馈

第十一站进入 Django 的质检车间：模型测试检查数据规则，表单测试检查输入，客户端测试跑请求链路，API 测试守住对外契约，调试工具负责还原案发现场。测试不是给代码写悼词，而是让你敢于修改它。

**测试基础** ---- 掌握测试用例、测试数据库、事务隔离、测试发现、测试命令和测试环境配置；每个测试都应该能独立运行，不依赖上一个测试留下的好运气

**模型与查询测试** ---- 覆盖模型方法、约束、关系、QuerySet、自定义 Manager、聚合和边界数据；不要只测对象能创建，还要测它在错误输入下会怎样

**迁移测试** ---- 检查迁移可执行、迁移顺序、数据迁移、历史数据兼容和大表变更风险；迁移也是代码，也需要被审查

**表单与校验测试** ---- 验证必填、格式、跨字段、权限字段、文件上传和错误消息；表单测试是批量赋值与业务规则的安全网

**视图与客户端测试** ---- 检查状态码、模板、上下文、重定向、登录状态、权限矩阵和请求方法；地址应该通过路由反向解析生成，别让测试和 URL 字符串互相绑架

**API 测试** ---- 覆盖序列化、分页、过滤、认证、权限、错误格式、版本和重复提交；正常路径重要，401、403、404、422 同样重要

**数据工厂与夹具** ---- 了解固定数据、数据工厂、测试夹具和测试数据隔离；数据要像真实业务，但不要让每个测试都手工盖一座数据城

**Mock 与外部服务** ---- 对邮件、支付、对象存储、第三方 API 和任务队列做边界替换；Mock 的目标是隔离不稳定依赖，不是把所有真实逻辑都 Mock 成绿色

**调试工具** ---- 使用 SQL 查询面板、断点、日志、请求追踪和性能分析定位 N+1、慢查询、重复请求与模板问题

**覆盖率与 CI** ---- 把测试、迁移检查、格式检查、静态检查和覆盖率接入持续集成；绿色流水线不是质量证明，但没有反馈的流水线更像装饰

**测试分层** ---- 区分模型、服务、视图、API、端到端和冒烟测试的边界；测试数量不是越多越好，关键是失败时能阻止哪类回归

**重点在这** ---- 测试要围绕用户可观察行为、业务不变量和权限边界；覆盖率数字可以参考，真正重要的是它能否让团队安心修改代码

## 第十二站：部署、性能与持续交付

最后一站来到生产车站：代码通过测试只是拿到车票，真正发车还要处理服务器、数据库、静态文件、迁移、日志、监控、回滚和容量。Django 的成熟感不只在于能写页面，还在于它能让团队把上线变成流程，而不是节日限定的勇气测试。

**生产服务器** ---- 区分开发服务器、WSGI、ASGI 和长连接服务器的适用边界；进程数、线程数、超时和连接数要根据负载验证，不要只背一个公式

**反向代理与 HTTPS** ---- 了解代理如何终止 TLS、转发请求、提供静态文件、设置代理头与缓存；应用知道自己在 HTTPS 后面，安全跳转才不会自我打架

**静态与媒体部署** ---- 规划静态资源收集、CDN、对象存储、媒体访问和缓存策略；静态文件是构建产物，用户上传文件是业务数据，不能混为一谈

**数据库发布** ---- 设计生产数据库、连接池、备份、恢复演练、迁移顺序和数据兼容；发布时先让旧代码能理解新结构，再逐步切换

**容器化** ---- 了解镜像、非 root 用户、环境变量、健康检查、日志输出、网络和多服务编排；容器不是把开发目录压缩后搬到服务器

**日志与错误监控** ---- 配置结构化日志、请求标识、异常上报、敏感数据脱敏和日志轮转；线上错误要能回答哪个请求、哪一步、花了多久

**性能第一层：查询** ---- 优先排查 N+1、缺失索引、重复查询、过度取列、不必要聚合和慢 SQL；预加载是起点，不是性能优化的终点

**性能第二层：缓存与任务** ---- 将热数据缓存、慢任务异步化、列表分页、响应裁剪和文件交给合适的存储；缓存命中率与失效策略要一起观察

**性能第三层：容量** ---- 根据请求耗时、数据库连接、队列长度、内存、CPU 和外部服务延迟调整进程与扩容策略；加机器之前先确认瓶颈到底在哪

**健康检查与发布** ---- 设计存活、就绪、依赖检查、优雅停机、回滚、版本记录和发布后的验证；部署成功的标准不是进程没退出，而是服务能稳定接客

**持续交付** ---- 把测试、迁移、静态收集、镜像构建、发布、监控和回滚串成可重复流程；上线不靠某位同事记得所有命令，是工程成熟的重要信号

**重点在这** ---- 生产能力是代码、数据库、网络、运行时和团队流程的合奏；性能优化先测量，部署变更先留回滚路，出了问题先保留证据

## 通关标准

**Django 新手村能跑通项目** ---- 能创建项目和 app，配置 URL、模板、静态文件和数据库，完成一个最小 CRUD。页面能打开只是第一关，manage.py 还没有开始对你发出神秘命令。

**初级后端能交付业务** ---- 能用模型、迁移、QuerySet、表单、登录、权限和 Admin 做出可用后台，知道可空与表单可空、单值预加载与多值预取不是面试用的双胞胎。

**中级后端能守住边界** ---- 能设计清晰的视图分层、输入校验、对象权限、缓存、文件处理和 API 契约，能定位 N+1、重复提交和越权访问。代码不只会跑，还知道不该跑到哪里。

**高级后端能稳定扩展** ---- 能做出带认证、权限、分页、过滤、错误格式和版本策略的 API，能结合任务队列、Redis、事务和测试设计可靠流程。异步任务不会因为一句“应该只执行一次”就真的只执行一次。

**Django 老兵能负责生产** ---- 能完成安全配置、部署、监控、性能分析、迁移发布和回滚，能根据业务选择同步、异步、任务队列或其他服务。Django 替你做了很多决定，但真正的工程师知道什么时候接受约定，什么时候明确拒绝默认值。

## 下一站去哪

- **Python** ---- 补齐语言、标准库、类型、并发和工程基础
- **数据库** ---- 深入 SQL、索引、事务、PostgreSQL 和数据建模
- **Web 安全** ---- 把认证、授权、输入输出和部署安全串成完整防线
- **API 设计** ---- 从服务端渲染页面走向稳定的资源契约
- **任务队列** ---- 把耗时工作从请求链路中搬出去
- **部署与监控** ---- 把“本地能跑”升级成“线上可维护”

## 结语

Django 的魅力不在于它把每件事都做成最轻量的零件，而在于它把成熟 Web 应用常见的骨架、默认安全和工程流程提前摆到你面前。先沿着约定把项目做出来，再理解 ORM、请求生命周期、权限、缓存和部署背后的取舍；当你能解释为什么这样设计，Django 就不再是全家桶，而是一套可以被你驾驭的工程系统。
