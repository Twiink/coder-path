# JUnit 学习路线

JUnit 是 Java 测试世界那位穿着实验服、做事讲生命周期的老教授：JUnit 5 把平台、引擎和 Jupiter 编程模型拆开，让测试既能在 IDE 里单步调试，也能在 Maven、Gradle 和 CI 里稳定运行。它不替你决定测试什么，只提供一套清晰的实验规矩；真正的难题仍然是把行为、边界、依赖和失败写成可信证据。

这是一条独立的 JUnit 学习地图，从工程配置、生命周期和断言走到参数化、Mockito、Spring、Testcontainers、并行、覆盖率与测试设计。每一站同时覆盖日常最常用的能力、容易忽略的边界和值得深挖的机制；代码示例保持少量，重点放在测试层次和维护判断。

路线按 **平台模型 → 生命周期 → 断言 → 参数化 → 替身 → Spring/真实依赖 → 并行 → CI → 诊断 → 设计** 推进。

## 第一站：JUnit 平台与第一个测试

欢迎来到 JUnit 的实验楼。平台是楼宇，测试引擎是电梯，Jupiter 是你实际使用的实验室；先分清谁负责发现、谁负责执行，失败时才知道该找哪位管理员。

**JUnit 5 架构** ---- 理解 Platform、Jupiter、Vintage、Launcher、引擎和 IDE/构建工具的关系，知道“JUnit 5”不是一个单独的黑盒

**依赖与目录** ---- 配置 Maven 或 Gradle 测试依赖，遵循测试源码、资源、命名和包结构约定

**测试发现** ---- 掌握 `@Test`、测试类可见性、命名、标签和引擎选择，排查测试不被发现或被重复执行

**运行入口** ---- 区分 IDE 单测、构建工具、控制台 Launcher 和 CI 运行，保持不同入口的报告与过滤语义一致

**测试元数据** ---- 使用显示名称、标签、测试方法来源和报告信息，让失败报告能读懂，而不是只吐出一个方法名

**重点在这** ---- 能解释一次测试从发现到执行的完整路径，知道失败发生在测试、引擎、构建配置还是环境

## 第二站：生命周期、嵌套与隔离

第二站是实验楼的清洁与排班处。Before 是准备器，After 是收尾员，Nested 是分组房间；它们配合得好，实验互不污染，配合不好，昨天的咖啡会出现在今天的结果里。

**生命周期钩子** ---- 掌握类级与方法级初始化、清理、继承和执行顺序，明确每个资源由谁创建、由谁关闭

**测试实例模式** ---- 理解每方法实例与每类实例的隔离差异，谨慎共享可变字段与昂贵资源

**嵌套测试** ---- 用 `@Nested` 按场景、状态和边界组织测试，保持层级服务于行为而不是制造目录深度

**条件执行** ---- 按操作系统、JDK、环境变量和系统属性启用或跳过测试，并为跳过保留可追溯理由

**禁用与预期失败** ---- 对暂时禁用的测试记录原因、负责人和恢复条件，避免黄色标记变成项目背景色

**隔离与清理** ---- 重置静态状态、临时文件、系统属性、线程、端口和数据库，确保失败路径也执行清理

**重点在这** ---- 测试可以任意顺序、单独或重复运行，生命周期只是帮助隔离，不是用来藏副作用

## 第三站：Assertions 与 AssertJ

第三站是证据审查室。JUnit 的断言负责给出结论，AssertJ 负责让结论更易读；但再流畅的链式 API 也不能把模糊的测试目标变清楚。

**基础断言** ---- 掌握对象、数组、集合、字符串、数值、空值、身份和类型断言，区分相等与同一对象

**异常与超时** ---- 测试同步异常、异常类型、消息、原因和超时，避免用过大的超时掩盖死锁或未完成异步

**组合断言** ---- 使用分组断言收集多个字段差异，让一次失败给出完整证据而不是只报第一个伤口

**AssertJ 流式断言** ---- 学会集合过滤、提取、递归比较、异常和时间断言，保持链式表达仍然能被团队读懂

**业务断言** ---- 对金额、时间、排序、状态、错误码和领域对象建立有语义的断言，少把业务逻辑散落进测试表达式

**实现耦合** ---- 断言公开行为、状态和契约，谨慎验证私有调用顺序与内部字段，给重构留出空间

**重点在这** ---- 每个断言都能解释“证明了哪个承诺、没证明哪个风险”，测试不是对象字段点名册

## 第四站：参数化与边界组合

第四站是数据实验室。参数化测试让一个场景换上不同样本，但数据表太大时会遮住真正的问题；好的参数像探照灯，不是仓库盘点。

**参数来源** ---- 使用值源、方法源、枚举、CSV 和自定义提供器，选择可读、可复现、易维护的输入方式

**显示名称** ---- 为参数样例生成包含场景和边界的名称，让失败报告直接告诉人是哪组输入出了问题

**边界数据** ---- 覆盖空值、极值、非法值、重复、顺序、时区、权限和状态转换，避免只测试黄金路径

**组合控制** ---- 识别参数笛卡尔积、共享资源和执行耗时，用等价类、代表值和风险优先级压缩组合

**参数化异常** ---- 为每组输入验证成功、失败、异常类型和错误信息，确认预期不是被错误的输入格式绕过去

**自定义参数提供器** ---- 在复杂数据生成时保持数据来源可追溯，避免提供器自身变成一套没人敢改的小框架

**重点在这** ---- 参数化的价值是扩大有意义的探索范围，而不是让报告里出现更多相似的绿色圆点

## 第五站：Mockito 与依赖替身

第五站是 Java 的替身剧场。Mockito 很会扮演接口，但如果所有依赖都被替成“永远成功”，测试就会住进一栋没有楼梯的样板房。

**Mock、Stub 与 Spy** ---- 区分提供固定结果、验证交互、观察真实对象和使用 Fake 的场景，围绕测试目标选择替身

**注入方式** ---- 理解构造器注入、字段注入、注解初始化和测试对象生命周期，优先让依赖关系在生产代码里清晰可见

**交互验证** ---- 验证关键参数、次数、顺序和不应发生的调用，避免把每个内部调用都钉成不可变契约

**异常与超时替身** ---- 模拟依赖失败、延迟、空响应和重复响应，覆盖被测逻辑的恢复路径

**静态与构造替身** ---- 了解静态方法、构造器和最终类替身的能力与风险，优先修正难测试的设计而不是无限加魔法

**严格程度** ---- 认识严格 Mock、未使用 Stub、默认返回值和参数匹配器陷阱，保持失败信息有方向

**重点在这** ---- 每个 Mock 都要说明隔离了什么、保留了什么真实行为、测试结束后是否会污染其他用例

## 第六站：Spring Boot 与真实集成

第六站进入整合实验室。Spring 测试可以启动整个应用，也可以只拎出一片切片；启动得越大，真实度可能越高，反馈速度和隔离成本也会一起长胖。

**单元测试与切片测试** ---- 区分纯 Java 单测、Web、数据、JSON 和安全切片测试，按风险选择最小必要上下文

**应用上下文** ---- 理解上下文缓存、配置、Profile、Bean 替换、端口和测试顺序，排查“单独通过、全量失败”的污染

**事务与数据库** ---- 处理事务回滚、迁移、隔离级别、连接池和真实数据库差异，不把内存数据库当生产数据库的双胞胎

**HTTP 与安全** ---- 测路由、序列化、错误、认证、授权、CSRF、会话和过滤器链，覆盖用户真正能触达的边界

**消息与外部依赖** ---- 规划队列、缓存、搜索和第三方服务的替身、容器或契约测试，明确每层测试证明什么

**上下文性能** ---- 复用稳定上下文、拆分测试切片、避免无谓启动，同时警惕缓存让隐藏状态继续活着

**重点在这** ---- 集成测试要更真实，但不必把整座应用搬进每个测试；真实度和反馈成本要一起计算

## 第七站：Testcontainers、并行与资源

第七站是测试基础设施机房。容器可以带来更接近生产的数据库和消息服务，但它们也会占 CPU、磁盘和端口；真实不是免费的。

**Testcontainers** ---- 使用真实数据库、消息系统、浏览器和依赖服务验证协议、版本与迁移，理解镜像、启动和等待策略

**容器生命周期** ---- 规划每测试、每类、每套件和共享容器的成本与隔离，保证失败后容器和网络能收尾

**迁移与种子数据** ---- 在测试中验证 schema、索引、约束、初始数据和回滚，避免应用能连上数据库却不知道它长什么样

**并行执行** ---- 处理共享容器、端口、文件、静态缓存和数据库 schema，只有隔离完成后并行才是加速器

**线程与异步资源** ---- 关注 Executor、定时任务、连接池和后台线程，解决测试结束后 JVM 仍然不退场的问题

**环境差异** ---- 记录 Docker、JDK、操作系统、架构和镜像版本，避免“在开发机上很真实”成为唯一证据

**重点在这** ---- 真实依赖测试要验证协议和恢复，而不是把 CI 变成一台每天启动几十个服务的暖气片

## 第八站：覆盖率、报告与 CI

第八站是质量控制室。覆盖率像一张走过的地图，报告像值班记录；它们能帮你发现盲区，但不能替你判断这条路值不值得走。

**覆盖率维度** ---- 理解行、分支、方法和条件覆盖率，优先观察关键决策、异常路径和权限分支

**质量阈值** ---- 按模块风险设置门槛，避免为了数字给 getter 和无意义分支举办涂色比赛

**报告保留** ---- 输出测试结果、失败堆栈、覆盖率、日志、截图和容器信息，保证 CI 失败可复盘

**标签与分组** ---- 区分单元、集成、慢、冒烟和环境相关测试，为提交、夜间和发布流程提供不同集合

**并行分片** ---- 按耗时和资源拆分测试，处理报告合并、顺序依赖和共享基础设施

**构建门禁** ---- 将测试失败、关键漏洞、覆盖率风险、许可证和构件生成纳入发布决策

**重点在这** ---- 质量门禁要拦真正的风险，报告要帮助人行动，而不是只负责让仪表盘变绿

## 第九站：稳定性、诊断与升级

第九站是测试急救室。Flaky 测试是会间歇性咳嗽的病人；重跑一次可能暂时安静，但不能算治好了。

**失败重现** ---- 记录随机种子、参数、环境、并发、资源和时间，建立最小复现而不是只保存一句“偶发失败”

**超时与死锁** ---- 区分测试超时、线程死锁、锁竞争、连接泄漏、未完成异步和 CI 资源拥塞

**日志与调试** ---- 使用 IDE 断点、测试报告、线程转储、数据库日志和失败产物定位根因

**测试顺序** ---- 随机化或改变顺序发现共享状态，同时确保测试设计不依赖某个幸运顺序

**框架升级** ---- 分层升级 JUnit、构建插件、Mockito、Spring、AssertJ 和容器依赖，保留兼容矩阵与回退点

**安全诊断** ---- 避免在报告中输出令牌、密码、个人数据和完整请求头，测试日志也要遵守最小暴露原则

**重点在这** ---- 测试套件本身要可观察、可复现、可升级；没有诊断能力的绿色只是一种礼貌

## 第十站：测试设计与长期维护

最后一站是架构讨论室。JUnit 负责把测试跑起来，团队负责决定哪些行为值得锁定；测试多不代表保护多，关键是风险有没有被说清。

**命名与结构** ---- 用场景、条件和结果组织测试，保持准备、执行、断言的边界可读

**风险优先** ---- 优先覆盖资金、权限、数据一致性、并发、外部协议、恢复和高频旅程

**分层与契约** ---- 用单元测试保护规则，用集成测试保护协作，用契约测试保护接口，用端到端测试保护关键旅程

**测试数据** ---- 使用最小、可读、可复现的数据，控制时间、时区、随机与身份，隔离敏感信息

**重构友好** ---- 少测私有实现、少依赖全局状态、少使用巨大上下文，让测试成为设计反馈而非重构阻力

**删除低价值测试** ---- 清理重复、永不失败、过度 Mock 和只验证框架默认行为的测试，把维护预算花在风险上

**重点在这** ---- 读完测试套件，应该能看见系统的承诺、边界、失败路径和仍然缺少的证据

## 通关标准

**JUnit 新手能写单测** ---- 能配置 JUnit 5、运行测试、使用生命周期和写出清晰断言。

**初级 Java 开发者能测模块** ---- 能参数化、隔离依赖、测试异常，并保持数据与资源干净。

**中级工程师能测应用** ---- 能处理 Spring 上下文、数据库、容器、消息、并行和 CI 报告。

**高级工程师能建体系** ---- 能按风险设计测试层、治理 flaky 与性能、维护质量门禁，并让测试支撑架构演进。

## 结语

JUnit 的老练不在于注解多，而在于它让测试可以成为工程系统的一部分：能被构建、被过滤、被诊断、被审计、被长期维护。先把隔离和边界做好，再引入 Mock、容器与并行；先让失败有证据，再让流水线变快。等你能用测试解释一条业务规则为什么成立、哪里会失败、失败后如何恢复，JUnit 就不只是绿色小图标，而是团队敢于重构的底气。
