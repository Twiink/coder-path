# Pytest 学习路线

Pytest 是 Python 测试世界里那位穿着运动鞋的实验员：普通函数就能开工，`assert` 直接说人话，fixture 负责准备现场，参数化负责把边界一网打尽。它的简洁不是“少写几个字符”这么简单，而是把测试重点从框架仪式转回行为、数据和风险。只是 fixture 一旦无限套娃，运动鞋也会踩进自己的电缆。

这是一条独立的 Pytest 学习地图，从发现测试、断言和 fixture 走到参数化、替身、异步、Web/数据库测试、插件、覆盖率、并行与 CI。每一站都覆盖常用能力、少见边界和底层机制；路线尽量少放代码，把注意力留给测试为什么可信、为什么会失真。

路线按 **运行模型 → 断言 → Fixture → 参数化 → Mock → 异步与外部依赖 → 插件 → 诊断 → CI → 测试设计** 推进。

## 第一站：测试发现、配置与运行

欢迎来到 Pytest 的实验室前台。测试文件和函数是登记信息，配置是实验室规章，命令行是排班表；先让它找到正确的测试，再讨论测试写得漂不漂亮。

**默认发现规则** ---- 掌握测试文件、测试函数和测试类命名约定，理解目录、包和导入路径如何影响发现

**配置文件** ---- 认识 `pyproject.toml`、`pytest.ini`、配置优先级、测试路径和默认参数，让本地与 CI 使用同一套规则

**运行范围** ---- 能按文件、节点、关键字、标记和失败记录选择测试，区分快速反馈与完整验证

**输出与失败** ---- 理解捕获输出、详细模式、失败即停、最大失败数和报告内容；失败信息是线索，不是需要立刻删除的噪音

**导入环境** ---- 处理工作目录、包安装、路径配置和 editable 安装，识别“本地能导入、CI 不能导入”的环境差异

**插件加载** ---- 了解插件发现、启动错误和版本兼容，知道一个插件为什么能改变命令行、fixture 和报告

**重点在这** ---- 能明确一次运行覆盖什么、遗漏什么、使用什么环境，以及测试到底有没有被 Pytest 找到

## 第二站：assert、异常与精确表达

第二站是 Pytest 的断言柜台。它不给你一整排 `assertEqual` 按钮，而是让 Python 的比较运算直接发言；发言越具体，失败时越像一位有用的证人。

**基础断言** ---- 掌握相等、身份、包含、真假、类型、长度和对象属性断言，理解值相等与对象相同的区别

**断言重写** ---- 了解 Pytest 如何展示比较差异、集合差异和字符串差异，写出能让失败自动解释自己的断言

**异常测试** ---- 使用异常上下文验证类型、消息和自定义属性，覆盖异常发生与不应发生的两条路径

**警告测试** ---- 捕获弃用警告、运行时警告和警告属性，避免重要迁移信号被默认输出吞掉

**近似比较** ---- 处理浮点、时间、金额和测量数据的容差，先定义业务精度，再选择比较方式

**失败信息** ---- 给复杂断言补充业务语义，不要在失败时只看到一个巨大的字典和一声叹息

**重点在这** ---- 断言应证明行为和契约，而不是把实现细节包装成一串难以维护的比较

## 第三站：Fixture——Pytest 的现场管理系统

第三站是 Pytest 的后勤部。fixture 会准备对象、数据库、客户端和临时目录，也可能悄悄把依赖关系藏到第七层；好的 fixture 像清晰的工具车，坏的 fixture 像打开就掉出十把扳手的抽屉。

**Fixture 声明** ---- 理解依赖注入、fixture 名称、返回值、yield 收尾和 fixture 图，知道测试依赖了哪些现场

**作用域** ---- 掌握函数、类、模块、包和会话作用域，按资源成本与隔离要求选择共享范围

**自动使用** ---- 谨慎使用 autouse，区分真正的全局环境准备与隐藏副作用；自动发生的事最需要被写在脸上

**工厂 Fixture** ---- 为不同输入创建对象、用户、订单和临时资源，避免把一个万能实例改到谁都不认识

**参数化 Fixture** ---- 让同一现场适配多数据库、多配置、多权限和多平台，注意组合爆炸与报告可读性

**清理与失败** ---- 确保文件、连接、进程、临时服务和环境变量在成功与失败路径都能清理

**fixture 分层** ---- 将基础设施、领域数据和测试场景分离，防止业务测试被底层配置细节淹没

**重点在这** ---- 读一个测试时，能顺着 fixture 图还原现场、共享状态、资源成本和清理责任

## 第四站：参数化、标记与边界覆盖

第四站是测试的数据车间。参数化让一个测试走多条路，但参数越多不代表覆盖越高；一百个重复的阳光样例，不如三个能照出边界的阴影。

**参数化测试** ---- 使用参数集覆盖正常值、空值、极值、非法值和异常组合，给每组数据起可读名称

**参数组合** ---- 理解参数化 fixture 的笛卡尔积，控制组合数量，避免测试报告变成电话号码簿

**标记体系** ---- 设计 unit、integration、slow、network、database 等标记，按风险和反馈速度组织运行

**条件跳过** ---- 按操作系统、Python 版本、可选依赖和环境能力跳过真正不适用的测试，并写清理由

**预期失败** ---- 使用 xfail 记录已知缺陷、版本差异和临时能力，防止它变成永远不修的装饰标签

**边界矩阵** ---- 用业务规则而非随机堆数据选择等价类、边界值、状态转移和组合风险

**重点在这** ---- 每组参数都应该带来新的信心或新的失败信息，而不是只让 CI 的计数器更勤快

## 第五站：Mock、Monkeypatch 与替身边界

第五站是替身剧场。Monkeypatch 可以把时间、环境变量和外部服务请下台，但如果连被测逻辑也替掉，测试就只剩一群演员互相鼓掌。

**替换与观察** ---- 区分 Mock、Spy、Stub、Fake 和真实依赖，按测试目标选择替身，而不是看到网络就全 Mock

**Monkeypatch** ---- 修改属性、字典、环境变量、路径和模块引用，理解作用域与测试结束后的自动恢复

**Mock 调用验证** ---- 验证关键参数、次数、顺序和错误处理，避免把无关内部调用变成脆弱契约

**时间与随机** ---- 控制日期、时钟、随机数、UUID 和重试间隔，覆盖边界后确保全局状态恢复

**网络与文件系统** ---- 在 HTTP、文件、队列和第三方 SDK 边界建立可控替身，保留真实序列化与错误形态

**Fake 与契约** ---- 对复杂外部系统使用轻量 Fake 或契约测试，减少 Mock 与现实接口逐渐分家的风险

**过度替身** ---- 识别测试全绿但生产失败、Mock 返回不可能数据和实现耦合，必要时提升测试层级

**重点在这** ---- 每个替身都要说明隔离了什么不确定性、保留了什么真实行为、何时恢复环境

## 第六站：异步、Web 与数据库测试

第六站进入真实世界。请求会超时，数据库会拒绝连接，后台任务会晚到；测试如果只会测纯函数，遇到这些角色就会开始装睡。

**异步测试** ---- 使用异步插件与事件循环测试协程、超时、取消、并发和资源关闭，区分同步 fixture 与异步 fixture

**Web 客户端** ---- 测试路由、请求体、响应、状态码、认证、错误格式和中间件，保持单元测试与接口测试的边界

**数据库隔离** ---- 选择事务回滚、临时数据库、容器数据库或 Fake，评估真实度、速度、并行与迁移覆盖

**消息与后台任务** ---- 覆盖重复投递、顺序、失败重试、幂等、取消和死信，别让任务队列在测试里永远风平浪静

**外部服务契约** ---- 验证第三方响应、超时、限流和版本变化，避免测试只记录“服务正常时大家都很开心”

**资源收尾** ---- 关闭客户端、连接池、事件循环、线程和子进程，处理进程不退出与端口被占用的尾巴

**重点在这** ---- 真实依赖测试要回答边界与恢复问题，不能只把生产环境搬进 CI 然后希望它心情好

## 第七站：插件生态与高级测试能力

第七站是 Pytest 的扩展集市。插件能把覆盖率、并行、异步、随机、基准和报告都接进来，但每个新插件也会带来一位需要照顾的依赖。

**插件机制** ---- 理解 hook、fixture、命令行选项和插件加载顺序，知道扩展改变了哪些运行行为

**覆盖率** ---- 使用 coverage.py 统计语句、分支和上下文，处理源码映射、排除生成文件和质量门槛

**并行执行** ---- 使用 xdist 等能力分片测试，解决会话级资源、数据库、端口、日志和非隔离测试

**属性与生成测试** ---- 了解 Hypothesis 通过生成数据寻找反例、缩小失败样本和维护策略，把示例测试推进到性质测试

**基准测试** ---- 区分功能测试与性能基准，记录环境、样本、热身、波动和回归阈值，不用一次运行宣判性能真相

**插件兼容** ---- 管理 Python、Pytest、Web 框架和插件版本，升级时保留最小复现与迁移检查

**重点在这** ---- 插件的价值是补足测试能力，不是让配置文件成为一座需要专人祭拜的神殿

## 第八站：调试、稳定性与性能

第八站是测试急救室。Flaky 测试像偶尔响一次的报警器，最危险的不是它响，而是大家听久了开始把它当背景音乐。

**失败重现** ---- 保留参数、随机种子、环境、日志和失败样本，先让偶发失败变成可观察事件

**调试工具** ---- 结合详细输出、断点、日志、临时目录、失败重跑和最小节点定位根因

**不稳定来源** ---- 排查时间、时区、随机、网络、并发、共享状态、资源耗尽和平台差异

**超时判断** ---- 区分代码死锁、未等待协程、外部服务慢、测试夹具泄漏和 CI 资源拥塞

**测试性能** ---- 通过选择性运行、fixture 缓存、数据库策略、并行分片和报告分析缩短反馈

**失败清理** ---- 即使断言失败，也要保留关键现场并释放资源；诊断信息与清理职责不能互相牺牲

**重点在这** ---- 不用“重跑直到绿”掩盖问题，测试系统应当能解释失败、稳定重现并快速恢复

## 第九站：CI、质量门禁与安全

第九站来到流水线。CI 没有本机上那堆神秘环境，所以会把路径、凭据、时区和依赖问题一股脑交出来；这不是它针对你，这是它终于诚实。

**环境固定** ---- 锁定 Python、依赖、系统包、时区、区域和数据库版本，减少本地与 CI 的行为分叉

**流水线分层** ---- 先跑快速单测，再跑集成、端到端、覆盖率、静态检查和安全扫描，按风险安排反馈

**质量门禁** ---- 结合失败率、覆盖率、关键路径、漏洞等级和测试耗时设门槛，不用单一数字代表质量

**测试凭据** ---- 使用专用、短期、最小权限凭据与合成数据，防止日志、报告和失败产物泄露秘密

**并行与重试** ---- 重试只用于确认基础设施瞬态故障，不得把产品缺陷包装成绿色结果；记录重试原因与次数

**报告留存** ---- 保留失败日志、覆盖率、JUnit XML、截图、录屏和环境摘要，支持审计与回溯

**重点在这** ---- CI 测试要快、稳、可追溯，最重要的是失败之后有人能知道下一步该查哪里

## 第十站：测试设计与长期演进

最后一站是测试设计室。Pytest 可以让测试写得很短，但短不等于浅；好的测试让未来的维护者知道系统承诺了什么，也知道哪些地方故意不承诺。

**测试命名** ---- 用场景、条件和结果描述行为，避免只写函数名而不说明用户能观察到什么

**风险驱动** ---- 优先覆盖钱、权限、数据完整性、外部依赖、恢复流程和高频业务，而不是平均撒胡椒粉

**分层策略** ---- 让纯逻辑保持快速，让接口和真实依赖测试覆盖边界，让端到端测试只承担关键旅程

**契约与性质** ---- 对 API、序列化、状态机和不变量建立契约或性质测试，减少样例遗漏

**公共辅助函数** ---- 抽取真正稳定的测试语义，避免 helper 把关键准备步骤藏起来让读者猜

**删除无价值测试** ---- 清理重复、永不失败、全靠 Mock 和只验证框架行为的测试，给剩下的测试更多信任

**重点在这** ---- 测试套件应当像一张风险地图：知道哪里安全、哪里危险、哪里仍然没有证据

## 通关标准

**Pytest 新手能跑测试** ---- 能配置发现规则、写 assert、测试异常并读懂失败差异。

**初级开发者能管现场** ---- 能设计 fixture、参数化和标记，保持测试隔离并正确清理资源。

**中级工程师能测真实系统** ---- 能处理异步、Web、数据库、消息、Mock、插件、并行和 CI。

**高级工程师能建设体系** ---- 能按风险设计测试层、治理 flaky 与性能，建立可信的质量门禁和安全边界。

## 结语

Pytest 的魅力是把仪式感降到很低，把判断力留给开发者。先写能说明行为的断言，再设计可见的 fixture；先覆盖失败和边界，再追求跑得快；先修掉 flaky 根因，再谈重试。等你能让测试报告告诉团队“哪里值得信、哪里需要查、哪里还没有证据”，Pytest 就不只是一个测试命令，而是项目的实验记录员。
