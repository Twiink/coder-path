# Selenium 学习路线

Selenium 是 Web 自动化世界里的元老级司机：它通过 WebDriver 协议驾驶真实浏览器，能跨语言、跨浏览器、跨平台工作，老系统、兼容性矩阵和大规模 Grid 仍然离不开它。它的能力很大，方向盘也比较重；定位、等待、窗口、iframe、Shadow DOM 和并行一旦没安排好，测试就会像一辆在雾里找停车位的车。

这是一条独立的 Selenium 学习地图，从 WebDriver 模型走到定位、等待、页面对象、认证、数据、Grid、CI、稳定性与选型。每一站覆盖常用能力、少见边界和底层机制；代码保持少量，重点放在浏览器状态、测试信号和故障证据。

路线按 **WebDriver → 定位 → 交互 → 等待 → 浏览器边界 → 页面对象 → 数据与认证 → Grid → 诊断 → 设计** 推进。

## 第一站：WebDriver 架构与浏览器会话

欢迎来到 Selenium 的车库。测试代码是司机，WebDriver 是翻译官，浏览器是那辆有自己脾气的车；先理解指令如何到达页面，后面才不会对着一个空白窗口念咒。

**WebDriver 协议** ---- 理解测试客户端、驱动、浏览器和远程端点的关系，知道每一步命令在哪一层执行

**会话生命周期** ---- 掌握创建、配置、导航、操作、收尾和会话失效，确保浏览器进程、端口与临时目录被释放

**浏览器选项** ---- 配置无头、窗口大小、代理、下载目录、证书、语言、用户数据和日志，区分测试便利与真实行为

**驱动管理** ---- 处理浏览器、驱动、Selenium 和操作系统版本矩阵，优先使用可验证的自动管理方式

**能力协商** ---- 了解本地与远程能力、浏览器特性和平台差异，避免把 Chrome 的便利误当成 Web 标准

**重点在这** ---- 能从“会话创建失败、浏览器打不开、命令无响应”判断问题位于客户端、驱动、浏览器还是环境

## 第二站：元素定位与选择器设计

第二站是导航课。页面元素像城市里的门牌，ID、CSS 和 XPath 是不同地图；地图越依赖临时广告牌，页面一装修，测试就会迷路。

**定位方式** ---- 掌握 ID、名称、标签、链接文本、CSS 和 XPath 的能力与成本，优先选择语义稳定、唯一的定位器

**测试钩子** ---- 与前端约定 data 属性、可访问角色和稳定标识，避免依赖颜色、样式类、层级索引和动态文案

**CSS 选择器** ---- 使用属性、后代、组合、伪类和结构选择，保持选择器短、明确、对布局变化不敏感

**XPath** ---- 理解属性、文本、轴、祖先和兄弟关系，作为复杂结构与旧页面的工具，不把每个按钮都写成考古报告

**单元素与多元素** ---- 区分找不到、找到多个和找到隐藏元素的结果，明确测试应断言数量、可见性还是最终行为

**iframe 与 Shadow DOM** ---- 认识上下文切换、影子根、开放与封闭 Shadow DOM 的边界，理解“元素明明在页面上却找不到”

**重点在这** ---- 选择器要表达元素身份，而不是表达当前 HTML 恰好长什么样；稳定定位是团队协作，不是测试人员的独角戏

## 第三站：元素操作与浏览器控制

第三站是驾驶训练场。点击、输入、滚动和提交都可能触发异步更新；浏览器会检查元素是否可见、可用、被遮挡，你不能只把命令一脚油门踩到底。

**元素状态** ---- 区分存在、可见、启用、可交互和位于视口内，理解 Selenium 为什么拒绝操作某些元素

**输入与清理** ---- 处理文本、键盘、组合键、焦点、清空和输入法边界，验证表单实际收到的值

**点击与提交** ---- 覆盖普通点击、双击、悬停、拖拽、键盘提交和遮挡元素，优先使用真实用户可行的路径

**滚动与视口** ---- 管理滚动容器、懒加载、固定头部和视口尺寸，避免“元素在 DOM 里但用户看不见”的假成功

**文件上传与下载** ---- 处理文件路径、下载目录、文件存在性、命名和清理，禁止把真实用户文件带进测试环境

**浏览器导航** ---- 测试前进、后退、刷新、URL、标题、历史和新页面加载，区分浏览器导航与单页应用路由

**重点在这** ---- 操作前验证必要状态，操作后验证用户可观察结果，不用 JavaScript 强行点击来掩盖真实交互失败

## 第四站：等待、同步与动态页面

第四站是交通信号室。页面不是静态海报，网络、动画和渲染都在偷偷换灯；固定睡眠只是闭眼等车，显式等待才是在看信号。

**隐式等待** ---- 理解全局轮询对元素查找的影响、与显式等待叠加的复杂度和隐藏延迟，谨慎设置全局策略

**显式等待** ---- 按存在、可见、可点击、文本、属性、URL、标题和自定义条件等待业务状态

**流式等待** ---- 调整轮询间隔、超时和忽略异常，保证等待条件具体、失败消息可读

**页面稳定条件** ---- 等待请求、加载、动画、组件状态和业务完成，而不是只等某个无关的 DOM 节点出现

**竞态与过期元素** ---- 处理页面重绘导致的 stale element、元素替换、重复请求和状态回退

**超时诊断** ---- 区分元素不存在、定位错误、页面没加载、网络慢、权限不足和条件写错

**重点在这** ---- 等待的是用户可观察的状态变化，不是给测试线程安排一段“希望它已经完成”的午休

## 第五站：窗口、标签、iframe 与 Shadow DOM

第五站是浏览器的多房间公寓。窗口句柄、标签页、iframe 和影子树各有自己的门；门没切对，Selenium 会一本正经地告诉你墙上没有按钮。

**窗口句柄** ---- 管理当前窗口、窗口集合、切换顺序和关闭策略，避免句柄泄漏与不同浏览器顺序差异

**新标签页** ---- 处理链接打开新页、弹窗、等待新句柄和回到原页，验证 URL、标题与页面状态

**iframe 上下文** ---- 进入、退出和嵌套切换 frame，理解元素定位始终发生在当前文档上下文

**Shadow DOM** ---- 区分开放影子根、封闭影子根、组件内部定位和测试钩子设计，尽量从组件契约解决可测性

**浏览器弹窗** ---- 处理 alert、confirm、prompt、权限提示和下载对话框，分清浏览器原生 UI 与页面 DOM

**跨域边界** ---- 认识同源策略、第三方 iframe、认证域和浏览器安全限制，避免用不安全开关换取假测试

**重点在这** ---- 切换上下文是状态操作，必须显式记录进入、验证、退出和失败后的恢复

## 第六站：Page Object、组件对象与测试架构

第六站是车队调度室。Page Object 不是把每个 CSS 选择器换个文件藏起来，而是把页面行为、定位边界和导航责任组织成可维护的接口。

**页面对象** ---- 封装页面导航、元素定位和用户动作，避免测试用例重复堆砌底层 WebDriver 调用

**组件对象** ---- 抽取表格、日期选择器、弹窗、菜单和表单等可复用组件，保持局部状态与定位范围

**页面状态** ---- 让对象表达已加载、错误、空数据和权限状态，避免所有页面都只有一个“打开成功”布尔值

**断言边界** ---- 决定断言放在页面对象、业务流程还是测试用例，保持对象可复用而测试仍然说明行为

**等待封装** ---- 把稳定、通用的等待抽成语义动作，避免自定义等待吞掉真实失败

**分层夹具** ---- 管理浏览器、用户、数据、服务和页面对象生命周期，避免全局登录与共享状态互相污染

**重点在这** ---- 抽象的目标是让测试读起来像用户旅程，而不是让定位器从一处搬到另一处继续躲猫猫

## 第七站：认证、数据与业务流程

第七站是测试的后勤仓库。登录、数据和状态决定了页面会长什么样；如果每条用例都从注册用户开始，测试套件很快会比用户增长计划更慢。

**登录策略** ---- 比较 UI 登录、预置会话、API 登录和浏览器配置文件，按覆盖目标与安全风险选择入口

**会话隔离** ---- 管理 Cookie、Local Storage、Session Storage、Token、退出和多用户并行，防止身份串台

**测试数据** ---- 使用工厂、种子、唯一标识和可清理数据，避免依赖共享生产快照与固定数据库顺序

**状态机流程** ---- 覆盖草稿、提交、审核、取消、失败、重试和过期状态，不只验证从首页到成功页的黄金路线

**权限场景** ---- 用不同角色、租户和资源所有者验证可见性与操作边界，防止 E2E 只带管理员眼镜看世界

**外部依赖** ---- 对支付、邮件、地图、对象存储和第三方登录规划沙箱、Stub 或契约测试，明确真实度边界

**重点在这** ---- 测试数据要可追踪、可隔离、可回收，认证流程要证明权限，不只是证明某个密码被输入过

## 第八站：Grid、并行与跨浏览器

第八站是车队中心。单机跑一条路不难，几十台浏览器同时出发才会暴露端口、资源、数据和浏览器差异；并行之前，先把车道画清楚。

**Selenium Grid** ---- 理解 Hub、Node、远程 WebDriver、能力匹配和会话路由，知道测试如何被派到不同浏览器

**容器与云执行** ---- 管理浏览器镜像、版本、分辨率、字体、代理和网络，记录远程环境而不是只记“某云平台”

**并行分片** ---- 按套件、文件、耗时和浏览器拆分，处理共享用户、数据库、端口和文件资源

**跨浏览器矩阵** ---- 识别标准行为、浏览器差异、WebKit/Firefox/Chromium 特性和版本支持，按用户占比与风险排优先级

**资源容量** ---- 规划 CPU、内存、浏览器进程、连接、磁盘和会话上限，避免并发一开所有浏览器一起打喷嚏

**失败重试** ---- 只把重试用于确认基础设施瞬态问题，保留第一次失败证据，不用重试把产品缺陷漂白

**重点在这** ---- 并行的前提是数据与会话隔离，跨浏览器的价值是发现真实差异，不是收集更多绿色截图

## 第九站：稳定性、调试与 CI 证据

第九站是事故调查室。E2E 失败时，页面截图只是现场照片；还需要 URL、DOM、控制台、网络、浏览器日志和环境信息，才能知道是谁把按钮藏走了。

**失败产物** ---- 保存截图、页面源、录屏、控制台、网络日志、浏览器日志和测试数据摘要

**稳定性来源** ---- 排查定位脆弱、等待错误、动画、共享状态、网络、浏览器版本、资源拥塞和测试顺序

**最小复现** ---- 缩小到单用例、单浏览器、单数据和单步骤，先让问题可重现再讨论修复

**CI 环境** ---- 固定浏览器、驱动、操作系统、字体、时区、屏幕尺寸、代理与服务版本

**超时与资源** ---- 监控会话启动、页面加载、网络请求、元素等待、脚本执行和清理时间

**安全证据** ---- 脱敏截图、日志、Cookie、Token、请求头和表单数据，测试产物也可能成为秘密仓库

**重点在这** ---- 一次失败要能回答发生在哪个步骤、哪个环境、哪个页面状态，以及下一步如何重现

## 第十站：E2E 设计、可访问性与选型

最后一站是路线规划室。Selenium 能驾驶真实浏览器，但不应承载所有测试；让它守住关键用户旅程，把细节交给更快的测试层。

**关键旅程** ---- 选择登录、购买、支付、权限、发布和恢复等高价值流程，控制 E2E 数量与维护成本

**可访问性** ---- 通过角色、名称、键盘、焦点和语义结构验证真实用户路径，稳定定位与无障碍通常是好朋友

**测试分层** ---- 把纯逻辑交给单元测试，把接口交给集成测试，把浏览器留给跨层契约和关键体验

**安全边界** ---- 不关闭浏览器安全策略来换取通过，不把真实凭据和生产数据带进自动化环境

**Selenium 与替代品** ---- 根据语言、浏览器矩阵、Grid、调试体验、并行、团队经验和遗留系统做选择

**长期维护** ---- 管理选择器契约、浏览器升级、失败率、运行时长和弃用页面，定期删除低价值流程

**重点在这** ---- E2E 是生产风险的探测器，不是网页每一颗螺丝的显微镜；少而关键，才能长期可信

## 通关标准

**Selenium 新手能驾驶浏览器** ---- 能创建会话、定位元素、完成交互、等待页面状态并正确关闭资源。

**初级测试工程师能写流程** ---- 能处理窗口、iframe、文件、登录、数据和 Page Object。

**中级工程师能跑规模化测试** ---- 能治理 Grid、并行、跨浏览器、CI、失败产物与 flaky 问题。

**高级工程师能做 E2E 体系** ---- 能按风险选择测试层、设计可访问且稳定的旅程，并控制安全、性能与维护成本。

## 结语

Selenium 的老练来自它愿意驾驶真实浏览器，代价是每个页面状态都可能影响方向盘。先把定位和等待设计好，再谈并行；先保证数据隔离，再谈规模；先保留失败证据，再谈重试。等你能让一条关键用户旅程在多浏览器、干净环境和夜间 CI 中稳定跑完，Selenium 就不再是“会点网页的脚本”，而是一支懂得观察真实体验的测试车队。
