# Cypress 学习路线

Cypress 是现代 Web 测试里那位住在浏览器里的前端工程师：命令自动等待，失败可以回放，网络可以拦截，页面状态还能在调试器里被看见。它让 E2E 不再像隔着电话指挥浏览器，但也有自己的边界——单浏览器上下文、跨域、多个标签页和真实外部服务，都会提醒你它不是万能遥控器。

这是一条独立的 Cypress 学习地图，从运行模型、选择器和断言走到交互、网络、认证、组件测试、跨域限制、CI、并行与选型。每一站兼顾常用能力、少见边界和底层机制；代码保持少量，重点放在自动重试、状态同步和可维护测试设计。

路线按 **运行模型 → 查询断言 → 交互 → 网络 → 会话 → 组件 → 浏览器边界 → CI → 稳定性 → 选型** 推进。

## 第一站：运行模型与项目配置

欢迎来到 Cypress 的浏览器工作室。测试代码在浏览器旁边工作，命令进入队列再执行；它不是同步脚本披了一件异步外套，先理解这个模型，后面才不会和链式命令争论谁先到。

**Cypress 架构** ---- 理解测试运行器、浏览器、代理、命令队列和应用之间的关系，知道它与外部 WebDriver 模型的差异

**项目初始化** ---- 组织 E2E、组件、fixtures、support、插件与配置文件，让测试入口和共享能力有清晰边界

**基础配置** ---- 设置 base URL、视口、超时、重试、环境变量、视频、截图、浏览器和报告输出

**命令队列** ---- 理解命令排队、链式 subject、回调执行时机和不能直接当作同步返回值使用的边界

**运行模式** ---- 区分交互模式、无头运行、单测试、关键字过滤、浏览器选择和 CI 模式

**重点在这** ---- 能解释一个 Cypress 命令何时排队、何时执行、拿到什么 subject，以及失败证据从哪里来

## 第二站：查询、选择器与断言

第二站是 Cypress 的寻路课。查询会自动重试，选择器决定它找谁，断言决定它何时算到站；把 class 当身份证，页面一换衣服，测试就会报警。

**稳定选择器** ---- 优先使用 data 属性、语义角色、可访问名称和稳定文本，避免依赖样式类、层级和动画状态

**查询命令** ---- 掌握 get、contains、find、within、first、eq 和过滤，理解查询范围、subject 和重试边界

**断言匹配器** ---- 覆盖存在、可见、启用、文本、属性、值、数量、URL 和自定义条件，保持断言说明用户可观察结果

**不存在断言** ---- 正确区分元素不存在、暂时没出现、隐藏和被卸载，避免用固定等待赌页面已经稳定

**选择器契约** ---- 与组件开发约定测试钩子和可访问语义，选择器稳定性是产品代码与测试代码的共同责任

**断言位置** ---- 在查询链上等待最终状态，避免过早取值、脱离 Cypress 重试链或把内部状态当界面契约

**重点在这** ---- 好的查询像用户在找东西，好的断言像用户确认结果；两者都不应依赖页面偶然长相

## 第三站：交互、表单与页面状态

第三站是浏览器游乐场。点击只是第一声铃，随后可能有校验、请求、渲染、焦点和错误提示；测试要跟着状态走，不要只确认鼠标动过。

**用户交互** ---- 测试点击、输入、清空、选择、键盘、悬停、焦点和滚动，保持操作路径接近真实用户

**表单流程** ---- 覆盖必填、格式、边界、重复提交、禁用、服务端错误和成功反馈，不只测试按钮能不能按

**异步 UI** ---- 等待加载、骨架屏、请求完成、列表更新、弹窗和路由状态，利用自动重试而不是到处写 sleep

**文件操作** ---- 处理上传、下载、文件名、大小、类型、失败与清理，避免把本机文件系统变成隐形测试依赖

**视口与响应式** ---- 在关键尺寸、触摸行为和滚动容器下验证布局与交互，区分 CSS 问题和测试定位问题

**错误与恢复** ---- 覆盖网络失败、表单回填、重试、取消、刷新和返回，验证用户是否能从坏状态继续走

**重点在这** ---- 操作不是终点，操作之后的状态、反馈、可访问性和恢复路径才是测试真正要保护的东西

## 第四站：网络拦截与数据契约

第四站进入网络控制室。Cypress 可以观察和拦截请求，让测试不必每次都等第三方服务心情好；但拦截若与真实契约脱节，绿色只是布景。

**请求观察** ---- 识别方法、URL、请求体、响应、状态码、查询参数和请求次数，验证前端与服务端契约

**请求拦截** ---- 为成功、错误、慢响应、空数据、分页和重复请求建立可控场景，理解拦截发生的时机

**别名与等待** ---- 给关键请求命名并等待业务相关响应，避免等待固定时间或一个不相关的 DOM 变化

**响应校验** ---- 同时验证页面行为与网络边界，不把“收到 200”误当成用户真的看到了正确内容

**数据夹具** ---- 管理固定数据、动态数据、敏感字段、版本和组合，防止 fixture 与真实 API 长期分家

**契约同步** ---- 通过 schema、接口契约或少量真实集成测试校准拦截数据，记录字段、错误码和兼容策略

**重点在这** ---- 网络拦截是控制实验条件，不是取消接口责任；测试要既快又不脱离现实

## 第五站：认证、会话与多用户状态

第五站是登录大厅。每条测试都重新输入密码，像每次进办公室都重新办身份证；完全跳过认证，又会错过真正的权限问题。

**登录策略** ---- 比较 UI 登录、API 登录、预置 Cookie、session 缓存和测试用户工厂，按覆盖目标选择入口

**会话复用** ---- 管理登录缓存、过期、退出、刷新和失败恢复，缩短运行时间同时保持测试隔离

**Cookie 与存储** ---- 处理 HttpOnly Cookie、Local Storage、Session Storage、Token 和多标签状态，避免凭据互相串台

**角色与租户** ---- 为管理员、普通用户、资源所有者、访客和不同租户准备数据，验证可见性、操作权和数据隔离

**跨域认证** ---- 理解 origin、第三方登录、同源策略和安全上下文限制，选择受支持的认证测试方式

**秘密与数据** ---- 使用专用、短期、可撤销账号，禁止把真实密码、Token、个人数据打进配置、截图或日志

**重点在这** ---- 认证测试既要高效进入业务，也要真正证明身份、会话、权限和退出边界

## 第六站：自定义命令与组件测试

第六站是 Cypress 的工具间。自定义命令像工具箱，放对了能减少重复，放错了会把所有业务魔法藏在一个名字里；组件测试则让局部 UI 有了自己的实验场。

**自定义命令** ---- 抽取稳定、通用、可读的用户动作，明确参数、失败信息和副作用，不把整条业务流程藏进一个黑盒

**命令组合** ---- 设计 subject 传递、链式调用、异步完成和类型声明，避免普通函数与 Cypress 命令混用造成时序错乱

**组件测试** ---- 测试组件渲染、属性、事件、状态、路由、网络和错误，选择比完整 E2E 更快的反馈层

**挂载环境** ---- 配置 Provider、路由、主题、国际化和测试数据，保持组件实验与真实应用边界一致

**组件与页面契约** ---- 将组件测试与少量关键 E2E 组合，既保护局部行为，也保护真实旅程

**辅助工具治理** ---- 给命令、fixture、选择器和共享配置设命名、版本与删除规则，避免测试工具本身变成遗留系统

**重点在这** ---- 抽象应让测试更像用户故事，而不是让真实步骤消失得无影无踪

## 第七站：浏览器边界与特殊场景

第七站是 Cypress 的边界围栏。它很擅长在一个浏览器上下文里观察应用，但跨域、多个标签页、下载、原生弹窗和第三方窗口会要求你换一条路。

**同源与跨域** ---- 理解 origin、端口、协议、站点、跨域切换和安全限制，使用受支持的 origin 能力而不是关闭安全策略

**多标签页** ---- 认识 Cypress 的单窗口模型，改造测试流程、验证链接目标或在合适层级测试多窗口行为

**第三方登录与支付** ---- 采用沙箱、API 准备、契约测试和少量真实回归，避免把外部服务的偶发波动当产品失败

**浏览器原生 UI** ---- 区分 alert、confirm、下载、权限和页面 DOM，使用对应事件与配置处理边界

**时间与动画** ---- 控制定时器、动画和过渡，保持等待条件与用户最终能观察到的状态一致

**浏览器差异** ---- 了解 Chromium、Firefox、WebKit 支持范围与行为差异，关键兼容性不要只在单一浏览器里假设通过

**重点在这** ---- 遇到框架边界先重新划分测试层，不要用脆弱的绕过方案换一个漂亮的绿色数字

## 第八站：CI、并行与失败产物

第八站是测试调度台。开发机上的交互面板很友好，CI 更关心无头、资源、并行和证据；它没有耐心看你手动悬停，所以日志要自己会说话。

**无头运行** ---- 配置浏览器、视口、系统依赖、字体、代理、时区和 base URL，保证本地与 CI 的关键条件一致

**流水线分层** ---- 组织组件、快速 E2E、完整回归、跨浏览器和发布前冒烟测试，按反馈速度与风险安排

**并行与分片** ---- 按测试耗时、文件和浏览器拆分，处理共享账号、数据、端口、网络和报告合并

**重试策略** ---- 区分产品失败、环境瞬态和测试不稳定，保留第一次失败并统计重试，不能让重试替缺陷洗白

**失败证据** ---- 留存截图、视频、命令日志、网络、控制台、环境和测试数据摘要，敏感信息必须脱敏

**资源治理** ---- 关注浏览器进程、磁盘、内存、超时和并发上限，防止 CI 因为录像和缓存把自己吃掉

**重点在这** ---- CI 的目标不是“无人看见地跑完”，而是失败时让人能快速复现、定位并采取行动

## 第九站：稳定性、性能与可维护性

第九站是 Cypress 的维修厂。Flaky 测试不是天气，它通常有来源：选择器飘、等待错、数据共享、网络抖，或者测试正在假装用户会瞬移。

**自动重试边界** ---- 理解查询和断言会重试，而任意回调、副作用和外部动作不一定会重试，避免重复提交或重复写数据

**不稳定来源** ---- 排查动画、异步请求、时间、随机、共享状态、第三方服务、浏览器资源和 CI 拥塞

**测试性能** ---- 优化登录复用、数据准备、拦截、组件测试、并行和视频策略，先找慢点再改配置

**资源清理** ---- 关闭服务、清理数据、还原环境和隔离会话，确保一个测试的尾巴不会缠住下一个测试

**失败重现** ---- 固定浏览器、数据、网络和随机条件，缩小到最小测试与最小步骤

**升级管理** ---- 关注 Cypress、浏览器、Node、组件框架和插件版本，保留配置迁移与兼容性验证

**重点在这** ---- “自动重试”减少等待代码，但不能替代稳定选择器、清晰数据和正确的测试分层

## 第十站：E2E 设计、可访问性与选型

最后一站是测试路线规划室。Cypress 适合把浏览器变成可观察的实验场，但测试数量要克制；否则每次改一个按钮，整座城市都要重新通车。

**关键用户旅程** ---- 优先覆盖登录、核心业务、支付、权限、错误恢复和发布冒烟，控制 E2E 的数量与反馈成本

**可访问性** ---- 使用角色、名称、键盘、焦点和语义结构进行查询与验证，让测试不只为鼠标顺手的人服务

**测试分层** ---- 把纯逻辑交给单元测试，把组件状态交给组件测试，把浏览器留给跨层协作与高价值旅程

**契约与真实度** ---- 组合拦截、契约、集成和少量真实外部回归，平衡速度、稳定性和现实可信度

**安全边界** ---- 保护凭据、屏幕、网络日志和测试数据，不关闭安全策略来获得虚假的通过

**工具选型** ---- 比较 Cypress、Selenium、Playwright 等工具的运行模型、浏览器范围、语言、调试、并行和团队成本

**重点在这** ---- E2E 是风险探测器，不是每个函数的显微镜；关键、可读、稳定，才能活过下一次重构

## 通关标准

**Cypress 新手能跑页面** ---- 能配置项目、查询元素、完成交互、写断言并理解命令队列。

**初级前端能测流程** ---- 能拦截网络、处理异步 UI、登录、会话、表单和失败状态。

**中级工程师能测系统** ---- 能写组件测试、治理跨域边界、并行、CI、录像和 flaky 问题。

**高级工程师能建体系** ---- 能按风险设计测试层、保证可访问与安全、控制运行成本，并做出清晰的工具选型。

## 结语

Cypress 把浏览器拉到身边，让调试更像现场观察；它的自动等待让测试少写许多睡眠，但不会替你设计好契约。先理解命令队列，再写交互；先把网络和会话边界讲清，再谈复用；先把关键旅程分层，再打开并行。等你能让测试既像用户操作、又像工程证据，Cypress 就不只是一个会回放失败的工具，而是前端团队的现场记录员。
