# Claude Code 学习路线

Claude Code 像一位能读项目、改文件、跑命令、解释差异的协作工程师：它不会只在聊天框里给建议，而是愿意走进仓库现场。但它越能动手，人越要负责边界、授权、验证和最后签字。

这份路线是 **通用基础 → 工具与工作流 → Claude Code** 的独立学习地图。它覆盖代理式编程、项目上下文、权限安全、任务拆解、编辑验证、工具扩展、团队协作和自动化，不是提示词收藏夹。

**适合谁** ---- 想用 Claude Code 辅助读代码、修复 Bug、实现功能、重构、测试、文档和日常工程任务，或希望把 AI 协作变成可靠流程的开发者

**先记住一件事** ---- AI 是执行力很强的协作者，不是拥有最终责任的项目负责人；它可以加快手脚，但方向、权限和验收仍然需要人看守

**推荐总顺序** ---- 运行方式与边界 → 项目上下文 → 任务沟通 → 读改测闭环 → 权限与安全 → 计划与协作 → 工具扩展 → 自动化与团队治理 → 成本与质量

**本页怎么用** ---- 先让 Claude Code 学会“在哪、要做什么、不能动什么、如何验证”，再逐步开放能力；任务越大，越要拆成可检查的小步。

## 第一站：代理式编程与运行边界

普通编辑器等你点哪里，代理式工具则会主动读文件、规划动作和执行命令。它像一位很勤快的同事，勤快到需要先给它划好施工区域。

**代理式工作模型** ---- 理解模型、上下文、工具调用、观察、计划、行动、反馈和循环执行

**交互与非交互运行** ---- 区分对话任务、一次性任务、脚本化、CI、管道输入和会话续接

**工作目录与仓库边界** ---- 明确当前目录、项目根、Git 状态、生成文件、外部资源和可修改范围

**能力与限制** ---- 认识读文件、搜索、编辑、命令、版本控制、网络、工具协议和模型不确定性

**人机协作责任** ---- 建立授权、复核、验证、回滚和最终合并责任，不把“模型说完成了”当作验收结果

**重点解释** ---- 这一站通关是能说明 Claude Code 当前能看到什么、能做什么、在哪里做，以及谁对结果负责

## 第二站：项目上下文与协作说明

AI 刚进项目时像新同事，既不知道仓库规矩，也不知道哪个目录碰了会引发地震。清晰的上下文说明，就是给它的入职手册。

**项目概览** ---- 说明技术栈、入口、运行方式、关键领域、依赖和部署边界

**架构与目录** ---- 指明模块职责、数据流、公共工具、生成文件、禁止修改区域和约定

**命令与验证** ---- 提供开发、测试、Lint、类型检查、构建、迁移和部署前验证流程

**上下文层级** ---- 理解仓库、目录、用户、会话和临时指令的作用范围与冲突处理

**任务范围** ---- 明确目标、非目标、文件所有权、兼容要求、风险和完成标准

**上下文维护** ---- 让说明随架构、工具链、命令和约定更新，避免 AI 依据过期地图施工

**重点解释** ---- 这一站要能让一个新协作者快速知道“项目是什么、改哪里、怎么测、什么不能碰”，并让上下文成为可审查资产

## 第三站：任务描述、计划与对话控制

模糊任务会让 AI 像一只拿着地图却不知道目的地的快递员。好的任务描述不是写得长，而是把目标、边界、证据和停止条件说清楚。

**目标与验收** ---- 把愿望拆成结果、范围、约束、非目标、验收条件和输出形式

**先读后改** ---- 要求先定位文件、总结理解、指出风险，再进入编辑；复杂任务不要一上来就挥铲子

**计划与分步** ---- 学习探索、设计、实现、测试、审查和交付的阶段划分

**上下文控制** ---- 处理会话过长、相关文件、日志、历史、摘要和无关信息

**追问与假设** ---- 区分可安全假设、需要验证和必须由人决定的分支

**会话恢复** ---- 记录当前状态、未完成事项、验证结果、阻塞点和下一步

**重点解释** ---- 这一站通关是能把大任务交给 AI 后仍然知道它正在做什么、为什么这样做、什么时候算完成

## 第四站：读代码、改代码、运行验证

Claude Code 的真正价值不在于生成一段孤零零的代码，而在于把阅读、修改、测试和回顾连成闭环。代码写完只是故事中间，不是结尾。

**代码探索** ---- 掌握文件搜索、符号定位、调用关系、配置追踪、测试定位和最小相关上下文

**局部编辑** ---- 关注小步修改、复用现有模式、保持边界、避免无关格式化和尊重未提交改动

**差异审查** ---- 查看 diff、文件列表、删除/新增、依赖变化、配置变化和意外改动

**测试与构建** ---- 运行针对性测试、回归测试、Lint、类型检查、构建和最小运行验证

**失败处理** ---- 让模型读取真实错误、定位根因、提出修复、再次验证，避免用猜测覆盖证据

**结果说明** ---- 记录改了什么、为什么、验证了什么、没验证什么和剩余风险

**重点解释** ---- 这一站通关是能让 AI 走完“读 → 改 → 测 → 看差异 → 解释”的闭环，而不是收到一段看似漂亮但未验证的补丁

## 第五站：权限、安全与提示注入

一个能读仓库、执行命令的协作者，当然也可能读到秘密、执行危险操作或被恶意文本带偏。安全不是把工具关掉，而是让能力、信任和审批匹配。

**权限分级** ---- 区分只读、编辑、测试、网络、提交、部署和破坏性操作，按任务最小化授权

**批准机制** ---- 理解命令确认、自动接受、信任范围、危险操作、生产环境和人为复核

**仓库内容不等于指令** ---- 识别 README、注释、第三方代码、日志和网页中的提示注入与不可信内容

**秘密保护** ---- 防止环境变量、密钥、Token、证书、个人数据、日志和 diff 泄露

**命令与文件风险** ---- 关注删除、覆盖、迁移、权限、网络上传、外部脚本、依赖安装和部署

**供应链与工具** ---- 审查扩展、MCP、Skills、钩子、脚本、插件来源和数据访问范围

**重点解释** ---- 这一站通关是能画出模型、仓库、工具、命令、秘密和生产系统的信任边界，知道哪些动作必须停下来请人确认

## 第六站：调试、重构与复杂任务

复杂任务像一栋老房子：模型可以帮忙搬砖，但不能只看一面墙就宣布整栋安全。计划、回归和分阶段审查是它的安全绳。

**Bug 调查** ---- 收集复现、日志、堆栈、输入、环境、最近变更和最小案例

**根因分析** ---- 区分症状、触发条件、直接原因、系统原因和修复范围

**重构边界** ---- 先锁定行为，再小步改动，保持 API、数据、错误和性能契约

**迁移与升级** ---- 处理依赖、框架、数据库、配置、版本、兼容窗口和回滚

**多文件协调** ---- 建立文件所有权、顺序、共享接口、冲突和集成检查

**审查循环** ---- 使用独立审查、测试、静态检查、差异复盘和风险清单

**重点解释** ---- 这一站通关是能把复杂任务拆成可验证的小步，让 AI 的速度服务于可控性，而不是让风险一起加速

## 第七站：Git、分支与协作交付

AI 改代码时，Git 是那位负责记账的同事。每次动手前后都看状态和差异，模型就不容易把别人的改动顺手当成自己的行李。

**工作区卫生** ---- 检查当前分支、未提交改动、生成文件、冲突和用户已有工作

**小步提交** ---- 设计原子提交、提交信息、回滚点和可审查差异

**分支与隔离** ---- 使用分支、工作树、临时目录或其他隔离方式承载不同任务

**评审与合并** ---- 让 diff、测试、风险、迁移、依赖和发布说明进入评审

**恢复与撤销** ---- 掌握回滚、revert、恢复文件、reflog 和误操作后的证据保留

**自动生成提交的边界** ---- 明确模型可以准备变更，但提交、推送、合并和部署需遵循团队授权

**重点解释** ---- 这一站通关是能让 AI 参与交付而不破坏版本历史，随时知道哪些改动来自哪里、是否已经共享

## 第八站：工具扩展、MCP、Hooks 与 Skills

当 Claude Code 学会连接更多工具，它就像从自行车换成了工具车：能搬更多东西，也需要更严格的装载清单和刹车检查。

**工具协议** ---- 理解工具调用、输入输出、权限、超时、失败、上下文和数据边界

**MCP 类连接** ---- 认识外部服务、资源、提示、工具、凭据、网络和第三方数据访问

**Hooks 与自动检查** ---- 了解事件触发、格式化、Lint、秘密扫描、阻断、日志和脚本安全

**Skills 与工作流** ---- 规划可复用指引、适用范围、前置条件、验证、失败回退和版本

**扩展最小权限** ---- 限制文件、网络、命令、外部系统和写入范围，避免“为了方便全部开放”

**扩展故障排查** ---- 诊断工具不可用、输出异常、权限不足、超时、版本和环境差异

**重点解释** ---- 这一站通关是能判断一个工具扩展是否值得接入、拿什么权限、失败如何隔离，以及谁能审查它

## 第九站：自动化、CI 与团队治理

AI 一旦进入 CI，就不再只是个人桌边助手，而是团队流水线的一位新员工。新员工要有岗位说明、权限、考核和请假流程，不能靠“它应该懂”。

**脚本化任务** ---- 设计非交互运行、输入输出、退出码、超时、重试、日志和制品

**CI 使用边界** ---- 区分读检查、自动修复、生成变更、提交、推送、部署和生产操作

**审查与审批** ---- 建立人工门禁、分支保护、环境保护、差异审查和变更记录

**团队上下文** ---- 维护项目说明、命令、架构、禁止事项、测试和发布约定

**成本与限额** ---- 关注上下文、模型调用、并发、工具耗时、网络和缓存成本

**可观测与审计** ---- 记录任务、版本、输入范围、工具动作、审批、输出、验证和失败

**重点解释** ---- 这一站通关是能让 AI 自动化变成可追踪、可暂停、可回滚的团队能力，而不是一台没有日志的黑箱流水线

## 第十站：质量、评估与长期使用

AI 协作不能只看“这次写出来了没有”，还要看正确率、返工率、风险、时间和团队是否更安心。模型会成长，项目也会记账。

**结果质量** ---- 评估正确性、完整性、可维护性、兼容性、性能、安全和文档

**验证充分性** ---- 区分运行了什么、没运行什么、Mock 了什么、真实验证了什么

**返工与失败记录** ---- 记录误解、错误假设、注入、失败命令、回滚和改进规则

**工作流指标** ---- 关注交付时间、评审时间、缺陷、回滚、测试稳定性和上下文成本

**模型升级与兼容** ---- 关注工具行为、指令、输出格式、权限、成本和验证差异

**人类判断力** ---- 保留需求澄清、架构决策、风险承担、代码审查和最终验收的责任

**重点解释** ---- 这一站通关是能让 Claude Code 长期服务于工程质量，既享受速度，也不把判断力外包出去

## 学习路径建议：从会话到可靠协作

**第一阶段：安全使用** ---- 掌握运行边界、项目上下文、权限、提示注入和差异审查

**第二阶段：开发闭环** ---- 让 AI 参与探索、实现、测试、调试、重构和 Git 协作

**第三阶段：工具扩展** ---- 逐步接入工具协议、Hooks、Skills、外部服务和团队脚本

**第四阶段：自动化治理** ---- 进入 CI、审批、审计、成本、质量评估和长期维护

## 通关标准

**使用通关** ---- 能清楚描述目标、边界、验收和停止条件

**工程通关** ---- 能让 AI 完成读、改、测、审查和交付闭环

**安全通关** ---- 能识别权限、秘密、提示注入、命令、依赖和外部工具风险

**协作通关** ---- 能用 Git、上下文、计划、评审和恢复点保持团队可控

**治理通关** ---- 能把自动化接入 CI，同时保留审批、审计、成本和人类最终责任

## 结语

Claude Code 像一位手脚很快的工程师：它可以帮你翻文件、找线索、改代码、跑测试，也可能在没有边界时热心过头。给它清楚的地图、合适的钥匙和明确的验收，它就能成为很好的搭档；真正成熟的 AI 协作，不是让人退出现场，而是让人把时间从重复搬砖转向判断、设计和负责。
