# 前后端协作学习路线

前后端分离之后，接口就是双方的合同，浏览器和服务器就是两个都很有主见的部门。URL、字段、错误、认证、分页、时间、版本和发布只要有一项没说清楚，联调就会从工程问题迅速升级成“你这边是不是没更新”的悬疑剧。

这份路线专门训练全栈工程师的协作能力：从需求边界和数据流开始，走到 API 契约、类型、鉴权、联调、测试、发布、观测与变更治理。它是方法和检查清单，不替代具体框架文档；本页只设计协作路径。

**适用范围** ---- React / Vue + Node / Python / Java / Go，前后端同仓、前后端分离、BFF、移动端 API 和第三方开放接口都适用

**协作总顺序** ---- 需求与边界 → 数据与 API → 错误与鉴权 → 类型与文档 → 开发环境 → 测试与联调 → 版本与发布 → 观测与治理

**本页怎么用** ---- 每站先形成一份团队约定，再用真实接口和失败场景验证；口头约定可以开会，不能稳定运行

## 第一站：需求、边界与数据流

协作的第一步不是开 Swagger，而是确认系统到底要解决什么问题。需求没边界时，前端会猜页面，后端会猜接口，数据库会被迫替大家做产品经理。

**用户目标与业务流程** ---- 梳理角色、主流程、异常流程、状态转换、权限动作、数据生命周期和验收条件，区分“用户想做什么”和“页面要放什么按钮”

**系统边界** ---- 明确浏览器、前端应用、BFF、后端服务、数据库、缓存、队列、文件存储和第三方系统的责任；边界不清，问题就会在层之间踢皮球

**数据流与状态流** ---- 画出输入、验证、保存、异步处理、读取、缓存、展示和回写的路径，区分客户端状态、服务端状态、派生状态与最终状态

**领域词汇表** ---- 统一用户、账户、组织、订单、状态、时间、金额、删除和归档等术语，防止同一个词在前后端各自拥有不同人生

**非功能约束** ---- 提前确认延迟、吞吐、可用性、隐私、合规、可访问性、数据保留、审计和部署限制，避免开发结束才发现产品需要另一种物理定律

**重点解释** ---- 这一站的产出是边界、词汇、流程和约束；没有这些，API 设计只是把猜测排成了 JSON

## 第二站：API 风格与资源设计

第二站进入接口设计室。REST、GraphQL、RPC、BFF、Webhook 和实时协议各有适用场景，重点不是选一个时髦名字，而是让客户端和服务端对行为有同一份理解。

**REST 资源模型** ---- 按资源、集合、关系、动作和状态设计 URL，理解方法、状态码、幂等、缓存、条件请求与重定向的语义

**GraphQL 查询模型** ---- 了解 schema、查询、变更、订阅、resolver、查询深度、批量加载、缓存与权限，知道它不能自动消灭 N+1

**RPC 与 BFF** ---- 理解内部 RPC、面向用户的 API、后端聚合、移动端适配和领域服务边界，避免把内部对象直接暴露给所有客户端

**Webhook 与事件接口** ---- 设计签名、重试、幂等、顺序、版本、回调状态、超时和重放，第三方回调不能只靠“对方应该只发一次”

**实时接口** ---- 比较轮询、SSE、WebSocket 和消息推送的方向、连接、心跳、断线、重连、广播与扩容

**资源命名与字段风格** ---- 统一路径大小写、复数、字段命名、枚举、布尔、空值、时间和金额格式，命名争论要在第一天结束

**重点解释** ---- 这一站要能根据客户端类型、实时性、缓存、演进和部署边界选择 API 风格，而不是所有需求都套同一件外套

## 第三站：请求、响应与错误契约

第三站是合同正文。成功响应看起来很轻松，真正决定协作质量的是失败、空数据、部分成功、分页、字段错误和未知错误如何表达。

**请求契约** ---- 定义路径、查询、Header、Cookie、请求体、文件、默认值、必填项、未知字段和大小限制，区分缺失、空值与默认值

**成功响应** ---- 约定资源、列表、操作结果、批量结果、异步任务和空结果的结构，避免前端为了判断“成功没有”到处考古

**错误响应** ---- 设计状态码、稳定错误码、用户消息、字段错误、追踪 ID、重试提示和内部日志关联；机器读 code，人读 message

**分页与排序** ---- 比较页码、游标、时间线、稳定排序、总数、下一页标记与大数据集成本，分页一旦上线就会成为公共设施

**过滤与搜索** ---- 明确字段、操作符、大小写、模糊、全文、权限过滤、排序白名单和查询上限，避免把数据库查询语言直接暴露给客户端

**部分成功与批量** ---- 定义批量校验、逐项错误、事务边界、重复项、失败重试和结果顺序，批量接口不能只返回一句“有几条失败了”

**空值与兼容** ---- 区分 null、缺字段、空数组、空字符串和默认值，设计新增字段、未知字段和客户端降级策略

**重点解释** ---- 这一站的验收是前端能在不读后端源码的情况下处理成功、空、失败、分页、部分成功和重试

## 第四站：认证、授权与跨层安全

第四站是门禁系统。前端需要知道如何展示登录态，后端必须决定请求能不能通过；“前端把按钮藏起来了”只能算用户体验，不算安全。

**登录态模型** ---- 比较 Session、Cookie、JWT、短期访问令牌、刷新令牌、OAuth 2.0 与 OpenID Connect，明确存储、过期、撤销和轮换

**完整认证流转** ---- 约定登录、凭证携带、服务端验证、当前用户注入、401、刷新、请求重放、刷新失败、退出和多设备会话

**刷新并发** ---- 设计多个请求同时过期时的刷新排队、失败传播、旧令牌淘汰和重放上限，避免刷新接口被自己家的请求淹没

**授权与对象权限** ---- 区分角色、权限、资源范围、对象归属、租户、组织和服务身份，前后端对同一个动作使用同一套词汇

**跨域与 CSRF** ---- 理解同源、CORS、预检、凭证、Origin、Referer、SameSite 与 CSRF Token 的不同职责

**敏感数据** ---- 约定密码、Token、个人信息、支付信息、文件和审计数据的传输、展示、日志、缓存与删除策略

**重点解释** ---- 这一站要能画出登录和越权请求的时序图，明确谁负责体验、谁负责安全、谁负责记录与恢复

## 第五站：Schema、类型与文档先行

第五站是契约的自动化办公室。文档、类型和运行时校验各有职责：只写文档会漂移，只写类型会在运行时消失，只写校验会让人不知道如何调用。

**OpenAPI 与 Schema** ---- 描述路径、参数、请求、响应、错误、安全、分页、示例和版本，让契约可以被检查和生成

**共享 TypeScript 类型** ---- 共享稳定的请求、响应、错误和枚举类型，规划包边界、依赖方向、发布、版本和独立部署

**代码生成客户端** ---- 了解生成 API Client、类型、Mock、文档和变更差异的收益与限制，生成物要有来源，不能变成没人敢改的黑盒

**运行时校验** ---- 在浏览器边界、服务端入口、数据库出口和第三方响应处校验数据，理解编译期类型不能保护生产请求

**DTO、领域模型与视图模型** ---- 分开请求模型、响应模型、数据库模型、领域模型和前端视图，避免一张表的字段变化震动整个生态

**文档可发现性** ---- 统一接口目录、负责人、环境、认证方式、示例、弃用时间、变更记录和故障联系人

**契约差异检查** ---- 在 Pull Request 中比较 Schema、类型、数据库迁移和客户端变化，提前识别删除、改名、改类型与语义变化

**重点解释** ---- 这一站的目标是让契约有单一来源、有运行时验证、有变更记录、有消费方式，而不是多一份没人打开的文档

## 第六站：开发环境与联调工作流

第六站解决“我这里怎么调不通”。环境、代理、Mock、种子数据、账号和日志都要成为流程的一部分，不能每次联调都重新召唤一位熟悉端口的巫师。

**环境分层** ---- 区分本地、共享开发、测试、预发布和生产，明确数据隔离、配置、密钥、域名、依赖版本与访问权限

**前端代理与反向代理** ---- 规划本地路径、代理、跨域、Header、Cookie、HTTPS、WebSocket 和生产路由，让开发体验尽量接近真实部署

**Mock 与沙箱** ---- 用契约生成或维护 Mock，区分静态假数据、行为 Mock、第三方沙箱和真实集成，避免 Mock 变成另一个不受维护的后端

**种子数据与账号** ---- 准备可重复的用户、角色、组织、边界数据、过期数据、冲突数据和文件，测试账号不能靠某位同事的记忆传承

**联调排查顺序** ---- 按 URL、方法、查询、请求体、Header、Cookie、状态码、响应体、环境和数据库十层定位，不要从“前端肯定没问题”开始

**本地观测** ---- 让前后端共享请求 ID、日志格式、错误码和时间戳，浏览器 Network 与服务端日志能拼出同一条请求

**重点解释** ---- 这一站通关是开发者能独立启动依赖、准备数据、复现请求、定位差异并在本地完成闭环

## 第七站：变更、版本与兼容治理

第七站是变更管理处。接口一旦被多个客户端使用，任何删除、改名和语义变化都可能成为事故；兼容不是保守，而是给迁移留时间。

**兼容性分类** ---- 区分新增字段、删除字段、改名、改类型、改默认值、改变错误、收紧校验和改变排序的风险

**向后兼容** ---- 优先新增而非替换，允许客户端忽略未知字段，服务端保留过渡期，明确弃用通知与截止时间

**版本策略** ---- 比较 URL 版本、Header 版本、媒体类型、能力协商与无版本演进，按客户端生命周期和发布方式选择

**数据库与 API 联动** ---- 处理 schema 迁移、旧代码、新代码、双写、回填、读兼容、删字段和回滚顺序，接口变更不能脱离数据变更

**灰度与功能开关** ---- 用用户、租户、地域、比例或内部账号逐步放量，明确开关默认值、审计、过期和回滚

**客户端升级** ---- 管理 Web、移动端、第三方、缓存、生成客户端和旧浏览器的升级节奏，不能假设所有消费者今天都更新

**重点解释** ---- 这一站要能回答“谁会被这次变更影响、旧版本能活多久、失败如何回退”，而不是只改版本号

## 第八站：契约测试与联调验收

第八站把合同变成自动检查。单元测试保证局部逻辑，契约测试保证双方说同一种语言，端到端测试保证用户真的走得通。

**Schema 校验** ---- 验证请求、响应、错误、枚举、必填、未知字段、分页和安全定义，防止实现悄悄偏离契约

**消费者驱动契约** ---- 从前端或客户端真实使用方式验证服务端，发现“后端认为可选、前端认为必填”这类跨层冲突

**接口集成测试** ---- 覆盖认证、权限、数据库、事务、文件、超时、第三方失败和错误结构，尽量保留真实依赖边界

**前端行为测试** ---- 验证加载、空、错误、重试、401、403、分页、乐观更新、回滚和断网体验

**端到端流程** ---- 用少量关键流程覆盖注册、登录、核心业务、文件、支付或任务完成，锁住真正的用户路径

**破坏性变更检查** ---- 在 CI 中识别删除字段、收紧参数、状态码变化、错误码变化和响应结构变化，变更要有人接住

**联调验收清单** ---- 逐项确认环境、数据、认证、请求、响应、错误、日志、性能、权限与回滚，不用“看起来差不多”作为验收标准

**重点解释** ---- 这一站通关是接口变更能在合并前暴露，关键流程能在发布前验证，失败场景也有明确验收结果

## 第九站：发布、观测与事故协作

第九站是上线后的联合指挥部。上线不是前端点发布、后端点部署就结束，双方要能从同一份指标和日志判断问题属于哪里。

**发布顺序** ---- 规划前端、后端、数据库迁移、缓存、队列消费者、配置和第三方变更的先后与兼容窗口

**版本关联** ---- 在前端产物、后端服务、数据库迁移、配置和客户端日志中记录可追溯版本，事故现场不靠猜 commit

**统一观测字段** ---- 关联请求 ID、trace ID、用户或租户、路由、状态码、耗时、版本、依赖与业务结果，过滤 Token 和隐私

**错误归属** ---- 区分浏览器运行时、网络、网关、服务、数据库、缓存、队列和第三方错误，避免双方互相转发截图

**告警与升级** ---- 约定错误率、延迟、可用性、队列、数据一致性和业务指标的阈值、负责人、响应时间与升级路径

**回滚与降级** ---- 准备前端回退、服务回滚、数据库兼容、功能关闭、缓存失效、任务暂停和人工补偿方案

**事故复盘** ---- 记录影响、时间线、根因、检测、缓解、修复、后续行动与责任系统，不把复盘写成寻找替罪羊的文学作品

**重点解释** ---- 这一站的通关是双方能用同一条证据链发现、定位、缓解和复盘线上问题

## 第十站：团队机制与协作文化

第十站是软硬结合部。工具能减少重复沟通，但不能替代责任人、评审、变更通知和共同语言；最好的协作机制是让正确的信息在正确的时间到达正确的人。

**契约评审** ---- API、数据模型、权限、错误、性能和兼容性在开发前评审，减少写完后才发现方向不对

**变更通知** ---- 通过 Pull Request、变更记录、负责人、弃用公告和联调日管理接口变化，拒绝悄悄改字段

**责任矩阵** ---- 明确需求、契约、实现、测试、发布、监控、回滚和数据修复的负责人，不能所有人负责等于没有人负责

**Definition of Done** ---- 把文档、校验、测试、日志、指标、权限、迁移、部署和回滚纳入完成标准

**代码评审视角** ---- 同时检查协议语义、边界、错误、安全、性能、可观测与兼容，不只看格式和变量名

**共享词汇与决策记录** ---- 保存关键取舍、拒绝方案、兼容期限和已知风险，避免团队每隔三个月重新发明同一个轮子

**重点解释** ---- 这一站的目标是把个人经验变成团队机制，让协作质量不依赖某位“接口记忆大师”是否在线

## 学习路径建议：从一次联调到稳定交付

**第一阶段：画边界** ---- 选一个真实业务，画角色、状态、数据流、系统边界和异常流程

**第二阶段：定契约** ---- 设计资源、请求、响应、错误、分页、认证、时间、金额和版本，先让双方对同一张地图点头

**第三阶段：做闭环** ---- 前端和后端各自实现一条核心流程，用真实数据库、真实认证和可追踪日志完成联调

**第四阶段：锁行为** ---- 加入 Schema、契约、接口、组件与关键 E2E 测试，覆盖成功、空、失败、过期、权限和重复请求

**第五阶段：练变更** ---- 做一次新增字段、一次弃用、一次数据库迁移和一次失败回滚，体验兼容窗口的价值

**第六阶段：上生产** ---- 接入 CI/CD、版本、指标、告警、灰度、回滚、备份和事故复盘，完成从联调到交付的闭环

## 通关标准

**需求层通关** ---- 能画出角色、状态、数据流和系统边界，区分用户需求与实现细节

**契约层通关** ---- 能设计 REST、GraphQL 或 RPC 契约，统一请求、响应、错误、分页、时间、金额和版本

**安全层通关** ---- 能讲清认证、刷新、授权、CORS、CSRF、敏感数据和服务端最终校验

**工程层通关** ---- 能使用 Schema、类型、文档、Mock、契约测试和变更检查降低沟通成本

**联调层通关** ---- 能独立定位 URL、请求、认证、响应、环境、数据库和日志关联问题

**交付层通关** ---- 能完成兼容发布、灰度、监控、告警、回滚、备份与事故复盘

**协作主线毕业** ---- 能让前后端在不互相猜测的情况下共同交付，并在接口变化和线上故障时保持可解释、可追踪、可恢复

## 结语

前后端协作的本质，是把隐性约定变成显性契约，把契约变成可验证行为，再把行为接到可观测的发布流程上。这样接口变了会被发现，错误发生会有线索，版本升级有过渡，线上事故有退路。

别把协作理解成“多写几份文档”。真正有效的协作，是双方共享边界、词汇、数据、错误、权限和证据。**好的接口让人少猜，好的流程让人少等，好的观测让人少熬夜。**
