# 操作系统学习路线

操作系统是计算机的"资源大管家":CPU 归它调度、内存归它分配、文件归它管理、设备归它驱动。你写的每个程序都活在它的地盘上——你开的每个线程、每次文件读写、每个网络连接,都是在向它"申请资源"。

很多后端问题追到根上都是操作系统问题:高并发上不去、内存泄漏、进程假死、IO 瓶颈……所以它既是面试重灾区,也是区分"会用框架"和"真懂系统"的分水岭。学完组成原理再来,你会觉得处处是熟脸。

## 第一站:它到底在管什么

操作系统干三件事:**管理资源**(CPU、内存、磁盘、设备)、**提供抽象**(进程、文件、虚拟内存、套接字)、**保护隔离**(你的程序不能乱碰别人的内存和硬件)。

关键概念是**用户态与内核态**:普通程序跑在用户态,想碰硬件必须通过**系统调用**(syscall)请内核代劳——`read`、`write`、`fork` 都是系统调用。你在语言里调用的文件读写函数,最终都通向这里。为什么不能直接碰硬件?想象一个程序能随便改内存,蓝屏和崩溃就是家常便饭;内核态是唯一可信的"管理员模式"。

## 第二站:进程与线程

**进程**是"资源容器":每个进程有独立的地址空间、文件表、环境变量,进程间互不干扰(隔离)。**线程**是"执行单元":同一进程内的线程共享内存,所以通信方便,但也因此容易互相踩踏(下一站见)。

进程有生命周期:**就绪 → 运行 → 阻塞**,阻塞的典型是等 IO。**上下文切换**是操作系统的核心开销:换进程要切换地址空间,比换线程贵得多——这就是"线程比进程轻"的由来。

进程之间要通信(IPC):管道(Shell 里 `a | b` 就是管道)、消息队列、共享内存(最快,但要自己处理同步)、信号。线程间通信更简单:共享变量,但简单也意味着危险。

现代语言还给线程加了新花样:**协程**(用户态调度,切换成本极低):Go 的 goroutine、Python 的 async、JavaScript 的事件循环,本质都是"一个线程内自己调度多个任务"。学操作系统时你会恍然大悟:语言层面的并发模型,全是操作系统线程模型的"换皮优化"。

## 第三站:CPU 调度——谁先跑

多个就绪进程抢一个 CPU,谁先上?调度算法各有取舍:

- **先来先服务**:公平但"长任务堵车",短任务体验极差。
- **短作业优先**:吞吐高,但长任务可能饿死。
- **时间片轮转**:每人跑一小会儿,交互体验好——现代系统的基础。
- **多级反馈队列**:前面的合体,优先级高先跑、跑太久降级,Linux 的 CFS(完全公平调度)也是类似思路:按"虚拟运行时间"保证公平,还要处理优先级与多核负载均衡。

这一站只需要建立直觉:调度就是"在公平、吞吐、延迟之间做权衡"。

## 第四站:并发与同步——多线程的修罗场

两个线程同时改一个变量,结果取决于运气——这叫**竞态条件**。解决办法是**同步**:

- **互斥锁**:进临界区前加锁,出来解锁,保证同一时刻只有一个线程进。
- **读写锁**:读读不互斥、读写互斥,读多写少的场景(缓存)效率高。
- **信号量**:一个计数器,允许多个线程同时访问(比如连接池)。
- **条件变量**:让线程"等一个条件"(比如队列空了就等生产者),配合互斥锁用。

然后是面试名场面:**死锁**。四个必要条件缺一不可:互斥、持有并等待、不可剥夺、循环等待。破法也对应四条:破坏任一条件即可——最常见的实践是"按固定顺序加锁"和"加锁超时"。你以后排查线上"服务假死",八成就是在处理死锁或活锁。

进阶话题:**原子操作与 CAS**(比较并交换):不靠锁、靠硬件指令保证原子性,无锁编程的基础,Java 的 AtomicInteger、Go 的 atomic 都是它。对应到数据库世界,就是乐观锁与悲观锁——两条路线在这里又握了一次手。

## 第五站:内存管理——虚拟内存的魔法

虚拟内存是操作系统最伟大的魔术:每个进程都以为"我独占整个地址空间"(32 位是 4GB,64 位是 256TB 起),实际上物理内存被分页管理,页表负责把虚拟地址翻译成物理地址,不常用的页还可以被换出到磁盘。

这解决了三个问题:

隔离(进程互看不见):每个进程有独立的虚拟地址空间,进程 A 的地址 0x1000 和进程 B 的 0x1000 映射到不同物理页——不能越界访问,安全;

简化编程:程序总是从固定地址(如 0x400000)开始,链接器编译器不用考虑"程序会被加载到物理内存哪里";

超额使用(Overcommit):可用虚拟地址远大于物理内存(100 个进程各申请 1GB,实际物理内存可能只有 8GB,按需分配,大部分虚拟内存未真正使用)。

分页机制:虚拟地址空间与物理内存都按页(Page,Linux 默认 4KB,可配大页 2MB/1GB)划分——虚拟地址 = 页号 + 页内偏移,通过页表(Page Table)翻译:页号查页表得到物理页帧号(Frame),拼上偏移得物理地址。页表项(PTE)包含:物理页帧号、存在位(在内存还是磁盘)、读写执行权限位、访问位/修改位(用于页面置换算法)。

多级页表:直接页表太大(32 位 4KB 页,需要 2^20 个页表项,每项 4 字节 = 4MB 每进程),现代系统用多级页表(x86_64 是 4 级:PML4 → PDPT → PD → PT)——按需分配,未使用的虚拟地址范围不分配中间层,省内存。

TLB(Translation Lookaside Buffer,快表):页表在内存里,每次访存要额外访问页表(慢),TLB 是 CPU 内的页表项缓存(几十到几百项)——命中直接得物理地址,miss 才查内存页表(Page Walk)。进程切换会清空 TLB(地址空间变了),频繁切换性能下降的原因之一。大页(Huge Page)能减少 TLB miss(一个 2MB 大页顶 512 个 4KB 小页,TLB 覆盖更多地址)——数据库/虚拟机等大内存应用优化点。

缺页中断(Page Fault):访问的虚拟页不在物理内存(页表项存在位 = 0)→ CPU 触发缺页异常(Trap)→ 操作系统处理:

Minor Fault:页已分配但未加载(如首次访问 mmap 的文件、COW 写时复制)——从磁盘/文件读入、更新页表、返回重新执行指令;

Major Fault:页被换出到 swap——从交换区读回(耗时,几毫秒到几十毫秒,磁盘 IO);

Segmentation Fault(段错误):访问未分配的地址、权限错误(写只读页)——进程被杀(SIGSEGV)。

缺页中断是正常现象(按需分配内存,malloc 只分配虚拟地址,首次写入才分配物理页),但频繁 Major Fault(抖动,Thrashing)说明物理内存不足、频繁换页,性能雪崩。

页面置换算法(物理内存满时,选哪个页换出):

最优算法(理论不可实现):换出"未来最久不用的页"——只能离线分析,无法在线实现;

FIFO(先进先出):最简单但性能差(老页可能是热页);

LRU(最近最少使用):最优的近似——硬件支持访问位,操作系统定期清访问位,下次置换时选未被访问的;实现:时钟算法(Clock,二次机会)——环形链表,指针扫描,访问位 = 1 给机会(清零继续)、= 0 换出;

工作集模型:进程当前活跃使用的页集合——保证工作集在内存里,减少缺页;

局部性原理(内存管理的哲学基础):时间局部性(刚用的页很快再用)与空间局部性(相邻页一起用)——LRU 有效的原因。

写时复制(Copy-On-Write, COW):fork 子进程时不立即复制父进程内存,而是父子共享物理页(页表项标记只读)——任一进程写入时触发缺页,此时才复制该页(写时复制)。好处:fork 极快(只复制页表不复制内存)、节省内存(只复制修改的页)——Redis BGSAVE、shell 管道、多进程服务器都受益于 COW。

内存映射(mmap):把文件直接映射到进程地址空间——访问内存就是访问文件,操作系统按需加载(缺页时从文件读)、修改会写回(可配 MAP_PRIVATE 不写回)。用途:大文件读写(免 read/write 系统调用与用户空间缓冲区复制)、进程间通信(共享内存,映射同一文件或匿名映射)、动态库加载(so/dll 文件映射到内存,多进程共享代码段)。对比普通文件 IO:read/write 是复制(内核缓存 → 用户空间),mmap 是映射(页缓存直接映射,零拷贝)——大文件/随机访问/多次读写场景 mmap 更快。

堆与栈的内存布局(进程地址空间经典图):

低地址:代码段(.text,只读可执行)、数据段(.data 初始化全局变量、.bss 未初始化全局变量)

往上:堆(Heap,向上生长,malloc/new 动态分配)

往下:栈(Stack,向下生长,函数调用栈、局部变量)

高地址:内核空间(用户态不可访问,系统调用时切换)

栈溢出(Stack Overflow):递归太深、局部数组太大,栈指针撞到堆或超出限制(ulimit -s 查看,Linux 默认 8MB)——进程崩溃(SIGSEGV);尾递归优化、改迭代、增大栈限制是解法。

堆内存泄漏:malloc/new 忘记 free/delete,指针丢失但内存未释放——堆占用越来越大,最终 OOM(Out Of Memory,Linux OOM Killer 会杀高分进程)。检测:valgrind、AddressSanitizer、语言自带工具(Go pprof、Node heapdump)。现代语言 GC(垃圾回收)解决大部分泄漏,但循环引用、全局容器持有引用仍可能泄漏。

## 第六站:文件系统——数据怎么安家

文件系统把磁盘组织成你熟悉的**目录树**。文件在磁盘上不是"一整块",而是靠 **inode** 记录元数据(大小、权限、数据块位置),文件名只是目录里的一个指针——所以才有**硬链接**(多个名字指向同一 inode)和**软链接**(指向路径的快捷方式,可以跨文件系统)。

几个实用知识点:文件删除不是真删,只是标记空闲(所以能恢复);**页缓存**让刚读过的文件留在内存,第二次读飞快;数据库为什么要求 `fsync` 落盘——因为操作系统默认"先写缓存再说",断电就丢,数据库的 ACID 里 D(持久性)必须强制刷盘。

Linux 的 ext4/xfs、Windows 的 NTFS、macOS 的 APFS 都是具体实现,命令行的 `ls -l` 权限位(`rwxr-xr-x`)背后就是 inode 里的权限字段——这块的操作细节见 [Linux 学习路线](/learning-paths/devops/linux)。

## 第七站:IO 模型——高并发的胜负手

网络高并发的本质,是"大量连接在等数据,CPU 不能傻等"。IO 模型进化史:

1. **阻塞 IO**:一个线程等一个连接,连接多了线程不够用。
2. **非阻塞 IO**:轮询"好了没",不阻塞但浪费 CPU。
3. **IO 多路复用**:一个线程同时盯几千个连接,谁就绪处理谁——`select`(上限低)、`poll`(没上限但每次全量扫描)、`epoll`(事件驱动,只返回就绪的,Linux 高并发标配;macOS 对应 kqueue)。
4. **异步 IO**:内核做完直接回调,连"等就绪"都省了。

Node.js 的"单线程却高并发"、Go 的 goroutine + netpoller、Netty 的 Reactor 模型,全是 epoll 这套思路的上层封装——这就是为什么学后端绕不开它。**零拷贝**(sendfile)是另一个优化神器:数据从磁盘到网卡不经过用户态,传输大文件时 CPU 几乎不干活。

## 第八站:容器、虚拟化与开机

**虚拟机**模拟整台机器,每个虚拟机有自己的内核; **容器**(Docker)共享宿主内核,靠 namespace 隔离视图、cgroup 限制资源——所以容器秒级启动、密度高,但也意味着"容器逃逸"能直接威胁宿主机。理解了这层,你就明白为什么说"容器不是轻量虚拟机"。[Docker 学习路线](/learning-paths/devops/docker) 会接着展开。

最后把整条线串起来:按下电源 → **BIOS/UEFI** 自检 → 引导加载程序找到内核 → 内核初始化(内存、驱动、调度器)→ 启动第一个进程 → 登录 → 你的程序跑起来。整个计算机系统,从组成原理的硬件,到这里的软件大管家,闭环了。

## 通关标准

能讲清楚:进程与线程的区别和通信方式、死锁四条件与破解思路、虚拟内存解决了什么问题、epoll 为什么适合高并发、容器与虚拟机的本质区别——操作系统主线就算通关。再进一步,能用工具(ps/top/htop/strace)定位"进程为什么卡住",你就有了排查线上问题的内功。
