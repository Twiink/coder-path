# 云原生模式学习路线

云原生不是把“云”两个字贴在旧应用门口，而是让应用学会在动态、分布式、可替换的环境里生活。它面对的是会自动扩缩的资源、会漂移的地址、会重启的实例、会延迟的网络和会突然涨价的账单；如果应用还把本机磁盘当保险柜，把进程内存当数据库，它会很快发现云并不负责哄睡。

这条路线把常见模式、底层运行时、资源与网络、调度与弹性、发布、安全、可观测性、可靠性、成本和演进串成一条线。每一站都追问三个问题：这个模式解决什么问题，增加什么代价，出现故障时如何证明它仍然有效。

**推荐顺序** ---- 云原生应用心智模型 → 生命周期与健康 → 配置、秘密与状态 → 运行时、资源与网络 → 弹性与调度 → 可靠性模式 → 可观测性与 SLO → 安全与供应链 → 发布与演进 → 成本、多租户与平台化

## 第一站：云原生应用与 12-Factor 心智模型

第一站先让应用和云握手。云喜欢替换实例，应用却常常把实例当成祖传家具；这一站要把“服务是可复制的进程”这件事讲清楚，让应用不再因为换了一台机器就开始闹脾气。

**应用与基础设施边界** ---- 区分业务代码、运行时、平台服务、托管数据库、消息系统、对象存储和交付系统；应用负责业务语义，平台负责通用运行能力，边界清楚才能替换实现

**进程模型** ---- 把 Web、Worker、Scheduler、一次性迁移和管理任务视为可独立启动的进程类型；进程应无状态、可横向复制，状态交给外部可靠系统

**依赖显式化** ---- 通过锁文件、镜像、包管理和构建清单声明依赖，不依赖某台机器手工安装的“祖传环境”；依赖版本、证书和系统库都属于交付输入

**配置外置** ---- 将环境差异放进运行时配置，区分普通配置、秘密、动态开关和不可变构建产物；代码包相同，配置可审计、可回滚，才有真正的环境一致性

**一次性与可替换实例** ---- 让进程能被终止、重启、迁移和并行扩展；本地缓存、临时文件和连接都应被视为可丢失资源

**日志作为事件流** ---- 应用输出结构化日志到 stdout 或统一采集接口，由平台负责路由、保留和检索；应用不要把日志轮转、磁盘清理和远程传输全塞进业务进程

**管理任务与迁移** ---- 将数据迁移、回填、清理和诊断设计成可审计、可重试、可停止的任务；一次性任务也需要权限、资源、日志、超时和恢复策略

## 第二站：启动、健康与生命周期

第二站请应用参加体检。平台只看得到进程是否在呼吸，用户关心的是能不能办事；健康检查写得太随便，系统会把昏迷误报成精神饱满，把短暂依赖故障升级成重启风暴。

**启动阶段** ---- 区分加载配置、迁移、建立连接、预热缓存、绑定端口和开始接流量；启动过程应有超时、阶段日志和失败原因，不要无限等待依赖

**存活、就绪与启动探针** ---- 存活回答进程是否长期失活，就绪回答是否能接收流量，启动探针保护慢启动；三者检查不同问题，不应共用一条昂贵业务 SQL

**优雅关闭** ---- 收到终止信号后停止接收新请求、从发现系统摘除、等待在途请求、提交或取消任务并关闭连接；配置终止宽限期，避免发布像拔电源

**优雅重启** ---- 让实例可以滚动替换、自动扩缩和故障迁移，确保启动与关闭都幂等；重启不是修复手段，只有在根因可接受时才让平台自动重启

**依赖就绪与降级** ---- 启动时区分必需依赖与可选依赖，运行时使用超时、缓存、默认值或降级；不要让一个非关键统计服务阻止核心 API 启动

**生命周期事件** ---- 观察启动、就绪、摘除、终止、重试、驱逐和迁移；将版本、实例、原因和时间写入日志或事件，便于把平台动作与业务影响对齐

**本地与生产一致性** ---- 本地测试覆盖信号、探针、超时、配置缺失和依赖不可用；只有“正常启动”测试不能证明应用能在云平台活下来

## 第三站：配置、秘密与状态

第三站由配置管理员和数据管理员共同值班。ConfigMap 不是密码箱，环境变量也不是万能抽屉；状态放错位置时，应用往往在重启那一刻才想起自己曾经拥有过记忆。

**配置分类** ---- 区分静态构建配置、环境配置、运行时开关、实验参数和秘密；每类配置应有来源、版本、权限、校验、默认值和回滚方式

**秘密管理** ---- 使用密钥服务、短期凭证、工作负载身份和自动轮换，避免秘密进入 Git、镜像、命令行、日志和错误页面；读取秘密的权限应按服务拆分

**动态配置** ---- 配置热更新要明确传播延迟、并发可见性、旧值保留和失败回退；涉及连接地址、认证或线程池的变更，通常需要安全重载或重启

**无状态与外部状态** ---- 会话、文件、缓存、队列偏移和业务真相分别放在合适的外部系统；不要用实例内存、临时目录或容器可写层冒充持久化

**数据一致性边界** ---- 选择强一致、最终一致、幂等写入、版本号、乐观锁或补偿事务；分布式系统没有免费的一致性，必须说清延迟和失败时的行为

**缓存模式** ---- 了解 cache-aside、刷新、过期、穿透、击穿、雪崩和失效广播；缓存可以提高性能，但不能成为唯一数据来源或隐藏源站故障

**事件与消息状态** ---- 为事件设计唯一 ID、版本、时间、来源、重放和去重策略；消费者应能面对重复、乱序、延迟和未知字段

## 第四站：运行时、资源与网络

第四站把应用放到真实的云上跑。这里的员工不是在同一台机器里排队，而是在会抖动的网络和有边界的 CPU、内存、连接、线程、文件描述符中协作；每个边界都要有超时和退路。

**进程与容器运行时** ---- 理解 PID 1、信号、namespace、cgroup、文件系统层和容器入口；应用要正确接收信号、写日志、处理时区并尊重资源限制

**CPU、内存与文件描述符** ---- 根据峰值和尾延迟设置 requests/limits、堆大小、线程、连接池和句柄上限；限制过小会 OOM 或节流，过大则浪费容量

**线程池与连接池** ---- 为每个下游设置连接数、排队长度、空闲回收、建立超时和最大生命周期；池子无限大只会把压力更快传给下游

**网络超时** ---- 分别设置 DNS、连接、TLS、写、读、整体请求和空闲超时；默认无限等待是最隐蔽的资源泄漏之一

**服务发现与地址** ---- 使用动态发现、健康后端和短期连接，避免把实例 IP 固定写入配置；发现系统也会延迟和失败，客户端要能重试与刷新

**协议与负载** ---- 选择 HTTP、gRPC、消息或批量协议时考虑连接复用、压缩、大小、流式传输和向后兼容；大文件走对象存储或直传，不要穿过所有业务层

**时间与时钟** ---- 统一 UTC 存储和可读展示，处理时钟漂移、超时、租约与夏令时；分布式系统不应假设所有机器的时间完全相同

## 第五站：弹性、调度与流量控制

第五站是交通调度中心。流量一来，所有服务都想加车；资源一紧，调度器又要给车找座位。真正的弹性不是无限复制，而是在容量、延迟、成本和下游承受力之间保持可控。

**水平与垂直扩缩** ---- 水平扩容增加实例，垂直扩容增加单实例资源；横向扩展要求无状态、共享外部状态、可分区和不依赖本机身份

**调度约束** ---- 用资源请求、亲和性、反亲和性、污点、容忍、拓扑分布和专用节点表达放置要求；约束越多越可靠地符合意图，也越可能导致 Pending

**自动扩缩反馈** ---- HPA、队列长度、并发、延迟和自定义业务指标都可能驱动扩容；指标采样、冷却、启动时间和缩容滞后要纳入控制回路

**限流与背压** ---- 在入口、服务、租户、队列和数据库边界设置限流，使用队列、批处理和流控吸收尖峰；拒绝一部分请求通常比拖垮全部请求更可靠

**负载均衡** ---- 理解随机、轮询、最少连接、权重、区域和一致性哈希的适用场景；带状态的会话粘性会削弱弹性，能外置就外置

**领导选举与定时任务** ---- 多副本任务需要租约、续期、时钟与失联处理，避免所有实例同时执行迁移或清理；选主失败时要安全停止而非双主工作

**资源配额与优先级** ---- 为团队、命名空间、租户和任务设置配额、优先级、抢占与预算；平台调度的公平性也是可靠性和成本治理的一部分

## 第六站：可靠性模式与故障隔离

第六站请级联故障这位“热心邻居”离开现场。它最擅长把一个下游超时传遍整条调用链；这一站要学会让每个服务在压力、重复、乱序和部分失效下仍有边界。

**超时** ---- 让每个调用都有合理超时，并确保上游总预算大于下游局部预算；超时过长会占住线程和连接，过短则把正常抖动误判成失败

**重试与退避** ---- 只对幂等或可安全重试的瞬态错误重试，使用指数退避、抖动、次数上限和预算；重试风暴会把小故障放大成大故障

**熔断与舱壁** ---- 熔断在下游异常时快速失败，舱壁隔离线程、连接、队列或租户；两者都要定义恢复、半开、监控和人工旁路

**幂等与去重** ---- 用幂等键、唯一约束、状态机、去重表和安全重放处理客户端重试、消息重复和超时未知结果；“只执行一次”通常需要更贵的协议，不要轻易承诺

**事务与补偿** ---- 跨服务操作用 Saga、补偿动作、Outbox、Inbox 或事件最终一致性拆解；补偿不是撤销魔法，要处理补偿失败和人工介入

**降级与静态响应** ---- 对非核心能力使用缓存、默认值、只读、排队、部分结果和功能开关；降级必须可观测并有恢复条件，不能把错误藏到永远

**混沌与故障演练** ---- 注入延迟、丢包、进程终止、磁盘满、凭证过期和依赖不可用，验证超时、重试、告警、恢复和数据完整性；先在小范围、可回滚的环境演练

## 第七站：可观测性、SLO 与运维闭环

第七站给应用发一面镜子。没有指标、日志、追踪和变更记录，分布式系统的每次事故都像“大家同时凭感觉讲故事”；有了统一信号，故事才开始有时间线。

**应用指标** ---- 设计请求速率、错误率、延迟分布、并发、队列、依赖、资源和业务结果指标；避免把高基数字段直接放进指标标签

**结构化日志** ---- 统一时间、服务、环境、版本、请求 ID、trace ID、错误类型和脱敏规则；日志要能被检索、聚合和关联，而不是只适合肉眼翻页

**分布式追踪** ---- 透传上下文，记录入口、服务、队列、缓存、数据库和外部 API 的跨度；采样策略保留错误、慢请求和关键业务路径

**健康与合成探测** ---- 用黑盒探测验证 DNS、TLS、入口和关键业务动作，用白盒信号解释内部原因；探测本身也要监控误报、漏报和成本

**SLI 与 SLO** ---- 以可用性、延迟、正确性和数据新鲜度定义用户承诺，用错误预算管理发布速度、技术债与风险；SLO 不应只写在墙上

**变更关联** ---- 在指标、日志、面板与追踪中关联提交、镜像、配置、迁移和发布批次；发现“发布后变慢”时，不必先召唤占卜师

**运行手册与复盘** ---- 每条关键告警有负责人、分层排查、缓解、升级、回滚与恢复步骤；事故复盘关注系统条件和改进项，不把责任归结为某个人按错按钮

## 第八站：安全、身份与供应链

第八站由安全官守门。云原生系统里身份会移动、服务会扩缩、制品会经过多个仓库；“在内网”“在容器里”“在流水线里”都不是自动获得信任的理由。

**身份优先** ---- 为用户、服务、Job、CI 和平台控制器使用独立身份与短期凭证；授权围绕资源、动作、环境和租户，而不是围绕一台固定主机

**最小权限** ---- 将读取、写入、部署、审计和管理权限分开，定期回收闲置绑定；默认拒绝和显式放行比全网互信更可解释

**网络分段** ---- 限制入口、东西向和出站流量，按服务、命名空间、租户、端口和身份控制；网络隔离要兼顾 DNS、观测、备份和应急通道

**制品与依赖** ---- 固定基础镜像、锁依赖、生成 SBOM、扫描漏洞、签名并验证来源；漏洞处理要结合可达性、运行时暴露和修复窗口

**运行时防护** ---- 使用非 root、只读文件系统、seccomp、强制访问控制、无特权和异常行为监测；平台策略需要例外审计与到期治理

**数据保护** ---- 传输与静态加密、密钥轮换、备份访问、脱敏、保留和删除都要有责任人；日志与追踪也可能是敏感数据

**安全响应** ---- 准备凭证吊销、制品隔离、流量阻断、取证、恢复和对外沟通流程；安全事件不能只靠“重新部署一遍”收尾

## 第九站：发布、渐进交付与演进

第九站是发布剧场。云原生发布不是把新进程扔进集群然后祈祷，而是把制品、配置、数据迁移、流量、观测和回滚编排成一场有护栏的演出。

**不可变制品** ---- 构建一次、测试一次、签名一次，再将同一摘要推广到不同环境；环境差异进入配置与权限，不进入“生产现场重新编译”

**滚动、蓝绿与金丝雀** ---- 滚动逐步替换实例，蓝绿切换两套环境，金丝雀按比例或用户分群放量；选择取决于流量控制、容量、回滚速度和数据兼容性

**功能开关** ---- 将代码发布与功能启用解耦，支持租户、区域、百分比和紧急关闭；开关必须有所有者、默认值、监控和清理期限

**数据库迁移** ---- 使用扩展、回填、切换、收缩阶段，让新旧版本兼容；回滚应用时先确认 schema、事件和缓存不会造成不可逆冲突

**GitOps 与策略即代码** ---- 用版本库记录环境期望，用策略阻止不安全制品、过量资源和越权配置；自动同步仍要保留审批、紧急修复和漂移审计

**回滚与前进修复** ---- 定义什么时候回流量、恢复旧制品、关闭开关、暂停任务或继续修复；数据写入后常常只能前进修复，不能机械回滚

## 第十站：成本、多租户与平台工程

最后一站请财务和平台工程师坐下。云原生会让扩缩变简单，也会让无效副本、过高日志、跨区流量和过度复杂的平台悄悄长胖；自动化如果没有预算，最终只是自动烧钱。

**成本可观测性** ---- 将 CPU、内存、存储、网络、日志、追踪、负载均衡、备份和托管服务账单关联到团队、服务与环境；看单位请求、单位订单或单位构建的成本

**资源右-sizing** ---- 用真实峰值、尾延迟、启动时间和故障余量调整请求与限制；过度预留浪费钱，过度压缩则增加驱逐、节流和告警成本

**弹性与预算** ---- 把自动扩缩上限、配额、优先级、Spot/抢占资源和预算告警一起配置；成本保护本身也要避免影响关键恢复与备份

**多租户隔离** ---- 用命名空间、身份、网络、配额、节点池、数据分区和计费标签隔离团队与客户；强隔离场景要评估多集群、虚拟集群或独立账户

**平台自助服务** ---- 将部署、策略、观测、证书、备份和回滚封装为模板与 API；平台隐藏重复复杂度，但必须暴露状态、日志、限制和逃生通道

**复杂度预算** ---- 每引入一个 Operator、服务网格、消息系统或多云抽象，都要记录资源、学习、排障和迁移成本；不是所有云原生能力都值得现在安装

**演进与退出** ---- 设定版本、弃用、数据迁移、平台迁出和供应商切换的路径；可迁移性不是复制所有服务，而是掌握边界、制品、数据和恢复能力

## 通关标准

能把一个服务设计成可替换、可扩缩、可观测、可恢复的云原生进程；能说明配置、秘密、状态、缓存、消息和数据一致性的边界；能为资源、网络、调度、超时、重试、熔断、限流、幂等和补偿制定策略；能用 SLI/SLO、日志、指标、追踪和变更记录定位一次故障；能设计最小权限、供应链验证、渐进发布、迁移与回滚；能计算资源、网络、日志和人工维护成本，并判断哪些平台能力值得引入。

去 Kubernetes 把声明式控制、调度、网络、存储和发布落地；去监控路线完善 SLO 与告警；当服务数量和多语言治理复杂到需要统一流量层时，再学习服务网格与 Serverless 的取舍。

## 结语

云原生的核心不是某个产品，而是对变化的预期：实例会换、网络会慢、依赖会坏、版本会共存、预算会见底。把这些变化写进生命周期、资源、协议、发布和恢复设计里，应用才算真正学会在云上生活。
