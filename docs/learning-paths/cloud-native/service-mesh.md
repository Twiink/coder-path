# 服务网格学习路线

服务网格是微服务之间那位穿反光背心的交通管理员：它不负责写订单逻辑，却负责服务发现、流量路线、加密、授权、重试、指标和追踪。它把治理能力从应用代码下沉到代理与控制面，同时把一部分复杂度搬进了集群；所以它是工具箱，不是每个项目都必须佩戴的勋章。

这条路线从东西向流量和数据面开始，经过 Sidecar、Ambient、控制面、xDS、服务发现、路由、弹性、安全、可观测性、多集群、资源、成本和选型。学习时始终与 Kubernetes 的调度、应用自身的业务语义和入口网关的南北向职责对照。

**推荐顺序** ---- 网格边界与双平面 → 代理运行时 → 控制面与配置 → 服务发现与网络 → 流量管理与发布 → 弹性治理 → mTLS 与授权 → 可观测性 → 多集群与出站 → 资源、成本、排障与演进

## 第一站：为什么需要服务网格

第一站先给“要不要上网格”做体检。十几个单语言服务、框架自带治理、没有灰度需求的团队，可能只需要把超时写好；服务数量、多语言、合规和流量策略一起增长时，网格才开始值得占一个席位。

**东西向与南北向** ---- 网格主要治理服务到服务的东西向流量，API Gateway、Ingress 或 Gateway API 主要治理外部到内部的南北向入口；两者可以协作但职责不同

**重复治理问题** ---- 微服务常常重复实现发现、负载均衡、TLS、重试、熔断、限流、指标和追踪；网格提供统一策略，但不理解每个业务动作是否可重试

**适用条件** ---- 服务数量、多语言栈、跨团队治理、渐进发布、零信任和观测需求是价值来源；规模小、延迟极敏感、团队没有平台能力时，新增的复杂度可能大于收益

**不解决的事情** ---- 网格不会修复错误业务逻辑、数据库一致性、消息幂等、资源不足或糟糕的 API 契约；它能执行通信策略，不能替业务做决定

**应用与网格边界** ---- 应用负责业务指标、语义幂等、事务与用户授权，网格负责网络身份、路由、连接和通用遥测；边界模糊会造成双重重试和权限冲突

**渐进采用** ---- 从少量命名空间、低风险链路和只读观测开始，逐步加入 mTLS、授权、灰度和弹性；每一步都先测资源、延迟、失败与回滚

## 第二站：数据平面、Sidecar 与代理运行时

第二站参观数据平面。Sidecar 像每个服务旁边都站着一位翻译兼保安：请求先经过它，再到应用；它很勤快，但每个 Pod 多一个邻居，资源和故障面也会跟着增加。

**Sidecar 模式** ---- 在工作负载旁注入 Envoy、Linkerd proxy 等代理，拦截进出流量并执行策略；应用通常不改代码，但要处理代理注入、退出和端口冲突

**透明流量劫持** ---- 通过 init 容器、iptables、eBPF 或等价机制将流量导入代理；排障时要知道原始目的地址、监听端口和排除规则，否则很容易把策略问题误认成应用问题

**数据面职责** ---- 负责连接、协议、负载均衡、路由、TLS、策略执行、指标和访问日志；它按控制面下发的配置工作，不负责存储业务状态

**代理进程与信号** ---- 关注代理的 PID、优雅退出、监听器、连接池、线程、缓冲区和配置热更新；代理崩溃或退出顺序可能让应用看似健康却无法通信

**Sidecar 资源** ---- 每个 Pod 额外消耗 CPU、内存、临时存储和网络处理，服务跳数增加延迟；设置 requests/limits、采样和日志级别，测量真实开销而不是背一个固定百分比

**Ambient 与无 Sidecar 模式** ---- 节点级或共享代理减少每 Pod 开销，可能改变流量、隔离和调试模型；它不是“零代理”，要理解 ztunnel、waypoint 或具体实现的边界

**旁路与兼容** ---- 非 HTTP 协议、长连接、WebSocket、UDP、主机网络和特殊端口可能需要明确配置；加入网格前先做协议矩阵与回滚方案

## 第三站：控制面、xDS 与资源对象

第三站来到控制面办公室。它不亲自搬运每个请求，却要把服务、证书和路由翻译成代理能执行的配置；控制面忙时，新规则可能迟到，但数据面通常会继续使用最后一份有效配置。

**控制面与数据面** ---- 控制面发现服务、生成配置、签发身份并下发策略，数据面代理实际转发与观测；控制面故障和数据面故障的影响范围不同

**Istiod 与 Envoy** ---- 以 Istio/Envoy 为代表理解控制器、服务注册、证书、配置分发和代理管理；产品版本、安装方式和默认策略要以实际平台为准

**xDS 配置** ---- 认识 CDS 集群、EDS 端点、LDS 监听、RDS 路由和 SDS 密钥等动态配置；“我写了资源”不等于“代理已经收到并采用了它”

**VirtualService** ---- 描述匹配条件、路由、权重、超时、重试、重定向和故障注入；匹配顺序、默认路由和无匹配行为必须明确

**DestinationRule** ---- 定义子集、负载均衡、连接池、熔断、离群检测和 TLS；策略需与服务版本标签、协议和下游容量对齐

**Gateway 与 ServiceEntry** ---- Gateway 管理边缘入口，ServiceEntry 描述网格外部服务与出口；外部依赖接入后，DNS、TLS、审计和故障边界仍要单独设计

**策略作用域与配置校验** ---- 理解全局、集群、命名空间、工作负载、端口和优先级；用静态分析、代理实际配置和小范围验证确认生效

## 第四站：服务发现、连接与网络路径

第四站是网格交通地图。Service、DNS、Endpoint、代理集群、连接池和底层 CNI 一层套一层；“Service 存在”只说明有地址牌，不说明后面真的有健康商店。

**服务注册与发现** ---- 网格从 Kubernetes Service、EndpointSlice、DNS、VM 注册或外部目录获得服务实例；发现延迟、失效和跨集群同步会影响流量选择

**负载均衡** ---- 了解轮询、最少请求、随机、权重、一致性哈希、区域优先与故障转移；粘性会削弱弹性，连接复用会改变请求分布

**连接池** ---- 设置最大连接、请求、空闲连接、排队和生命周期，避免代理把下游连接打爆；连接池与应用线程池、数据库池需要共同计算

**协议识别** ---- HTTP、HTTP/2、gRPC、TCP、TLS passthrough 和升级连接的识别方式不同；协议识别错误会导致路由、指标和重试语义失真

**DNS 与地址** ---- 代理可能基于服务名、集群 IP、端点或原始地址建立连接；排查时分别验证 DNS、代理配置、Endpoint、路由表和 NetworkPolicy

**跨命名空间与跨集群** ---- 跨边界调用要明确身份、出口、延迟、故障转移、数据驻留和计费；跨区流量不是免费，也不是瞬间到达

**入口与出口** ---- 入口网关处理外部证书、认证、限流与路由，出口网关集中控制外部 API；两者都要防止绕过网格直接访问敏感服务

## 第五站：流量管理与渐进发布

第五站是网格的发布剧场。新版本先站在后台，流量管理员按权重、用户或请求特征给它一点掌声；指标不好看时，权重可以退回，但数据副作用不会自动消失。

**版本子集** ---- 用稳定标签把 v1、v2 映射为目标子集，避免依赖临时 Pod 名或 IP；版本标签、镜像摘要和配置要关联

**权重灰度** ---- 按百分比分流，逐步观察错误率、尾延迟、业务结果、资源和依赖，再扩大范围；权重变化要审计、可回滚且考虑连接复用

**按请求路由** ---- 按 Header、Cookie、用户、租户、地域或 URI 做 A/B 与定向测试；用户分组要稳定、隐私合规并防止绕过授权

**蓝绿切换** ---- 两套版本并行，入口一次切换；切换前后都要验证连接、缓存、数据库 schema、异步消费者和回滚容量

**流量镜像** ---- 将请求复制给影子版本并丢弃响应，观察性能与错误；写操作、隐私、随机性和副作用必须隔离，否则影子会真的动手

**自动渐进交付** ---- Flagger、Argo Rollouts 或类似工具可根据指标调权、暂停、回滚；自动化规则要防止指标缺失、低流量和业务信号滞后造成误判

**故障注入** ---- 注入延迟、状态码、断连和流量比例，验证超时、重试、熔断、降级与告警；实验要限定范围、时间和清理责任

## 第六站：超时、重试、熔断与限流

第六站是网格的急救室。代理很喜欢帮忙重试，但它不知道一次扣款是否已经成功；通用网络策略要和业务幂等、方法语义、下游容量一起使用。

**超时预算** ---- 从入口总预算倒推每一跳的连接、TLS、读写和整体超时；代理超时、应用超时和数据库超时不一致时，故障会表现得很像魔术

**重试策略** ---- 只对幂等方法或有幂等键的请求重试，设置次数、退避、抖动、每次超时和重试预算；同时在应用和网格重试会造成倍增

**熔断与异常点** ---- 通过连接池、并发、队列和连续错误限制保护下游，离群检测暂时摘除异常实例；半开恢复、误摘除和低流量判断要被观测

**限流** ---- 入口、服务、租户和方法级限流可以在代理或外部限流服务执行；网格本地限流和全局配额的准确性、状态与成本不同

**负载保护** ---- 使用舱壁、最大请求、缓冲区、连接上限和快速失败防止一个租户或接口占满代理；保护规则不能让健康流量一起饿死

**降级与故障转移** ---- 可返回缓存、默认值、只读结果或备用区域；降级要记录业务影响，故障转移要考虑数据一致性、DNS、连接和恢复后的回切

## 第七站：mTLS、身份与授权

第七站是零信任检查站。网格可以为服务发证书、加密链路、验证对端身份，但“拿到证书”不等于“允许访问订单”；认证和授权必须各自清楚。

**mTLS** ---- 双向 TLS 同时提供加密与服务身份认证，代理代替应用处理证书协商和轮换；证书颁发者、有效期、信任域和时钟同步要可审计

**工作负载身份** ---- 以服务账号、命名空间、SPIFFE 等方式标识工作负载，不把 IP 当成永久身份；实例替换后身份策略仍应稳定

**PeerAuthentication** ---- 以全局、命名空间、工作负载或端口控制明文、兼容和严格模式；从宽到严迁移时先确认所有调用方和旁路流量

**AuthorizationPolicy** ---- 以来源身份、目标、方法、路径、端口、命名空间和 JWT claims 形成显式放行；默认拒绝前先有观测、例外清单和回滚

**用户与服务身份** ---- 入口可以验证用户令牌，网格验证服务身份，业务仍需执行对象级授权；不要把用户 claims 无条件当成服务权限

**外部 PKI 与密钥** ---- 对接企业 CA、Vault、cert-manager 或云密钥服务时，明确签发、轮换、吊销、备份和故障模式；密钥服务挂起不能让所有服务同时失明

**策略绕过** ---- 检查 hostNetwork、特殊端口、未注入 Pod、出口直连、调试容器和管理员旁路；安全策略的例外要有负责人和过期时间

## 第八站：网格可观测性与排障

第八站让代理打开黑匣子。它能自动看到服务间请求，却看不懂“订单已扣款但页面没刷新”这种业务语义；网络视角与应用视角要拼接，不能互相冒充。

**代理指标** ---- 观察请求速率、状态码、延迟分布、连接、重试、熔断、TLS、配置推送与资源；按源、目标、服务、版本和响应方向聚合

**访问日志** ---- 记录来源、目标、路径、状态、耗时、响应大小、重试、trace ID 和策略结果，并做采样、脱敏与保留；全量高频访问日志可能先把预算打穿

**分布式追踪** ---- 透传 trace context，关联入口、代理、应用、队列和数据库；代理自动生成跨度不等于应用具备完整业务跨度

**拓扑与依赖** ---- Kiali、Grafana、服务目录或类似工具展示调用边、流量和错误；拓扑是导航，不是根因，仍需检查实际配置与应用日志

**配置排障** ---- 先看对象是否匹配，再看代理实际下发的 CDS/EDS/LDS/RDS/SDS，最后确认监听、路由与策略；不要只看 Git 里的配置文件

**流量不通排障** ---- 依次查注入、端口、DNS、Service/Endpoint、NetworkPolicy、代理监听、路由、mTLS、授权和应用；每层都要有正向证据

**延迟与重试排障** ---- 将总延迟拆成客户端、代理、排队、连接、TLS、应用和下游，查看重试放大、连接池等待与资源节流；P99 往往比平均值诚实

## 第九站：多集群、外部服务与调度边界

第九站开始办理跨城交通。网格能治理跨集群和外部服务的通信，却不负责决定 Pod 应该落在哪台机器；调度仍是 Kubernetes 或云平台的工作，网格不要越俎代庖。

**多集群服务发现** ---- 选择扁平网络、服务导出、入口转发或应用层联邦时，评估身份、DNS、延迟、故障域和运维；跨集群发现失效要有局部降级

**区域与故障转移** ---- 按地域优先、权重或健康状态路由，处理数据驻留、跨区费用、回切和连接缓存；把流量切走不等于数据已经同步

**外部服务接入** ---- 通过 ServiceEntry、出口代理或专用网关管理第三方 API、遗留系统和数据库；证书、域名、审计、限流和供应商故障要单独建模

**工作负载调度** ---- Pod 的资源、节点、污点、拓扑与扩缩由 Kubernetes 调度控制，网格只影响流量路径和代理资源；两套策略冲突时要明确优先级

**多租户与边界** ---- 隔离命名空间、身份、入口、出口、路由和策略，限制跨租户可见性；共享控制面要评估故障半径与配置误发

**网格外流量** ---- 非网格服务、批处理、节点代理和管理流量可能绕过代理；列出旁路清单并监控其身份、加密和出口

## 第十站：资源、成本、可靠性与演进

最后一站是网格的年度体检。每多一个代理、规则、指标和跳转，就多一份 CPU、内存、延迟、学习与排障成本；网格越强大，越需要用证据决定开哪一盏灯。

**资源预算** ---- 计算 Sidecar/共享代理、控制面、入口出口网关、指标、日志和追踪的资源；为代理和网关设置 requests/limits 与扩缩上限

**性能预算** ---- 测量代理跳数、TLS、路由、重试、连接池、采样和协议转换的 CPU 与尾延迟；统一治理若显著拖慢关键链路，应调整范围或方案

**成本来源** ---- 成本包含节点资源、跨区流量、负载均衡、日志、追踪、存储、证书服务、控制面运维与团队培训；把成本分摊到服务和租户

**故障半径** ---- 控制面错误配置、证书问题、注入 Webhook、网关故障和代理升级都可能影响大量服务；分批升级、版本兼容、最后配置和紧急旁路不可缺

**高可用与升级** ---- 控制面多副本、网关分布、代理滚动升级、证书轮换和配置回滚要演练；升级前检查 Kubernetes、CNI、Ingress、CRD 和应用协议兼容性

**什么时候不要上** ---- 服务少、单语言、有成熟应用治理、没有复杂流量和零信任需求，或团队无能力维护代理与控制面时，应用库或网关可能更合适

**选型与演进** ---- Istio 功能丰富，Linkerd 更聚焦轻量，也可评估 Consul、Kuma、云托管网格或 ambient 模式；以协议、资源、策略、生态、迁移和团队能力做小规模验证

**退出与降级** ---- 保留应用直连、证书、路由、策略和观测的替代路径；能关闭注入、回退明文或绕过单项策略不等于忽视安全，而是为故障恢复准备受控逃生门

## 通关标准

能解释服务网格的东西向边界、数据面、控制面、Sidecar、Ambient、xDS 和代理资源；能描述服务发现、连接池、协议、DNS、入口出口与跨集群路径；能设计版本子集、权重灰度、镜像、蓝绿、超时、重试、熔断、限流和故障注入，并说明业务幂等边界；能用 mTLS、工作负载身份、默认拒绝授权和审计构建零信任策略；能用代理指标、访问日志、追踪、拓扑和实际配置定位故障；能按服务规模、语言栈、流量复杂度、资源、成本和团队能力决定是否采用以及如何渐进演进。

## 下一站去哪

回到 Kubernetes 巩固调度、资源、网络和发布，再把服务网格接入监控与 CI/CD；如果工作负载以事件、短任务和不规则流量为主，去比较 Serverless，而不是强行让网格治理一切。

## 结语

服务网格把许多治理能力变成平台策略，却也把复杂度搬到了代理、控制面、证书、配置和排障路径里。成熟的做法不是全量开启，而是从真正的痛点出发，小范围验证、持续观测、逐步扩大，并始终保留清楚的回滚和退出路线。
