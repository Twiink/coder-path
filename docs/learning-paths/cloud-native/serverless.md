# Serverless 学习路线

**Serverless(无服务器)不是"没有服务器",而是"你不用管服务器"**:云厂商负责容量、补丁、扩缩,你只写代码(或只配置服务),**按实际使用付费**——零流量零成本、有流量自动扩展。它是继 IaaS(虚拟机)→ PaaS(托管平台)→ **FaaS/BaaS** 之后的抽象最高层。**一句话画像**:它是"事件驱动 + 免运维 + 按量付费"的武器,**不是银弹**——长任务、强状态、可预测高负载、极致性能场景有更好的选择(容器/K8s)。本页以 AWS 生态为主线讲通用概念,并标注国内对应(阿里云函数计算/腾讯云 SCF)与开源方案。

这条线按 **核心概念与计费 → 平台与函数运行时 → 冷启动 → 触发与集成 → 架构模式 → 数据与状态 → 性能与成本 → 可观测与安全 → 定位选型** 推进。

## 第一站:核心概念——FaaS、BaaS 与计费模型

**Serverless = FaaS + BaaS + 托管服务**:①**FaaS(函数即服务)**:以"函数"为单位的计算——**执行模型:触发器 → 冷启动环境 → 执行 → 返回 → 销毁**;函数**无状态**(每次调用独立,不保证上下文);生命周期秒级到分钟级;主流:AWS Lambda(标杆)/Azure Functions/Google Cloud Functions/**阿里云函数计算、腾讯云 SCF**(国内常用)。
②**BaaS(后端即服务)**:数据库、对象存储、认证、推送、API 开箱即用——Firebase/Supabase/Auth0/云厂商托管服务;**"前端直连 BaaS、后端只写业务函数"是小团队极速开发的配方**。③**事件驱动(灵魂)**:函数被**事件**触发而非常驻——事件源:HTTP 请求、文件上传(S3/OSS)、消息队列(SQS/Kafka)、数据库变更(Streams)、定时器(cron)、事件总线(EventBridge/EventGrid);**异步解耦 + 削峰填谷**是 Serverless 架构的核心价值——"上传一张图,自动触发缩略图+鉴黄+入库"这类管道零服务器实现。
**计费模型(先看懂再上车)**:①**调用次数**(每百万次计费);②**执行时长(GB-秒 = 内存 × 运行秒数)**;③流量与日志另计——**免费额度大方(每月百万次调用级),但要警惕三巨头:高频调用、长耗时函数、海量日志**;优势:无流量零成本(对比常驻服务器吃空饷);**陷阱**:不规则但量大的流量也可能比包月贵——**上线前用成本计算器估算**。

## 第二站:平台与函数运行时

**函数长什么样**(各平台同构):一段处理函数(接收事件对象、返回响应)+ 配置:**内存(决定 CPU:多数平台内存与 CPU 成正比——128MB 到数 GB)**、**超时(上限:Lambda 15 分钟/Azure 无上限计划——**超过上限的任务别硬塞函数,拆异步或换容器**)**、环境变量(配置外置)、运行时(Node/Python/Java/Go/.NET/Rust + 自定义)。
**平台选型**:AWS Lambda(生态最全,触发器最多,学习首选)、Azure Functions(Durable Functions 编排是特色)、**阿里云函数计算(国内生态:HTTP 触发器、定时、OSS/MNS 集成、支持自定义容器镜像)**;**开源/自托管 FaaS**:Knative(K8s 之上的 Serverless 平台——"K8s 集群里跑 Serverless 工作负载"的主流开源答案)、OpenFaaS(轻量)。
**容器化 Serverless(重要中间态)**:Cloud Run(AWS Fargate/阿里云 SAE 类似)——**把容器交上去,平台按请求扩缩到零**:比函数灵活(任意语言/框架/长任务),又免管服务器——**"函数不够用、K8s 太重"时的甜点位**。**函数执行环境细节(影响正确性)**:同一实例可能被**复用**(全局变量在复用期间存活——**不能假设全新,也不能假设持久:状态必须外置**);`/tmp` 是临时盘(复用期间在,不保证);**幂等性是第一原则**:平台可能重试(尤其异步触发)——**函数必须能安全执行多次**(用幂等键/数据库唯一约束)。

## 第三站:冷启动——Serverless 的头号敌人

**冷启动**:首次调用或实例回收后,平台要**拉起运行时再执行**——延迟几十毫秒到几秒(语言越重越慢:Java/C# 慢,Node/Python 中,Go/Rust 快)。**影响因素**:运行时与依赖大小、是否在 VPC(进 VPC 要建弹性网卡——**冷启动显著变慢,非必要不进**)、代码包大小、内存配置。**缓解手段(按性价比)**:①**预留并发(Provisioned Concurrency/阿里云预留实例)**:预先热好 N 个实例——**冷启动归零,但常驻计费(等于为确定性付费),只给关键路径用**;②**最小化依赖与代码体积**(大树摇、按需导入——冷启动与包大小强相关);③选轻运行时(Go/Rust/Node);④合理内存(内存大启动略快);⑤**架构规避**:把"要快"的路径(用户同步请求)与"可慢"的路径(异步处理)分开——**同步 API 用预留+轻依赖,异步任务不在乎冷启动**。**度量**:X-Ray/日志里看 Init 阶段耗时——**别猜,测了再优化**。

## 第四站:触发器与集成——Lambda 的一半价值

**触发器生态(AWS 为例,各云同构)**:**API Gateway**(HTTP/REST/WebSocket→函数:Serverless API 的入口,自带限流/缓存/鉴权)、**S3 事件**(对象上传/删除→函数:图片处理/文档转换/日志摄取)、**SQS**(队列消息→函数:可靠异步,**配合 DLQ 死信**)、**SNS**(发布订阅广播)、**DynamoDB Streams**(表变更→函数:同步派生数据)、**EventBridge**(**定时任务 cron + 跨服务事件路由**:报表/清理/编排的触发器)。**国内对应**:函数计算的 HTTP 触发器/OSS 触发器/定时触发器/消息队列触发器。**设计要点**:①触发器即"事件契约"——**函数签名随事件源定**(读事件里的字段,别自定义 HTTP 协议硬套);②**异步触发自动重试**(SQS/EventBridge 语义不同——搞清重试与乱序语义,幂等兜底);③一个函数一个触发器语义(别让一个函数同时被 HTTP 和队列以不同语义调用——**除非你清楚自己在干嘛**)。

## 第五站:架构模式——Serverless 的套路

**七种经典配方(背下来,遇到需求直接套)**:①**API 后端**:API Gateway + 函数 + 托管数据库——**中小 API/不规则流量/快速迭代**(对比常驻后端:免运维但冷启动与供应商绑定要认);②**事件驱动处理管道**:S3 上传 → 函数(缩略图/转码/解析)→ 结果入库——**批处理与媒体处理的零服务器实现**;③**定时任务**:EventBridge cron → 函数(报表生成/数据清理/爬虫调度——**比服务器 cron 省一台机器**);④**静态站 + API(JAMstack)**:S3/OSS 托管前端 + CDN + API——博客/营销页/SPA;⑤**实时应用**:API Gateway WebSocket + 函数(聊天/推送——**注意连接管理与横向扩展的边界**);⑥**流处理**:Kinesis/Kafka → 函数(实时聚合——**量与复杂度上来后,流处理引擎更合适**);⑦**微服务化**:每个服务 = 一组函数(独立部署扩展——**函数粒度微服务的"过度拆分"是反模式:函数间调用走网络,拆太细延迟与成本双升;一个服务一个函数包更常见**)。
**有状态工作流(函数无状态,编排有状态)**:**AWS Step Functions / Azure Durable Functions(状态机:步骤编排/人工审批/重试补偿/长流程(订单、ETL、审批))**——**"函数 + 状态机"是 Serverless 处理复杂流程的标准姿势**(长于单函数超时的任务也用它拆步)。

## 第六站:数据与状态——Serverless 的数据库选择

**无状态设计铁律**:函数不存状态——状态放:**托管数据库**(Serverless 友好型:**DynamoDB/Azure Cosmos DB(自动扩缩、按量付费)与 Aurora Serverless(关系型按需)**——**别在 Serverless 里用"常驻连接池"思维:函数并发高时连接数爆炸,关系库要配 RDS Proxy/Serverless 版**)、缓存(ElastiCache/Redis——函数内全局变量"缓存"只在实例复用期有效,别当真缓存)、对象存储(S3/OSS——**大文件上传用预签名 URL 直传,别经函数中转**)。**会话**:无状态 API 用 JWT(见 [认证](/learning-paths/security/auth));下载/导出:生成预签名 URL 让客户端直连存储——**函数只做"签发"不做"搬运"**。

## 第七站:性能、成本与可观测

**性能调优清单**:内存基准测试(加内存=加 CPU:IO/计算型任务找到性价比拐点——**Lambda 每档内存的定价与性能要实测**);并发控制(账户并发限制与预留分配——关键函数预留,防被突发流量挤掉);异步化与批处理(合并消息减少调用次数——**次数也是钱**);超时设置别浪费(函数该 3 秒完成别配 15 分钟——**长超时 = 计费炸弹+难排查**)。
**成本四巨头(账单审计就查这四个)**:调用次数、执行时长(GB-秒)、日志(CloudWatch/阿里云 SLS **日志费用常被忽略且涨得快——设保留期/只留 error**)、数据传输——配预算告警(Cost Explorer/预算),**上线前用定价页估算**。**可观测(Serverless 排障三板斧,对应 [监控](/learning-paths/devops/monitoring) 的 RED)**:①日志:stdout 自动收集(CloudWatch Logs/云日志服务——**打结构化 JSON 日志**(含 requestId)才能查);②指标:Invocations/Errors/Throttles/**Duration(看 P50/P99——冷启动与慢代码现形)**/并发;③**追踪:X-Ray/链路追踪(跨函数与下游——Serverless 分布式排障的命脉)**。
**本地开发与测试**:SAM CLI/serverless framework offline(本地模拟)、LocalStack(本地 AWS 模拟)、单元测试(模拟事件注入——**函数逻辑与平台解耦后可测**)。**错误处理**:异步源(SQS/EventBridge)自动重试 + **DLQ 死信队列收尸(重试耗尽进 DLQ,人工/补偿处理)**;同步(API)错误由客户端重试——**幂等 + DLQ + 告警三件套**。

## 第八站:安全与锁定

**安全清单**:①**IAM 最小权限(Serverless 安全第一课)**:每个函数独立执行角色、只给需要的资源权限——**函数权限过大 = 被攻破后的横向移动**;②密钥:环境变量加密(KMS)、Secrets Manager——别硬编码;③API 鉴权:API Gateway 的 Lambda Authorizer/JWT/Cognito(见 [认证](/learning-paths/security/auth));④VPC:访问内网数据库才进(权衡冷启动);⑤依赖漏洞扫描(CI 里做——见 [GitHub Actions](/learning-paths/devops/github-actions));⑥事件源防滥用(S3 公开桶 + 函数 = 账单炸弹——**触发器与权限要锁**)。**厂商锁定(选型要认的账)**:函数代码大体可移植,但**触发器/托管服务/工具链深度绑定**——架构上把"业务逻辑(纯函数,可测可移植)"与"平台胶水(事件适配/服务调用)"分层;**多云策略**:核心逻辑容器化(可跑 Cloud Run/K8s),边缘才用各家 FaaS。

## 第九站:定位、选型与学习路径

**Serverless vs 容器/K8s(决策树,面试常问)**:选 Serverless——事件驱动型工作负载(上传/消息/定时)、**流量不规则或间歇**(零流量零成本)、小团队快速交付、不想管服务器;选容器/K8s——长连接/WebSocket 大规模、有状态复杂服务、GPU/高性能计算、可预测高负载(包月更划算)、强合规与多云自由(见 [K8s](/learning-paths/devops/kubernetes) 与 [云原生](/learning-paths/cloud-native/cloud-native-patterns));**中间答案:容器化 Serverless(Cloud Run/Fargate)** 兼得灵活与免运维。
**Serverless 是云计算的未来吗**:不是全部,但"事件驱动 + 按量付费"已是现代应用的重要形态——**会用它的人把它用在刀刃上**(削峰、管道、原型),不用它硬扛一切。**学习路径**:选一个平台(AWS 免费额度或阿里云)跑通三个配方:HTTP API(网关+函数+DB)、上传触发处理(对象存储+函数)、定时任务(EventBridge+函数)——再补状态机与成本监控;**进阶**:Terraform 管 Serverless 资源(IaC——见 [云原生](/learning-paths/cloud-native/cloud-native-patterns) 章)、Knative 自托管、Edge Functions(CDN 边缘计算新热点)。

## 通关标准

能独立做到:说清 FaaS/BaaS/容器化 Serverless 的边界与计费模型(含三个成本陷阱);在任一平台部署"API Gateway + 函数 + 托管 DB"的完整 API 并讲清冷启动的成因与三种缓解;用对象存储触发实现一条"上传即处理"管道并配好 DLQ 与幂等;用状态机编排一个多步流程(含人工审批);写出 Serverless 安全清单(最小权限/密钥/鉴权)并解释"为什么函数权限要最小";给出"这个需求该不该用 Serverless"的有依据判断——Serverless 主线通关。

Serverless 教你的不是某个平台的 API,而是**"事件驱动 + 按价值付费"的架构视角**:能异步就异步、能按量就别常驻、状态该外置就外置——这套思维与容器/K8s 互补,共同构成云原生应用的选择面。别被"免运维"忽悠得放弃架构思考:冷启动、幂等、成本、锁定,每个都是要还的账。**先把一个真实小功能(上传缩略图/定时报表)用 Serverless 跑进生产**,你会比读十篇"Serverless 指南"更懂它的甜与苦。下一步:[云原生模式](/learning-paths/cloud-native/cloud-native-patterns) 把 Serverless 放进架构全景,或回 [K8s](/learning-paths/devops/kubernetes) 学容器派的对策。
