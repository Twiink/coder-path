# Serverless 学习路线

Serverless 是云平台那位按次收费、下班很快的临时工：没有请求时可以休息，有事件时迅速开工，做完就把工位交还给平台。它减少了服务器管理，却没有消灭架构问题；冷启动、并发、幂等、状态、权限、网络和账单仍然会准时上门。

这条路线以 FaaS、BaaS 和容器化 Serverless 为入口，逐步覆盖函数运行时、资源与冷启动、事件与网络、状态、工作流、可靠性、安全、可观测性、发布、成本、供应商锁定和选型。重点是理解“按价值付费”的边界，而不是背某一家云的按钮位置。

**推荐顺序** ---- FaaS/BaaS 与计费 → 函数运行时 → 冷启动与资源 → 事件、网络与触发器 → 状态与数据 → 工作流与可靠性 → 安全与身份 → 可观测性 → 发布与版本 → 成本、锁定与选型

## 第一站：FaaS、BaaS 与按量模型

第一站先把“没有服务器”这句宣传语请到事实核查室。服务器没有消失，只是由平台替你管理；你仍需为执行时间、内存、请求、并发、日志、网络和托管服务付费。

**FaaS** ---- 函数即服务按事件或请求运行短任务，平台负责调度、扩缩、补丁和实例回收；函数边界应围绕清晰职责和可测试逻辑划分

**BaaS** ---- 托管数据库、对象存储、队列、认证、API 网关和事件总线提供后端能力；BaaS 减少运维，但 API、数据模型、权限与价格会形成新的依赖

**容器化 Serverless** ---- Cloud Run、Fargate、Knative 等以容器为交付单位，提供部分按量、自动扩缩或托管运行；适合需要自定义运行时、长一点处理时间或更强可移植性的场景

**计费维度** ---- 关注调用次数、执行时长、内存或 vCPU、并发、网关、日志、存储、队列、数据库、数据传输和公网出口；“函数便宜”不代表整条链路便宜

**同步与异步** ---- 同步请求适合短、可直接返回的交互，异步事件适合削峰、批处理和长流程；同步超时与异步重试的错误语义完全不同

**适用工作负载** ---- 事件驱动、流量间歇、突发明显、团队小且希望快速交付的任务通常更合适；持续高负载、长连接、GPU、复杂状态和严格低延迟场景要谨慎

## 第二站：函数生命周期与运行时

第二站拜访函数的“短暂人生”。它可能被创建、初始化、复用、并发执行、冻结或回收；全局变量偶尔能留住记忆，却没有资格冒充可靠数据库。

**初始化阶段** ---- 运行时加载语言、依赖、扩展、配置和连接，形成冷启动成本；初始化失败、超时和版本不兼容应有明确日志与告警

**调用阶段** ---- 函数处理事件并返回结果，运行时可能复用同一个执行环境；代码必须假设下一次调用会落到全新实例，不能依赖调用顺序或本地状态

**并发模型** ---- 理解每实例串行或并发、平台并发上限、保留并发、预置实例与队列批量；并发增加会同时放大连接数、下游压力和账单

**执行上限** ---- 了解超时、请求体大小、响应大小、临时磁盘、文件描述符、线程、进程和环境变量限制；长任务应拆分、排队或交给工作流与容器任务

**临时文件与内存** ---- 运行时本地文件通常只在实例寿命内有效，内存缓存也可能随回收消失；大文件应通过对象存储直传或分段处理

**运行时版本** ---- 固定语言、基础镜像、扩展、操作系统库和架构，关注平台弃用与升级窗口；供应商更新运行时可能改变冷启动、证书和依赖行为

**连接管理** ---- 不要按传统常驻服务创建无限连接池，使用连接复用、代理、连接上限、超时和释放；关系库连接爆炸是 Serverless 常见的第一张账单

## 第三站：冷启动、资源与性能

第三站是冷启动的心理咨询室。函数刚醒时还要穿衣、找钥匙、加载依赖，用户却已经在门口敲了半天；优化前先测量初始化、业务、网络和下游各占多少时间。

**冷启动来源** ---- 运行时启动、依赖加载、代码解压、扩展初始化、VPC 网络准备和首次连接都会增加延迟；不同语言、包体、区域和平台的表现不同

**热实例复用** ---- 平台可能复用执行环境，但不保证复用时间、顺序或数量；可缓存只放非关键、可重建数据，不能依赖全局变量保存业务状态

**预置与保温** ---- Provisioned Concurrency、最小实例、定时预热和轻量入口可降低冷启动，但会产生持续资源费用；用 P95/P99 和真实流量计算是否值得

**内存与 CPU** ---- 很多平台内存档位同时影响 CPU、网络或临时存储；提高内存可能缩短执行时间并降低总费用，也可能只是买来浪费，必须基准测试

**包体与依赖** ---- 删除无用依赖、拆分函数、延迟加载、减少扩展和选择合适运行时；不要为了冷启动把所有业务强行拆成几十个网络调用

**并发与下游容量** ---- 设置最大并发、批量大小、队列深度和数据库连接上限；函数扩得越快，下游越可能先倒下

**性能预算** ---- 为网关、函数初始化、业务、外部 API、数据库和序列化分配总延迟预算；逐段测量，不用“函数本身很快”掩盖网络时间

## 第四站：事件、网络与触发器

第四站是事件邮局。HTTP、对象存储、队列、定时器、数据库流和事件总线寄来的信件格式各不相同；函数要验证事件契约，也要接受信件可能重复、延迟或乱序。

**HTTP 与 API Gateway** ---- 网关负责路由、TLS、鉴权、限流、缓存、请求大小和超时，函数负责业务；入口超时应大于函数处理预算但小于用户可接受范围

**对象存储事件** ---- 上传、删除或完成分段上传可触发处理；事件通常只携带对象标识，函数应处理版本、重复通知、权限和大文件直传

**队列与死信** ---- 队列吸收峰值并提供重试，DLQ 保存无法处理的消息；可见性超时、批量部分失败、重试次数和死信回放必须设计

**发布订阅与事件总线** ---- SNS、EventBridge、Kafka 等可以广播、过滤和路由事件；事件 schema、版本、来源、顺序和消费者幂等是长期契约

**定时调度** ---- cron 或平台调度器适合报表、清理和巡检；调度可能延迟、重复或并发触发，任务应加租约、幂等键和执行窗口

**网络与 VPC** ---- 访问内网数据库或私有 API 时才引入 VPC、子网、路由、安全组和 NAT；网络接入可能增加冷启动、地址耗尽、跨区流量和排障复杂度

**出站与入站安全** ---- 用私有端点、出站白名单、TLS、DNS、代理和网关控制网络；函数能访问公网不应被当成默认权限

**事件契约验证** ---- 校验 schema、来源、时间、大小和权限，未知字段要兼容或拒绝；事件格式变化应通过版本和消费者测试传播

## 第五站：状态、数据与长流程

第五站请函数的记忆管理师出场。函数本身记性短，业务流程却可能跨小时甚至跨天；把状态外置，把大文件放对象存储，把长流程交给有状态编排，系统才不会靠运气接着上次梦境。

**无状态函数** ---- 每次调用都可在任一实例独立完成，状态写入数据库、缓存、对象存储、队列或状态机；本地内存只做可丢失优化

**关系数据库** ---- 使用连接代理、短事务、幂等键和容量保护，关注并发连接、锁、事务时长与扩缩边界；Serverless 不会消除关系库的容量上限

**键值与文档数据库** ---- DynamoDB、Cosmos DB 等适合按访问模式建模、自动扩缩和高并发；先写清分区键、热点、强弱一致与查询边界，再决定是否使用

**缓存与会话** ---- Redis 等外部缓存保存可重建数据与短会话，设置 TTL、容量、淘汰和故障回退；JWT 或外部会话服务适合无状态入口，但仍要处理撤销

**对象存储与预签名 URL** ---- 大文件由客户端直传或直取对象存储，函数只负责签发、校验和编排；避免函数成为昂贵的文件搬运工

**幂等与去重** ---- 用事件 ID、业务键、唯一约束、状态机和去重记录应对重试与重复交付；处理“超时但实际已成功”是关键场景

**工作流与状态机** ---- Step Functions、Durable Functions、Temporal 或其他编排器负责步骤、等待、重试、补偿、人工审批和长时状态；编排器本身也要监控和定价

## 第六站：可靠性与错误语义

第六站是函数的急救课。平台重试很勤快，却不知道你的操作是否可重复；没有幂等和死信的重试，就像让一只兴奋的小狗不断按同一个门铃。

**同步失败** ---- 为客户端返回可理解的错误、请求 ID 和重试建议；同步调用不应把内部堆栈、秘密和不确定状态直接暴露给用户

**异步重试** ---- 了解平台、队列和事件总线的重试次数、退避、最大事件年龄、批量失败与顺序语义；不能假设所有触发器使用同一套重试规则

**幂等处理** ---- 先检查处理记录或业务状态，再执行副作用；对支付、发货、发邮件和写入外部系统尤其要使用幂等键与状态机

**超时与取消** ---- 函数超时前主动停止新工作、释放资源并记录未完成阶段；上游取消、下游超时和平台终止都可能留下未知结果

**DLQ 与人工恢复** ---- 死信要有负责人、告警、查看、修复、重放和过期策略；重放前确认数据与代码版本兼容，避免把坏消息重新撒回生产

**限流与熔断** ---- 在网关、函数并发、队列和下游客户端设置限制；第三方服务故障时快速失败或降级，保护函数预算和关键链路

**故障演练** ---- 模拟冷启动、依赖超时、重复事件、区域故障、权限失效、DLQ 堆积和成本异常；验证恢复速度与数据完整性，不只验证函数是否能返回 200

## 第七站：安全、身份与供应链

第七站由云平台保安值守。函数代码短小，不代表权限可以豪放；一份过大的执行角色就像给临时工发整栋大楼的万能钥匙。

**执行身份** ---- 每个函数使用独立角色，按资源、动作、环境和数据范围最小授权；读取数据库、写对象、发消息和管理部署要分开

**调用身份** ---- 区分用户 JWT、服务身份、事件源身份和平台管理身份；入口认证通过不等于函数已经完成业务授权

**秘密与密钥** ---- 使用 Secrets Manager、KMS、短期令牌和轮换，避免秘密进入代码、环境输出、事件、日志和制品；函数访问秘密也应有审计

**网络安全** ---- 私有子网、安全组、出站白名单、TLS、私有服务端点和 WAF 只按需使用；VPC 并非自动安全，错误路由和过大出站权限同样危险

**输入与事件安全** ---- 校验大小、schema、来源、租户和权限，防止注入、资源耗尽、递归触发和恶意对象；对象存储触发器要防止上传函数自己再触发自己

**依赖与制品** ---- 锁定依赖、扫描漏洞、生成 SBOM、签名函数包或镜像并在部署前验证；运行时升级和第三方扩展也属于供应链

**数据保护与审计** ---- 加密敏感数据，限制日志、追踪和错误响应中的个人信息；保留调用、权限、配置与部署审计，满足最小可见性

## 第八站：可观测性与调试

第八站给短命函数装上记事本。实例会消失，日志和追踪不能跟着一起蒸发；结构化记录 request ID、冷启动、版本、事件来源和下游耗时，排障才不用靠猜。

**函数指标** ---- 观察调用量、错误、拒绝、节流、并发、执行时长、初始化时长、内存、超时和重试；按函数、版本、区域和触发器分组

**事件指标** ---- 关注队列年龄、积压、DLQ、批量部分失败、事件处理延迟和最老事件；“函数成功”不等于消息已经按时完成业务

**结构化日志** ---- 输出版本、请求 ID、trace ID、租户、阶段、错误类别和安全脱敏字段；禁止把完整事件、令牌和用户敏感数据原样打印

**分布式追踪** ---- 透传上下文，从网关到函数、队列、数据库和外部 API 关联跨度；异步链路要记录事件 ID 与父子关系

**冷启动分析** ---- 单独记录 Init 与业务处理，比较不同运行时、包体、内存、VPC 和预置策略；没有测量就不要宣称某种优化有效

**本地与契约测试** ---- 对函数逻辑、事件 schema、权限、超时、重试和基础设施配置测试；本地模拟不能替代云上限额、网络与真实权限验证

**告警与值班** ---- 对用户影响、错误预算、DLQ、节流、持续积压、异常成本和权限失败告警；告警要带函数、版本、事件源、日志和恢复入口

## 第九站：发布、版本与渐进交付

第九站是函数发布台。函数小而多，发布频率可能像下雨；没有版本、别名、流量切分和自动回滚，雨伞很快就会漏水。

**版本与别名** ---- 固定函数包或镜像版本，用别名、环境或部署清单指向实际版本；生产不能引用漂移的 latest

**基础设施即代码** ---- 用 Terraform、SAM、Serverless Framework、CDK 或同类工具管理函数、触发器、角色、队列、告警和权限；代码与平台胶水要可审查

**构建与制品** ---- 构建一次、测试、扫描、签名并推广同一制品，记录源码、依赖、运行时和配置；部署失败时保留日志与上一个版本

**蓝绿与金丝雀** ---- 用别名权重、网关路由、版本分流或阶段环境逐步放量；按错误率、延迟、业务结果、冷启动和成本自动暂停或回滚

**事件兼容发布** ---- 消费者先兼容新旧事件 schema，再切换生产者；消息重放和延迟到达会让旧版本在新版本之后继续工作

**迁移与回滚** ---- 代码、权限、配置、数据库和事件契约要分别规划回滚；函数版本能回退，不代表已经写入的数据和外部副作用能回退

## 第十站：成本、供应商锁定与选型

最后一站是 Serverless 的财务与职业规划课。平台说“只按使用付费”，账单却会把调用次数、日志、NAT、跨区流量、空闲预置实例和下游服务一项项请来开会。

**成本模型** ---- 计算调用、执行、内存、预置并发、网关、日志、队列、数据库、对象存储、NAT、跨区和公网出口的总成本；按业务请求或事件处理量归一化

**成本护栏** ---- 设置预算、配额、并发上限、日志保留、采样、对象生命周期和异常调用告警；防止递归触发、恶意公开端点和重试风暴制造账单爆炸

**供应商锁定** ---- 业务逻辑可较易移植，事件格式、权限、工作流、数据库模型和观测 API 往往深度绑定；将核心逻辑与平台适配层分离，保留数据导出和迁移方案

**可移植运行时** ---- 容器化函数、Knative、Cloud Run 或多云抽象可以增加选择，但也增加平台与运维成本；不要为了想象中的多云预先支付全部复杂度

**Serverless 与容器/Kubernetes** ---- 按事件、间歇流量、短任务和小团队偏向 Serverless；长连接、稳定高负载、GPU、复杂网络、强控制和可预测包月成本偏向容器或 Kubernetes

**选型实验** ---- 用一个真实小功能验证冷启动、并发、失败重试、恢复、观测、权限、账单和迁移；实验结果比“Serverless 永远便宜”或“函数一定不可靠”更值得相信

**退出策略** ---- 保留源码、构建文件、事件样例、数据导出、权限清单和基础设施代码；知道如何迁出，才不会把平台便利变成长期人质协议

## 通关标准

能解释 FaaS、BaaS、容器化 Serverless 与常驻服务的边界和计费维度；能设计函数生命周期、冷启动、并发、资源、连接和网络策略；能用对象存储、队列、定时器和事件总线构建可靠事件链，并处理幂等、重试、DLQ、乱序和长流程；能配置最小身份、秘密、供应链和审计；能用指标、日志、追踪和业务信号定位故障；能完成版本化、金丝雀、回滚和成本护栏；能为一个真实需求说明选择 Serverless 或容器平台的理由。

## 下一站去哪

去云原生模式补齐生命周期、弹性、SLO、安全与成本的通用心法；去 Kubernetes 理解长驻服务和复杂调度；当服务间流量治理变复杂时，再比较服务网格是否值得加入。

## 结语

Serverless 不是“没有运维”，而是把运维从机器搬到了事件、权限、并发、数据和账单上。把函数做小、状态放对、重试做安全、观测做完整、成本算明白，它会是很锋利的工具；把所有事情都塞进函数，它也会很快变成一把锋利的回旋镖。
