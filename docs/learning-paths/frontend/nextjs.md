# Next.js 学习路线

Next.js 是 React 走向应用与全栈的路线：路由、布局、服务端渲染、静态生成、服务端组件、数据缓存、接口处理和部署，都被放进同一套应用模型。它的难点不是“多几个文件夹”，而是同一份代码可能在浏览器、服务器、构建阶段和边缘运行时轮流上班。

这条路线是**索引和指引**。它以 App Router 为主线，同时保留理解旧项目 Pages Router 所需的概念。每一站只列学习范围和关键取舍，具体 API 与代码示例交给学习笔记，避免路线图变成配置文件展览。

## 第一站：渲染模式与 Next.js 心智模型

欢迎来到 Next.js 的多世界副本：同一段逻辑可能在构建机、服务器、边缘节点或浏览器上轮班。这里的第一条村规是先问“它在哪跑”，否则缓存、密钥和 window 会一起给你上课。

**客户端渲染** ---- 了解浏览器获取 JavaScript 后生成页面的方式，关注首屏、交互和 SEO；CSR 不是坏人，只是要知道它把工作推迟给了用户设备

**服务端渲染** ---- 理解请求时生成 HTML、服务端数据和客户端接管；首屏更快不代表服务器压力自动消失

**静态生成** ---- 认识构建时生成页面、内容更新和重新构建的关系；适合稳定内容，也要考虑数据新鲜度

**增量生成与重新验证** ---- 关注静态页面如何按时间、标签或事件更新；缓存越智能，失效策略越需要被认真设计

**预渲染与混合应用** ---- 同一个应用可以让不同页面采用不同策略；关键不是追求“全 SSR”，而是让内容与成本匹配

**运行位置** ---- 区分浏览器、Node.js、边缘、构建阶段和服务端组件环境；window、数据库和密钥不能随便跨境

**数据、渲染与缓存** ---- 将数据来源、渲染位置、缓存范围和失效方式一起考虑；只看“页面能显示”会错过真正的架构

**重点在这** ---- Next.js 的第一课不是记目录，而是给每段代码贴上“在哪里跑、何时跑、能不能缓存”的标签

## 第二站：App Router 与文件系统路由

第二站进入 App Router 的文件城：目录是街道，layout 是常驻建筑，page 是店铺，loading 和 error 是消防通道。文件夹不是收纳盒，而是 URL、布局和错误边界的城市规划图。

**路由段与页面** ---- 认识页面、路由段、根布局和嵌套布局；理解文件层级如何成为用户看到的导航层级

**动态路由** ---- 覆盖动态参数、多个参数、可选参数和通配路由；参数是 URL 契约，需要考虑校验、缓存和 SEO

**路由组** ---- 用不可见分组组织不同布局和业务区域；分组解决目录组织，不会改变 URL

**平行路由** ---- 了解同一页面同时渲染多个独立区域的模型，适合工作台、弹窗和多面板应用；复杂能力也意味着复杂状态

**拦截路由** ---- 处理从列表打开详情、保留背景页面和可分享 URL；它把导航体验与真实 URL 同时照顾到

**特殊文件** ---- 学习加载、错误、未找到、全局错误、模板和默认内容等边界文件；异常和等待状态应在靠近发生处被处理

**布局持久化** ---- 理解布局跨导航保留、页面重新渲染和状态放置；导航栏状态不应因为换个子页面就失忆

**元数据与站点地图** ---- 规划标题、描述、规范链接、社交卡片、机器人规则和站点地图；SEO 不是发布前最后十分钟的贴纸

**Pages Router 兼容** ---- 能读懂旧项目中的页面、应用入口、数据获取和 API 路由；迁移时按边界逐步搬，不要一夜之间重写整个地基

**重点在这** ---- 路由同时承载 URL、布局、数据、错误和缓存；只把它当页面跳转工具，会低估 App Router 的一半能力

## 第三站：Server Components 与 Client Components

第三站来到 Server Components 边境：有的组件住服务器，有的组件必须带浏览器通行证才能交互。别把“加 use client”当万能护身符，先搞清谁负责数据、谁负责点击、谁负责付出 JavaScript 体积。

**服务端组件** ---- 认识默认服务端组件、服务器数据访问、零客户端 JavaScript 和组件组合；它们适合读取数据与生成 UI，不适合浏览器事件

**客户端组件** ---- 了解交互、状态、Effect、浏览器 API 和客户端依赖；客户端边界会扩大 JavaScript 负担，要放在真正需要的地方

**边界与组合** ---- 理解服务端组件如何向客户端组件传递可序列化数据，以及客户端组件如何承载服务端内容；边界是数据和代码的边界

**可序列化 Props** ---- 关注函数、类实例、复杂对象、日期和自定义类型如何跨边界；传不过去不是框架小气，而是运行位置不同

**第三方组件** ---- 评估依赖是否需要浏览器环境、如何包装客户端组件、如何控制包体；引入一个 UI 库可能顺手带来一整车客户端代码

**服务端专属能力** ---- 识别数据库访问、密钥、文件系统和内部服务调用的边界；不要让敏感信息沿着客户端 Props 散步

**客户端专属能力** ---- 处理窗口、存储、媒体、权限和交互；浏览器能力应在客户端边界内被明确使用

**水合** ---- 理解服务端 HTML 如何被客户端接管、为什么内容和结构必须一致，以及随机值和时间会如何制造不一致

**RSC 心智模型** ---- 组件不仅是可复用视图，也是运行位置和数据访问策略的单位；这是 Next.js 与传统 SPA 最大的转弯处

**重点在这** ---- 默认站在服务端，交互才跨到客户端；边界越小，传输越少，架构越清楚

## 第四站：数据获取、缓存与重新验证

第四站进入缓存超市：请求是进货，渲染是上架，缓存是冷藏，重新验证是定期盘点。少设计一个失效规则，页面就可能把过期数据端得理直气壮。

**服务端数据获取** ---- 认识页面级、布局级、服务端组件和路由处理器中的数据来源；让数据尽量在离它最近且安全的地方获取

**请求去重** ---- 理解相同请求、并行请求、父子组件和缓存之间的关系；去重能省工作，但前提是请求语义稳定

**数据缓存** ---- 区分请求缓存、数据缓存、页面缓存和 CDN 缓存；“缓存了”不是一句话，必须说明缓存谁、多久和如何失效

**时间重新验证** ---- 处理固定时间刷新、后台更新和用户看到旧数据的取舍；新鲜度是产品选择，不是框架默认答案

**标签与按需失效** ---- 用业务标签组织缓存失效；保存文章、修改库存和更新权限应该能精准影响相关页面

**动态渲染** ---- 关注 Cookie、Header、用户身份、不可缓存数据和动态函数如何改变渲染策略；动态不是错误，只是需要算成本

**并行与串行请求** ---- 识别无依赖请求的并行机会、依赖请求的顺序关系和瀑布问题；等待越多，首屏越像在排队取号

**加载与错误边界** ---- 为数据加载设计占位、局部回退、重试和错误分类；页面不应因为一块推荐内容失败就整页失业

**客户端缓存** ---- 对比 SWR、React Query 等客户端数据层与 Next.js 服务端缓存；两者解决的问题不同，不要互相冒充

**数据安全** ---- 严格区分公开数据、会话数据、内部数据和密钥；服务端获取数据不等于可以把结果全部送到浏览器

**重点在这** ---- 数据获取要同时回答来源、运行位置、缓存策略、失效方式和错误回退；少回答一个，生产就多一个谜题

## 第五站：Server Actions 与数据变更

第五站来到数据变更办事大厅：读取只是查档案，保存、删除、上传才是要盖章的业务。Server Actions 能把窗口开在服务器，但校验、授权、幂等和回滚仍然要人工值班。

**服务端动作** ---- 理解动作的运行位置、调用方式、序列化边界和错误返回；动作是服务端入口，不是绕过 API 设计的隐形通道

**表单渐进增强** ---- 关注无 JavaScript 时的基本能力、提交状态、失败反馈和重定向；网络慢时，可靠比炫酷重要

**输入校验** ---- 服务器必须重新校验字段、权限、资源归属和业务规则；客户端校验是体验，服务端校验才是门锁

**缓存失效** ---- 数据写入后精准更新相关路径和标签；写成功但页面仍显示旧内容，是缓存策略没有参加会议

**乐观更新** ---- 设计立即反馈、失败回滚、重复提交和冲突；乐观不是盲乐，要准备好悲观的退路

**并发与幂等** ---- 关注重复点击、重试、网络重放、竞态和唯一约束；保存操作不能只在“用户很乖时”正确

**文件与大数据提交** ---- 处理上传大小、类型、存储、进度、取消和服务端扫描；文件上传是安全、成本和体验的三科联考

**错误与状态** ---- 区分校验错误、权限错误、业务冲突、网络错误和未知异常；每类错误都要有用户可理解的结果

**Server Actions 与 API** ---- 判断何时适合动作、何时需要公开 API、Webhook 或独立服务；内部调用和外部契约不是同一件事

**重点在这** ---- 变更流程必须具备校验、授权、幂等、失效和回退；少一项，系统就可能在高峰期表演即兴喜剧

## 第六站：导航、加载与错误体验

第六站进入导航调度室：页面可以边走边加载，布局可以先留在原地，某块数据也可以单独报错。不要让全站一起转圈，好的导航会告诉用户哪班车到了、哪班车晚点、还能不能重试。

**客户端导航** ---- 理解链接、预取、软导航和浏览器历史；预取提升速度，也要关注数据新鲜度与带宽

**加载边界** ---- 通过局部 loading 设计骨架、占位和渐进显示；等待状态应接近用户等待的内容

**错误边界** ---- 设计路由级、布局级和全局错误回退；错误页应能解释、重试和提供离开路径

**未找到页面** ---- 处理资源不存在、权限隐藏和错误混淆；404 不是一句“没有了”，还能提供搜索和下一步

**导航后状态** ---- 关注表单反馈、滚动、焦点、筛选条件和返回恢复；用户记得自己刚才在哪里，应用也应该尽量记得

**预取与缓存** ---- 认识链接预取、路由缓存、数据缓存和失效；快是好事，预取错数据会让快变成旧

**流式渲染** ---- 理解分段 HTML、Suspense 边界、先到内容和后到内容；流式不是把完整页面打碎，而是按重要性交付

**并发导航** ---- 处理用户快速点击、重复导航和旧请求；页面更新顺序要以当前意图为准

**重点在这** ---- 加载、错误、空状态和成功状态都是页面设计，不是边角料；用户体验通常在异常路径上见真章

## 第七站：样式、图片、字体与资源

第七站来到资源物流中心：图片是大件货，字体是易碎品，第三方脚本是未经预约的访客。组件再快也不能让它们堵住首屏，所以要学会排优先级、控体积、稳布局。

**样式方案** ---- 对比 CSS Modules、全局 CSS、CSS-in-JS、Tailwind 和设计系统；选择要考虑服务端、主题、构建体积和团队习惯

**层叠与组件边界** ---- 管理全局 reset、主题变量、局部样式和第三方样式；组件封装不代表 CSS 可以随意越界

**图片优化** ---- 关注尺寸、格式、响应式、懒加载、优先级、占位和布局稳定；图片是最会偷偷变胖的资源

**字体优化** ---- 处理字体子集、预加载、交换策略、回退字体和布局偏移；字体加载也会影响用户第一次看到的内容

**静态资源** ---- 区分 public 资源、模块导入、CDN、缓存和版本指纹；资源地址和缓存策略要一起设计

**图标与媒体** ---- 选择 SVG、图标字体、精灵、视频和第三方媒体方案；考虑无障碍、体积、交互和跨域

**第三方脚本** ---- 管理分析、广告、客服和支付脚本的加载时机、权限与性能；每段脚本都可能是首屏的隐形房客

**主题与响应式** ---- 统一设计令牌、暗色模式、断点、用户偏好和高对比度；资源与样式应共同服务体验

**重点在这** ---- 资源优化不是最后压缩一下；加载优先级、尺寸、缓存和用户可见内容要从组件设计开始考虑

## 第八站：Route Handlers、Middleware 与边界服务

第八站进入服务端海关：Route Handler 处理接口，Middleware 看门，Webhook 偶尔敲门，边缘运行时还会检查你带没带 Node 专属行李。能写接口不等于后端毕业，边界、限流、日志和错误都要登记。

**Route Handlers** ---- 了解请求、响应、方法、参数、Cookie、Header 和流式返回；处理器要薄，业务规则应进入可测试服务层

**API 契约** ---- 设计状态码、错误格式、分页、幂等键和版本；前端和后端的契约要让失败也有形状

**Middleware** ---- 认识请求前置处理、重写、重定向、认证线索和地理或设备信息；Middleware 适合横切逻辑，不适合塞整套业务

**Webhook** ---- 处理签名、重复投递、顺序、重试、超时和快速确认；Webhook 是别人家的请求，不能假设它只来一次

**代理与 BFF** ---- 通过后端为前端聚合、裁剪和保护服务；BFF 可以减少客户端复杂度，也会增加维护边界

**边缘运行时** ---- 了解 Node 能力、边缘限制、冷启动、网络位置和数据库连接；运行时不同，依赖与部署策略也要不同

**日志与追踪** ---- 记录请求 ID、用户路径、错误上下文和耗时；没有现场信息的服务端错误只能靠占卜

**安全** ---- 关注 CSRF、CORS、注入、Cookie、速率限制、敏感日志和请求体大小；接口不是因为藏在同一个仓库里就自动安全

**重点在这** ---- 服务端边界要可验证、可限流、可观测、可恢复；页面能调用接口只是第一步

## 第九站：认证、数据库与全栈架构

第九站来到全栈财务处：认证是门禁，授权是权限表，数据库是金库，事务是保险柜。把查询写进组件不叫全栈，能让身份、数据和失败路径各自有边界才叫会做应用。

**认证与会话** ---- 区分登录、会话、Token、Cookie、刷新、退出和过期；会话生命周期比登录按钮复杂得多

**授权模型** ---- 设计角色、权限、资源归属、组织隔离和服务端校验；隐藏菜单只能改善体验，不能保护数据

**数据库访问** ---- 把查询、事务、连接、迁移和错误处理放在服务端边界；组件不应知道数据库表长什么样

**数据模型与缓存** ---- 关注一致性、索引、分页、缓存失效和并发更新；页面速度不能靠把旧数据永久钉死

**事务与幂等** ---- 订单、支付、库存、重复提交和重试都需要事务思维；网络不可靠，业务必须能承受重复与延迟

**多租户与隔离** ---- 组织、用户、资源和查询都要带上安全边界；忘记租户过滤一次，可能就获得一份非常昂贵的复盘报告

**密钥与环境** ---- 区分构建时变量、运行时变量、公开变量和秘密；任何会发到浏览器的内容都不能再算秘密

**错误与审计** ---- 设计用户可见错误、内部日志、审计事件和敏感信息脱敏；出了问题要知道谁做了什么、什么时候做的

**重点在这** ---- 全栈能力的核心是边界：浏览器不可信、服务端要授权、数据库要隔离、操作要可追踪

## 第十站：性能、测试与部署

第十站把作品交给真实世界验收：慢网络会来，旧手机会来，并发用户、冷启动、缓存失效和回滚也会排队来。开发机上的“飞快”只是试镜，生产才是正式演出。

**性能指标** ---- 关注首屏内容、交互响应、布局稳定、服务器响应和资源体积；指标是用户体验的体检报告

**包体与代码分割** ---- 识别客户端边界、第三方依赖、路由切分和预取；服务端组件减少浏览器代码，但不会自动消灭所有依赖

**缓存策略** ---- 规划浏览器、CDN、平台、数据和路由缓存；缓存层越多，失效和版本策略越要明确

**测试层次** ---- 组合单元、组件、集成、接口和端到端测试；关键业务链路优先，不要为了覆盖率数字给按钮写史诗

**可访问性与 SEO** ---- 把语义、键盘、元数据、结构化内容和错误体验纳入验收；性能不是唯一的“用户能否使用”

**部署平台** ---- 理解 Node、容器、Serverless、边缘、静态托管和 CDN 的约束；平台选择会影响运行时、缓存和日志

**环境与发布** ---- 区分预览、测试、生产、迁移、回滚和功能开关；发布是可逆流程，不是一次性把按钮按到底

**监控与故障恢复** ---- 建立错误上报、性能监控、日志、追踪、健康检查和降级；线上问题要能定位到页面、请求和版本

**升级与迁移** ---- 关注 Next、React、路由模型、缓存语义和构建器变化；迁移先理解行为，再改文件名

**重点在这** ---- Next.js 的终点不是“能 SSR”，而是能在性能、缓存、安全、测试和部署之间做完整取舍

## 通关标准

**Next.js 新手村能搭出页面** ---- 能用 App Router、布局、组件、样式、资源和表单构建完整页面。页面先跑起来，别让第一只 Server Component 还没渲染就被配置文件吓回家。

**初级前端能跑通应用** ---- 能组织服务端与客户端边界、数据获取、缓存、错误、认证和路由。知道什么时候该加 `use client`，也知道它不是“遇到报错就贴上去”的万能创可贴。

**中级前端能做全栈功能** ---- 能设计校验、授权、幂等、数据库访问、接口契约和审计边界。请求失败时有错误体验，重复提交时不制造两份订单，产品经理会觉得今天阳光明媚。

**高级前端能解释渲染** ---- 能说明 CSR、SSR、SSG、重新验证、Server Components 和水合的取舍，不会把所有慢页面都归因于“网络波动”。

**Next.js 老兵能稳定交付** ---- 能测试、分析性能、配置部署、监控错误并处理缓存与版本问题。缓存不会变成幽灵，部署不会变成抽卡，用户也不会替你参加线上排障副本。

## 结语

Next.js 像一座把前端和后端接在一起的立交桥。桥修得好，用户只觉得一路顺；桥修得随意，服务器、缓存和浏览器会轮流鸣笛。先学会判断代码在哪里跑，再学会让数据和缓存各司其职，全栈才不会变成“前端顺便会一点后端”。
