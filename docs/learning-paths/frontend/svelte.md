# Svelte 学习路线

Svelte 的风格很有意思：把更多工作放到构建阶段，让浏览器少搬一点运行时家具。它的组件写法接近 HTML、CSS 和 JavaScript 原生体验，但编译器、响应式规则、SvelteKit 和 SSR 让它远不止“少写几行代码”。

这条路线是**索引和指引**。它会同时覆盖 Svelte 传统语法与 Svelte 5 的 Runes 思路，避免把学习路线锁死在某一个版本的写法里；具体语法、迁移细节和 API 用法，请交给学习笔记。

## 第一站：编译器与响应式心智模型

欢迎来到 Svelte 的编译工坊：你交给编译器的是组件源码，它交付给浏览器的是更直接的更新指令。运行时家具少了，不代表开发者可以少思考；响应式边界一糊，编译器也只能摊手。

**编译时框架** ---- 理解 Svelte 如何把组件、模板和样式编译成 JavaScript 与 CSS；运行时更小不等于没有运行时，而是把通用工作提前做掉

**响应式赋值** ---- 认识传统语法中赋值触发更新的规则、数组与对象更新边界，以及为什么“改了对象内部”不一定等于“通知了框架”

**Runes 模型** ---- 了解 Svelte 5 的 state、derived、effect、props、bindable 等响应式原语；Runes 是显式依赖模型，不是给变量换一套花体字

**派生状态** ---- 区分可写状态、派生值和副作用；派生值应保持可推理，副作用要有清理和生命周期

**细粒度更新** ---- 理解编译器如何分析依赖、生成更新代码、减少无关 DOM 工作；性能来自编译边界与状态边界的配合

**旧语法与新语法共存** ---- 了解 legacy 模式、Runes 模式和迁移边界；读旧项目时要能识别两种心智模型，不要把版本差异误判成代码风格战争

**响应式陷阱** ---- 关注解构、闭包、异步回调、数组变更、对象引用和循环更新；编译器很聪明，但还没聪明到替你猜业务意图

**重点在这** ---- 学 Svelte 先学“什么会触发更新、更新代码在哪里生成”，再去背模板语法；不然每次不刷新都只能对着屏幕发呆

## 第二站：组件与模板

第二站进入 Svelte 组件厨房：模板、脚本和样式都在一间屋里，但 Props 是进料，事件是出餐，children 是可换配菜。文件看起来轻，组件契约不能也跟着变轻。

**组件文件结构** ---- 认识脚本、模板、样式、模块级脚本和编译边界；知道哪些代码每个实例执行，哪些代码只执行一次

**模板表达式** ---- 掌握插值、属性、事件、条件、循环和片段；模板接近 HTML，但拥有自己的编译规则和表达式限制

**组件 Props** ---- 了解传统 export props 与 Runes props、默认值、必需性和可变绑定；Props 是输入契约，不是组件之间的共享黑板

**事件与回调** ---- 比较事件指令、回调 Props 和事件委托；理解版本变化带来的事件写法差异，以及如何保持组件 API 清楚

**双向绑定** ---- 认识表单绑定、组件绑定、可绑定 Props 和绑定修饰；双向绑定方便，但要留意谁拥有最终状态

**条件和列表** ---- 关注列表 key、状态复用、空列表、嵌套循环和异步数据；列表没有稳定身份时，组件状态会开始玩捉迷藏

**片段与组合** ---- 用 snippets、children 和 render 思路组织可复用内容；组合能力要表达布局意图，不要把所有内容都塞成一块匿名插槽

**动态组件** ---- 处理组件切换、异步组件、组件身份和缓存；动态不是把所有组件都延迟加载，而是按用户路径决定加载时机

**样式作用域** ---- 理解组件样式局部化、全局规则、主题变量、预处理器和 CSS 自定义属性；样式隔离是默认值，依然需要设计全局语言

**可访问性** ---- 语义 HTML、键盘操作、焦点、表单标签和动态内容公告要从组件开始；编译器不会自动替用户按 Tab

**重点在这** ---- 组件 API 要说明输入、输出、内容和状态归属；写法可以很短，契约不能模糊

## 第三站：生命周期、Context 与副作用

第三站来到副作用清洁队：编译器负责更新，网络、订阅、DOM 和第三方库却不会自己下班。生命周期就是打卡表，开始、更新、销毁一个都不能漏，否则幽灵监听器会回来加班。

**生命周期钩子** ---- 认识挂载、更新、销毁和服务端执行差异；生命周期是资源管理时间线，不是把所有逻辑按日期排队

**Context** ---- 使用上下文在组件树中传递主题、服务、表单和配置；理解隐式依赖、键命名、响应式上下文和测试替换

**动作与 DOM 集成** ---- 用 actions 连接观察器、拖拽、焦点、第三方组件和浏览器 API；动作要有初始化、更新和销毁边界

**副作用清理** ---- 处理事件监听、订阅、定时器、观察器和请求取消；组件消失后仍在工作的副作用，是“轻量框架”最不轻量的事故

**浏览器与服务端分界** ---- 识别浏览器专属对象、构建阶段、服务端渲染和水合；服务端没有 window，这个事实不会因为你很想它存在而改变

**异步状态** ---- 设计加载、成功、失败、重试、取消和过期响应；异步数据应有明确状态，别让 undefined 承担全部人生

**错误边界** ---- 处理组件、加载、网络和服务端错误，设计可恢复的回退界面；错误页面也是产品的一部分

**重点在这** ---- 任何副作用都要回答“什么时候开始、何时更新、如何停止”；生命周期不是装饰，是资源合同

## 第四站：Store 与状态管理

第四站是状态分配处：组件状态住单间，Context 住楼道，Store 是共享仓库，服务端状态则在另一栋楼。先分清谁拥有、谁修改、谁订阅，再决定把哪件家具搬出去。

**可写与只读 Store** ---- 理解创建、订阅、更新、派生和只读暴露；读写边界明确，组件就不容易把业务状态改成自由市场

**派生 Store** ---- 从多个状态计算结果、组合异步数据和处理依赖；派生应避免副作用，复杂流程可以转移到服务层

**自动订阅** ---- 了解模板中的订阅便利、生命周期清理和命名规则；便利功能依然要知道背后何时订阅、何时取消

**Svelte 5 状态原语** ---- 比较 store 与 Runes 的适用边界；新项目可按业务选择，旧项目迁移要保持行为稳定，不必为了新而新

**Context 与 Store 的取舍** ---- Context 适合树内依赖，Store 适合跨树或独立模块；共享范围越大，越要考虑调试与生命周期

**服务端状态** ---- 区分远程缓存、用户会话、组件状态和全局配置；服务端数据需要失效、刷新和错误策略，不是放进 store 就结束

**持久化** ---- 处理本地存储、跨标签同步、版本迁移、隐私和失效；持久化之前先问它值不值得被未来的自己重新加载

**状态测试** ---- 验证更新、派生、订阅、取消和错误；可独立测试的 store 更容易被多个页面安全复用

**重点在这** ---- 状态管理是所有权问题；谁拥有、谁修改、谁订阅、谁清理，四个问题答清楚，库选型就没那么玄学

## 第五站：动画、过渡与用户感知

第五站来到动画片场：transition 负责入场退场，spring 负责弹性，列表动画负责处理群演换位。动画是解释状态变化的旁白，不是每个按钮都要配的烟花秀。

**进入与离开过渡** ---- 认识淡入、滑动、缩放、方向和自定义过渡；过渡需要服务状态变化，不要让每次按钮点击都像电影片头

**局部与全局动画** ---- 区分只影响节点、影响布局和跨组件的动画；动画范围越大，越要关注合成层与布局成本

**列表动画** ---- 处理添加、删除、重排和 FLIP 思路；列表动画最容易暴露 key 不稳定和布局抖动问题

**Tween 与 Spring** ---- 了解时间插值、弹簧物理、可打断更新和交互反馈；物理感不是弹簧越多越专业

**CSS 动画与 JavaScript 动画** ---- 选择浏览器可合成的 transform、opacity 与必要的脚本控制；动画应考虑性能、降级和可访问性

**prefers-reduced-motion** ---- 为减少动态效果的用户提供尊重和可用的体验；动画不是所有人都想看的烟花

**过渡与 SSR** ---- 关注服务端初始结构、水合一致和首屏动画触发；服务端页面不该一加载就自己改台词

**重点在这** ---- 好动画让变化更容易理解；如果用户开始研究动画本身，通常说明它已经抢戏

## 第六站：Actions、事件与浏览器能力

第六站进入浏览器工具间：action 是 DOM 小工，事件是门铃，观察器是巡逻员，表单是前台。把浏览器细节收进边界，组件才能少管杂事；但小工也要按时清理工具。

**Action 生命周期** ---- 理解初始化、参数更新、销毁和返回更新函数；每个 action 都要有清晰的资源边界

**焦点与键盘** ---- 处理自动聚焦、焦点陷阱、逃逸、 roving tabindex 和键盘导航；可访问交互不是最后补一条 tabindex

**拖拽与指针** ---- 关注指针捕获、触摸、取消、滚动、边界和拖放反馈；复杂拖拽本质是状态机与事件流

**Intersection 与 Resize** ---- 用观察器实现懒加载、可见性、响应式测量和虚拟列表；观察器回调也要清理和节流

**第三方 DOM 库** ---- 封装图表、地图、编辑器和播放器；让库拥有自己的 DOM，避免 Svelte 和第三方同时管理同一棵树

**表单与动作** ---- 处理提交、渐进增强、校验、错误和服务器反馈；表单应该在 JavaScript 暂时离场时仍有基本生命体征

**重点在这** ---- Action 是 DOM 能力边界；把浏览器细节收进 action，组件就能专注于业务语义

## 第七站：SvelteKit 与全栈路由

第七站登上 SvelteKit 全栈列车：文件路由是轨道，布局是车厢，load 是补给，form action 是售票窗口，服务端 API 是后勤站。全链路很顺，但每一站都要知道代码到底在哪运行。

**文件系统路由** ---- 认识页面、布局、参数、可选参数、通配路由、路由组和特殊文件；目录结构就是应用导航地图

**加载数据** ---- 理解页面加载、布局加载、服务端加载、父子数据和并行请求；数据在哪里加载会影响首屏、缓存和权限

**SSR、CSR 与预渲染** ---- 区分服务端渲染、客户端导航、预渲染和混合页面；渲染策略要跟内容新鲜度和交互需求匹配

**表单 Actions** ---- 处理渐进增强、校验、重定向、失败返回、乐观反馈和多动作；服务器表单是可靠性工具，不只是旧时代的回忆

**路由守卫与钩子** ---- 设计认证、权限、请求上下文、错误处理和服务端钩子；前端判断负责体验，后端仍负责安全

**服务端 API** ---- 了解端点、请求参数、响应、Cookie、文件和错误；将领域逻辑放在可测试的服务层，不要把端点写成巨型 switch

**水合与序列化** ---- 关注服务端数据传到浏览器的边界、不可序列化对象和浏览器 API；水合是一次协作，不是把服务器 HTML 粘过来就完事

**适配器与部署** ---- 认识 Node、静态站、边缘和平台适配器；运行环境不同，缓存、文件系统和请求生命周期也不同

**重点在这** ---- SvelteKit 的价值是把页面、数据和部署放在同一个应用模型里；先学清生命周期，再决定使用哪种渲染模式

## 第八站：性能、测试与工具链

第八站来到性能体检中心：编译器已经帮你减了运行时负担，但网络、图片、字体、第三方脚本和旧设备还在门口排队。真正的速度要用指标检查，不能只看开发机上秒开的幻觉。

**编译产物** ---- 了解组件如何生成更新代码、哪些代码会被消除、动态边界如何影响产物；编译器会优化已知信息，不会优化混乱的架构

**包体与代码分割** ---- 关注路由切分、动态导入、依赖体积和重复打包；小框架也能被大依赖拖成健身房会员

**大列表与昂贵计算** ---- 处理虚拟化、分页、派生缓存、节流和可见区域；性能优化要先找成本最高的工作

**图片与字体** ---- 优化格式、尺寸、懒加载、预加载、字体交换和布局稳定；用户等的是内容，不是你的构建日志

**组件测试** ---- 验证 Props、事件、状态、过渡、action 和错误；测试对用户有意义的行为

**SvelteKit 测试** ---- 覆盖加载、表单 action、路由、服务端端点和关键业务流程；服务端与客户端要分别测试，再测试协作

**端到端测试** ---- 守住登录、表单、导航、权限和关键转化路径；测试应该能在失败时告诉你用户卡在哪里

**开发工具** ---- 使用浏览器性能面板、网络面板、Svelte Devtools、测试报告和构建分析；别只凭“感觉很快”发性能毕业证

**重点在这** ---- 编译器帮你少付运行时税，但网络与业务复杂度仍会开账单；性能要看完整链路

## 通关标准

**Svelte 新手村能让组件动起来** ---- 会用模板、Props、状态、事件、绑定、action 和样式构建可复用组件，能做出一个会响应的页面。编译器还很贴心，但你不能把所有问题都甩锅给它。

**初级前端能跑通应用** ---- 能用 SvelteKit 组织路由、布局、加载、表单、服务端 API 和错误处理。页面能打开只是起点，表单提交后不把用户送去未知星球才算进步。

**中级前端能管住响应式** ---- 能说明传统响应式与 Runes、派生值、副作用和编译更新之间的关系，能定位状态不同步与重复请求。数据不再一变全家跟着搬家。

**高级前端能守住平台边界** ---- 能考虑 SSR、水合、浏览器 API、部署适配器、缓存和安全，知道哪些魔法只在浏览器有效。服务端不会因为一句 `window` 就当场昏倒。

**Svelte 老兵能稳定交付** ---- 能测试关键行为、控制包体、优化资源，并用真实指标判断性能。最后不只会说“编译后很快”，还能拿数据证明它确实没有在用户电脑上慢悠悠散步。

## 结语

Svelte 的魅力是让代码接近浏览器，让浏览器少做重复劳动。真正掌握它之后，你会发现“少运行时”并不意味着“少思考”：组件边界、状态所有权、SSR 和资源清理，一个都不会因为编译器勤快而消失。
