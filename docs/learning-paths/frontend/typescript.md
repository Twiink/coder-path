# TypeScript 学习路线

TypeScript 是 JavaScript 的类型护栏：它不能阻止你把咖啡洒在键盘上，但能在代码进生产前提醒你“这里可能要出事”。它的价值不只是给变量贴上 `string` 或 `number` 标签，而是把大型项目里的契约、边界、重构和协作变得可推理、可检查、可维护。

这条路线是**索引和指引**，不是把类型体操写成魔法咒语的教程。每一站只回答三件事：要认识哪些概念、它们如何串起来、继续深入时应该去学习笔记查什么。语法示例尽量少放，避免路线图变成“复制粘贴停车场”。

## 第一站：类型系统与推断

欢迎来到 TypeScript 的类型村：这里有 `string` 和 `number` 两位老实人，`any` 是谁都敢答应的社牛，`unknown` 则会先问一句“证据呢”。这一站先认识类型、推断和收窄，让编辑器从看热闹的同事变成真正会提醒你的搭档。

**原始类型与特殊类型** ---- 认识字符串、数字、布尔、空值、未定义、Symbol、BigInt，以及 `any`、`unknown`、`void`、`never` 这些特殊角色；先分清“没有值”“不知道是什么”和“永远不会回来”

**字面量类型** ---- 具体字符串、数字和布尔值也能成为类型；这是建模状态、权限、事件名和配置选项的基础，也是很多场景替代枚举的轻量方案

**联合与交叉** ---- 联合表达“可能是其中一种”，交叉表达“同时具备多种形状”；它们是 TypeScript 建模业务状态的两把主钥匙，不是把类型符号写得越长越高级

**类型推断** ---- 变量初始化、返回值、数组元素、回调参数都可能被自动推断；要理解宽化、窄化和最佳公共类型，知道什么时候让编译器推断，什么时候在边界处主动声明

**上下文类型** ---- 函数放进数组方法、事件处理器或配置对象时，外层环境会反向提供类型；读懂上下文类型，能少写很多注解，也能看懂“明明没写类型为什么有提示”

**类型收窄** ---- 通过条件判断、类型检查、真值检查、属性存在性和自定义守卫，把宽类型逐步缩小；这是 `unknown` 真正安全、联合真正有用的地方

**类型断言与非空断言** ---- 断言是告诉编译器“我比你更了解这里”，不是把运行时的石头变成黄金；要理解断言的边界、双重断言的风险，以及为什么收窄通常比断言更稳

**结构化类型系统** ---- TypeScript 默认按形状判断兼容性，不太在乎类型名字是否相同；理解鸭子类型、额外属性检查和可赋值关系，才能解释那些“看起来一样却报错”的瞬间

**严格空值检查** ---- `null` 和 `undefined` 不再自动混入所有类型；围绕可选属性、可选链、空值合并和初始化检查建立安全习惯，避免把空值问题推迟到用户点击按钮时

**枚举与字面量联合** ---- 了解数字枚举、字符串枚举、常量枚举的运行时差异和工具链限制，再判断什么时候使用枚举、联合、常量对象或 `satisfies`

**重点在这** ---- 先把“值是什么”“值可能是什么”“值永远不会是什么”分清；类型系统的第一关不是记语法，而是建立对不确定性的控制感

## 第二站：函数、对象与接口

第二站来到 API 门口：函数负责收发请求，对象负责带着一身属性来报到，接口和类型别名则负责检查证件。你要学会描述输入、输出和协作关系，别让调用者每次使用函数都像拆盲盒。

**函数参数与返回值** ---- 覆盖必选、可选、默认、剩余参数，以及返回值推断和显式标注；重点是函数边界清不清楚，而不是每一行都贴满类型便利贴

**函数类型** ---- 认识函数类型表达式、调用签名、构造签名和可调用对象；理解一个对象如何既能被调用又能携带属性，库类型定义里经常藏着这类设计

**重载** ---- 多个调用签名对外提供精确体验，一个实现负责运行时逻辑；学习重载顺序、实现兼容性和“什么时候用联合比重载更诚实”

**函数的 `this` 类型** ---- 显式描述调用上下文、回调中的 `this`、箭头函数与普通函数的差别；这是类型系统和 JavaScript 运行规则交叉的经典坑位

**对象类型字面量** ---- 描述属性、方法、可选成员、只读成员和索引签名；掌握对象形状的表达方式，后面学习接口、映射类型和工具类型会轻松很多

**接口** ---- 用接口表达可扩展的对象契约；学习继承、合并、实现、函数接口和第三方类型扩展，知道接口不是“比 type 更高级”的奖杯

**类型别名** ---- 用别名组合联合、交叉、元组、条件类型和映射结果；理解它与接口的重叠区域及各自更适合的表达场景

**可选与只读成员** ---- 可选属性背后通常带着 `undefined`，只读通常只约束编译期且可能是浅层的；要把“不能写”与“运行时真的不能改”区别开

**索引签名** ---- 描述字典、动态键和值的关系；理解索引签名会如何约束其他属性，避免为了省事把所有键值都放进 `any` 的黑洞

**额外属性检查** ---- 直接传对象字面量时更严格，先保存到变量后规则可能变化；这不是编译器喜怒无常，而是为了抓住配置对象中的拼写错误

**属性键与索引访问** ---- 认识 `keyof`、索引访问类型和安全取值模式；这是从对象类型走向泛型和映射类型的桥

**重点在这** ---- 把函数看成契约，把对象看成形状，把接口看成协作边界；类型声明应该帮人理解设计，而不是让人参加解谜综艺

## 第三站：类、面向对象与运行时边界

第三站进入面向对象片场：class 穿着 Java 风格的戏服，但后台仍是 JavaScript 的原型。接口、访问修饰符和抽象类会一起演戏，TypeScript 可以在排练时提醒你，不能替运行时请保安。

**类的成员模型** ---- 学习实例字段、实例方法、静态成员、构造函数、访问器和参数属性；区分类型层面的声明与运行时真正生成的 JavaScript

**访问修饰符** ---- 理解 `public`、`private`、`protected` 的编译期约束，以及 JavaScript 私有字段的运行时隔离；别把 TypeScript 的 private 当成保险箱密码

**接口与类的关系** ---- 类可以实现接口，接口可以描述类的公开形状；理解实现检查、继承契约和结构化类型带来的兼容规则

**抽象类** ---- 用于共享实现和约束子类；学习抽象成员、构造流程和何时应该用组合而不是堆继承树

**继承与组合** ---- 认识 extends、super、多态、Mixin 与组合式设计的取舍；继承不是坏人，但继承层级长到需要地图时通常就该刹车

**类字段初始化** ---- 理解严格属性初始化、声明字段、构造函数赋值和初始化顺序；这部分与 `strictPropertyInitialization` 关系密切

**声明合并** ---- 同名接口、命名空间和模块扩展可以合并声明；知道它能增强第三方库，也知道它会让全局类型变成“谁都往上贴便利签”

**运行时验证** ---- 接口和类型别名在编译后会消失，外部 JSON、表单、接口响应仍然需要运行时校验；建立“静态类型不等于数据可信”的边界意识

**品牌类型与名义约束** ---- TypeScript 默认结构化兼容，业务 ID、货币、单位等场景可能需要品牌化技巧模拟名义类型，避免不同含义的字符串互相串门

**重点在这** ---- TypeScript 负责设计时的护栏，JavaScript 负责运行时的现场；学会把两者分层，才能写出既准确又不自欺的模型

## 第四站：泛型——让类型也能复用

第四站是泛型健身房：它能让一套代码服务很多类型，但练过头就会长出只有作者看得懂的肌肉。这里要学会保持输入输出的关系，也要学会在复杂度开始冒烟时踩刹车。

**泛型的核心关系** ---- 关注输入与输出之间的对应关系，而不是把类型参数当成装饰；理解泛型为什么比 `any` 更安全、比复制多份类型更可维护

**泛型函数** ---- 让函数在保持类型关联的前提下服务多种数据；学习推断、显式指定、参数位置和返回值之间的关系

**泛型接口与类** ---- 把数据容器、仓储、事件映射和结果对象抽象成可复用契约；同时判断抽象是否真的减少重复，避免为了“看起来高级”泛型套泛型

**泛型约束** ---- 用约束表达“类型至少具备什么能力”；理解约束并不会把类型变成某个具体类型，只是给编译器一张可以依赖的通行证

**多个类型参数** ---- 认识键值关联、输入输出关联、映射关系和类型参数命名约定；多个参数不是越多越灵活，通常意味着调用者负担也在上涨

**默认泛型参数** ---- 为常见场景提供默认类型，减少调用噪音；理解默认值与推断、显式参数之间的优先级

**泛型在集合和 API 中的应用** ---- 关注数组、字典、Promise、响应结果、事件系统和分页数据等常见边界；学习笔记中再展开具体实现与案例

**泛型推断的边界** ---- 了解逆变、协变、函数参数位置和回调上下文对推断的影响；“为什么这个类型没有按我想的推断”通常不是编译器在报复你

**泛型约束的设计取舍** ---- 约束太宽失去信息，约束太窄失去复用；练习从业务能力而不是具体类名出发设计约束

**重点在这** ---- 泛型的目标是保留关系，不是制造复杂度；一眼看不出输入和输出怎么关联的泛型，通常已经走远了

## 第五站：高级类型编程

第五站下潜到类型深水区：映射类型会批量改造，条件类型会分叉，infer 会拆包，递归类型还会试图把自己复制下去。别急着参加类型体操奥运会，先学会读懂库的声明，并判断什么时候这把电锯不该启动。

**`keyof` 与索引访问** ---- 从对象得到键的联合，再通过键访问对应属性类型；这是类型安全映射、表单字段和 API 选择器的基础

**映射类型** ---- 遍历已有键批量增加、删除或修改属性；覆盖只读、可选、键重映射和模板字面量组合

**条件类型** ---- 根据类型关系选择结果，类似类型层面的分支；理解条件判断、约束位置和嵌套条件的可读性问题

**分布式条件类型** ---- 裸类型参数遇到联合时会逐成员分发；知道何时想要分发，何时需要用元组包裹阻止分发

**`infer` 推断占位符** ---- 从函数、数组、Promise、元组或字符串模式中提取内部类型；工具类型的“拆箱”能力大多从这里开始

**模板字面量类型** ---- 从字符串字面量组合事件名、路径名、CSS 属性名和命令名；它适合表达规律，不适合把整本词典塞进类型系统

**变长元组与参数保留** ---- 描述函数参数拼接、前缀和后缀参数、事件监听器参数等关系；这是库作者常用的高级表达

**递归类型** ---- 表达树、嵌套配置、深层只读和路径结构；同时学习递归深度、性能和可维护性边界，别让编译器在类型迷宫里过夜

**内置工具类型** ---- 熟悉 Partial、Required、Readonly、Pick、Omit、Record、Exclude、Extract、NonNullable、ReturnType、Awaited 等类别；重点理解原理和组合方式，不是背单词表

**品牌化与不透明类型** ---- 给相同底层类型附加不同语义，保护用户 ID、订单 ID、像素、毫秒等不可混用的值

**类型体操的性能** ---- 大联合、深递归、分布式条件和复杂模板类型可能拖慢编辑器与构建；学会拆分、缓存、降级和把复杂类型藏到声明文件

**重点在这** ---- 高级类型是放大器：设计好时减少重复，设计坏时把错误信息变成一篇悬疑小说；先解决问题，再展示技巧

## 第六站：模块、声明与类型边界

第六站来到模块海关：值和类型要分开过关，声明文件负责给陌生依赖办翻译，模块扩展则像给外来居民补办证件。项目一大，类型就要跨文件、跨包、跨团队旅行，这里负责把路线规划清楚。

**ES 模块类型语义** ---- 区分值导入、类型导入、值导出和类型导出；理解类型擦除后哪些导入会消失，哪些导入仍然影响运行时

**模块解析** ---- 认识 Node、Bundler、NodeNext 等解析策略，了解 package exports、条件导出、路径别名和扩展名规则

**类型声明文件** ---- 了解声明文件描述什么、如何组织模块、如何暴露函数重载、泛型和命名空间；声明文件是类型世界的接口文档，不是实现源码

**环境声明** ---- 学习全局变量、模块、脚本环境和第三方运行时对象的声明方式；明确“告诉编译器存在”不等于“真的创建了它”

**模块扩展与全局增强** ---- 为库补充缺失类型或为 Window、Request 等全局对象增加业务字段；范围要小，命名要稳，别把全局当公共留言板

**第三方类型包** ---- 理解社区类型包、内置类型、库自带类型和版本匹配；遇到类型不准确时，先确认运行时版本和声明来源

**类型与代码生成** ---- 对比手写类型、Schema 推导、OpenAPI 生成、GraphQL 生成和 RPC 类型共享；类型来源越自动化，越要关注生成流程是否可靠

**Monorepo 类型边界** ---- 认识项目引用、包边界、声明输出和增量检查；让每个包的类型契约清楚，避免整个仓库一起“类型地震”

**重点在这** ---- 模块和声明解决的是协作边界；类型写得再漂亮，如果导入导出混乱，最终还是会在构建时排队哭泣

## 第七站：tsconfig 与工程化

第七站进入 tsconfig 控制室：strict 像认真值班的门卫，module 和 target 负责安排出行方式，noEmit 则告诉 TypeScript“你检查就好，别抢打包器饭碗”。配置不是越狠越酷，而是要让本地、CI 和构建器说同一种方言。

**严格模式总开关** ---- 理解 strict 及其子选项，重点关注隐式 any、严格空值、函数参数、类属性初始化和未知捕获变量

**编译目标与运行环境** ---- 区分 target、lib、DOM 类型、Node 类型和实际运行时；编译目标写得再现代，也不能替运行环境凭空增加 API

**模块输出与解析** ---- 关注 module、moduleResolution、包导出、ESM 与 CommonJS 互操作；这部分和打包器、Node 版本、测试运行器经常互相拉扯

**检查与输出分离** ---- 理解 noEmit、声明输出、Source Map、增量编译和构建器接管；现代前端常让 TypeScript 负责检查，让 Vite 或其他工具负责转译

**单文件编译约束** ---- 认识 isolatedModules、verbatimModuleSyntax 等选项对类型导入、枚举和模块语义的影响；保证代码能被不同工具一致处理

**项目引用** ---- 将大型仓库拆成可独立检查和构建的项目；关注依赖方向、声明产物和增量缓存，而不是把所有源码塞进一个巨型配置

**编辑器与语言服务** ---- 了解 tsserver、自动导入、跳转、重构、错误提示和类型性能；编辑器卡顿有时不是电脑老，而是类型写成了迷宫

**质量工具链** ---- 了解 ESLint 类型感知规则、格式化、提交检查、CI 类型检查和编辑器版本一致性；工具要形成闭环，不要只在发布前临时祈祷

**升级与兼容** ---- 关注 TypeScript 版本、第三方声明、编译器行为变化和弃用选项；升级先看错误类别，再决定修代码还是调整配置

**重点在这** ---- 配置的终点是可预测：本地、CI、打包器、测试和编辑器对同一份代码给出同一套理解

## 第八站：框架与平台类型

第八站来到前端边境：浏览器事件、表单、路由、组件和接口响应都拿着“外部输入”四个大字。类型要在边界上站岗，但别把它写成某个框架的 API 族谱；这里学的是如何让数据进出有门票。

**DOM 与浏览器事件** ---- 认识元素、事件、表单、键盘、拖拽、Fetch 和存储 API 的类型层次；重点是事件目标、泛型元素类型和空值边界

**组件 Props 与事件** ---- 了解 React、Vue、Angular 等框架如何描述属性、事件、插槽、模板引用和上下文；比较框架类型推断的优点与盲区

**响应式数据类型** ---- 理解 ref、signal、observable、store 等不同响应式模型在类型层面的表现；区分容器类型、内部值和解包规则

**路由与表单类型** ---- 为路径参数、查询参数、表单字段、校验结果和提交状态建立稳定边界；用户输入默认不可信，类型不能替你做运行时校验

**网络响应与错误** ---- 认识 JSON 类型、请求状态、分页、错误联合和取消请求；不要把所有接口响应都声明成“万能对象加问号”

**Schema 与运行时校验** ---- 把外部数据先当未知，再通过校验得到可用类型；比较手写守卫、Schema 库、代码生成和后端共享类型

**库作者视角** ---- 了解泛型 API、声明输出、条件导出、类型测试和向后兼容；用 TypeScript 写库时，类型体验本身就是产品体验

**重点在这** ---- 前端类型最重要的不是“内部变量全都有类型”，而是边界上的数据来得清楚、出去稳定、坏了能解释

## 第九站：类型设计与实战策略

第九站是类型建筑事务所：不是把现实世界一砖一瓦复制进代码，而是决定哪些墙必须承重、哪些门需要上锁、哪些状态不能同时出现。建模建得好，团队少吵架；建模建得差，错误信息会写成连续剧。

**状态机建模** ---- 用可辨识联合表达加载、成功、失败、空状态和权限状态；避免多个布尔值互相矛盾，今天 loading 明天又 error 的荒诞剧

**Result 与错误类型** ---- 把可预期业务失败作为类型的一部分，把真正异常留给异常处理；建立错误码、错误详情和展示层之间的边界

**外部数据先未知** ---- JSON、localStorage、URL、表单、第三方 SDK 和后端响应都要经过验证；不要因为接口文档写得很自信就跳过现实检查

**避免 any 扩散** ---- 识别 any 如何沿着返回值、数组和回调传播；优先用 unknown、泛型、联合或局部断言收窄范围

**泛型适度原则** ---- 先有重复和稳定关系，再抽象泛型；业务代码不需要把每个对象都改造成可变形宇宙飞船

**类型命名与可读性** ---- 名称表达业务含义，类型层级不过深，错误信息能被新人读懂；好的类型会让代码像说明书，坏的类型像藏宝图

**类型测试** ---- 对公开 API、库类型、复杂工具类型和关键推断写类型测试；运行时测试证明行为，类型测试证明契约

**渐进式迁移** ---- JavaScript 项目可以从边界、公共函数、数据模型和高风险模块逐步迁移；先让类型带来收益，再扩大覆盖面

**性能与维护成本** ---- 关注检查耗时、声明体积、编辑器响应和错误信息长度；类型系统也是工程资源，不是无限免费的魔法

**重点在这** ---- 类型设计的评价标准是减少误解和返工；能让团队更快发现错误、更放心重构的类型，才是好类型

## 第十站：编译器与类型系统内部

第十站坐上编译器观光车：源码先被扫描，再进语法树、符号表、类型检查和发射流水线。这里不要求你马上造一个 TypeScript，但至少要知道错误发生在哪一站，别每次都把锅甩给编辑器的星座运势。

**扫描与语法树** ---- 了解源码如何变成 token 和 AST，知道语法错误发生在类型检查之前

**绑定与符号表** ---- 理解声明如何建立作用域、符号和引用关系；模块、命名空间和重载的很多规则都能在这里找到影子

**类型检查器** ---- 认识可赋值性、结构化比较、推断、控制流分析和类型标志；类型错误本质上是在问两个值能否安全地一起工作

**控制流分析** ---- 编译器会根据分支、返回、抛错和赋值更新变量的可能类型；理解它，就能解释为什么换一个判断顺序结果会不同

**类型擦除与发射** ---- 类型大多不会进入运行时 JavaScript；需要运行时行为的校验、装饰器或转换必须由其他机制负责

**编译器 API 与工具** ---- 了解 AST 遍历、类型查询、转换器和语言服务的能力边界；适合代码生成、迁移工具和编辑器插件方向

**类型性能诊断** ---- 关注大型联合、递归条件、声明合并和复杂推断带来的检查成本；必要时用更简单的公共类型换取更快反馈

**重点在这** ---- 这一站不是为了把自己变成 TypeScript 编译器，而是为了在遇到奇怪行为时，有一张能定位问题的内部地图

## 通关标准

**类型村新手能拿到护符** ---- 会用基础类型、联合收窄、函数和对象契约，看到常见报错不会立刻给它盖上 `any` 的被子。能把数据说清楚，但遇到泛型长句还需要暂停呼吸。

**初级前端能给边界站岗** ---- 能为组件、接口响应、表单和错误状态建模，知道静态类型与运行时校验各自负责什么。类型开始像门卫，而不是装修贴纸；面试问 unknown 和 any 的区别，你不再只说“一个更安全”。

**中级前端能读类型迷宫** ---- 能看懂泛型、工具类型、条件类型、声明文件和框架类型，能为库与业务边界写出可维护契约。遇到一百行类型定义不会马上截图发群里，而是知道从哪一层拆开。

**高级前端能让类型服务团队** ---- 能维护严格配置、模块解析、项目引用、类型测试和升级流程，能判断何时抽象、何时保持简单。类型错误能提前发现，错误信息也能让新人看懂；这时编译器终于像队友，不像审判官。
