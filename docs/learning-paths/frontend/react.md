# React 学习路线

React 的核心思想可以浓缩成一句话：UI 是状态的函数。听起来像数学，写起来却经常像在和状态、闭包、渲染、缓存一起玩密室逃脱。React 不替你规定完整应用架构，它给你组件模型、渲染模型和一套组合能力，然后把“如何组织大型系统”的作业留给你。

这条路线是**索引和指引**，不是 Hooks 速查表。它会同时覆盖常用写法、容易忽略的边界和渲染器背后的深层机制；具体代码写法与 API 细节，请沿着知识点去查学习笔记。

## 第一站：组件、元素与 JSX

欢迎来到 React 的函数剧场：JSX 是 JavaScript 穿上的 UI 戏服，组件是把输入变成界面的演员，元素只是节目单上的描述。看起来像 HTML，后台却是 JavaScript；先别被服装骗了。

**JSX 心智模型** ---- 了解 JSX 如何成为元素描述、表达式边界、属性命名、片段、条件与列表；它看起来像 HTML，脾气更像 JavaScript

**元素与组件** ---- 区分 React Element、组件函数、DOM 节点和组件实例；元素是描述，组件是生成描述的逻辑，不要把它们混成同一位演员

**函数组件** ---- 理解函数组件的输入、返回值、纯度和重新执行；组件函数每次渲染都可能重新运行，不是只在页面首次打开时执行一次

**Props 输入** ---- 设计只读输入、默认值、组合内容、回调和类型契约；Props 是数据流入口，不是子组件偷偷修改父组件的后门

**Children 与组合** ---- 掌握内容组合、插槽式布局、复合组件和渲染属性的思想；React 不提供 Vue 式 slot，但组合能力很强

**事件模型** ---- 了解合成事件、冒泡、捕获、事件委托、默认行为和事件处理器身份；事件只是触发状态变化的入口，不要把所有业务塞进点击回调

**条件渲染** ---- 关注假值、短路表达式、分支组件和状态保留；数字零在页面上突然出现，是 React 给粗心者发的入门纪念品

**列表与 key** ---- 理解 key 的稳定性、唯一性、状态复用和重排；key 是 React 判断“这是老朋友还是新面孔”的身份证

**受控与非受控** ---- 区分表单由 React 管理还是由 DOM 管理，理解 ref、默认值、校验和同步成本；不是所有输入都要实时汇报给中央政府

**组件边界** ---- 按职责、数据流、复用稳定性和渲染频率拆分组件；组件过大难维护，过碎则像把一张纸撕成雪花

**重点在这** ---- JSX 是表达式，组件是转换器，Props 是输入，key 是身份；先把这四件事分清，后面的 Hooks 才不会变成背口诀

## 第二站：状态、事件与渲染

第二站进入 State 调度中心：普通变量改了就改了，React 状态改了要排队、合并、重新渲染，还要看组件住在树上的哪个位置。搞懂快照和批处理，才能不再追问“我明明改了，页面怎么还在装没看见”。

**useState 基础** ---- 了解初始值、惰性初始化、状态更新函数和状态类型；状态更新不是立即修改当前变量，而是请求下一次渲染

**状态快照** ---- 每次渲染看到的是当时的快照；理解闭包、事件处理器和异步回调为何会拿到旧值

**批量更新** ---- 认识事件中的批处理、连续更新、函数式更新和更新队列；多个更新不是排队把变量改三遍，而是排队计算下一份状态

**状态保留与重置** ---- 组件位置、类型和 key 决定状态是否保留；重置表单、切换账号和复用列表项都依赖这个规则

**派生状态** ---- 能通过现有状态计算出来的值通常不必再存一份；重复存储会制造同步问题，状态越多，越容易出现“两个真相”

**事件与状态分工** ---- 用户行为、网络结果和渲染计算应有清晰边界；事件处理器负责发起变化，渲染负责描述结果，副作用负责和外界握手

**useReducer** ---- 用 reducer、action 和初始化组织复杂状态；适合状态转换规则多、更新来源多和需要可追踪事件的场景

**状态机思维** ---- 把加载、成功、失败、编辑、提交和禁用等状态建模为互斥或可组合状态；少用互相打架的布尔值

**状态提升与下沉** ---- 共享状态提升到最近公共父级，局部状态留在使用处；不要因为“以后可能复用”就提前把一切送进全局

**状态初始化与恢复** ---- 关注懒初始化、重置、从 URL 恢复、从存储恢复和服务端初始数据；初始化也是产品体验的一部分

**重点在这** ---- React 状态更新是调度，不是赋值；搞懂快照、队列、身份和派生状态，能解决大量“为什么页面不是我想的样子”

## 第三站：Hooks 与组件生命周期

第三站来到 Hooks 训练营：useState 管状态，useRef 管小秘密，useEffect 管外部世界，useMemo 则负责偶尔把昂贵计算请进冷藏室。规则不能乱，依赖不能瞒，每个 Hook 都有自己的时间表。

**Hooks 规则** ---- 只在组件或自定义 Hook 顶层调用，保持调用顺序稳定；规则不是风格偏好，而是 React 识别 Hook 状态位置的前提

**useEffect** ---- 区分渲染、提交和副作用；学习依赖、清理、重复执行、竞态和组件卸载，不要把所有逻辑都塞进 effect 里

**事件逻辑与 Effect** ---- 用户点击、提交和选择通常属于事件逻辑；同步外部系统才属于 Effect，别为了“代码跑起来”给每个函数套一层 useEffect

**useLayoutEffect** ---- 理解它在浏览器绘制前执行，适合测量和同步布局；它会阻塞绘制，能用普通 Effect 时不要抢跑

**useRef** ---- 保存不触发渲染的值、引用 DOM 和跨渲染稳定容器；ref 不是隐藏版 state，也不是逃离数据流的万能地道

**useMemo 与 useCallback** ---- 认识缓存计算值、缓存函数身份、依赖比较和优化收益；缓存本身也有成本，没测量就缓存往往只是增加心理安慰

**useContext** ---- 共享主题、语言、会话和依赖配置；理解 Provider 边界、更新扩散和拆分上下文，避免一个 Context 让整棵树一起抖

**自定义 Hook** ---- 抽取状态、Effect、请求、订阅和浏览器能力；好的 Hook 返回清楚的能力，坏的 Hook 把一整个应用藏进一个函数名

**Effect 清理与取消** ---- 处理订阅、定时器、事件监听、请求取消和过期响应；组件消失了，副作用还在工作，就是前端版的离职不交接

**Strict Mode 语义** ---- 理解开发环境中的额外检查、重复调用和副作用暴露；不要为了让警告消失而关闭探照灯

**Hook 依赖的诚实性** ---- 依赖数组应该反映闭包使用的值；忽略依赖可能暂时安静，长期会把 bug 变成考古项目

**重点在这** ---- Hook 是时间与依赖的组合，不是工具箱抽屉；先问“这段逻辑属于渲染、事件还是副作用”，再决定用哪个 Hook

## 第四站：组件通信与状态架构

第四站是状态搬家公司：Props 负责楼上楼下传递，Context 负责跨层电梯，Reducer 负责统一办事流程，外部状态库则是共享仓库。自由很香，失控也很快，所以先找状态的主人，再决定搬到哪里。

**父子通信** ---- 通过 Props 向下、回调向上建立单向数据流；让数据拥有者负责修改，子组件报告事件，不要让状态在树里到处开分店

**组合优于穿透** ---- 通过 children、复合组件、渲染函数和自定义 Hook 组织变化；组合常常比层层传递一串“只为经过”的 Props 更清楚

**Context 的边界** ---- 适合低频、跨层级、语义明确的数据；高频业务状态要关注重渲染、选择器和 Provider 拆分

**Reducer 与 Context** ---- 将状态转换集中管理，再通过 Context 提供能力；适合中等复杂度，但不是所有组件都需要自制 Redux

**外部状态库** ---- 认识 Redux Toolkit、Zustand、Jotai 等不同模型的取舍；关注更新粒度、调试、持久化、异步和团队约定

**服务端状态** ---- 远程数据的缓存、失效、重试、分页和乐观更新与客户端 UI 状态不同；可关注 React Query、SWR 等专门工具的思想

**表单状态** ---- 选择受控、非受控或表单库，处理校验、异步提交、错误、脏状态和撤销；表单不是十几个 input 的大合影

**状态持久化** ---- 设计本地存储、URL、Cookie、跨标签同步和版本迁移；持久化前先问数据是否敏感、是否过期、是否值得恢复

**权限与会话** ---- 前端状态负责展示体验，真正授权仍在服务端；路由保护、按钮隐藏和接口拒绝要分层处理

**状态架构判断** ---- 用状态所有权、更新频率、共享范围和生命周期决定放置位置；“全局方便”通常会在半年后收取利息

**重点在这** ---- 状态管理不是选库比赛，而是让状态有主人、更新有路径、错误有归属

## 第五站：副作用、数据获取与异步 UI

第五站进入副作用动物园：请求会迟到，订阅会赖着不走，旧数据会假装自己还是最新，加载状态还会催你给个说法。副作用不可避免，但可以用取消、清理、缓存和状态机把它们驯服。

**副作用分类** ---- 区分网络请求、订阅、DOM 操作、分析上报、存储同步和第三方 SDK；不同副作用需要不同的取消、重试和清理策略

**数据获取位置** ---- 比较事件触发、路由加载、组件 Effect、服务端获取和数据缓存层；不要让每个组件都各自 fetch 同一份数据

**加载与错误状态** ---- 处理初次加载、刷新、后台更新、空结果、部分失败、重试和取消；用户需要的是状态解释，不是一个永远转圈的图标

**竞态条件** ---- 关注快速切换参数、旧请求晚到、组件卸载和重复提交；取消请求或校验请求身份，避免旧数据穿越时空覆盖新数据

**并发与过渡** ---- 理解 transition、deferred value、优先级和非阻塞更新；不是所有更新都要和用户点击抢同一把椅子

**Suspense** ---- 认识加载边界、异步组件、数据资源和错误边界的关系；Suspense 是协调机制，不是自动把所有网络请求变快

**错误边界** ---- 捕获渲染、生命周期和子树错误，设计回退 UI、重试和上报；事件处理器与异步回调的错误需要其他路径处理

**乐观更新** ---- 先更新界面再等待服务端确认，处理失败回滚、冲突和重复提交；速度感和一致性必须一起设计

**取消与资源释放** ---- 使用 AbortController、清理回调、订阅解除和组件生命周期协作；停止使用的资源要有明确的退场仪式

**重点在这** ---- 异步 UI 的本质是状态机与时间管理；Promise 解决不了产品问题，清楚的加载、错误和恢复路径才行

## 第六站：路由、错误边界与应用结构

第六站来到 React Router 交通枢纽：路由负责铺轨，布局负责候车厅，错误边界负责隔离事故，数据加载负责安排班次。React Router 是工具，真正要学的是页面如何抵达、加载、失败和恢复。

**路由匹配** ---- 认识静态路径、动态参数、嵌套路由、索引页、通配路径和查询参数；URL 是用户可分享的应用状态，不只是导航按钮的副产品

**布局与嵌套** ---- 用共享布局承载导航、侧栏、面包屑和局部出口；布局层级应与用户看到的页面层级一致

**导航状态** ---- 处理加载中、导航取消、重复导航、滚动恢复和返回前进；导航也是异步流程，别只盯着地址栏变没变

**路由数据加载** ---- 了解 loader、预加载、缓存和错误边界的组合；让路由知道页面需要什么数据，常常比页面挂载后再请求更稳

**路由级代码分割** ---- 按页面、功能和权限拆分包；处理预加载、加载失败、缓存和离线场景，用户不应被一段 chunk 名称吓退

**错误边界分层** ---- 在应用、布局、页面和组件级别设置回退；错误隔离越合理，越不会因为一个小组件让整站变白

**认证与权限路由** ---- 关注会话恢复、登录跳转、返回地址、权限变化和服务端最终校验；前端守卫是体验，不是安全墙

**路由与状态同步** ---- 决定哪些状态进 URL，哪些留在内存，哪些进服务端缓存；可分享、可刷新和可恢复的状态通常值得进入 URL

**重点在这** ---- 路由是应用级数据流和错误流的骨架；组件只会显示页面，路由决定页面如何抵达、加载和退场

## 第七站：渲染机制与性能

第七站下潜到 React 发动机舱：Fiber 是调度骨架，reconciliation 是比对裁判，优先级是排队系统，commit 才是把结果交给 DOM。别再听见“重新渲染”就脑补整页推倒重建。

**渲染与提交** ---- 区分计算 UI、提交 DOM、运行布局副作用和浏览器绘制；渲染阶段可以被打断，提交阶段必须保持一致

**Reconciliation** ---- 了解元素类型、key、位置和子树比较如何决定复用、卸载和重建；性能和状态正确性都依赖身份判断

**Fiber** ---- 认识 Fiber 节点、工作单元、父子兄弟关系和可中断遍历；它是 React 调度复杂更新的内部骨架

**并发渲染** ---- 理解优先级、可中断、可重启和过渡更新；并发不是多线程，而是让渲染更愿意把时间让给用户

**记忆化** ---- 判断 React.memo、useMemo、useCallback 和选择器是否真的减少工作；引用稳定与业务正确性要分开思考

**组件拆分与更新边界** ---- 用数据流、上下文、列表项和高频更新区域划分边界；拆分不是为了文件数量破纪录

**列表与窗口化** ---- 关注 key、虚拟列表、分页、懒渲染和可见区域；页面上同时出现几万行，通常是产品和渲染器共同的噩梦

**代码分割与预加载** ---- 通过动态导入、路由分割、资源预取和预加载平衡首屏与交互；小包不等于快，关键是用户何时得到关键内容

**服务端渲染与水合** ---- 关注 HTML 生成、客户端接管、不一致、流式输出和延迟水合；服务器和浏览器必须对同一棵树达成共识

**React Server Components** ---- 理解服务端组件、客户端组件、边界、序列化和交互能力；它改变的是代码运行位置与数据边界，不只是多一个文件后缀

**性能度量** ---- 使用 Profiler、浏览器 Performance、网络瀑布和 Web Vitals；先找真实热点，再决定是否优化，拒绝“凭感觉加 memo”

**重点在这** ---- 性能优化的核心是减少不必要的工作、让高优先级交互先完成、让大资源晚一点来；不是给每个组件贴一张“已优化”奖状

## 第八站：测试、可访问性与团队工具

第八站进入交付质检线：测试负责抓回归，无障碍负责让更多人进场，DevTools 负责还原案发现场，CI 负责提醒你别把半成品推上去。组件能跑只是入场券，能稳定交付才算毕业。

**组件测试** ---- 关注用户看到的文本、角色、交互、Props、错误和加载状态；测试行为与可访问语义，不要把私有实现当公共 API

**Hook 测试** ---- 验证状态变化、异步流程、清理、错误和边界；能独立测试的逻辑才更容易复用

**集成测试** ---- 将路由、状态、请求和多个组件放在一起验证真实协作；很多 bug 单测各自通过、合在一起却开始跳舞

**端到端测试** ---- 守住登录、支付、表单、关键导航和核心业务链路；数量少而关键，胜过到处撒脆弱脚本

**可访问性** ---- 语义元素、键盘操作、焦点管理、表单标签、屏幕阅读器、颜色对比和动态公告都要纳入组件设计

**类型与静态检查** ---- 结合 TypeScript、ESLint、React Hooks 规则、格式化和 CI；静态检查越早介入，代码评审越能讨论真正的问题

**Storybook 与组件文档** ---- 用隔离环境展示状态、变体、错误和无障碍行为；组件库不是堆截图，而是可验证的契约

**调试工具** ---- 熟悉 React DevTools、Profiler、网络面板、错误边界与生产 Source Map；会还原现场，胜过在群里发送“我这里没问题”

**重点在这** ---- 团队工程的终点不是测试数量，而是让每次修改都更有信心、让真实用户少遇到惊喜

## 通关标准

**React 新手村能让组件开口说话** ---- 会写 JSX、Props、State、事件、表单和列表，能做出一个会交互的页面。闭包和 Effect 还像神秘生物，但至少不会把所有数据都塞进 Context。

**初级前端能控制状态** ---- 理解快照、批处理、key、受控表单和基础 Hooks，能组织路由与数据请求。面试问“为什么 state 没立刻变”，你会先解释队列，而不是指责网速。

**中级前端能管住副作用** ---- 能处理取消、竞态、缓存、错误边界、代码分割和性能，能理解 Fiber、并发和提交阶段。Promise 不再在角落长蘑菇，旧请求也不会回来抢新数据的戏份。

**高级前端能设计 React 生态** ---- 能在 Context、状态库、服务端状态、RSC、可访问性、测试和性能之间做取舍，能让团队稳定交付。组件可以自由组合，架构不能自由散架。

React 把选择权交给你，也把架构责任交给你。学会它不是背完 Hooks，而是能在自由度、可读性、性能和团队约定之间做出清醒选择。组件可以函数式，项目不能随缘式。
